## ⚠️ 這份報告錯了兩次，最後的結論是「不遷」

> **底下的原始判定不要照著做。** 兩次修正的過程留著，因為那個過程本身就是這份報告
> 最有用的部分 —— 它示範了一種掃描方法怎麼連續失敗兩次。

### 最終結論（計畫席 2026-09-03 裁定）

|              |                                                                                                                                   |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **遷移**     | **不做。** 四支全部是雙軌（斷點內隱藏表格、顯示手刻手機版）—— **沒有破版**，而 pattern 是為破版寫的。遷移是純迴歸風險、零體驗改善 |
| **交付的**   | 雙軌漂移造成的真缺陷：兩支唯讀 dialog 的不及格在手機上**只有顏色**（WCAG 1.4.1）→ PR #259                                         |
| **自然時機** | 下次有人要改這幾張表的欄位時，才遷那一張（那時反正要碰兩軌）                                                                      |
| **gate**     | 掃「斷點內 `display: none` 掉 `__table-wrap`」，現有 4 支進 baseline，**擋新增的雙軌** → infra 佇列                               |

### 兩次錯誤，同一個根因

| 輪次           | 我的判定                                           | 錯在哪                                                 |
| -------------- | -------------------------------------------------- | ------------------------------------------------------ |
| 初版           | 「4 處在用 overflow 扛表格」                       | 沒查有沒有手機版                                       |
| 修正 1         | 「#1、#3 是雙軌；**#2 是唯一沒手機版的，真缺陷**」 | **#2 也有**，只是叫 `__record-cards` 不叫 `__mobile-*` |
| 修正 2（最終） | 「四支全部雙軌，沒有破版」                         | —                                                      |

**根因不是漏了某一個檔案，是我一直在掃命名慣例。**

修正 1 我以為補上了第三種訊號，但我補的是 `grep mobile` —— **那還是命名**。四支的手機版叫
`__mobile-list` / `__record-cards` / `__mobile-row` / `__mobile-subjects`，**沒有共同的命名**。

可靠的訊號是**結構**：

```scss
@include respond-to(…) {
  .block__table-wrap {
    display: none;
  } // ← 這個
}
```

用它重掃，四支全部命中，一次到底。

> **「命名慣例」在存量程式碼裡從來不是可靠的掃描依據** —— 慣例是後來才形成的，
> 而存量比慣例老。要掃就掃它**做了什麼**，不是掃它**叫什麼**。

### 為什麼這一種最難掃

第三種訊號難掃的原因不是技術上難，是**它看起來像已經處理好了** —— 而它確實處理了破版，
只是用了會分岔的方式。**雙軌的病不是破版，是分岔**（計畫席原句）。

而分岔已經證實發生：兩支 dialog 的手機版掉了桌機有的 icon 與 `aria-label`，
**沒有任何錯誤、沒有任何 gate 抓到**。

## 附錄：原始判定與修正 1（保留供對照）

### 修正 1（2026-09-03，開工時發現）：掃描漏了第三種訊號

**這份報告原本的判定有兩處是錯的。** 開始遷移 #1 時發現它**已經有一份手刻的手機
卡片清單**（`__mobile-list`，在 `mobile` 斷點下 `display: grid`，表格則隱藏）。

我掃了 `<table>` 與 `overflow-x`，但**沒掃「有沒有平行的手機版實作」** ——
而那是判斷「這裡到底出了什麼問題」的關鍵訊號。

### 修正後的實況

| #   | 位置                          | 實況                     | 問題其實是                |
| --- | ----------------------------- | ------------------------ | ------------------------- |
| 1   | `class-scores-dialog`         | 表格 **+ 手刻手機卡片**  | **雙軌實作**，不是破版    |
| 2   | `student-score-detail-dialog` | **只有表格，沒有手機版** | **真的破版** ← 唯一的缺陷 |
| 3   | `academy-score-editor`        | 表格 **+ 手刻手機卡片**  | 雙軌實作                  |
| 4   | `score-edit-dialog`           | 只有表格，4 欄           | 需要先量                  |

### 這對優先級的影響

**#2 是唯一沒有手機路徑的** —— 它才是缺陷。#1 與 #3 的手機版是**能用的**，
遷移它們換到的是「兩份變一份」。

兩者都值得做，但**理由不同，而理由不同會影響怎麼驗**：

- **#2**：驗「390px 下不溢出、身分欄還在」
- **#1／#3**：驗「遷移後的手機版跟原本那份手刻的**一樣好或更好**」——
  這是迴歸風險，不是新功能。手刻那份可能有針對性的處理是通用元件做不到的

### 為什麼雙軌本身值得修

專案已經有三個實例證明「同一件事宣告兩次，分岔必然發生」（`page-actions` 那一刀的
理由）。表格 + 手刻手機清單是同一個形狀：**改欄位時要記得改兩處，而忘記的那一次
不會有任何錯誤**。

### 掃描方法的教訓

「表格在手機上的處理」有**三種**訊號，而我只掃了兩種：

1. `<table>` 標籤 ✔
2. `overflow-x: auto` ✔
3. **平行的手機版實作（`__mobile-*`、`display: none` + 斷點切換）** ✘ ← 漏了

第 3 種最難掃，因為它**看起來像已經處理好了** —— 而它確實處理了破版，只是用了
會分岔的方式。**下一次掃描三種都要。**

## 掃描方法（先講怎麼找的，因為漏掉的方式就藏在這裡）

三輪，因為第一輪一定不夠：

1. **`<table>` 標籤** —— 全站 7 處
2. **`overflow-x: auto`** —— 全站 7 個檔案。這一輪抓到的是「不是 `<table>` 但同樣症狀」的候選
3. **交叉比對** —— 兩份清單的交集是真正的目標；差集各自要交代（見〈查過但不是問題〉）

第 2 輪是必要的：只掃 `<table>` 會漏掉「用 div/grid 排成表格」的頁，而只掃 `overflow-x`
會把橫向 chip 列誤判成表格。**兩份都要，而且差集比交集更需要解釋。**

## 優先級：按「手機使用頻率」，不按欄數

判準是**這張表會不會在手機上被打開**，而那取決於它是**查詢**還是**輸入**：

|                      | 情境                                                                                              | 手機頻率 |
| -------------------- | ------------------------------------------------------------------------------------------------- | -------- |
| **查詢型**（#1、#2） | 「這個學生考得怎樣」「這個班這次考試怎樣」—— **跟家長講電話時、或在走廊上被家長攔住時**會查的東西 | **高**   |
| **輸入型**（#3、#4） | 批次登錄分數。要鍵盤、要對照紙本，實務上在桌機做                                                  | **低**   |

所以順序是 **#1 → #2 → #3 → #4**，而不是按破版嚴重程度。

> 這也是 pattern 頁那條例外的真正意思：「大數據網格在**桌機**上的兜底」之所以成立，
> 不是因為表格大，是因為**那個任務本來就在桌機做**。

## 逐處的欄位收合建議

### #1 `class-scores-dialog` —— 這個班這次考試的成績

欄位：`# ／ 學生姓名 ／ 分數 ／ 狀態 ／ 備註`

| priority | 欄位     | `collapsible` | 理由                                                             |
| -------- | -------- | ------------- | ---------------------------------------------------------------- |
| 1        | 學生姓名 | **false**     | 身分。收掉就剩一排無名分數                                       |
| 2        | 分數     | true          | 看成績就是在看分數                                               |
| 3        | 狀態     | true          | 缺考／未登錄，是分數的限定詞                                     |
| 4        | 備註     | true          |                                                                  |
| 5        | `#`      | true          | **手機上第一個該收的** —— 它是名次序號，只有在整表可見時才有意義 |

### #2 `student-score-detail-dialog` —— 這個學生的成績歷程

欄位：`日期 ／ 考試名稱 ／ 類型 ／ 科目 ／ 分數`

⚠️ **這張表的身分是兩欄的組合，不是一欄。** 每一列講的是「某次考試的某一科」——
單獨的「考試名稱」分不出是哪一科，單獨的「科目」分不出是哪一次。而
`collapsible=false` 是**逐欄**的設定。

**兩種解法，建議第二種：**

|          | 做法                                                      | 取捨                                                                           |
| -------- | --------------------------------------------------------- | ------------------------------------------------------------------------------ |
|          | 考試名稱與科目**都**設 `collapsible=false`                | 手機上兩欄都留，身分欄佔掉大半寬度，分數可能被收掉 —— 而分數是這張表存在的理由 |
| **建議** | 遷移時把科目**併進考試名稱那一格**（`第一次段考 · 數學`） | 一格承載身分，其餘全部可收；分數留得住                                         |

| priority | 欄位                    | `collapsible` |
| -------- | ----------------------- | ------------- |
| 1        | 考試名稱 · 科目（合併） | **false**     |
| 2        | 分數                    | true          |
| 3        | 日期                    | true          |
| 4        | 類型                    | true          |

### #3 `academy-score-editor` —— 校內考批次登錄

欄位：`學生 ／ 年級 ／ 分數 ／ 狀態 ／ 備註`

**分數是輸入欄位** —— 手機上收掉它，這一頁就沒有功能了。

| priority | 欄位         | `collapsible`          |
| -------- | ------------ | ---------------------- |
| 1        | 學生         | **false**              |
| 2        | 分數（輸入） | true（但實務上留得住） |
| 3        | 狀態         | true                   |
| 4        | 年級         | true                   |
| 5        | 備註         | true                   |

**這一處要問一個範圍問題**：pattern 說大網格的桌機兜底可以留、但「手機版仍應收合」。
遷到 `responsive-table` 之後**寬螢幕本來就全欄顯示**，所以不需要「留 overflow 給桌機」——
遷移即可，容器可以整個拿掉。**除非**批次輸入需要橫向 tab 鍵動線而 detail row 會破壞它，
那要實測（`score-entry` 有鍵盤動線，admin-pages 席正在收斂）。

### #4 `score-edit-dialog` —— 單筆學生的多科分數

欄位：`科目 ／ 分數 ／ 狀態 ／ 備註`（**只有 4 欄**）

**我不敢說它違規，因為我沒有量過。** 4 欄在 390px 下可能根本不溢出 ——
而 pattern 針對的是「撐破版面」，不是「用了 overflow 容器」。

**建議：先量再決定。** 若沒破版，那個 `overflow-x: auto` 是**無害但也無用**的，
可以順手拿掉（減少一個誤導下一個人的訊號），但不算遷移工單。

| priority | 欄位 | `collapsible` |
| -------- | ---- | ------------- |
| 1        | 科目 | **false**     |
| 2        | 分數 | true          |
| 3        | 狀態 | true          |
| 4        | 備註 | true          |

## 查過但不是問題

### 兩張列印表 —— 正確，不要動

`invoice-detail-dialog.component.html:288` 與 `:335` 的 `print-doc__table`。

驗證方式不是看名字，是看它在哪：它們包在 `.invoice-detail__print-source` 裡，
而那個容器是 `display: none`（`…scss:199-201`，註解寫著「列印版面搬到獨立視窗才渲染，
畫面上永遠不顯示」）。**畫面上根本不存在的表格不會破版。**

### 三個 `overflow-x: auto` 不是表格

第 2 輪掃出來、但交叉比對後排除的：

| 位置                                           | 是什麼                           | 為什麼正確                                         |
| ---------------------------------------------- | -------------------------------- | -------------------------------------------------- |
| `sessions/components/session-filters/…scss:18` | `&__row` 篩選 chip 橫向列        | 橫向捲的 chip 列是行動端的既定模式，不是被迫的盲捲 |
| `staff/staff.page.scss:79`                     | `&__stats` 統計數字橫向列        | 同上，而且每一格都是獨立完整的資訊                 |
| `teacher/pages/schedule/…scss:52`              | `&__track` 水平 scroll-snap 軌道 | **老師端今日流刻意的主軸**（一屏一天），不是表格   |

> 這三個是「pattern 不適用」而不是「pattern 的例外」—— 差別在於它們不是表格，
> 而不是「是表格但情況特殊」。**混在一起會讓下一個人以為橫向捲動一律該修。**

### 行政區的五張表 —— #174 已遷完

`enrollments`、`changes`、`invoice-detail`（明細＋收款記錄兩張）、`teaching-log`。
掃描時它們不會出現在 `<table>` 清單裡，因為 `responsive-table` 的用法是
`ng-template` 裡直接寫 `<tr>` —— **這是「掃不到」不是「沒有」**，值得記一筆：
下一次掃描要記得 `appRtColDef` 也是一種表格。

## 需要你確認的一件事

**#3（`academy-score-editor`）的範圍。** 它是 pattern 明文允許的「大數據網格桌機兜底」，
但那條例外的下半句是「手機版仍應收合」。

- 若照 pattern 全文 → **要遷**（遷完寬螢幕自然全欄，不需要保留 overflow）
- 若把它讀成「批次編輯整個豁免」→ **不遷**，只在註解標明是知情的例外

我傾向前者，但它牽動 `score-entry` 的鍵盤動線（admin-pages 席正在收斂那一塊），
**要遷的話得跟他們對一次**，不然兩邊會撞在同一個檔案上。
