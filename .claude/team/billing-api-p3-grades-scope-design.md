# P3 切片二設計：成績的 teacher-scope + 補登窗伺服器強制

> 2026-08-30，billing-api 席。**設計文件，STOP gate 前不寫實作碼。**
> 基準 `origin/main` @ `267bdb7`。
>
> 裁決依據：使用者 2026-08-30 的 ③「老師可以自己建考試」與 ⑤「補登窗後端強制」。

---

## 先講三個查證出來、會改變題目的事實

### 1. `school_exams` 根本不是「老師的考試」

```sql
CREATE TABLE public.school_exams (
  id, org_id, academic_year, semester, exam_type, name, label, ...
);
```

**沒有 `created_by`、沒有 campus、沒有班級關聯。** 它是**學校段考的機構層目錄**
（學年 × 學期 × 考試類型），不是某個老師辦的考試。

→ 「老師可以自己建考試」這個裁決**只適用 `academy_exams`（校內考）**。
兩個老師各自建一筆「第一次段考」只會製造重複資料。

### 2. `academy_exams` 有 `created_by`

所以「誰建的」判斷得出來，**不需要新欄位或新 migration**。

### 3. 補登窗的現行規則跟工單描述的不一樣

工單寫「server 端 **7 天**強制」，但：

- `attendance_retroactive_days` 的**預設是 `0`，而 `0` 代表「無限制」**
  （欄位 `COMMENT`，`20260401000001:21`）
- 而且前端的鎖有**第二個條件**：只有 `attendance_responsible = 'teacher'` 的機構才鎖
  （`teacher/schedule.page.ts:122-127`）

**寫死 7 天會改變每一個機構的行為**（目前全部是無限制），那不是「把前端的限制搬到
伺服器」，是新增一條規則。這一點需要你確認要哪一種。

## 提案 A：老師可以編輯哪些考試

### 選項

|           | 規則                                                                                       | 問題                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| **A1**    | 只能編輯**自己建的**（`created_by = me`）                                                  | 管理員建的考試日期打錯，最清楚的任課老師改不了 —— 又要回頭找管理員，正是 P3 想消滅的來回              |
| **A2**    | 可編輯**自己任課班**的所有考試（含管理端建的）                                             | 一場考試可以跨班（`academy_exam_classes`）。老師 A 改了跨三班的考試，影響另外兩班 —— 而他看不到那兩班 |
| **A3 ⭐** | **自己建的**：改／刪／關閉／重開都可以。**管理端或別人建的**：只能登錄成績，不能動考試本身 | 老師仍需為別人建的考試找管理員改，但那是**罕見**情況；A2 的越權是**每次**都在                         |

### 建議：A3

理由：

1. **破壞性動作要跟權責一致。** 刪除一場跨三班的考試會連帶刪掉其他兩班的成績
   （`academy_exam_classes` 是 CASCADE）。做這件事的人必須看得到全部影響範圍，
   而老師依定義看不到自己不任課的班。
2. **A1 的成本是真的，但發生頻率低。** 管理員建考試是少數情境（多半是跨班統考），
   而老師自建是 P3 要開的常態路徑。用罕見情況的不便，換常態路徑的越權為零，划算。
3. **判斷不需要新 schema** —— `created_by` 已經在。

### A3 底下還有一個邊界要一起釘：**編輯參加範圍**

老師編輯自己建的考試時，可以改 `academy_exam_classes`。這裡有提權風險：

- **只能加自己固定任課的班**（伺服器驗證，不是前端不顯示）
- **不能移除自己不任課的班** —— 若管理員事後把別班加進來，老師不能把它踢掉

沒有這兩條的話，「老師可以建考試」會變成「老師可以把任何班拉進自己的考試」。

### 三支路由各自的結論

| 路由            | 老師的權限                                                                              |
| --------------- | --------------------------------------------------------------------------------------- |
| `academy-exams` | 讀：自己任課班的考試。寫：**自己建的**（含 close/reopen）；建立時參加範圍限自己任課的班 |
| `school-exams`  | **唯讀**。它是機構層目錄（見事實 1），不是老師的東西                                    |
| `scores`        | 讀寫：**自己任課班的學生**。不分考試是誰建的 —— 登錄成績本來就是老師的工作              |

## 提案 B：補登窗要不要豁免管理員

### 選項

|           | 規則                         | 評價                                                                                                |
| --------- | ---------------------------- | --------------------------------------------------------------------------------------------------- |
| **B1 ⭐** | 只擋 `teacher`，管理員不受限 | 現行 spec 就寫「修改過期出勤需找管理員」——「找管理員」是既有的逃生門                                |
| **B2**    | 一視同仁，管理員也擋         | 逃生門被焊死。要改窗外的資料只能先改 org 設定再改回來 —— 那個過程本身沒有留痕，比讓管理員直接改更糟 |

### 建議：B1（管理員豁免），但**管理員在窗外的修改要寫 audit log**

補登窗的目的是「**老師**不要無限期回頭改點名」，不是「資料不可修正」。把管理員也擋住
會逼出一個更難稽核的繞道（改設定 → 改資料 → 改回設定）。

留痕的部分：`attendance` 目前沒有 `logAudit`。窗外修改是低頻但高風險的動作，值得記。

### B 底下的子問題：伺服器要不要照抄前端的**兩個**條件？

前端現行規則是 `isTeacherLed() && days > 0 && 超過天數`。

|            | 規則                                            | 影響                                                                                                     |
| ---------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **B1a ⭐** | 照抄兩個條件                                    | **行為零改變**，只是把前端已經在做的限制搬到伺服器、堵掉直接打 API 的繞道                                |
| **B1b**    | 不管 `attendance_responsible`，老師一律受窗限制 | 行政負責點名的機構，老師突然被擋 —— 那些機構的老師本來就不點名，所以影響應該是零，但「應該」不等於「是」 |

**建議 B1a。** 這個切片的任務是「把限制搬到伺服器」，不是「改變限制」。要改規則的話那是
一個獨立的、需要跟使用者確認的決定。

### ⚠️ 「7 天」要怎麼處理

工單寫「7 天強制」，但目前**所有機構的設定值都是 0（無限制）**。三種可能：

1. 保持讀 org 設定（**建議**）—— 伺服器強制的是「機構自己設的窗」，行為零改變
2. 把 `attendance_retroactive_days` 的**預設值**改成 7（新 migration，只影響之後建立的
   org；既有 org 仍是 0）
3. 把既有 org 的 0 一律改成 7（**資料搬遷，會改變現有行為**）

1 是這個切片該做的；2 和 3 是產品決定，需要使用者拍板。**我不會自己選 2 或 3。**
