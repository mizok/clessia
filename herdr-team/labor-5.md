## 一、`#749` 為什麼做成共用元件，不是 shell 或路由層

計畫席指定「修在一處」，我去看了三個候選，**結論是都不行**：

| 候選                                 | 為什麼不行                                                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ShellLayoutComponent`               | **admin / teacher / parent 三角色共用**，放 parent 專屬邏輯要加角色判斷，而且會蓋到 `/parent/notifications`（公告不吃 `childId`，沒有孩子照樣該看得到） |
| `/parent` 路由層 wrapper             | 那棵子樹**沒有 wrapper 元件**（直接 `roleGuard` + children）                                                                                            |
| 無路徑父路由包住四個 child-scoped 頁 | 那四條路由**在 `app.routes.ts` 裡不連續**（中間夾著六個佔位頁），要搬動它們                                                                             |

所以是 `app-child-scope-gate`：**規則與措辭集中在一支元件，插入點在每頁看得見。**

**下一個做同類題的人要知道的**：「修在一處」有兩種意思 —— **「只改一個檔」** 與
**「規則只有一份」**。這個 repo 的家長端做不到前者，而後者才是真正要保護的
（計畫席擔心的是「各頁各長一種說法」）。

### 那一題最容易寫錯的地方

`children()` 在載入完成**之前**也是空陣列。只看長度的話，**每次進頁都會先閃一下
「你沒有綁定學生」** —— 對有孩子的家長也說謊，比原本的缺陷更糟。條件必須是
`status() === 'ready' && length === 0`，而且 `failed` 不算（讀不到 ≠ 沒有）。
**三條都有反向對照測試守著。**

## 二、替身描述了一個不存在的世界，而它一直是綠的

包 `child-scope-gate` 的那一刻，**16 支既有測試同時變紅**。查下去不是 gate 錯：
`attendance` / `grades` / `payments` 的 `ChildScopeService` 替身都是
**`children: () => []` + `status: 'ready'`**，而 `activeChildId` 只會從 `children[0]` 來 ——
**那個狀態在現實中不存在。**

**可操作的版本：替身的欄位之間有沒有矛盾，沒有人會檢查。**
它們各自合法、合起來不可能，而測試照樣綠。下次寫替身時把「這幾個欄位的關係」
當成一條斷言來想，不要只想「這個欄位要放什麼」。

## 三、地圖這一批裡，public / parent 特有的東西

- **`showInMenu: false` 的路由，生成區塊的「角色」欄會說謊**（`#693` 已修）：
  它讀 `RoutesCatalog.role`，看不到 `app.routes.ts` 的 guard。`/login` 掛 `guestGuard`
  （**登入著的人反而進不去**）、`/link-line` 與 `/select-role` 掛 `authGuard`。
- **家長端「有資料」與「沒資料」是兩張不同的地圖**：本機預設孩子（`parent01` 的
  林子璿）**所有表都是 0 筆**，照它量會漏掉整類元素（方法頁坑 8 就是這樣長出來的）。
  **要量家長端先查哪個孩子有資料**，不要用預設的那個。
- **`p-select` 的清除鍵是 `<svg>`**，方法頁那段標準 DOM 查詢抓不到它 —— 它是一個
  真的可以按、會改變畫面的東西，卻不會出現在可見元素計數裡。

## 四、指過去就好的

- **「編譯失敗的紅」與「斷言的紅」** → `labor-2.md` 第 7 條。這一輪我踩到兩次
  （`#738` 的 TestBed 未重置、`#464` 的 500 來自 `mint`），
  **兩次都是「把實作暫時拿掉再跑一次」才確認的** —— 那個動作值得變成反射。
- **背景分頁讓動畫不跑、真滑鼠不落地** → 方法頁坑 12（成因是這一席查出來的，
  但知識已經住在那裡，不要複製）。**只補一句**：它是**先量 `document.visibilityState`**
  才分辨得出來的，而在那之前它整整一天被當成「元件壞了」。
- **量測前後都打 `GET /api/me`** → 方法頁坑 7。**不要從畫面讀身分** ——
  shell 不會因為 cookie 變了而重繪，角色徽章會給你一個假的安全通過。

## 五、跨席協作：兩條這一輪長出來的

1. **改共享資源的人，改之前也要發一則，不只改完發。** labor-4 改 DB 時我正在量，
   同一組查詢十分鐘內兩種結果（`demo.%` 帳號 8 → 0）。**我沒把它寫成缺陷，
   是因為去查了 DB** —— 而症狀（登入成功、下一次呼叫 403）跟真缺陷一模一樣。
2. **轉述別人的發現時，原文的等級標記不會自己跟過來。** `#714` 與 `#722` 兩次：
   原始地圖只寫「整列可點」「header-actions 是空的」，**而工單多了一句原文沒有的斷言**
   （「補 `closable` 不會出現 ×」「沒有 tabindex」）。兩次都是**開檔查前提**才擋下來的。
   `#722` 的前兩支測試因此是**前提確認**（修前就綠），留在 suite 裡擋下次同一張單。
