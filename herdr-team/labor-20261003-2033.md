## 一、`sessions.ts` 的非交易寫入：順序與補償

這個 repo 不引入 RPC（c1，計畫席在 #1109 二度裁定）。所以「主寫入＋流水」一律走同一個形狀：
**① 先做主寫入 → ② 再寫流水 → 流水失敗就補償回去**。目前有四處：makeup、加開單堂、批次代課、批次改到別天。

| 端點 | 補償方式 | 補償也失敗時，查得出來的殘跡 |
| --- | --- | --- |
| `POST /api/sessions`（加開） | 刪掉剛建的 session | `schedule_id IS NULL` 但沒有對應的 `creation` 流水列 |
| `batch-substitute` | 照**原老師**分組，改回原老師 | 老師已經換了，但沒有 `substitute` 流水 |
| `batch-reschedule` | 照**原落點**分組，搬回原日期／時段 | 課堂已經搬了，但沒有 `reschedule` 流水 |

- **批次的 update 要分組，不要逐堂打。** 每堂的目標值不一樣時（日期、原老師），逐堂寫最多會打 1000 次請求，會撞上 Workers 的 subrequest 上限。
  照目標值分組，每組一次 `.update().in('id', ids)`；一整期大約 16–20 組。
- **分組 update 循序執行**，並記住「已經搬走的是哪些」。中途失敗時只搬回那些。撞到唯一鍵（`23505`）回 409，其他失敗回 500。
- 既有的 batch-cancel／batch-update-time／batch-uncancel 在流水寫失敗時**不補償**，直接回 400。這是舊寫法，還沒有人改。

## 二、分校範圍：單堂與批次各一種寫法（#1110、#1221）

- 分校一律取 `classes.campus_id`，**不取 `events.campus_id`** —— 未來的堂還沒有 event。
- 單堂：`loadSessionOperationState` 有回 `campusId`，搭配 `resourceCampusAllowed` 判斷，不在範圍回 403。
- 批次：只要有一堂不在範圍，**整批 403，dryRun 也照擋**（計畫席裁）。用 `batchOutOfCampusScope(scope, ids, campusById)`，
  它的 map 用班級 id 或課堂 id 當 key 都可以。撈目標堂時要 embed `classes!inner(campus_id)`，再用 `sessionCampusId(row)` 取值。
- 判準寫在 `kb/wiki/architecture/authorization-scope.md` 的「課表寫入」那段。

## 三、替身綠了，但綠的原因不是你以為的那個（這一席踩過的形狀）

- **planner 本來就會排除自己**（`peer.id !== target.id`）。所以「同一批要搬走的堂不擋位」這條測試，fixture 裡擋位的那堂如果就是自己，
  測試什麼都沒驗到 —— 陷阱塞進去照樣綠。**擋位的要是同一批裡的另一堂。**
- 斷言「沒有寫入」時要把 `audit_logs` 濾掉，`logAudit` 也是一次 insert。
- 同一批裡兩堂如果是同一個老師、落在同一個時段，`teacher_conflict` 是**正確**行為，不是 bug。測試想看兩堂都寫入的話，fixture 要給不同老師。
- 星期幾的編號：repo 慣例是 **1=週一、7=週日**（`schedules.weekday`、`toWeekdayFromDate`）。設計稿寫成 0–6，最後跟 repo 一致。

## 四、本機實打的時機

- **實打之前先看 labor-db-reset 的 pane。** 2026-10-03 那次，RESET #16 剛好在兩發請求之間跑起來，回應變成 500，
  psql 也報 `relation "sessions" does not exist`。**那跟你的程式碼無關**，但看起來就像你把東西弄壞了。
  db-reset 正在量測前後值的時候也不要登入：登入會寫 `ba_session`／`ba_verification`，會干擾它的對帳。
- **migration 還沒套到本機時，實打得到的是補償路徑**。enum 沒有新值，流水一定寫失敗。這反而是唯一能在真的 DB 上驗證補償的機會：
  前後筆數不變就是證據。成功路徑等合併、apply、重置之後再補。
- 想打「受限管理員打別校」：`admin02@demo.clessia.app` 有 `manage_courses`，只被指派一個分校。
  **但它的分校裡一堂課都沒有**，所以「同校打得過」這半只能由 spec 驗。

## 五、herdr 送訊的兩個新形狀

- 對方停在互動對話框（例如「Background this session?」）時，`herdr agent prompt` 會回 `agent_blocked`。
  **不要替對方按**，等它離開對話框再重送；重送的訊息開頭標「重送」。
- **送出前讀到輸入框是空的，不代表送出那一刻也是空的。** 使用者可能正在計畫席的輸入框打字。
  你的訊息會接在他打到一半的字後面，一起被排進佇列（2026-10-03：「其實現在已經不用尊[labor-20261003-2033] 佇列盤點…」）。
  發生了就**照實告訴使用者**，請他在那邊按 ↑ 編輯排隊中的訊息。不要自己去動對方的輸入框。
