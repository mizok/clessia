# admin-pages 席

> 管理端頁面。**session 會死，席位不死** —— 接手先讀這份，再讀 [README](README.md) 的通用協定。

## 管什麼

- `apps/web/src/app/features/admin/pages/**` —— 功能區一個目錄，**看目錄不要看清單**
- 被 admin 頁用到的 `apps/web/src/app/shared/components/**`（dialog、responsive-table、
  empty-state、page-breadcrumb 等）。要共用就往 `shared/` 提，feature 之間不互相 import（c5）

**不碰**：`apps/api/**` 與 schema（billing-api 席）、`styles.scss` 與 design tokens（design-web 席）、
CI/harness/依賴（infra 席）。需要新 API 或改 schema → 回報計畫席，不自己動。

4. `kb/wiki/lessons/empty-array-hides-loading.md` —— 空陣列把「還沒載入」講成「真的沒有」，
   含盤點方法與一個 known issue
5. `kb/wiki/architecture/admin-dashboard-v1.md` —— 卡片/索引模式與失敗態
6. `kb/wiki/architecture/teacher-students-view.md` —— 「一個功能一個家」

## 先例（照抄，不要重新發明）

- **路由單一真相是 `core/smart-enums/routes-catalog.ts`。** 跳轉一律
  `RoutesCatalog.X.absolutePath`，不要寫字串字面值 —— 字面值不會被 `app.routes.spec.ts` 守到
- **併發取數 + 每個區塊自己失敗**：`features/admin/pages/dashboard/dashboard.component.ts`
  的 `failSoft()`。`forkJoin` 預設 fail-fast，任一支掛掉整頁空白；每支 source 各自
  `catchError(() => of('error'))` 才做得到部分失敗。三態用 `null` = 載入中、`'error'` = 失敗、
  數字 = 有值
- **有邊界條件的計算抽成純函式 + spec**：`dashboard.util.ts`、`enrollments/enrollment-event.util.ts`、
  `staff/teaching-log-dialog/teaching-log.util.ts` 都是先例。元件測試很難把跨日、空值、
  時間邊界測乾淨，純函式很容易
- **細部權限走 `RouteObj.permission`**（PR #58 建立）：填了它就要兩邊都動 ——
  `NavigationService` 過濾選單（不要讓人點到必然 403 的按鈕）+ `app.routes.ts` 掛
  `permissionGuard`（藏起入口擋不住直接打網址）。**permission 是每條路由自己的值**：
  金流頁 `manage_finance`（會寫）、營收報表 `view_reports`（唯讀）—— 兩者在
  `core/staff.service.ts` 的 union 裡是不同的東西，別當成一個「財務」開關。
  元件內的 `auth.hasPermission()` 留給次級動作（某顆按鈕），要在 `computed` 裡呼叫
  （隨 signal 反應），不要在 field initializer 取快照
- **讓「接對了沒」可斷言 —— 必要時給執行期的東西留一個可讀的標記。** 這是坑 #1 的推廣：
  坑 #1 是「有沒有接」，它的下一階是「接的是不是**對的那個**」，後者更安靜。
  `permissionGuard` 回傳的是一個閉包，從外面看不出它守哪個權限，所以它把權限名
  `Object.assign` 到回傳的 function 上，`app.routes.spec.ts` 才驗得到「選單過濾與路由守衛
  守的是同一個權限」。兩行程式碼換掉一整類「兩邊都有東西但守的不是同一件事」的錯。
  遇到 factory 產生的 guard / interceptor / resolver 都適用
- **前端不承諾後端沒有兌現的東西。**（PR #66 / #68 建立，計畫席指定入 charter）
  這條有兩個面孔，都是「畫面看起來能用、實際會騙人」的同一個病：
  - **不要做只篩得到當頁的篩選。** `/api/invoices` 有分頁又沒有 `status` 參數，
    前端自己篩狀態只篩得到當頁 20 筆 —— 使用者看到「未繳 3 筆」而真相是 47 筆。
    繳費頁因此不做狀態下拉，改用每列的 Tag + API 真的支援的 `overdue=true`。
  - **不要掛後端不檢查的 `permissionGuard`。** `/api/contact-book` 的 mount 只有角色
    沒有 permission，前端硬掛一個只會得到「選單藏起來但直接打網址就進得去」，
    而且沒有人會發現不一致。上面那條「填了就要兩邊都動」的前提是**後端真的守著它**。
    推廣：交付前問一次「這個畫面承諾的事，後端做得到嗎」。做不到就少做一項並回報，
    不要用前端補一個假的 —— 假的那個會被信。
- **冪等做在後端，信心做在文案。** 月結（`POST /api/billing-runs`）是冪等的 ——
  它只撈沒蓋章的、處理完就蓋上 `invoice_item_id`，所以同一個月跑第二次不會重複開帳單。
  但**行政不知道這件事就不敢按第二次**，而「這個月到底跑過沒」正是他們會猶豫的地方。
  所以 UI 上直接寫「同一個月可以重複跑」。**危險操作的按鈕不是只要能按，還要按得下去** ——
  把工程性質翻譯成一句人話，比任何確認對話框都有用
- **後端刻意暴露出來的東西，前端不要蓋回去。**（#90 建立）
  營收報表的分組有 `（跨分校）` / `（跨課程）` / `（未分類）` 三個桶：一張帳單可以跨班
  也可以完全沒有班，後端**刻意**不做比例拆分（拆出來的數字沒人能跟收據對得起來）也
  不重複計入多個組（那會讓小計大於總計），而是多給一列把模糊**明著標出來**。
  前端把它藏起來、合併掉或改名，等於把那個設計蓋回去，而且會變成「小計加不回總計」
  的無聲錯誤。**照實顯示，再加一句說明它為什麼存在。**
  通則：後端註解裡寫「刻意」「不做 X 因為 Y」的地方，那是設計不是缺陷。
- **後端的形狀決定 UI 能給什麼能力 —— 判斷順序是先看後端吃什麼，再決定畫面給不給那個動作。**
  （#87 建立）餐費的區間模式是**唯讀**的：`GET /api/meals` 區間只回實際記錄、沒有
  「候選」概念（`classNames` 空、`mealDefault` false），而 `POST /batch` 吃的是
  **單一 `date`** —— 跨天的修改沒有對應端點。所以欄位全部 `disabled`、沒有確認按鈕，
  **而不是讓人改了卻存不進去**。這是「前端不承諾後端沒有兌現的東西」在**動作**層的版本
  （上一條是在**資料**層）
- **改一個 design token 的語意時，要掃它的「用途」而不只是找它的名字。**（#100 建立）
  `--accent-*` 從天藍換成品牌橘之後，所有拿 accent 強調**數值**的地方一夜之間跟警示色
  撞在一起（`--accent-600` 與 `--warning-600` 的 RGB 距離只有 34），營收報表的「退款」
  與「應收未收」變成同一個顏色 —— **換色的 PR 全綠，因為沒有任何測試在看顏色的語意**。
  掃的方法：找 `color: var(--token-` 的每一處，用 selector 名稱（value/amount/count/
  total/score…）篩出資料強調用途，再**逐一開檔看上下文**分成「數據」與「互動／狀態」。
  批次套規則會誤傷 —— 「已選 N 個」是選中態不是數值，`--dirty` 是狀態語意組的一員。
- **「前端能不能篩」看的是資料完不完整，不是「前端篩」這個做法本身。**
  同一個動作在兩支 API 上一個騙人一個不騙：`/api/invoices` 有分頁（前端篩會漏），
  `/api/contact-book` **沒有分頁**且 `meta.total` 是 `count: 'exact'`（前端篩與前端分頁
  都誠實，因為手上就是全部）。**先確認那支 API 有沒有分頁，再決定篩選放哪一端。**
- **顏色是有預算的 —— 每天都出現的常態花不起警示色。**（刀 3，2026-09 建立）
  餐費頁 8 列有 8 列是黃的、聯絡簿 6 列有 5 列是黃的，而那**就是每天早上的正常樣子**。
  沒人授權過「常態 = 警示」這個宣稱，它是一顆一顆 `severity="warn"` 累積出來的。
  三個可操作的判準：
  - **先問這一態是不是常態。** 是的話它必須沒有色相 —— 否則整欄都是警示，警示就沒有意義
  - **深淺表示「還在等 vs 不再等」，色相才表示「好 vs 壞」。** 一個還沒到期的待辦不是壞事
  - **`opacity` 會穿過對比 gate。** harness 的對比檢查看的是 `color` 與 `background` 的配對，
    `opacity: 0.6` 之後的實際對比它算不到 —— 要淡就調 token，不要調透明度
- **會動的東西要在手指落下之前就不動了。**（#169 建立）
  進度文字歸零就不渲染，footer 縮 25px、儲存鈕往上跳 —— 而那正是點下去的那一刻。
  修法不是撐 `min-height`（永遠多佔）也不是留空元素（白佔一格），是**發現那一刻其實
  有話講**：「全部標記完成」。我當初把「沒有待辦」讀成「沒有內容」，**優化版面的時候
  順手把一句該講的話刪掉了**。
  第二層同樣會咬人：**幾種狀態的文案長度要接近**，否則換行本身又是一次位移 ——
  等於換個地方跳。那條約束值得寫進註解，因為下一個人會想加一句長的。
- **訊號的設計者是最看不見它盲點的人 —— 因為訊號和驗證訊號的方法出自同一組直覺。**
  （#304 建立，措辭出自 infra 席）
  我做 API 參數覆蓋率 gate 時，用「我注意到的三個實例」設計訊號，再用那三個驗證它 ——
  **而那三個之所以被我注意到，正是因為它們的名字夠特別**（`billingMode` /
  `hasInvoice` / `attendanceTaken`）。名字普通的漏失我沒注意到，那個訊號也抓不到。
  同一天 infra 用 `grep __mobile` 驗證 `__mobile` 訊號、回報「三支全符合」——
  **漏掉的那支在定義上就不會出現在結果裡**。兩個實例，兩個人，當下都覺得自己驗過了。
  三個可操作的動作：
  - **反例測試，不是正例測試。** 拿掉一個**確定支援**的東西，看訊號會不會紅 ——
    那比再找三個它看得到的例子有力。`invoices` 的 `status` 就是這樣打臉我的第二版：
    註解裡有 `` `status` ``，所以刪掉組 query 那行也不紅
  - **兩個方向都要探。** 拿掉支援的測**漏報**、拿一個確定支援的測**誤報**，
    它們是不同的探針。我只做了前者，誤報（11 處物件簡寫被報成缺漏）是別人 grep 出來的
  - **誤報比漏報糟。** 漏報只是少擋一次；誤報會讓人**關掉整道 gate**，而且會污染
    baseline —— 假債收進去之後，去「修」它的人會發現根本沒東西可修
    **把別人審出來的東西變成每次都跑的測試** —— #304 的 6 個 self-test 有 4 個直接
    對應審查者指出的 4 個洞，那些洞現在不需要他在場也擋得住。
- **金額相關的選擇不該有預設值 —— 系統可以幫你算，不可以幫你決定。**（B3 建立）
  三個都是同一條：**試算算好了要按一下才填進去**（規則 5.2 說試算是建議值）、
  **收費期間第一個選項是「未選擇」**（不替人挑一段期間）、
  **沒有金額就不給開帳**（開一張金額是猜的帳單比不開更糟）。
  預設值在別的地方是體貼（點名的「全部出席」、選一個人時預設開帳），
  在錢上面是**替人做了一個他要負責的決定**，而且他不會知道那是預設的。
- **「沒有值」常常是一種值，不要為了消掉警告而消滅它。**（#162 建立）
  工單要把班級日期改必填來消除「無未來排程」的警告。但 `end_date IS NULL` 是**不限期**，
  API 靠它判斷班還在（`classes.ts:426`）、頁面靠它判斷歷史班；改必填等於刪掉一個合法狀態。
  另一半同樣重要：**那個警告不是誤報**，它算的是 sessions 表有沒有未來課堂，跟日期無關。
  **現象對不代表歸因對** —— 收到「A 導致 B」的工單，自己把因果鏈重走一遍：
  這次真正的病灶是補救路徑上多了一道門，不是 A 也不是 B。
  這跟 `empty-array-hides-loading` 是同一族的反面：那邊是把「不知道」寫成一個值，
  這邊是把一個有意義的值當成「還沒填」。**兩邊都要問一次：這個 null 在說什麼。**
  **常見的第三態是「還不知道」**（#169 的 `eventId`：`string` 可點名 / `null` 停課 /
  `undefined` 摘要 API 沒回來）。壓成兩態的話，那支 API 一掛整頁的入口全部灰掉 ——
  把「沒問到」講成「不能」。三態值得一個型別註解，因為它一定會有人想化簡。

## 坑（都是實際踩過的）

1. **選單與路由表之間的縫。** 頁面寫好、`showInMenu` 打開、測試全綠，路由卻還是
   `redirectTo` —— 功能等於沒交付而所有 gate 都綠。現在 `apps/web/src/app/app.routes.spec.ts`
   對每個 `showInMenu` 項目斷言「路由找得到」且「載入的是頁面不是 redirect」。
   **開新頁時它是你的安全網，別跳過它。** 通則：grep 一行不足以證明接線正確，
   路由/註冊/掛載這種「一個位置決定行為」的東西要連上下文一起讀
2. **`GET /api/attendance/sessions` 的 `date` 會蓋掉 `dateFrom`/`dateTo`**
   （`apps/api/src/routes/attendance.ts`）。想同時要「今天」和「一個回溯區間」必須發兩個請求 ——
   這也剛好讓兩個區塊各自失敗，不會一起死
3. **`OrgSettingsService.settings` signal 不是自動填的**，沒有 APP_INITIALIZER。要用
   `attendance_mode` 這類機構設定就自己 fetch，別假設它有值
4. **列表 API 的 `pageSize` 多半上限 100。** 要顯示「這段期間有幾筆」就取 `meta.total`；
   抓單頁明細自己數，會在量大的月份**悄悄少算而且錯得沒有徵兆**
5. **`nx test web --filter=...` 會騙人。** 它是 vitest 的 regex 且比對的不是檔案路徑；
   我試過的寫法讓 0 個測試跑到，卻印 `Successfully ran`。**全部 skip 也是綠的。**
   要嘛跑全套，要嘛核對測試數有沒有增加
6. **模板型別錯誤在 `typecheck` 那步就會紅**（#211 起，2026-09-03 訂正 —— 這條原本寫
   「web 沒有 typecheck target」）。web 的 typecheck 跑的是 `ngc -p tsconfig.app.json
--noEmit` 而**不是 `tsc`**：後者看不到模板，`{{ 不存在的屬性 }}` 它一個都不報。
   **Stop hook 跑 `nx affected -t typecheck`，所以本機收工就會擋** —— 以前要 push 才紅。
   `build web` 仍然不能跳，但它守的是別的東西：bundle budgets、fileReplacements、
   以及實際打包得起來。
7. **生成檔在分支上不要重生，撞到了才重生、絕不手併。** `roadmap.md` 的 `FEATURE-MAP`
   在分支上過期只是**提醒不紅燈**（PR #70 起），main 的 verify workflow 會自動重生 ——
   harness 自己會叫你別跑，照它說的做。真的撞了才 `harness:write`（自帶 prettier）；
   `kb/wiki/index.md` 與各 `_moc.md` 用 kb-wiki 的 `map` 重生。**任何情況都不手併生成區塊。**
8. **`map` 會保留既有的 curated summary**，frontmatter 的 `summary` 只對索引裡還沒有的新頁生效。
   改了既有頁的 summary，`index.md` 與該分類 `_moc.md` 那兩行要手動同步，或跑 `map --regen-summaries`
9. **`kb/` 的 design token 不是 `--color-*`。** 實際存在的是 `--zinc-*` / `--accent-*` /
   `--space-*` / `--text-*` / `--radius-*` / `--font-*`（看 `styles.scss`，或直接抄
   `campuses.page.scss`）。我照別的專案的習慣寫了 `var(--color-text-primary)`，
   編得過但整頁沒有顏色 —— **CSS 變數打錯不會報錯，只會靜靜地不生效**
10. **`enrollments.page.ts` 是唯讀瀏覽列表，不是報名表單。** 工單說「去報名頁加欄位」時
    先確認它指的是哪一個 —— **建立**走班級名單的 `student-picker-dialog`
    （`POST /api/enrollments/batch`），**單筆修改**走名單的動作選單
    （`PUT /api/enrollments/{id}`）。而且**沒有「單筆報名」這個入口**：
    `enrollmentsService.create()` 至今零呼叫端，一個人也是走 batch。
    （2026-09-03 訂正：這一條原本寫「batch 不吃計費欄位」—— **錯的**，
    它從一開始就吃，只是 web 的型別漏了三個欄位所以沒人送。見坑 #14 第三型。）
11. **不要對 `index.md` / `_moc.md` 跑 prettier** —— 它們是 generator 原始輸出，
    prettier 會在每個 `## 標題` 後插空行製造反向雜訊。`roadmap.md` 相反，它是 prettier 對齊過的
12. **送出時「清空一個欄位」要送 `null` 不是 `undefined`。** 後端把 `undefined` 當成
    「沒給」而保留原值 —— 餐費的備註因此清不掉。`note: row.note.trim() || null` 而不是
    `|| undefined`。這類 null 語意值得一個測試，因為它**只在「把有值的欄位清空」那條
    路徑上錯**，新增與修改都是對的。
13. **渲染大量列的 PrimeNG 輸入元件會 `Maximum call stack size exceeded`。**
    餐費頁的「超過 300 筆擋住」測試原本走 `fixture.whenStable()`，301 列直接爆掉。
    **驗邏輯的測試直接設 signal 不要走渲染** —— 它要驗的是擋不擋得住，不是畫不畫得出來。
14. **自己查出來的推論，比別人給的前提更危險** —— 因為它披著「我親自查過」的外衣。
    工單的前提我會驗，自己掃出來的結論反而不驗。三個實際踩過的形狀，共同點是
    **查到的東西證明的不是你以為的那件事**：

    | 你查到                    | 你推論             | 實際                                                         |
    | ------------------------- | ------------------ | ------------------------------------------------------------ |
    | grep 到 `subscribe`       | 這份資料非同步載入 | 那是批次操作的 subscribe，資料 `config.data` 同步傳入        |
    | grep 自己想的命名，沒命中 | 這件事沒做         | 做了，用的是別的名字（別席誤判 #169 沒做 `exemptCount`）     |
    | API schema 有欄位         | 有人在送           | web 的型別漏了它，呼叫端一個都沒送（#186 的 `billingMode`）  |
    | 別人給的一份分析          | 那是它現在的主張   | 它自己早就更正過了 —— 我對著沒有人還在主張的東西寫了整段反駁 |
    | 別人凍結給我的介面        | 照著寫就對         | 實作時改了而沒通知我（#300 的 `recordScope`）                |

    **陽性結論跟否定結論一樣要開檔確認。** 第三型特別會咬人，因為前後端契約看起來
    是權威來源 —— **契約說得通不代表有人走過那條路**。

    後兩型是同一件事的兩面：**程式碼是權威，訊息是快照。** 第四型的教訓是
    **查證做得再紮實，對象錯了就是零** —— 我那段證據鏈每一句都對，只是在反駁一個
    已經被作者自己撤掉的版本。第五型省事的做法是：**照 main 上的實作寫，不照訊息寫**。

    還有一個更陰的變體：**列出證據的形狀，不等於證據支持那個結論。** 一份分析列了
    檔案路徑和變數名，讀起來像查證 —— 但它可能只是把「我以為的呼叫方式」寫得很具體
    （infra 那次假設了 `appendTo` 的值，而每一句單獨看都對）。
    更便宜的版本：**單次觀察不足以斷定缺陷** —— 我從一次沒點中的滑鼠回報過「死區」，
    用 `elementFromPoint` 量五個位置才發現全在列內。**發現「怪」到宣稱「壞」之間，補一次測量。**

15. **交付新頁面要把它認領進 `tools/agent-harness/feature-map.mjs` 的 AREAS**，
    否則 `npm run harness` 會紅（「頁面 未被任何功能區認領」），`harness:test` 也跟著 fail。
    那是 infra 席的檔案，但**這一行是 gate 明確要求交付者補的**，不是主動動 infra ——
    就像新增 skill 之後要跑 `harness:write`。**只補那一行、不要順手重生 roadmap**（坑 #7）；
    PostToolUse 的 prettier 若順手重排了檔案裡其他地方，把那些還原 —— 那是別人的檔案。
    **區分**：紅燈擋住交付 → 自己補；只是顯示不準（route 歸錯功能區之類）→ 回報計畫席。
16. **別人造成的紅燈不要自己補，但一定要回報。** 坑 #15 的「自己補」只適用**自己的交付
    造成的**紅燈。這一輪 main 紅過一段時間（`c8` allowlist 過期，別席改完沒清），
    補它會把不相關的改動混進自己的分支；但不回報的話，**下一個開分支的人會以為是自己
    弄壞的** —— 我就花了一次來回切到乾淨的 `origin/main` 重跑才確認不是我。

17. **standalone 元件的 `imports` 陣列沒有人幫你對帳。** 把模板裡最後一個 `<p-tag>` 換掉之後
    `TagModule` 還留在 `imports` 裡，**編譯、測試、build 全綠** —— 沒用到的 import 不是錯誤。
    改模板時順手掃一次自己動過的元件：移掉的是**依賴**，不是錯誤，所以沒有任何 gate 會提。
    跟坑 #9（CSS 變數打錯不報錯）同族：**靜靜地不生效與靜靜地留著，都不會有紅燈。**
18. **`attendance_records.status` 漏送會收到 500，那是設計。** `DEFAULT 'absent'` 已經
    拔掉（`20260902020758`）—— 忘了給 `status` 的 INSERT 直接失敗，而不是安靜寫一筆
    假缺席。看到那個 500 不要去「修好」它，要修的是漏送的那一端。
19. **`toISOString()` 是 UTC。** `new Date().toISOString().slice(0, 10)` 在 UTC+8 的
    00:00–08:00 之間回**昨天** —— 三個正式站的地方加兩個測試踩過。要今天的日期用
    `shared/utils/session-time.util.ts` 的 `todayLocal()`。連帶：**測試不要依賴牆上時鐘**，
    把 `now` 當參數傳進去，否則它只在某些時段是綠的。

20. **手邊的狀態不等於你以為的那件事。** 坑 #14 是「查到的東西證明的不是你以為的事」，
    這條是它的近親：**沒查就用**。兩個實際踩過的：
    - **`git add -A` 在切過分支的工作區裡不安全** —— 它收的是「現在工作區有什麼」，
      不是「我這支要什麼」。我在 charter 分支改完沒 commit 就切去開 hotfix，
      未提交的改動跟著走，被 `add -A` 收進那支 commit，於是一支「只改 SCSS」的急件
      夾帶了 12 行 charter（而且那 12 行有順序依賴）。**開分支前先 `git status`**，
      急件更容易踩到，因為急著開分支就不會先看。
    - **`str.replace` 沒有 assert 等於沒有回饋** —— pattern 沒命中時它靜靜地什麼都不做，
      下一個替換就參照到不存在的東西。**每個替換都 `assert old in s`**；
      prettier 折過行的簽名尤其會咬人（單行 pattern 對不上多行原文）。
21. **查證「成因」不等於查證「現象」，兩者可以一真一假。** Tester 報家長端一則提示
    看起來像錯誤樣式（紅字粉底），我查到程式碼寫的是 `severity="info"`、git log
    從沒改過，就把「成因不成立」跳成「現象不成立」——但兩者是不同的事，計畫席核對
    色票後發現 `--accent-600`/`--error-700` 視覺上根本分不開，**現象是真的，我查錯
    的是它的解釋**。查到「程式碼語意寫對」之後，正確的下一步不是「所以沒問題」，
    是「那為什麼看起來像有問題」——這個問題才會把人帶到真正的成因（這次是色票）。
    這條的推廣後來被同一天的 sticky 表頭（#12：`z-index`/`background` 都設對，
    下一列還是被切掉）與 CSS 死規則（`session-filters` 的 `&--date-range` 寫對了
    語法，模板卻套了另一個 class 家族）驗證：**「宣告的語意」與「渲染/觸發的
    結果」是兩件事，程式碼只證明前者**，完整案例集見 [[lessons/broken-looks-identical-to-normal]]。

    **同一天我自己又犯了一次條件層的版本**（P0-2，Tester 報點名漏掉請假學生）：
    `attendance-roster-panel` 的 footer 有三個分支（未標記/全班請假/完成），
    我確認「三個分支都存在、邏輯看起來對」就回報不成立。計畫席重查發現第二個
    分支多寫了 `markedCount() === 0`，只涵蓋「全班都請假」——標了一部分又有人
    請假的混合情況會落到 else，顯示「全部標記完成」但其實有人根本沒被標記。
    **我查的是「分支存不存在」，沒查的是「這個分支在 tester 講的那個具體情境
    下會不會觸發」。** 「功能存在」與「功能在這個情境下會觸發」是兩件事，
    後者才是決定性的——下次查證「不成立」之前，拿報告裡的具體數字（幾人標記、
    幾人請假）親手把條件式跑一遍，不要只看分支覆蓋得夠不夠。

## 這一席的工作習慣

- **設計文件沒到手不要動工。** 遇過工單說「設計在 main 上」但檔案根本不存在（從沒 commit）。
  查不到就回報計畫席要，不要拿工單摘要當設計自行補完
- **工單裡的前提要實際驗證再信 —— 資料前提如此，它建議的修法也一樣。**
  儀表板 v1 六張卡有一張的 API 前提是錯的（以為有進出聚合，實際只有明細加 total），
  照原設計做會顯示錯數字。派唯讀 agent 逐項確認 API 存不存在、回傳什麼形狀，比事後改便宜。
  **修法的部分**：#162 的工單給了兩個傾向，查完兩個都會製造新問題（見先例「沒有值也是一種值」），
  兩個都沒採用、改提第三條。計畫席的回覆把這件事定了性 ——
  **工單的傾向僅供參考，查證後推翻是本分。** 推翻時要帶著證據回報，不是默默改成別的
- **從空結果推否定結論之前先確認工具沒洞。** 我用 `find -type d` 找一個 symlink 目標，
  回空就斷言「不存在」並寫進 PR —— 是錯的
- **認領 GitHub issue 之前，先 `gh pr list --state all --search <關鍵字>` 查它描述的東西
  是不是已經做完了。** #429（科目平均改幾分之幾）動工前照 issue 自己的提醒去查證，
  結果不是「還沒做」，是**已經做完**——PR #333 一天前就合了，issue 沒有跟著關。
  這是「假閘門」（工單說某個前提已成立、實際沒有）的反面：**閘門真的開了，也真的有人
  走過了，只是工單文字沒跟著更新。** 兩種情況查證的動作一樣（先查現況再信文字），
  結論不一樣（一個是動工，一個是回報關單）——**差別只在「查完之後」，不在「要不要查」**，
  所以查證這一步不能因為「聽起來像已經做過」或「聽起來像還沒做」而省略任何一邊。
- **既批 spec 涵蓋的頁面不用補設計文件。** `clessia-feature-slice` 的設計文件是為了
  **取得批准**；工單說「STOP gate 由既批 spec 覆蓋」時，決策記在 commit message 與 PR 即可。
  事後補一份沒人會讀的存檔違反「實作計畫不進 KB」的精神（2026-08-30 計畫席裁定）。
  **但別在 spec 裡引用一份你沒寫的設計文件** —— 我一度寫了 `[[architecture/admin-meals-page]]`
  才發現那頁不存在
- **修一個 UX 問題之前，先確認同樣的畫面有沒有第二份實作。** 分岔不是靠時間長出來的，
  是靠一次一次「只修我手上這份」長出來的：「預設全班缺席」在 #135 / #138 各修一次、
  #159 只給 panel 加請假感知、#161 只修 academy 那份成績登錄（school 的鍵盤處理至今是 0）。
  每一支都是好 PR，合起來是兩套會各說各話的東西。
  **真的要收斂時，先列「只有 A 有」與「只有 B 有」兩欄。** 分岔久了兩邊都會長出東西，
  而後長出來的那些正是別人踩過坑才加的 —— 挑一份當基底、另一份直接刪，
  會靜靜地弄丟一道防線，而那是最貴的損失：沒有測試會紅，沒有人會發現
  （#169 收兩份點名時，panel 有請假感知、我的 dialog 有未完成防護，各缺對方一半）。
- **`disabled` 是把「為什麼不行」藏起來，而那正是使用者最需要知道的。**
  按不下去的按鈕不會解釋原因，按得下去的才會 —— 點名的儲存鈕刻意不 disable，
  按了才說「還有 N 人沒標記」。**例外是按下去會產生後果的按鈕**（送出付款那種），
  那裡 disable 是對的，因為誤觸的代價高於困惑。
  **判準是「按下去會發生什麼」，不是「現在能不能按」。**
- **防線分四層，距離不一樣 —— 挑得動的那一層。**

  | 防線                 | 擋得住誰                         |
  | -------------------- | -------------------------------- |
  | **拿不到錯的工具**   | **所有人**                       |
  | 函式簽名（必填參數） | **呼叫它的人** —— 沒呼叫就沒防線 |
  | 測試                 | 正在改這段的人                   |
  | 註解／規則           | 願意停下來讀的人                 |

  **第一層是 2026-09-04 補上的，而且是被推翻出來的。** 家長端授權設計原本寫
  「查詢走強制吃 scope 的 helper，必填參數讓忘記編不過」—— billing-api 指出它
  **守不住「根本沒呼叫」**：route 直接寫 `c.get('supabase').from(…)` 照樣編過，
  **而從 admin 端複製過來的 route 天生就是那個形狀**。改成家長端拿不到原始
  `supabase`、只拿得到已綁 scope 的 `childDb` 之後，**正確的寫法比錯的短**，
  要繞過得先去拿原始入口 —— 那是一個看得見的動作，不是一個忘記。

  這條原本寫成三層，第一層是「函式擋所有呼叫端」。**字面沒錯，但我自己引用它的時候
  讀成了「擋所有人」** —— 那兩個差一個「呼叫」。表格會被誤讀，包括寫表格的人。

  **小尺度的同一招：相鄰的 optional 參數改成物件。** `isFailingScore(score, 100, 70)`
  傳反了不會有型別錯誤，而錯的結果是**整班被標成不及格、或整班都及格**。
  改成 `{ passScore, totalScore }` 之後，**順序不存在了** —— 不是「記得順序」，
  是拿不到那個錯。兩個以上同型別的 optional 參數就該考慮這件事。
  第二層的兩個實例：`session-time.util.ts` 把「這堂課上完了沒」變成一個函式，兩個畫面就不可能
  各說各話；而「teacher dashboard 那支同名概念的 `null` 行為跟這支相反，這是兩個函式
  不是重複」原本只是一句註解，寫成一個**測試**之後，才擋得住「看起來重複所以合併了、
  然後跑 CI」的那個人 —— 而那正是會做這件事的人。**發現一個誤會容易發生時，
  先問這句話能不能升級成程式碼。**
  同一節裡的反面：**型別是一個會過期的保證。** `Session.startTime` 型別上不可為 null，
  但欄位語意會變、schema 會改，執行期的判斷該自己守住 `if (!startTime) return false`。
  型別擋的是**現在**的呼叫端，不是未來的資料

- **判斷一個狀態值的意思，值域和標籤兩邊都要看 —— 然後去讀那個動作的確認文案。**
  考試的 `active`/`closed` 我從值域讀成「啟用/停用」的開關，design-web 從標籤讀成
  「進行中/已結束」，**兩邊都只對一半**。真正的權威定義在按下那顆按鈕的確認對話框裡：
  「結束後將無法再登錄分數」—— 一句話同時給了語意和不可逆性。
  **要知道一個狀態代表什麼，去找改變它的那個動作怎麼跟使用者解釋。**
- **視覺改動可以在部署前用「模擬法」預覽**：在已部署的頁面上用 JS 把那個元素的
  computed style 改成新值 → 截圖 → **改完還原**。比跑本機 dev + seed 便宜得多，
  而且能給出視覺證據。**兩個前提缺一不可**：回報時明講「這是模擬不是部署實況」，
  以及做完把頁面還原（留一個被改過的頁面給別人看比沒截圖更糟）。
- **「工單派了」不是跨過席位邊界的依據。** charter 寫著不碰 `apps/api/**` 與 schema，
  而 backlog 曾派給我「migration + API + UI 一條線」。**我沒動手，先問** ——
  結果是計畫席的檔案疏漏（裁決落在別的段落沒同步進席位區塊），補齊後拆席。
  同一輪還有一次：ops-warden 轉述「四項全裁」，而 backlog 上只有一項存在。
  **不照轉述動 migration**。（延伸自坑 #14：程式碼是權威，訊息是快照。）
- **看不出可以先行的部分，就明說在等 —— 那比硬擠一個空殼 PR 好。**
  及格線那條線的前端半可以先行（`passScore` 是 optional，欄位未生時行為不變）；
  科目平均那條**不行**（顯示「130/150」需要那兩個數字，沒有就沒東西可顯示）。
  兩者的差別是**有沒有一個不改變現況的退路**，有就先接、沒有就等。
- **判準先給人審，再寫 code。** 做 gate 或任何「訊號」類的東西時，把判準寫成一段
  文字寄出去 —— **審的人不用讀 code 就能否決一個錯的判準**，而讀 code 才發現判準錯
  是最貴的順序。#304 那四輪收斂全部發生在寫完之前或剛寫完，成本是重寫幾行 regex；
  如果等到接進 harness 才發現，成本是一道帶著假綠燈上線的 gate。
- **通報了一個角色，不等於通報了所有人。** 決定變了要報裁決者，介面變了要報**消費者** ——
  那是兩件事，做了前者很容易以為做完了（infra 改 `recordScope` 時報了計畫席、
  沒報拿著凍結介面的我）。同一個形狀：我把「合併文件 ≠ 批准動工」寫在 PR 頂端給
  計畫席看，卻沒寫給**將來讀那份 KB 文件的人**。**問一次「誰手上拿著我剛剛改掉的東西」。**
- **測試的替身要照著真實那一端的行為做。** 未點名卡改用伺服器篩選之後，我讓 mock
  也依 `attendanceTaken` 篩 —— 不改的話測試會對著一個**真實環境不存在的回應**斷言，
  那個綠燈是假的。（billing-api 那邊的說法是「替身要跟著路由變」，同一件事。）
- **同一個語意出現在兩條路徑時，測試裡放一張「差異對照表」—— 不是強求一致。**
  未點名卡的數字來自兩段（昨天以前走 API 的 `attendanceTaken=false`、今天走前端的
  `countUntakenSessions`），而 #310 那個不一致**測試全綠** —— 因為沒有人把兩段
  並排看過。修法不是把兩段抽成同一個函式（一段在 SQL、一段在 TS，**強求一致會逼出
  假抽象**），是在測試檔頭放一張表，**列出差異並說明每一列為什麼是安全的**。
  #314 就是這樣抓到第三列的：前端有 `hasSessionEnded` 而 API 沒有，
  **API 之所以不會把還沒上的課算進去，完全是靠呼叫端只查到昨天** ——
  一個藏在參數裡的前提，有人改 `dateTo` 就破。
  **那張表的價值不在證明一致，在逼人問「這一列為什麼可以不一樣」。**
- **測行為，不要測實作 —— 那樣的測試在別人重構之後還能用。**
  #207 那份匯入測試餵的是 `xlsx` 現場寫出來的真 workbook（不 mock 解析），
  所以 xlsx 從同步 import 改成 `await import` 之後**一個字都不用改**，
  而且我在那支 PR 還沒合之前就把 spec 複製到它的分支上跑出對照表 ——
  **事前的對照組比事後的確認有用**。同一輪 #196 也一樣：academy 的 16 個測試
  在鍵盤邏輯抽成 util 之後不改就綠，那就是等價驗證。
  反面：測「有沒有呼叫某個私有方法」的測試，重構一次就要改一次，
  而它改完之後你也不知道行為有沒有變。
- **理由成立只是「准不准」，程序是防止「准了之後出事」—— 兩件事不互相抵銷。**
  我提疊 PR 時把「豁免理由成立」講成了「程序可以跳」。計畫席准了理由、
  但要求照疊 PR 鐵律轉 Draft（base 沒落地前不得 ready）—— 那條鐵律是上一次
  幽靈合併換來的。**豁免的是規則的適用，不是規則存在的原因。**
- **charter 是自己寫的，所以讀它的時候不會懷疑它。** B3 設計我照抄了自己 charter 裡
  「`POST /enrollments/batch` 不吃計費欄位」那句 —— 它早就過期了，開工第一天就撞上。
  **過期的條目比沒有那條更糟，因為它會被信。** 引用 charter 裡的事實類敘述
  （API 形狀、有沒有某個 target、欄位吃不吃）之前開檔確認一次；
  判斷類的（「為什麼這樣做」）不會過期，事實類的會。
- **交付有順序依賴時，把它寫在 PR 標題底下第一行。** #186 送 `adjustmentNote`，
  而批次收它是 #184 補的 —— 先合的話使用者剛填的原因會被後端 strip 掉。
  **「合了會怎樣」比「依賴誰」有用**：計畫席排順序時看的是後果，不是相依圖。
- **不要留一個新的 build warning 給下一個人。** SCSS 有 6 kB 預算（超過只 warning 不紅燈，
  所以很容易放著）。我加計費區塊超了 102 bytes，壓的方法是刪掉能靠繼承拿到的宣告、
  把 contextual override 換成直接子選擇器 —— **沒有一項是視覺妥協**。
  貼著預算的檔案本來就在邊緣，加東西之前先看它在不在警告清單裡。
- 收工前照 `.github/workflows/verify.yml` 的序列在本機重放一次，不要只跑 affected
- **判定「不算缺口/不算不一致」時，要指出它跟哪個既有模式同族，不是只說「我覺得可以」。**
  `fee-templates` 兩顆「新增」查證後是跟 `courses.page.html` 每個課程群組底下的
  「新增班」同一種「巢狀次要新增」；`courses`/`exams` 的篩選改用 popover + 數量
  badge，是跟篩選維度太多的頁面同一種「刻意的漸進式揭露」。**一致性工作最大的
  風險不是漏改幾頁，是把有意義的差異抹平** —— 抹平之後那個當初刻意不同的理由
  就永遠消失了，沒有人會為「我們曾經刻意不一樣」寫紀錄。
- **確認「不用改」要寫下來，這本身就是一次有效交付。** 查完請假頁四條確認訊息、
  對照 API 真的有 `revert_leave_attendance`/`truncate_leave` 兩個 action 之後，
  直接回報「確認不用改，記在這裡」而不是沉默結案。**沒有被記錄的「查過了沒
  問題」，跟沒查過在帳面上長得一模一樣** —— 下一個人分不出這兩種狀態，只能
  重新查一次。
- **「最近的正確答案優先於最好的正確答案」，字面意思是去找同一份文件/同一排
  標頭裡現成的寫法，不是去借風格最像的。** 課程層級的刪除鈕原本要照抄班級層級
  的 ⋮ 選單，但同一排標頭裡「新增班」按鈕自己就有 `[disabled]+[pTooltip]` 的
  現成模式——比借班級列的選單更近，而且不用把「新增班」這個常用主要動作也
  收進選單裡（那會是體驗倒退）。**目標是「使用者按之前就知道能不能按」，
  選單只是達成那個目標的一種載體，不是需求本身。**
- **UI 對使用者做出的承諾，要先問後端兌不兌現得了 —— 兌現不了就老實說「可能」，
  不要假裝擋住了。** 科目刪除在後端還沒查 `academy_exams` 用量之前，確認文案
  只能寫「可能影響已使用此科目的課程與考試」，不能寫成「已檢查無影響」——
  一個寫著「已檢查」的對話框，在後端沒檢查的情況下比沒有對話框更糟，它把
  「使用者知道自己在冒險」換成「使用者以為系統確認過了」。**這條要記得回頭
  兌現**：後端補上真的檢查（用量欄位到位）之後，文案要跟著從「可能」升級成
  確定的說法，不要留著舊的免責聲明——這是「等 X 成立就回頭檢查」的正面案例：
  條件明確標了（等 API 補上檢查），條件成立時真的被回頭兌現，不是留著等別人發現。
