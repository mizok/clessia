## 一、補授權缺口的工具箱（`apps/api/src/lib/org-scope.ts`）

- `findInOrg(supabase, table, orgId, id, cols)`：寫入前的存在檢查。**別 org 的 id 跟不存在一樣回 null → 404**
  （403 等於告訴對方「id 存在」）。查詢失敗**丟例外（500）**，不折成 null —— 「DB 掛了」≠「沒有這筆」。
- `inOrg(query, orgId)`：**寫入本身也帶**，不只前面讀一次。兩層各有偵測器：讀取那層由路由 spec 釘，
  寫入那層由 harness **A23** 釘 —— 只拿掉寫入的 `inOrg`，spec 會是綠的（讀取守衛先 404），**那一半只有 gate 看得到**。
- `missingInOrg(...)`：body 帶一批 id。**任何一個不屬於本 org 就整批 404**，不略過（略過會讓回應的計數混進別 org，
  部分成功會讓人以為整批都處理了）。
- **存在檢查排在所有守門查詢之前**：否則別 org 的 id 先拿到 409「此班級已有歷史課堂」—— 那是資訊洩漏。
- ⚠️ TS2589：`.in()` 之後的 builder 丟進 `inOrg` 的泛型推導，**當 table 是 `OrgTable` union 時**會撞
  「excessively deep」。那種地方直接寫 `.eq('org_id', orgId)`（gate 兩種都認）。具體表名（`'classes'`）不會撞。

## 二、回傳型別改了，就把名字也改掉 —— 讓編譯器找出每個呼叫點（B6）

`isStudentInScope` 要從 boolean 改成三態（`'ok' | 'not-found' | 'out-of-scope'`）時，**名字一併改成
`studentWriteScope`**。理由：回字串的函式若還叫 `is…`，漏改的 `if (!(await isStudentInScope(…)))`
**永遠是 false（非空字串是 truthy）—— 靜靜全放行**，而且 typecheck 不會報（`!string` 合法）。
改名之後舊呼叫點全部編不過，`nx typecheck` 逼出全部 8 處。

> 一般化：**語意變了但型別仍然相容的改動，是最容易漏改呼叫點的改動。**
> 同一招在 B3：`getStaffById(supabase, id)` → `getStaffById(supabase, orgId, id)`，多一個參數，
> 9 個呼叫點（實際 8 個）一個都漏不掉。**根因在共用函式時，改簽名而不是逐個呼叫端補條件。**

為什麼是三態而不是只改 helper（計畫席裁定）：只改 helper 的話別 org 的 id 會得到 403
「沒有這個分校的權限」—— 既跟 B1–B5 的 404 不一致，又等於確認 id 存在。代價是每次寫入多一次查詢（寫入路徑、量小）。

## 三、harness 帳面（A23，`org-scope-baseline.json`）怎麼壓

- 逐檔計數，**只能往下**：超過帳面紅（新增違規），**低於帳面也紅**（修掉了要把帳面改小 —— 否則下一個人免費加回去）。
- 壓帳面：`npm run harness:write`。它**只會把每一行往下壓（min）**，不會替新違規開帳。
- **幾支並行 PR 各壓各的行時，會在 baseline 相鄰行衝突**：誰後合誰 rebase，**採任一邊之後再跑一次 `harness:write`**
  就是對的答案（它取 min）。不要手算。
- 寫 gate 一定塞陷阱：拿掉一處 `inOrg` → 紅；`harness:test` 紅綠各一條。gate 的集合（哪些表有 `org_id`）
  **從 migration 推導**，再對照 `OrgTable` union —— 不抄清單（c11）。
- **gate 看不到 insert／upsert**。收尾時要另外掃 `onConflict`：**衝突鍵不含 `org_id`、payload 寫 `org_id: orgId`
  的 upsert，只要 key 的 id 沒先驗 org，就會把別 org 那一列整列覆寫**（B4 meals、B6 三支都是這個形狀）。

## 四、multi-org 記憶體替身（`apps/api/src/test-utils/multi-org-db.ts`）

- **真的照條件過濾**：`eq('org_id', A)` 真的會濾掉 B 的列，所以能斷言「B 的列沒變」，不是「查詢長得像有帶條件」。
- **沒實作的方法一律丟例外，不放行**。撞到就補實作（B3 補 `gte`／`lte`、B2 補 `or`、B6 補巢狀欄位與 `limit`），
  **不要改成回 `this`** —— 「替身不認識所以回空」正是過去空轉測試的來源。
- `upsert` 的衝突比對**跨 org**（只看 `onConflict` 那幾欄），跟真 DB 一樣 —— 替身不能替 bug 擋掉。
- 別的批次也在改替身時：**把對方那個 hunk 逐字複製過來**（同位置、同內容），`git merge-tree` 會判成無衝突。
  ⚠️ **取 hunk 的 diff 基準要對**：`git diff origin/main <別人的分支>` 若對方分支比 main 舊，
  會**倒退掉 main 上已合的東西**（我在 B5a 踩過：一次倒退了 B2／B4 的 `upsert`／`not`／`or`）。
  要用 `git diff <對方的基底> <對方的分支> -- <檔>`。
- 驗「修前會紅」：把**被改的產品碼**換回 `origin/main` 版跑新 spec，跑完還原。zsh 要用陣列：
  `F=(a.ts b.ts); git checkout origin/main -- $F`（`F="a.ts b.ts"` 不會被拆開，整串當一個路徑）。

## 五、疊 PR 之後的 rebase 順序

1. 下層一 squash 進 main：`git fetch -p` → `git rebase --onto origin/main <下層本地分支> <上層>`
   （下層本地 ref 還指著 squash 前的 commit，正好當 `--onto` 的切點）。
2. `git range-diff <舊head>~N..<舊head> origin/main..HEAD`，`=` 就是逐字相同；貼進 PR 留言。
3. 新基底上重跑 harness、typecheck、相關測試 → `git push --force-with-lease=<分支>:<舊sha>`。
4. `gh pr edit <n> --base main` → `gh pr ready <n>`。回報新舊 head。

**更好的是不疊**：B1 合了之後其餘各批都從 `origin/main` 開，彼此用 `git merge-tree --write-tree A B` 兩兩試合，
回報「誰先合都可以」。只有 baseline 那一行會撞（見三）。
