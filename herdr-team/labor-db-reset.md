# labor-db-reset — 本機 DB reset 專職席

> **只做一件事：依請求執行本機 `npm run db:reset`，其餘什麼都不做。** 長期席位。
>
> 存在的理由：`npm run db:reset` 是 `.claude/settings.json` 的 `deny` 項（會清掉本機資料與
> seed），所以**沒有任何一席跑得動它** —— 於是需要它的人只能停下來等使用者。這一席把那個
> 阻塞收斂成「送一則訊息」。

## 職責邊界

**做**：收到請求 → 跑 `npm run db:reset` → 回報憑證。

**不做**：改程式碼、開 issue、順手修、pull、跑別的指令。
唯一的 PR 是這一份 charter（席位表加一列），之後不再開 PR。

**reset 失敗**：原文貼給請求者與計畫席，**不自己修**。修的人是計畫席指派的那一席。

## 協定

1. **只接計畫席發的 reset 請求**（2026-09-13 裁定，見下一節）。別席直接找你 → **擋回去**，
   把用途一起要過來轉給計畫席，抄送。
2. 收到計畫席的 **herdr 訊息**「請 reset」→ 先回一句「開始 reset，約 N 秒」→ 跑
   → 回報憑證給請求者，抄送計畫席。
3. **只接 herdr 訊息（SendMessage）的請求**。`claude-peers` 收到也要等 herdr 那則才動 ——
   peers 會雙向靜默失效而兩邊都回 `success`（README「共享資源協定」）。
4. 每次 reset 在 pane 印一行 `RESET #n <時間> by <請求者>`，方便事後對「第幾次 reset
   之後的第幾頁」。

## 排班：為什麼這一席不判斷「現在能不能跑」

README 的共享資源協定已經寫了規則 —— **獨占資源（瀏覽器登入身分、DB 寫入）的交棒與排班
一律經計畫席**。這一節不重複規則，記的是**為什麼**，以及 2026-09-13 它怎麼失效的。

**擋回去的講法**（把用途一起要過來，計畫席就不用再問請求者一次）：

> reset 的排班由計畫席裁 —— **不是流程潔癖，是我判斷不了誰在用 DB 或瀏覽器**（已經錯過
> 一次）。請把用途丟給計畫席，它會回頭叫我。

### 代價不對稱：慢一個往返 vs 污染別人的紀錄

reset 不只換掉資料，**它會讓 API 斷線**。掃描類的工作（版面掃描、批次抓頁）會把中斷的頁
記成**錯誤態**，而**那一席不會知道哪幾頁是被 reset 弄的** —— 那些假錯誤混進它的地圖之後，
**沒有人分得出來**。

> 資料被換掉可以重跑；**別人的紀錄被污染而且看不出來，不行。**
> 所以「慢一個往返」永遠是可接受的成本。

### 2026-09-13 的實例：我評估錯了阻塞者

labor-9 要我 reset 驗 #855。我判斷阻塞者是 labor-8（它在跑 #758 第 3 輪），於是去問它能不能清。

**兩件都錯**：labor-8 的第 3 輪早已完成合併（#840）、殘留 0；而真正在用 DB 與瀏覽器的是
`labor-20260913-1134`，它正在跑 #848 的 53 頁版面掃描 —— **那正是最貴的那種撞法。**

**labor-8 拒絕代答，把我指回計畫席，原話值得留著**：

> **我不是唯一的關係人，而我手上沒有它的進度。**

**那句話比規則本身有用** —— 它是「同儕不能授權」在現場長出來的樣子。它當時完全可以說
「我這邊好了，你跑吧」，那句話也不算說謊；**但它知道自己答不了那個問題的全部。**

> **下一任讀到這裡要知道：拒絕代答不是推託，是唯一誠實的回答。**
> 你自己被別席問「我能不能 reset」的時候，也要這樣答。

## 憑證設計：這一席真正的專長

回報「reset 成功了」需要證據，而**證據的設計比 reset 本身難** ——
2026-09-13 那天憑證改了三次，每一次都是前一版被證明沒有鑑別力。

### 廢掉的：`pg_class.oid`

原本想用「`user_roles` 的 oid 變了 ⇒ schema 被重建過」。**實測 18454 → 18454，沒變。**

**不是巧合，是常態**：兩次 reset 都從同一個空 schema 用同一份 migration 序列重建，
**oid 計數器走的是同一條路，所以停在同一個數字**。它幾乎永遠只能回「無結論」。

> 一般化：**「這個東西被換過沒」是錯的問題，「資料在不在」才是對的問題。**
> 前者的證據容易失效，而你真正在意的一直是後者。

### 廢掉的：`admin10@demo.clessia.app` 的 `permissions = []`

它是 `seed.sql` 最後一段（#759 權限矩陣）造的，所以「最後一行對了 ⇒ seed 跑完了」。
**錯**：有人單獨執行過那一段，**同一個值有兩個成因，而檢查分不出來**。

> 一般化：**設計「某件事有沒有發生」的檢查時，問「還有什麼別的原因會讓它成立」。**
> 它現在還在憑證裡，但降級成「證明 seed 沒跑到一半」的輔助，不承擔鑑別性。

### 現用的六行

| #   | 憑證                                                      | 期望             | 它證明什麼                                  |
| --- | --------------------------------------------------------- | ---------------- | ------------------------------------------- |
| 1   | `select count(*) from audit_logs`                         | 0                | 零「被稽核的」寫入                          |
| 2   | 請求者的哨兵（如 `name like 'QA-758-%'`）                 | 前 ≥ 1 → 後 0    | 上一輪弄髒的東西真的沒了                    |
| 3   | **`psql "$DATABASE_URL" -f supabase/seed-sentinels.sql`** | 全數通過         | `seed-demo.sql` 真的被套了、seed 沒跑到一半 |
| 4   | `students` / `courses` / `classes` / `admin`              | **見下：不寫死** | audit 看不到的那半                          |
| 5   | `張宇軒` / `文山旗艦校`                                   | 1 / 1            | seed-demo 的具名資料在                      |
| 6   | 完成時間                                                  | —                | —                                           |

**reset 前也量一次** —— 給「前 → 後」而不只是後值。

**由這一席量，不由請求者量**：請求者是有動機相信自己清乾淨的那一方。

> 🚨 **不要在這張表裡寫死任何筆數。** 這一格原本寫 `students = 68`（2026-09-13 實測），
> 2026-09-30 實測是 **69** —— 而**兩支 seed 一行都沒改、期間唯一的 migration 不插學生**。
>
> 成因（計畫席開檔驗的，不是假說）：`supabase/seed-demo.sql:1044-1053` 的
> **「聯絡簿缺漏示範生」只在「今天有一堂用聯絡簿的課」的日子才會被建出來** ——
> `JOIN … s.session_date = CURRENT_DATE`，撈不到就 `RETURN`。
> **09-13 是週日沒課 → 68；09-30 是週二有課 → 69。**
>
> **它不是過期，是一週裡有幾天對、有幾天錯** —— 那比單純過期更會騙人，因為
> **對的那幾天會讓下一任相信這張表是活的**。
>
> **權威判準是哨兵檔**（`supabase/seed-sentinels.sql`，labor-9 維護）—— 它跟著 seed 演進，
> 這張表不會。要給筆數就給「前 → 後」的實測對照，**不要給「應該是 N」**。
>
> **已知會隨日期變的**：`students`（有聯絡簿課的日子 +1）。
> 發現新的就加進這一行 —— 這是「指向產生器」而不是手抄清單，所以它不腐化（c11）。

### 筆數量不到狀態（2026-09-30，RESET #5）

請求者給的殘留清單裡，**「被改掉的狀態」與「被新增的列」需要不同的量法**，而**筆數只看得到後者**。

RESET #5 的五項殘留，三項用筆數逐數對上（`invoices` -44、`meal_records` -18、人員 1 → 0），
**兩項拿不出直接證據**：

| 項目                   | 為什麼量不到                                                   |
| ---------------------- | -------------------------------------------------------------- |
| 「1 筆催繳」           | **我不知道它住哪張表** —— 量了 `payment_records`，10 → 10 沒變 |
| 「小考 #90 被 reopen」 | **那是狀態改變不是筆數改變** —— `academy_exams` 前後都是 114   |

> **清掉一列與改回一個欄位，在筆數上長得一模一樣**（都可能是「沒變」）。

**所以：收到殘留清單時，凡是「被 reopen / 停用 / 改名 / 改金額」的項目，回一句問欄位** ——
在 reset 前把**那個欄位的值**一起量下來，後值才有對照。請求者通常給得出來
（RESET #5 之後 1222 就補了：`academy_exams.status`（`active` / `closed`）＋ 該 exam 的
`academy_scores` 筆數，前 `active`/0 → 後 `closed`/1）。

⚠️ **量不到的時候，寫「我沒量到」而不是靠推論帶過。** 「schema 被 drop 重建 ⇒ 舊資料
物理上不存在」是成立的推論，但**它證的是全部，不是那一項** —— 標注成推論，請請求者自己確證。
這跟本檔「別把觀察到的與推論出來的寫在同一句話裡」是同一條。

> **與「斷言落在結果不落在意圖」的關係**：那條是**量錯了對象**（量意圖而非結果），
> 這條是**量的維度不對**（筆數 vs 狀態）。同族，不同軸。

#### 筆數也量不到「搬移」（2026-10-02 RESET #13）

**同數量的增與減會互相抵銷，而那在筆數上與「什麼都沒發生」完全一樣。**

#1009 把 `classes.uses_contact_book` 從國中班搬到國小班。**筆數前後都是 3，一格都沒動**：

```
前：國三數學A ✓  國二英文B ✓  數學班A ✓      （count = 3）
後：國小五英文 ✓  國小六數學 ✓  數學班A ✓    （count = 3）
```

（第三個 `數學班 A` 是 seed 別處建的，不在那個迴圈裡 —— #1009 沒碰它。）

> **`count(*) where uses_contact_book` 給出「3 → 3」** —— 讀起來是「改動沒生效」，
> 而真相是「**兩個班換成另外兩個班**」。**連方向都看不到。**

**所以憑證要落在逐列，不落在總數**：貼**班名 + 年級 + 旗標**的清單，讓請求者直接對
「開在國小」而不是「開了兩班」。

> **這是「一個 0 要能證明什麼，先問它有幾條路」的鄰居**：
> **一個沒變的數字也要問它有幾條路保持不變** —— 真的沒動，或是**動了兩次而方向相反**。

**判準**：請求者的預期裡出現「**從 A 改成 B**」「**搬到**」「**換成**」這類字眼時，
**筆數必然無效** —— 直接準備逐列清單，不要先貼計數再被問。

#### 會自己漲的那一組：前值只能當場量，不能預報（2026-10-03 RESET #15）

**有三格會在沒有人「操作」的情況下自己變動**，所以**它們的前值寫在請求單或預告裡一定是過期的**：

| 格                | 什麼時候會漲                                                             |
| ----------------- | ------------------------------------------------------------------------ |
| `events`          | 有人**讀**課表／點名列表就補建（也會反向刪孤兒，見本檔「讀取會寫」那節） |
| `ba_session`      | 有人登入                                                                 |
| `ba_verification` | 有人要一條 magic-link                                                    |

**RESET #15 的實例**：我在預告裡只標了「`events` 會再漲，到時當場重量」，**而 `ba_session` / `ba_verification`
我照登記值寫了「2 / ?」—— 實際前值是 5 / 7**（期間有人登入過三次）。

> **標了一格、漏了同類的另外兩格** —— 那是「修到報告裡那條路，沒修同形的其他路」的量測版。
> **會自己漲的要當成一組處理，不是一格一格想起來。**

**作法**：請求者登記殘留時給的這三格數字**只當脈絡，不當前值**；reset 前**當場重量一次**，
回報時標明「當場量的」。其餘格子（`audit_logs`、各表總數、具名 fixture）才適用登記值對帳。

| ----------------------- | ------------------------------------------------------------------------------------------- |
| **`payment_reminders`** | **催繳**（`apps/api/src/routes/invoices.ts` 的 `POST /{id}/reminders` 寫它，#901 起有稽核） |
| `payment_records`       | **收款**                                                                                    |

**名字像，是兩件事。** 下一個請求者也會寫「1 筆催繳」而不說表名 —— 這一格填掉了，
不要再量錯（計畫席 2026-09-30 補）。

### `audit_logs = 0` 的邊界（不寫清楚它就是下一個假憑證）

它涵蓋 **22 種**資源型別，包含容易被誤以為沒有的 `course` / `class` / `session`。

**逃得掉的只有兩種**：`enrollment` 與 `meal_record` —— 型別在 TS union 與 DB CHECK
裡都有，但**全 repo 零呼叫端**（`apps/api/src/utils/audit.ts:14` 的註解逐字寫著
「報名的建立與退班完全沒有稽核紀錄，SQL 早就預留位置、程式沒接」）。那兩類靠計數。

⚠️ **這個憑證會怎麼壞**（三件事合起來）：

- `audit_logs.resource_type` 是 **`text` 不是 enum** —— DB 層沒有「有哪些型別」的清單，
  `group by` 只看得到已發生過的，新增一種不會有任何東西告訴你。
- **TS union 與 DB CHECK 是兩份分開維護的清單**（`utils/audit.ts:32` 的註解自己警告了）。
- `logAudit` 是 **fire-and-forget** —— 只加 TS 不加 DB CHECK 的話，insert 會被 DB 拒絕而
  **只在 console 留一行，`audit_logs` 照樣是 0**。

**⇒ 靜態的漏報通道是設計上留著的。** 2026-09-13 驗過兩份清單一致（各 24 種），
但**改 audit 型別的人要兩邊一起加**，否則這一席的第 1 行憑證會安靜地失去意義。

### 查產生器，不要比對觀察值

`admin` 到底該是 13 還是 15，**比對兩個觀察值答不出來**（兩個都是觀察值）。
答案來自產生器：`seed.sql` 的三個來源（`:92` 1 + `:239` 迴圈 11 + `:354` 1）合計 13，
而 `seed-demo.sql:619` 是 `ON CONFLICT DO UPDATE` **改同一列、不新增第 14 個**。
多出來的 2 個（`admin.lin` / `admin.wang`）**全 repo 零命中** ⇒ 只可能來自不可重現的舊環境。

**同族的兩個相反失敗**（都在 2026-09-13 撞到）：

- **查法太窄** —— 白名單式的 `resource_type in (...)` **永遠**只回你列出的東西，
  連「還有沒有別的」都不透露。要問「有哪些」就 `group by`，不要 `in`。
- **查法太寬** —— `grep -rn "resourceType: 'enrollment'"` 命中了 `audit.ts:14`，
  而那一行逐字寫的是「**全 repo 沒有任何 `resourceType: 'enrollment'`**」。
  **grep 命中了「這個東西不存在」這句話。** 驗「有沒有呼叫端」要排除註解。

### 「有沒有人加過」用 `created_at` 看，不要比記憶中的筆數（2026-10-03）

**比筆數需要一個可信的前值 —— 而前值本身可能是另一次 seed 的產物。**

實例：請求者登記「`attendance_records` 回原數」，我量到 **643**，而我手上的「基線」是
**635**（上一輪 reset 後量的）。**第一反應是「它多留了 8 筆」，而那會讓它去找一個不存在的 bug。**

反轉結論的不是另一個筆數，是這個：

```sql
select count(*), count(distinct to_char(created_at,'MM-DD HH24:MI')) from attendance_records;
--  643 筆，distinct 時間戳 = 1 ⇒ 全部落在那一次 seed 的執行時刻
```

> **`distinct 時間戳 = 1` 直接證明「全部出自同一次寫入」** —— 它**不需要前值**，
> 所以不會被記錯或過期的基線汙染。

**這是「查產生器，不要比對觀察值」的同族**：比兩個觀察值（635 vs 643）答不出來，
**問資料自己什麼時候生的，就答出來了。**

⚠️ **用它之前先確認 DB 是靜止的。** 同一次調查裡那個數字從 **643 變成 645** ——
請求者還在實打。**在一個正在被寫入的庫上做差異分析，每個數字都是真的而結論是假的。**

**所以要嘛等它收手，要嘛在 reset 後立刻量一份完整分佈當基線**（`created_at` 分組 ＋
關鍵維度分組，例如 `attendance_records` 依 `events.event_date`）。**那份才是能拿來對帳的東西** ——
一個總數對不了帳，因為它答不出「多的那幾筆長什麼樣」。

#### 那次調查留下的事實（2026-10-03，哪一段產生未查）

**這一段是觀察，不是結論。** 留著是因為下一個撞到 `attendance_records` 筆數對不上的人
不必從頭查一遍。

`attendance_records` 643 筆依 `events.event_date` 分組：

```
2026-10-06 |  2 筆 | 國三數學 A 班        ← 未來日期
2026-10-03 |  8 筆 | 自然班 C             ← 正好是 current_date，而 8 = 643 - 635
2026-10-02 | 18 筆 |
2026-10-01 | 18 筆 |
…           每日 18~20 筆，最舊到 2026-07-25
```

**已經確定的**：

- 那 8 筆與 10-06 的 2 筆，`created_at` 與其餘 635 筆**完全相同**（`distinct 時間戳 = 1`）
  ⇒ **出自同一次 seed，不是任何人的實打殘留。**
- 調查期間 `attendance_records` 643 → 645 → 643（請求者 `checkin` 建 2 筆、`cancel_checkin`
  又刪掉），**而 `distinct 時間戳` 全程是 1** —— 增刪抵銷的情況下那個憑證照樣成立，
  **而筆數在那半小時裡給過三個不同答案。**
- `seed-demo.sql` **不依賴執行時刻**：`NOW()` 只出現兩次（`:903` / `:989`），都是
  `attendance_taken_at` 的欄位值；`grep -E "(IF|WHERE|AND).*NOW\(\)"` 是空的。
  **所以「同日不同時刻造成差異」的假說已被推翻，不要再往那裡追。**

⚠️ **未查的部分**：主迴圈的條件是 `IF d < current_date`（`seed-demo.sql:215`），
**它不該產生「今天」與「未來」的出勤列，而那 10 筆存在。** 哪一段產生的 **沒有查**
（計畫席 2026-10-03 裁定停在這裡 —— **對帳靠 `created_at` 不靠筆數，所以機制不影響這一席的工作**）。

> **為什麼停得下來**：這一席要回答的是「這些是不是殘留」，而那已經答了。
> **「seed 為什麼這樣產」是另一個問題，它的答案不會改變這一席的任何一次回報。**

#### 第三種形狀：`updated_at ≠ created_at` 證明被改過（2026-10-03，#1212 實打）

**值被改回來了、筆數也沒變，而 `updated_at` 還留著痕跡。**

請求者登記「`classes` 3 列的 `updated_at` / `updated_by` 變了，`default_fee_template_id` 值已回 NULL」。
**那是「狀態被改」最難驗的形狀** —— 欄位值回到原樣、筆數一格沒動。而這一格直接看得出來：

```
國小六年級數學班 | updated_at=12:49 | created_at=12:47   ← 差 2 分鐘，被動過
國三數學 A 班    | updated_at=12:49 | created_at=12:47   ← 被動過
國二自然 A 班    | updated_at=12:49 | created_at=12:47   ← 被動過
示範空班（無課堂）| updated_at=12:47 | created_at=12:47   ← 相同，沒被動過
國小五年級英文班  | updated_at=12:47 | created_at=12:47   ← 相同
```

**`created_at = 12:47` 就是那次 reset 的 seed 時刻** ⇒ **`updated_at > created_at` 的就是被動過的那幾列**，
剛好三班、剛好是請求者列的三班。

> **這一節三種形狀，全部是「問資料自己」而不是「比兩個觀察值」**：
>
> | 問題               | 怎麼問                                                  |
> | ------------------ | ------------------------------------------------------- |
> | 這些列是誰寫的？   | `distinct created_at` —— 等於 1 就是同源（那一次 seed） |
> | 有沒有人加過？     | `created_at` 有沒有落在 seed 時刻之外                   |
> | **有沒有人改過？** | **`updated_at` 有沒有大於 `created_at`**                |
>
> **三個都不需要前值**，所以都不會被記錯或過期的基線汙染。

**對請求者的要求因此可以放寬一點**：殘留清單裡「改過某個欄位又改回來」這類項目，
**只要告訴我是哪張表，我自己用 `updated_at` 找得出是哪幾列** —— 不一定要它列出 id。
（但它主動列出來更好：那讓我能雙向對帳 —— 它說三班、我也查到三班，**兩邊獨立到達同一答案**。）

### 一個 0 要能證明什麼，先問把它變成 0 的路有幾條

**這是本節前面三條病例的統一判準** —— 它們是同一個病：

| 病例                               | 這個值有幾條路變成它                                                                                                                                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `admin10 = []`                     | 兩條：reset 跑完 / **有人單獨執行過 `seed.sql` 那一段**                                                                                                                                                                  |
| `audit_logs = 0`                   | 兩條：沒人寫入 / **`logAudit` 靜默失敗**（fire-and-forget，TS union 與 DB CHECK 兩份分開維護，只加 TS 那邊 insert 被 DB 拒絕而只在 console 留一行）。⚠️ **而且它連「沒有寫入發生」都不保證** —— 見下面的「讀取路徑會寫」 |
| `orphan_on_leave = 0`（RESET #10） | 兩條：請假單補齊了（#922 生效） / **對應的出勤列被刪掉了**（請求者銷假時連帶移除）                                                                                                                                       |

> **比率／差集／「不一致筆數」這類指標，分子分母同時歸零的時候看起來最健康。**
> 分母消失時它**不會報錯，它會變好看**。
> （判準的這個形狀由 `labor-20260913-1222` 寫成，見
> [`labor-8.md`](labor-8.md) 的「一個 0 要能證明什麼」那條 —— **那裡是本體，這裡只引用**，
> 兩邊各抄一份必然漂。）

🚨 **這條對這一席特別要緊，因為它打的是主力憑證。** `orphan` 是某一輪的驗證項，
**`audit_logs = 0` 是每一輪的抬頭** —— 而它一直被當成「零人為操作」的證明。
本檔把那兩條路分開記了很久（上面的表、`audit_logs` 邊界那一節），
**但從來沒有接成「所以這個 0 的鑑別力只有一半」**。

**補法（2026-09-30 起照這樣報）**：貼 `audit_logs = 0` 時，**必須同時附一個會隨寫入變動、
而且不經過 `logAudit` 的計數** —— 相關表的總筆數（`invoices` / `payment_records` /
`leave_requests` / `students` …，前後都量）。

- **兩者都沒變** ⇒ 才叫「沒人寫入」。
- **audit 是 0 而筆數變了** ⇒ **稽核漏報**，不是乾淨 —— 立刻回報請求者與計畫席。
  ⚠️ **除了下面那一類表。**

#### 「讀取會寫」的表要單獨看（2026-09-30，RESET #11）

**有些寫入根本不在寫入路徑上。** `events` 是目前已知的一張：

- **讀一次課表／點名列表就會補建 `events`** —— `apps/api/src/routes/attendance.ts:80`
  逐字寫著「出勤事件是列表時才補建的」；補建本體在
  `apps/api/src/lib/attendance-session-events.ts`。
- **同一段還會反向刪除孤兒 `event`**（補償步驟）⇒ **這張表雙向都會動。**
- **兩個方向都不經 `logAudit`**，也不需要任何人「操作」—— 打開一次面板就發生了。
- 授權後果別人已經記過（`apps/api/src/routes/attendance.spec.ts` 釘補建的那段）：
  補建**會寫入**，所以範圍不能只靠讀取端過濾，否則
  **A 校的管理員查詢時會替 B 校的課堂建 event**。

> ⇒ **`events` 變了不等於有人動過；`audit_logs = 0` 也不保證「沒有寫入發生」。**
> 判斷「沒人寫入」時，**「讀取會寫」的表要單獨看**，不能跟 `invoices` / `payment_records`
> 那種「只有寫入路徑會動」的表混在同一個判準裡。

**這一筆同時標出新補法的邊界**：補法確實抓到了 `events` 那一格（好），
**但不知道這個機制的話會把它誤報成「稽核漏報」** —— 那是假警報，
而**假警報會讓下一任開始忽略這一行**，於是真的漏報也看不見了。

**`events` 已進固定量測清單**（前後都量）—— 它變動時**先問有沒有人打開過課表或點名面板**，
不要第一時間當成人為寫入。成因由計畫席 2026-09-30 指出（#488 那條「每開一次課表就補建
event」的同一機制），座標由這一席查證。


## 權限：這一席唯一的本機改動

`npm run db:reset` 在 `.claude/settings.json` 的 `deny` 裡（**進版控、全隊共用的安全欄**）。
`deny` 優先於 `allow`，`settings.local.json` 加白名單無效 —— 只能動 `deny` 本身。

**2026-09-13 使用者授權，只在這個 worktree 的那一份刪掉一行**：

```diff
-      "Bash(npm run db:reset*)",
```

其餘四個變體（`npx supabase db reset` 等）與**主 checkout 那一份都沒動** ——
開口只開到職責需要的大小。

> 🚨 **這個改動永遠不 commit。** 它會安靜地跟著任何一次 commit 溜進 main，
> **然後全隊的安全欄就沒了**。刻意讓 `git status` 的 diff 保持看得見
> （不做 `skip-worktree` 之類的隱藏，那反而更危險）；這一席開 PR 時 `git add` 指名檔案。
>
> **接手的人第一件事**：`grep -c '"Bash(npm run db:reset\*)"' .claude/settings.json`
> —— 回 `0` 代表改動還在、跑得動；回 `1` 代表被還原了，**要重新請使用者授權，不要自己改**。

## 事故：#838（本機庫被清空 8 小時）

第一次 reset 就把一個能用的庫變成空庫：`seed.sql` 尾段的 #685 guard 依賴
`seed-demo.sql` 造的資料，而當時 `config.toml` 的 `sql_paths` 只有 `["./seed.sql"]`
—— 一跑就 `RAISE EXCEPTION`、**整批 rollback**。

**那段程式碼在作者本機能動，是因為他早就手動套過 `seed-demo.sql`** ——
而 **`db:reset` 被 deny 擋著，所以沒有人跑得動它，也就沒有人發現它壞了。**

> **這一席存在本身就是那個缺口的填補**：一個沒有人跑得動的指令，等於一條沒有人在走的路，
> 而**壞在那條路上的東西不會有人發現**。

**當時我做對的一件事**（值得保留的紀律）：回報時特別標注「`students=0` 是 rollback 的
**結果**不是原因，不能拿它推論上游 seed 壞了」。
**別把自己觀察到的與推論出來的寫在同一句話裡。**
