## 這個 domain 的坑

### Workers 執行環境

- **不能有模組層 singleton**。I/O 物件不能跨請求（`Cannot perform I/O on behalf of a
different request`）。方向永遠是 per-request 建、請求結束收。
- **`waitUntil(pool.end())` 會當場把池關掉。** `pool.end()` 是呼叫當下就同步設
  `ending = true`（`pg-pool/index.js:494`），而 `waitUntil` 只延長 isolate 壽命、
  **不延後 promise 執行**。收尾一定要在 `await next()` 之後的 middleware 裡做 ——
  `lib/get-auth.ts` 的 `authPoolCleanup` 就是。這條坑值得記住的形狀是：
  **「延長壽命」不等於「延後執行」**。
- **`c.executionCtx` 在沒有 ExecutionContext 時會丟例外**（測試的 `app.request()`）。
  用 try/catch，不是 optional chaining。
- **10ms CPU 上限**是很多設計的源頭：密碼登入整條路被移除就是因為 scrypt 超過它，
  而任何安全的雜湊都會超過。不要試著「優化」回來。

### Better Auth 與 c2

- `ba_*` **可讀不可寫**（c2）。新增使用者走 `admin.createUser()`，**刻意不給
  password**（harness gate A11 守著）。
- **既有的 c2 違規存量**：`me.ts` / `parents.ts` / `staff.ts` 有直寫 `ba_user` 的
  email/phone。**不要新增，也不要順手修** —— 已列「`ba_user` 寫入路徑收斂」切片。
  你若新增，pre-guard hook 會當場擋你（它只看新寫入的文字，所以存量它看不見）。
- **magic-link 的 capture callback 綁在實例上**。共用 auth 實例之後不能再用建立時
  綁死的 callback —— 走 `c.set('magicLinkCapture', ...)` 這個每請求的可變槽，
  **用完立刻清成 undefined**。見 `routes/login-links/mint.ts`。

### 已經死掉的東西（別復活）

- **`profiles` 表沒有任何建立路徑**（`handle_new_user()` 在 Better Auth 遷移時被
  DROP，沒有替代品）。顯示名稱走 `lib/display-name.ts` 的 fallback 鏈，
  **不要「到處補 profiles 列」** —— 那是跟殭屍賽跑。
- **`payment_cycle` 與它的 enum 已 DROP**，取代者是 `billing_mode`
  （`monthly` / `period` / `session_pack`），欄位在 `enrollments` 上。
- **密碼、忘記密碼、username 登入全部不存在。** 程式碼裡約 20 處「這個系統沒有密碼」
  的墓碑註解**是資產不要清** —— 它們回答「為什麼這裡少了一段」，那是最容易被下一個人
  重新加回去的地方。`ba_user.username` 例外：那是 phone-only 家長的唯一性鍵，刪了
  匯入的重複偵測會壞。

### 授權

- **角色在 `mount()` 宣告，忘了寫連編譯都過不了**（gate A7 守著）。
- **`requirePermission` 是新的（#49 才有）。目前只有兩支金流路由掛了它。**
  其餘 API 仍然只有角色層 —— `permissions` 在那之前只是畫面控制，API 裸奔。
  鋪到既有路由需要先跟使用者定映射表，是獨立切片。
- 一律 **fail-closed**：context 沒有 roles/permissions、清單是空的 → 拒絕。
  授權的洞幾乎都長在「不確定的時候放行」上。
- `*` 通吃，規則必須與 web 的 `auth.hasPermission()` 一致，否則會出現
  「畫面看得到、API 打不進去」。
- **開放一個角色之前先問「這張表是誰的資料」，不要把同一套 scope 套上去。**
  P3 開放成績給老師時，三支路由要三種處理：`academy_exams` 有 `created_by`（老師自建
  的自己管）、`school_exams` 沒有 `created_by` 也沒有班級關聯（它是機構層目錄，老師
  唯讀，但**成績照樣是老師登錄的**）、`scores` 依學生範圍。當時的設計文件寫「school-exams
  唯讀」，實作時才發現那會把段考成績登錄整個擋掉 —— **STOP gate 通過不等於停止思考**。
- **查詢參數可以繞過範圍。** 範圍算出一份 id 清單之後，使用者傳來的 `class_id` 之類的
  篩選要跟它取**交集**，不能覆蓋 —— 覆蓋等於給了一個用參數跳出範圍的入口，而它看起來
  完全像正常的篩選。
- **加上 fail-closed 之後既有測試變紅，那是證據不是災難。** 紅的通常是「沒有宣告身分
  的測試 context」，正確的修法是補上身分並註明那組測試的主題，不是放寬檢查。

### lazy 生成的東西，寫入端一定看不到全部

`sessions` 的出勤 `event` 是**懶生成的** —— `ensureAttendanceSessionEvents` 在有人查
課堂列表時才補建。所以任何「建立 X 時順便去更新相關的 event」的 eager 連動，
**只寫得到那一刻已經存在的 event**，之後才生出來的一筆都拿不到，而且沒有人會回頭補。

實際踩到（#153）：建立請假時 `leaves.ts` 把當日的 event 寫成 `on_leave`，但
「家長提前請假 → 那堂課之後才生成 event」是最常見的順序，於是**未點名的課堂完全不知道
學生請假**。修法是**讀取時推導**（roster join 當日有效的 `leave_requests`），
不是補更多 eager 連動 —— 要補就得在補建 event 時回頭查請假並寫入，
也就是在一個 GET 裡再多做一次寫入。

**判準：資料是懶生成的，跟它有關的衍生狀態就該用推導的。** eager 寫入只在
「來源與目標的生命週期一致」時才安全。

### 資料細節

- **postgrest 的 `numeric` 回來是字串。** mapper 一定要 `Number()`，不然前端加總會變
  字串串接。`agreedAmount` / `fee_templates.amount` 都是。
- 金額用 `numeric(10,0)` —— 台幣沒有小數，整數存避免 `1000.00 vs 1000.0`。

### 時區：UTC vs 台北，一整族的坑（2026-09-05，#402 觸發）

`leaves.ts` 用 `new Date().toISOString().slice(0, 10)` 算「今天」——這是 UTC，
在**台北時間 00:00–08:00**之間會算成前一天。這條把主幹 CI 燒到全紅，因為它只在
**每天 8 小時的窗口**裡是錯的：白天測、白天跑 CI，看起來永遠是對的。

**判準要記住的形狀：一個 bug 只在一天的固定時段發作時，「大家都測過沒事」不是證據，
是還沒測到那個窗口。** 修法一律用 `lib/taipei-date.ts` 的
`getCurrentTaipeiDateString()`（`Intl.DateTimeFormat` 取台北今天）與
`addDaysToDateString(date, days)`（純字串／`Date.UTC` 算術，不重新取「現在」）；
凡是對已知日期字串做加減，不要繞回 `new Date()` 再格式化。

修完之後全 repo grep 了一輪 `new Date()` 配日期格式化，分三批修（money 相關最先，
因為那裡是**篩選條件**不是預設值，篩錯比預設錯更貴）；每一批的回歸測試都用
`vi.setSystemTime('2026-09-05T17:00:00Z')`（= 台北 09-06 01:00，事故當時那個窗）
釘住邊界，不是隨便挑個日期就過。**這類 bug 的測試如果不特意把系統時間設到
台北凌晨，永遠測不到它** —— 這是「[[#靜默通過比靜默失敗危險]] 系列」的近親：
不是替身騙了測試，是**測試自己選的時間點**騙了測試。

**兩層觀測失效，這裡疊在一起發生：**第一層是「沒人在會發作的窗口觀測」（白天測、
CI 白天跑）；第二層是「觀測工具本身也可能是錯的」——`enrollments.spec.ts` 有一支
既有測試斷言 `effectiveFrom` 等於 `new Date().toISOString().slice(0, 10)`，跟被測
程式碼用的是**同一條錯公式**。兩邊一起錯，測試永遠綠；把程式碼修對之後，
這支測試反而會在台北凌晨那個窗口翻紅（因為現在程式碼對、斷言錯）。
**判準：測試的期望值不能用「被測程式碼自己的算法」重算一遍再拿來比對** ——
那不是驗證，是把同一個假設抄了兩遍。修法是斷言換成 `getCurrentTaipeiDateString()`
本身，讓測試的「正確答案」跟實作的「正確答案」來自同一個唯一定義，而不是各自推導。

### 效能

- **看到「空資料庫也慢」就別再找慢查詢。** 資料量無關的症狀要配資料量無關的原因：
  冷啟動、連線建立、每請求的固定成本、CPU 競爭。
- **fan-out 本身有成本，發生在任何 DB 工作之前。** 實測完全不碰 DB 的請求，並行 8 條時
  TTFB 從 0.46s 惡化到 ~1.1s（2.4 倍）。完整量測見
  [[lessons/workers-fanout-costs-before-the-db]]。
- 量到能**分開兩件事**為止：「重用連線 vs 新連線」分出網路／TLS，「並行 vs 序列」分出
  併發劣化。兩組對照就不用猜了。
- **N+1 在空資料庫上是隱形的。** 課堂列表原本每堂各發兩支查詢，空 DB 時是 0 次額外
  往返 —— 它不會出現在任何「空站很慢」的量測裡，但它隨資料線性成長。
- **延遲 ≈ 每請求的固定成本 × 一頁打幾支。減次數比減單次划算。**
  2026-09-03 拆段量測（報告見 scratchpad）：

  |                                         |                                                                     |
  | --------------------------------------- | ------------------------------------------------------------------- |
  | 查詢執行（`EXPLAIN ANALYZE`，真實形狀） | **0.7–1.2 ms**                                                      |
  | 同樣查詢走本機 PostgREST（零網路延遲）  | 93–121 ms，**且跟查詢複雜度無關**（最重的反而最快 —— 差異全是雜訊） |
  | 台灣→新加坡 Supabase 建立一條 HTTPS     | **60–85 ms**（TCP 1 個 RTT + TLS 再 2 個）                          |

  所以 design-web-2 量到的 1.3 秒差距**不可能是查詢造成的**。**要動的是請求次數，
  不是單次速度** —— 聚合端點與批次化都指向同一個方向。

- **「業務路由改走 pg 經 Hyperdrive」已結案：不立案。** 它能省的上限是
  「PostgREST 處理 + TLS 建立」，**省不掉網路往返本身** —— Hyperdrive 維持的是連線
  不是快取，一次 `pg` 查詢一樣要跑一趟新加坡。而成本是把每支路由改寫成 SQL。
  **分子未知就不能做這個交換。** 要重啟這個討論，先拿到「Worker 到 Supabase REST
  的單次呼叫耗時分布」——那個數字從外部量不到，只能在 Worker 內部量。

## 慣例與模式

### test-first 在這裡長什麼樣

- **先寫測試看它紅，再實作。** 紅的證據要留在回報裡。
- 路由測試的慣例是**測 exported 的純函式**，不是打整支 handler
  （`schools.spec.ts` 是範本）。所以寫 route 時把值得測的邏輯抽成 export。
- 假 supabase：物件字面量 + 呼叫端 `as never`（`enrollments.spec.ts`）。要**打整支
  handler** 時用可鏈式的版本 —— `select/eq/range` 各自回自己、`range()` 真的切、
  `order()` 回 `{ data, count }`，外面包一層 Hono 把 `supabase` / `orgId` set 進 context
  （`invoices.spec.ts` 是範本）。
- **測「會回歸的東西」而不是「好測的東西」**。例：`requirePermission` 最重要那條是
  「context 裡根本沒有 permissions 時拒絕而不是全開」；harness 的 c6 gate 最重要那條是
  「規則被改名時 gate 不能靜默變成空掃」。
- **驗證要打到出錯的那一層，不是最好測的那一層。七次了，這是模式不是巧合：**

  | 事故                       | 錯在哪一層                     | 純函式測試為什麼看不到       |
  | -------------------------- | ------------------------------ | ---------------------------- |
  | seed 42702                 | plpgsql 的名稱解析             | 抽出來的段落裡沒有那些變數   |
  | 帳單列表 `meta.total`      | total 取自 `.range()` 之後     | 它不知道 total 從哪裡來      |
  | 聯絡簿週彙總（#129）       | 用錯欄位分組（`session_date`） | 它拿到的是已經分好組的 Map   |
  | `recorded_by_role`（#145） | 路由寫死 `'admin'` 沒傳 roles  | 函式本身是對的，沒人呼叫它   |
  | 密集日 seed 的「不破壞」   | 重跑會不會刪掉既有資料         | 筆數比對看不到「刪了再種回」 |

  共同形狀：**bug 在「資料怎麼餵進純函式」那一層，而純函式測試從定義上就在那一層之後。**
  所以動手寫測試之前先問一句：**這條規則是誰決定的？** 答案若是查詢、分組、參數解析、
  或執行環境，那測試就得跨到那裡去，抽再乾淨的純函式都補不上。
  代價通常只是一個假 supabase —— 比事故便宜得多。

  **第七個案例：檢查指令自己有盲區**（2026-09-03）。harness 的失敗標記是 `✖`（U+2716），
  而我驗證時 grep 的是 `✓|✗`（U+2717）—— **紅的被我看成綠的，PR 推上去才在 CI 紅**。
  同一天 review-steward 也踩到同族的：合併流程「merge → 驗證 → 刪分支」串成一串，
  中間沒檢查 merge 是否成功，於是 merge 被衝突擋下時分支照樣被刪。
  **判準：驗證步驟本身要能失敗給你看** —— 看 exit code，不要 grep 符號；
  前一步的成功是要驗的，不是預設的。

  **第六個案例的盲區不在測試層級，在資料**（#158）：`profiles.id` 宣告成 `uuid`
  卻存 `ba_user.id`。Better Auth 產的是 nanoid，塞不進 uuid 欄位 ——
  但 **seed 的使用者 id 剛好都是 uuid 形狀的字串**，所以本機怎麼點都不炸，
  第一個真實的 LINE 帳號才踩到。
  **測試資料的形狀比正式資料窄時，型別／格式錯了也沒有一筆資料能證明它錯。**
  凡是「正式環境的值由外部系統產生」（Better Auth 的 id、OAuth 的 profile、
  第三方 webhook），就要問一句：**我的測試資料涵蓋得到它的形狀嗎？**

  **前面兩行是不同的兩種盲區，值得分開記：**
  - 第 4 行：函式正確但**沒人正確地呼叫它**。抽出純函式**沒有**讓路由被驗到，
    反而容易讓人以為驗過了。抽完要問「誰呼叫它、那個呼叫有被測到嗎」。
  - 第 5 行：**測量的指標本身有盲區**。冪等用筆數證明，而「刪掉 N 筆再種回 N 筆」
    在筆數上完全隱形。證「有沒有多出來」與證「有沒有弄壞既有的」是兩句話，
    要各自設計一個會失敗的情境。

  **第八個案例：測試用被測程式碼自己的算法當裁判**（`enrollments.spec.ts`，時區批次二）。
  一支既有測試斷言 `effectiveFrom` 等於 `new Date().toISOString().slice(0, 10)`——
  跟它要驗的那行程式碼**用的是同一條公式**。兩邊一起錯，測試就會一直綠，
  因為它驗的不是「答案對不對」，是「兩份抄本一不一致」。更陰的是**修好程式碼那一刻
  這支測試才會紅**（現在程式碼對、斷言錯），所以在事故發生前它看起來完全正常，
  甚至會在你修 bug 的當下反過來擋你。**判準：期望值要來自一個獨立的、可信的來源，
  不能是把被測程式碼的算法重新抄一遍。** 抄兩遍不是雙重驗證，是同一個假設算兩次。

### migration

- `npx supabase migration new <description>` 產檔，**已提交的不可改**（c3）。
- 新表**一律 `ENABLE ROW LEVEL SECURITY` 不建 policy** —— service role 會繞過它，
  這是 fail-closed 後盾（gate A8 會抓漏）。
- 改 `audit_logs.resource_type` 是 `DROP CONSTRAINT` + `ADD` **完整清單** ——
  也就是**時間戳最晚的那支說了算**（執行順序是時間戳，不是合併順序）。
  多軌並行時：由**時間戳最晚**的一方寫聯集；若兩軌時間戳交錯，後合的一方
  **另開一支時間戳最晚的 migration** 專門收斂清單（先例：
  `20260829110000_audit_logs_billing_resource_types.sql`，檔頭有完整的坑描述）。
  「先合的併進後合的清單」這條舊規則是錯的 —— 先合不代表先執行，照做會讓
  後執行的舊清單把新值靜默清掉，直到有人寫那種 audit log 才炸。
- 對應的 TS union 在 `utils/audit.ts`，**兩邊要一起改**否則 typecheck 紅。
- 換欄位時**不留雙軌**：兩個欄位並存的代價是每個讀寫點都要決定「聽哪一個」，
  而那個決定會在不同檔案裡做出不同答案。

### 內容驗證要挑「只有那支 PR 會產生的字串」

squash 倉庫裡「這支合了沒」只能用內容判斷（README 疊 PR 鐵律第 2 條）。
**但關鍵字挑錯，驗證本身就是假的。**

2026-09-03 實例：我要驗 #225 有沒有進 main，grep 了 `adminUpdateUser` → ✅。
但那是命中 **#228 的 kb 頁面**（它引用了這個 API 名稱），不是 #225 的程式碼。
改成驗「只有 #225 會產生的字串」（`api.updateUser` 出現在 `me.ts`、
「真債 0 筆」出現在帳本與文件）才問出真相：**#225 根本還沒合。**

判準：**挑一個「這支 PR 改出來的行」裡的字串，而不是「這支 PR 談論的東西」。**
名詞會被別的 PR 提到，改動不會。

**還有一條同族的：驗證要對齊來源。** 2026-09-04 我在同一次驗證裡用了兩種基準 ——
後端查 `git show origin/main:…`（對的），前端直接 `grep` 工作區的檔案（錯的，
工作區停在舊分支）。於是我得出「前端還沒接 `leaveStartDate`」的結論，
而 main 上早就接了。**不是時間差，是根本沒對齊來源** —— 一半比 remote、
一半比自己的暫存狀態，那不叫驗證。

### 在 A 問題上為真的性質，不能直接拿去答 B 問題

2026-09-04 踩到的，而且**我兩次在同一個資料上得出相反的結論，第二次是錯的**：

|      | 問題                                                                  | 答案                                                     |
| ---- | --------------------------------------------------------------------- | -------------------------------------------------------- |
| #185 | roster 回的 `[leaveStartDate, leaveEndDate]` 是**精確區間**還是包絡？ | **精確** —— 每一張假都涵蓋今天，所以聯集必然連續、沒有洞 |
| #265 | 那個區間能不能用來判斷**銷假會不會連坐取消後續日期**？                | **不能**                                                 |

`[4/4~4/6] + [4/6~4/8]`（今天 4/6）聚合成 `4/4~4/8`，跟一張長假 `[4/4~4/8]`
**完全同形** —— 但前者銷假是兩張各縮一天、零損失，後者是後段整段被取消。
**連續 ≠ 可預測連坐。**

危險的地方在於：**我先前「證明過」那個區間是精確的**，於是再次用它時感覺已經驗過了。
一個性質被證明時是綁著一個問題的，**換了問題就要重新推導，不能沿用結論**。

再用一次之前先問一句：**當初證明它的時候，我在回答哪個問題？**

#### 抓得到這種錯的測試長什麼樣

> **明著斷言兩個輸入同形，再斷言輸出不同。**

`attendance.spec.ts` 的接力假那條就是這樣寫的：先 `expect` 聚合值跟長假那筆
**一模一樣**，再 `expect` 預測值是 `null`。它釘住的不是某個數字，
是「**這個聚合值回答不了那個問題**」。

#### 順帶：預覽與動作要共用同一份實作

`cancelDropsLeaveUntil` 的預測**直接呼叫銷假自己的 `cancelLeaveForDate`**，
所以「預覽說會、按下去卻不會」在結構上不可能。同一個做法：
`proration-preview` 與月結批次共用 `prorateByDays`。

**凡是「先給你看結果再問你要不要做」的功能，預覽都不能是另一份實作。**

### 「兩支各自綠、合起來紅」是一整類問題

`audit_logs` 的 constraint（**先合併的不一定先執行** —— 判斷依據是時間戳）踩過一次；
c8 的 allowlist 又踩了一次（清掉違規的 PR 對著較舊的 base 是綠的，合進 main 才不同步）。

共同形狀：**gate 的結果同時取決於 main 的狀態與這支 PR 的改動**。這類 gate 至少有
`audit_logs` constraint、`feature-map` 的 route 認領、c8/c6 的 allowlist。
碰到它們的時候，「我的分支 CI 綠」不代表「合進去之後還綠」。

**ratchet 型 gate 有一個額外的存量風險：它上線的那一刻，所有已經開著的分支都是待爆彈。**
2026-09-03 第三個案例：A17 觸控 gate（#195，11:42 合）上線後，#186（分支開得更早，13:27 合）
帶著一段違規 SCSS 進來 —— **#186 自己的 CI 是綠的，因為它跑的時候 A17 還不存在**，
而合進去之後 main 紅了，所有人的新分支跟著紅。

要嘛在 gate 上線那一刻掃一次所有 open PR 的 base，要嘛接受「上線後第一批合併可能弄紅 main」
並讓巡檢席盯著。**沒有第三種選擇** —— ratchet 的定義就是「只准往好的方向走」，
而存量是它上線前就存在的。

### plpgsql 與 seed 的坑（2026-08-29 db:reset 事故後補）

- **plpgsql 變數一律 `v_` 前綴。** 裸名變數會跟同名欄位在 SQL 裡撞成 42702
  （column reference is ambiguous），而且**只在特定語句形狀發作** ——
  `ON CONFLICT` 的目標欄位、裸 `WHERE`。所以它可以潛伏很久，
  直到有人加了一句剛好那個形狀的 SQL。
- **transaction + ROLLBACK 抽段法驗不到 plpgsql 的名稱解析。**
  抽出來的版本裡沒有那些變數。**新程式碼落在 `DO $$ ... $$` 裡的話，
  必須把整份 seed 原樣執行**（一樣可以包在 transaction 裡 ROLLBACK，非破壞性）。

### transaction + ROLLBACK 驗證法

`npm run db:reset` 在這個席位的環境**被權限規則擋下**（會清空本機 DB）。替代做法：

```bash
{ echo "BEGIN;"; cat <新 migration>; echo "<斷言用的 SELECT>"; echo "ROLLBACK;"; } \
  | psql "postgresql://postgres:postgres@localhost:54322/postgres" -v ON_ERROR_STOP=1
```

**適用邊界**：它驗的是「這段 SQL 套到現行 schema 上會不會過、結果對不對」，
**不驗 migration runner 的排序與全新建庫**。而且本機 seed 常常沒有你要測的舊資料
（例：搬遷 `payment_cycle` 時 `UPDATE 0`）—— **要先在同一個 transaction 裡造資料，
不然你測到的是「空集合上跑得過」**。全流程 `db:reset` 要請有權限的人跑。

### 紅燈的「轉述根因」不能當事實用（三次了）

同一個形狀出現三次，而且**兩次的錯誤診斷剛好互換**：

| 事件 | 轉述的根因                               | 真正的根因                                                           |
| ---- | ---------------------------------------- | -------------------------------------------------------------------- |
| #199 | 「打真 DB，CI 無 DB 必紅」→ 刪掉那支測試 | 測試**已經 stub 乾淨**，紅的是我寫的時序斷言在滿載 runner 上翻盤     |
| #243 | 「假 supabase 替身缺 `.gte`」            | 那支 spec **一個替身、一個 `vi.mock` 都沒有** —— 真因**正是**打真 DB |

**轉述經過一手就會壓縮成一個標籤，而標籤會黏在錯的東西上。**
計畫席 2026-09-03 定的做法：**工單只給症狀與復現路徑，診斷留給修的人。**

接到「某某紅了，根因是 X」的工單時，**先自己復現再看 X 對不對**。判準仍是
review-steward 收進 charter 的那條：**看 FAIL 那一行跟改動有沒有關係**，
再往下查一層才下結論。

#### 一個具體的診斷徵象

> **測試「逾時」而不是「連線失敗」，是它打了真資料庫的徵象。**

連不到的 DB 不會馬上拒絕，它會**掛著等**（本機實測：`psql` 對 54322 掛超過 120 秒
都沒有回應），所以 vitest 是等到 5 秒 timeout 才放棄。症狀長得像 flaky，
不像「打了資料庫」—— 這就是為什麼它會被歸錯族。

`apps/api` 的不變量寫在 `vitest.config.mts` 的註解裡：
**spec 全部用假的 builder，不需要 Workers runtime 也不需要資料庫。**
違反它的那支要用 `vi.mock` 換掉真連線，而不是替它加一個不存在的替身。

### 靜默通過比靜默失敗危險，而假替身兩種都會製造

`maybeSingle` 那族是**靜默失敗**（稽核沒寫成，沒人知道）。#274 踩到的是另一半：

> 第一版的替身**無條件回傳全部既有列**，於是「沒有重疊」那條**因為錯的理由 409**、
> 「共用端點日」那條**因為錯的理由通過** —— 兩條都不再檢驗邊界，**但看起來是綠的**。

**靜默失敗至少會在 log 裡留一行；靜默通過什麼都不留，而且它長得跟成功一模一樣。**

#### 替身要跟著路由變，不要自己寫死行為

修法是**把路由呼叫的運算子記下來，然後照它過濾**：

```ts
lte: (col, v) => { predicates.push((row) => row[col] <= v); return query; },
lt:  (col, v) => { predicates.push((row) => row[col] <  v); return query; },
```

這樣路由把 `lte` 改成 `lt` 的時候，**替身的行為跟著變** —— 測試檢驗的是真的那條規則，
而不是替身作者當初以為的那條。

**寫替身時的自問：這個替身有沒有可能不管路由怎麼寫都回一樣的東西？**
會的話，它測的是「路由有沒有崩潰」，不是「路由對不對」。

#### 替身**分不出對錯**時，改測「送出去的查詢長什麼樣」

有些規則整個活在查詢的形狀裡，假替身的回傳值**在對與錯的實作下完全一樣**。
那時候不要去斷言回傳值，直接斷言**查詢**：用了哪種 join、條件下在哪一欄、下的是
哪個運算子。

2026-09-04 的 `attendanceTaken` 就是這種。本機 PostgREST 實測：

| 查詢                                                          | 回傳筆數             |
| ------------------------------------------------------------- | -------------------- |
| 全部課堂                                                      | 19                   |
| `events!event_id(...)` + `events.attendance_taken_at=is.null` | **19（什麼都沒篩）** |
| `events!event_id!inner(...)` + 同一個條件                     | **18**               |

> **對 embed 的欄位下條件，在 left join 上不會篩掉父列。**
> 少了 `!inner`，篩選會**靜靜地什麼都不做**，而回傳筆數看起來很正常。

所以那組測試斷言的是「select 裡有沒有 `!inner`」與「條件下在
`events.attendance_taken_at` 上」，不是筆數 —— 筆數在兩種實作下都可以被替身喬成一樣。

**兩條是同一個原則的兩面**：
替身跟著路由變（讓回傳值有鑑別力）／改測查詢形狀（回傳值沒有鑑別力時）。
共同的判準還是那句：**當「對的實作」與「錯的實作」會產生同樣的觀察值時，
這個測試就沒有在測那件事** —— 那就換一個看得出差別的觀察點。

#### 替身的第三種盲區：**它不管路由 `select` 什麼都回全欄位**

前兩條講的是「回傳值有沒有鑑別力」（替身跟著路由變）與「回傳值沒有鑑別力時改測查詢形狀」。
2026-09-06 撞到第三種，而**前兩條都抓不到它**：

> 路由**少撈一個欄位**。替身照樣回全欄位，於是對的實作與錯的實作產生一樣的觀察值。

實例：考試分母要用每場自己的 `exam_date` 算，而候選清單的查詢是
`.select('id, exam_date')`。我把它改成 `.select('id')` 當陷阱去撞 —— **撞不紅**。
真實後果是 `examDate` 變成 `undefined`，`isEnrolledOn` 對 `undefined` 不會報錯只會
回一個「像是沒套日期」的答案，於是**每一場的分母都變成 0、告警靜靜地永遠是空的**。

修法是讓替身**照 `select` 的欄位投影**（把 `select()` 收到的字串切開，只回那些鍵）。
補上之後陷阱才紅，而且紅的正好是「考完才轉入」那支已知真案例。

**判準補一句**：問「這個替身有沒有可能不管路由怎麼寫都回一樣的東西」時，
**「怎麼寫」包含它撈了哪些欄位**，不只是它用了哪些運算子。

#### 突變測試要用 `cp` 備份還原，**不要 `git checkout <file>`**

同一天的操作事故：我用 `git checkout apps/api/src/lib/session-roster.ts` 還原被突變的檔案，
**連同那個檔案裡還沒 commit 的抽函式一起還原掉了**（`isEnrolledOn` 整段消失）。
症狀是下一輪測試炸 `isEnrolledOn is not a function`，而那看起來像是 import 寫錯。

`git checkout <file>` 還原的是**整個檔案到 index/HEAD**，不是「還原我剛才那一筆突變」。
工作區有未提交的改動時，這兩件事的差別就是你的工作。
**突變前 `cp` 一份、突變後 `cp` 回來** —— 跟 README 對 `git stash` 的警告同一族：
**共用的還原機制不知道你只想還原哪一半。**

#### 推論：PostgREST 的 join 語意要實測，不要照直覺寫

`is.null` 下在 embed 欄位上「應該」會篩掉父列 —— 直覺是這樣，事實不是。
**這一族的錯誤不會報錯**，所以查文件或憑印象寫的成本會延後到「數字看起來正常但其實沒篩」
才浮現。一次 `curl` 加 `Prefer: count=exact` 就問得出來，比事後查便宜太多。

### 只斷言結果碼不夠 —— 因為錯的理由 409 跟因為對的理由 409 同色

#274 的「共用單日端點要 409」：把 `lte/gte` 改成 `lt/gt` 之後，
**那組測試資料仍然會 409**（還有別的天重疊），邊界悄悄鬆掉而測試全綠。

所以那條規則要**直接釘在條件本身**（斷言查詢下了 `lte(start_date, 新的迄)` +
`gte(end_date, 新的起)`），不是斷言回應碼。

判準：**當「對的實作」與「錯的實作」在這個測試上會產生同樣的觀察值時，
這個測試就沒有在測那件事。** 突變測試就是拿來問這個問題的。

### 跨功能的隱性依賴要寫在測試註解裡

`POST /api/leaves` 的重疊拒絕**沒有 DB 約束、只活在兩行路由碼裡**，
而 #265 的連坐預測之所以在正式資料上單純，**正是靠它擋掉了「兩張接力假」**。

那個依賴在程式碼裡完全看不見 —— 兩支檔案之間沒有任何連結。
**寫在守著它的那條測試的註解裡**，是下一個想動那兩行的人唯一會看到它的地方。

### 在飛清單用查的，不要用記的

2026-09-04 我連續三次回報過期的在飛清單（#232 / #225 / #265 各一次）。
問題不是「忘了重抓」，是**我在維護一份記憶中的清單**。

```sh
gh pr list --state open --json number,title -q '.[] | "#\(.number) \(.title)"'
```

一個指令的事。**任何「我手上有哪些東西還沒合」的回答都應該來自這裡。**

### 把「靜默失敗」變成紅燈，比逐次補清單便宜

`utils/audit.ts` 的 `logAudit` 把例外包在自己的 try/catch 裡只印一行
`[audit] log failed`。**那個設計是對的** —— 稽核寫入失敗不該讓使用者的操作失敗。
副作用是：測試替身少一個鏈式方法時整支稽核悄悄消失，**沒有任何測試會紅**。

`src/test-setup.ts`（#243）把它接起來：**印出那行警告的測試就紅**，
並在錯誤訊息裡指出 `logAudit` 走的是哪兩段。只在測試生效，正式站行為不變。

> **清單只防第二次，訊號防第三次。** 這一族補過一輪清單（#233 的四處 `maybeSingle`），
> 然後第二次就換了個方法名回來。把訊號打開只要做一次。

### 其他工具面的坑

- **`wrangler deploy --dry-run` 不驗證 binding 的 id 存不存在。** 實測填
  `<HYPERDRIVE_ID>` 照樣過 dry-run，只有真正的 deploy 才炸。所以凡是「要先 create
  才拿得到 id」的 binding（Hyperdrive、D1、KV…），**配置一律留成註解 + 啟用步驟**，
  不要填佔位值 —— 那等於在正式部署路徑上埋一顆下次有人裸跑 `wrangler deploy` 才引爆的雷
  （跟 2026-08-29 的 `--var` 事故同一類：只活一次的設定看起來像永久設定）。
- **`nx affected` 一律自己帶 `--base=main`**（`defaultBase` 指向不存在的 `dev`）。
- **web 沒有獨立 typecheck target** —— 模板改動（改個方法名）只有 `nx build web`
  抓得到，測試與 typecheck 都不會發現。動到 web 就跑 build。
- **root 依賴的升版流程在 [`infra.md`](infra.md) 第四節**，不在這裡抄一份（c11）。
  這裡只留一條跨席通用的：**絕不用 `--legacy-peer-deps`**（它會砍掉 67 個 peer
  帶進來的套件，含整包 eslint）。
  ⚠️ 這條原本寫著「root lock 無法從零重建、要用 `--force`」——**那個 ERESOLVE 已於
  #51 修掉**（workers-types 與 wrangler 一起升）。腐化的原因就是把別席的細節抄過來。
- `apps/api` 是獨立 package，要另外 `cd apps/api && npm ci`。

### 加欄位給消費端時的兩條預設

- **不要替既有欄位發明過濾規則。** #129 的課堂列表要標「這天有考試」，很容易順手把
  `status = 'draft'` 的濾掉 —— 但專案其他地方（`academy-exams` 列表）並沒有把 draft
  當隱藏。**同一個欄位在專案裡已有的處理方式就是預設值**；要偏離得有產品指示。
  自己加的過濾會製造「明明排了卻沒顯示」這種沒人查得出來的怪事，而且症狀離原因很遠。
  做法：照既有語意做，**把這個選擇寫進 PR 並附上「要改是一行」**，讓決定權回到產品。
- **形狀不同就另開端點，不要給舊端點加參數。** #129 的聯絡簿週彙總（每天一列）與既有的
  `/missing`（每生一列）是兩種形狀。同一個端點回兩種形狀，消費端就得先判斷自己拿到哪一種
  —— 那個判斷會在不同的呼叫點寫出不同答案。**加參數只在「同一種形狀、換一組資料」時才對。**

### 自動寫入 vs 人工修改（#145）

判準是**「來源是不是一個人的決定」，不是「是不是自動觸發的」**。

- 到班掃碼 → **不得覆蓋**既有紀錄（機器讀到一張卡，不該推翻老師的判斷）
- 請假 / 報名連動 → **覆蓋是刻意的**（請假也是人工，只是不同的人；業務規則允許事後補請）

兩者長得一模一樣（都是 upsert 撞既有紀錄），所以**看到後者不要當成前者那種 bug 修掉**。
完整說明在 `kb/wiki/rules/attendance-rules.md` 的「自動寫入與人工修改的優先順序」。

### 「可以呼叫的 helper 就是可以忘記呼叫的 helper」

2026-09-04 在 #295 的設計預審抓到的。文件寫著：

> TypeScript 的必填參數讓「忘記限縮」變成**編譯錯誤**而不是執行期的資料外洩。

**那個推論不成立。** 必填參數守的是**呼叫點**（呼叫它的時候不能不給 scope），
不是**呼叫這件事本身** —— 沒有任何東西阻止一支 route 直接寫
`supabase.from('academy_scores')`。

放進三層防線表看更清楚：「函式簽名」之所以「擋得住所有呼叫端」，是因為它**繞不過去**，
不是因為它**有提供**。一個可選的 helper 其實落在第三層（願意停下來讀的人）。

> **判準：問「錯的寫法還寫不寫得出來」，不是問「對的寫法方不方便」。**
> 寫不出來才是第一層；只是比較麻煩，那是第三層。

修法是把入口換掉（家長端拿不到原始的 `supabase`，只拿得到已綁 scope 的 `childDb`），
gate 只負責收尾。**正確的寫法要比錯的寫法還短**，gate 抓的是那個看得見的、
少數的例外。

### 欠準與誤報不是同一種錯，警示型的數字尤其

同樣一張「未點名課堂」卡，2026-09-04 有兩個修法：

|                                                          | 修的問題                              | 代價                                     |
| -------------------------------------------------------- | ------------------------------------- | ---------------------------------------- |
| 我建議的（`dateTo=今天` + `meta.total`）                 | **少算**（撈 100 筆自己數，破百就漏） | **每天早上整批還沒上的課都被算成未點名** |
| admin-pages 實作的（昨天以前走 API、今天用手上的明細算） | 同樣不少算                            | 沒有誤報                                 |

我只看了「數字會不會少算」，沒看「數字什麼時候會多算」。

> **每天早上都紅一次的卡，一週之內就會被學會忽略 —— 那時候它連原本能提醒的事都提醒不了。**
> 對警示型的數字，**誤報比欠準更致命**，因為它破壞的是這個訊號往後所有的可信度。

順帶：那個切法還讓「精確」與「零額外請求」不衝突 —— 今天那段的資料
（`workbench/today` 的明細）**本來就在手上**。

### 「該不該算進某個計數」是消費端的語意，不要塞進 API

同一件事的下半場：`workbench/today` 的 `sessions` **含停課**（`routes/workbench.ts:151-158`
沒有 status 過濾，schema 明著含 `cancelled`），所以消費端拿去數「未點名」時要自己排除。

被問到「要不要在 API 加一個已經濾好的欄位」時**拒絕了**：`sessions` 回全部是對的
（課表要顯示停課的灰底），而**「該不該算進某個計數」是消費端的語意** ——
塞進 API 只會讓下一個消費端拿到一份「別人定義的子集」，然後為了拿回全部再加一個參數。

（`rosters` 那條看起來有濾停課，其實是濾「有沒有出勤事件」而剛好重疊 ——
停課刻意不補建事件（#123）。**兩件事重疊不代表是同一件事**，下一個人不要把它當成
「這裡已經處理過停課」。）

### 先查語意再改，看見的不是修法是結構（時區批次三，#419）

`classes.ts` 有三處「這個班有沒有過去課堂」的判斷（列表顯示一處、單筆刪除守門一處、
批次刪除守門一處），各自嚴重度不同（一個只影響顯示、兩個是資料完整性守門）。
grep 只能告訴你「這裡有一段日期運算」，告訴不了你「這三段是同一個判斷邏輯被複製了
三次」——那要**先把每一處的語意寫出來、逐一比對**才看得見。比對之後才發現三處裡
有兩處字面上就是同一段程式碼。

被要求「先查語意，寫出每一處的語意，再改，再決定要不要一支 PR 出」時，
表面上像是「多一道報告手續」，但**價值不在確認修法對不對，在於看見結構** ——
沒有這一步，這次修時區只會在三個地方個別貼 OK 繃，下一次三處又會各自長出新的分歧。
查完之後把三處收斂進共用的 `checkClassesPastSessions()`，時區修正只需要改一個地方，
**合併反而讓這次改動的接觸面變小，不是變大。**

### fail-closed 的形狀：失敗查詢不能被讀成假的零

`{status:'ok'|'check-failed', ...}` 這種帶狀態欄位的回傳型別，是這個 session 第四次
複用同一個形狀（`checkEnrollmentAttendance` → `checkEnrollmentSessionPacks` →
`countSubjectUsage` → `checkClassesPastSessions`）。要守的陷阱是 `count ?? 0`：
一次失敗的查詢跟一次真正查到零筆，在型別上長得一模一樣（都是 `number | null` 被
`?? 0` 接住），但語意完全相反——前者是「不知道」，後者是「確定是零」。把兩者
壓成同一個值，會讓「查詢掛掉」被讀成「這裡沒有東西擋著，可以刪」，剛好是這一整族
資料完整性守門（session_packs / academy_exams / past sessions）最怕的方向。
**判準：查詢失敗要回一個查詢成功時不可能出現的形狀（status 欄位），不能回一個
跟真零同型的值。**

### 抽共用函式讓改動變小，這次數到第 8 次

這個 session 同一招用了 8 次：`checkEnrollmentSessionPacks`（#371）、
`class-log-query.ts` 的 `toClassLogResponse`（#381）、`countSubjectUsage`（#392）、
`addDaysToDateString` 統一 `session-end-time.ts` 私有的 `addDays`（#402）、
時區批次二把 `enrollments.ts` 四處日期預設收斂到同一個 `today` 變數（#418）、
`checkClassesPastSessions`（#419）……次數多到值得記下來的不是「又抽了一支函式」，
是**為什麼每次都值得做**：重複的判斷邏輯會各自漂移（同一條規則被抄三份，
下一個人改其中一份，另外兩份就悄悄變成不同的規則），抽成共用函式讓「漂移」
在結構上變得不可能，而不是靠 review 去抓。表面上看「多寫一支檔案」是額外工作，
實際上讓**這次要改的接觸面變小**——只改一個地方，而不是找出所有抄本各改一次。

### 抽共用時，第二個消費端要的常常是**同一條規則的不同形狀**（#454）

「抽共用函式讓改動變小」數到第 8 次的時候，抽的都是同一個形狀的重複。
第 9、10 次不是：**第二個消費端要的是同一條規則，但形狀不同。**

`countEnrolledOn(enrollments, classId, date)` 回的是**報名筆數**，出勤名單要的就是這個。
考試的分母要的是**不重複的學生集合** —— 一個學生可能同時在同一場考試的多個班裡
（數學 A 班 + 數學進階班），用筆數的話同一個人被算兩次，**分母永遠大於實際人數、
`N/M` 到不了滿**。

直接複用會得到一個錯的數字；不複用會得到第二份日期比較。正解是**把規則本身抽出來**
（`isEnrolledOn(range, date)`），讓原本那支也改成呼叫它。

> **判準：兩個消費端要的是同一條規則還是同一個答案？**
> 同一條規則、不同形狀 → 抽規則，兩邊各自組自己的形狀。
> 硬把第二個消費端塞進第一個的形狀，會得到一個**看起來對、數字錯**的結果。

（計畫席裁示時指定「走 `countEnrolledOn`」，實作時發現形狀不對 ——
**STOP gate 通過不等於停止思考**，這是第二次踩到同一句話。偏離要寫進 PR 讓它被看見。）

### 撤銷與寫入的守門條件不對稱時，「整段重做」不是空操作（#443）

請假編輯要同步出勤。最直覺的寫法是「舊區間整段撤銷、新區間整段寫入」——**那是錯的**：

| 方向 | 守門 |
| --- | --- |
| 撤銷 `on_leave` | **只碰 `attendance_taken_at IS NULL` 的課堂**（不回頭改寫別人做完的判斷，#169） |
| 寫入 `on_leave` | **不濾**（補請假覆蓋既有紀錄是業務規則允許的，#145） |

於是「刪掉再補回來」對**沒有變動的那幾天**不是空操作：已點名的那天刪不掉但補得上去，
**它會在一次編輯裡莫名換一個作者**。修法是算差集（`diffLeaveDateRanges`），
只動真的變了的那幾段。

> **判準：undo 與 apply 的守門條件不一樣時，「先全撤再全套」對中間沒變的部分也有副作用。**
> 這一族的通則是：**冪等性要自己證，不能從「兩個操作互為反向」推出來。**

### 弱守衛的代價是「讓人以為那裡有保護」（#443 的過去日期裁示）

請假編輯要不要擋掉「改到過去的日期」？**裁定是不擋**，而理由值得記下來：

1. **業務上它是日常不是例外** —— 家長週一打電話說上週五孩子發燒，行政補一張假單。
   擋掉過去日期等於讓這條路走不通。
2. **真正的保護是「已點名的不動」，不是「過去的不動」。** 前者是結構性的
   （撤銷只碰得到 `attendance_taken_at IS NULL`），後者是一道會誤傷正常操作的粗篩。

> **判準：一道弱守衛擋不住強守衛已經守住的東西，但它會讓人以為那裡有保護。**
> 加守衛之前先問「已經被守住的部分有多少」——如果答案是「全部」，那新加的那道
> 只剩下誤傷與誤導兩個作用。

### 一個數字加上分母，會改變依賴它的判定的語意（#454）

「已登錄 N」補上分母之後，「尚未登錄」這個詞的意思**自動變了**：
原本的告警數的是「一筆都沒有」，而畫面上一出現 `N/M`，使用者會把它讀成「還沒登完」。
兩者不一起改，就會出現「告警說 3 場、點進去篩出 8 場」——**而且沒有任何錯誤訊息**。

> **判準：加一個欄位如果會改變既有詞彙的讀法，那它不是加欄位，是改語意。**
> 改語意要把所有讀那個詞的地方一起盤點（這次是列表過濾與橫幅 count 兩處，
> 收斂成共用的 `classifyAcademyExamTodo`）。

### `ScopedIds`：讓繞過看得見，不是讓它做不到（#381）

家長端讀班級日誌，資料範圍要限制在自己小孩就讀的班。`lib/child-db.ts` 的
`ScopedIds`（`readonly string[]` 加一個不可構造的 brand）只能由 `childDb.pluck()`
產生，`fromScopedIds()` 拒收裸陣列——但**刻意留了逃生門** `as unknown as ScopedIds`，
沒有把它做成完全不可能。跟 #295 設計文件裡「錯的寫法要寫不出來」那條看似矛盾，
其實是同一個判準的兩種強度：**編譯期擋得住的地方就擋到底（介面簽名），
擋不住的地方至少要讓繞過變成一行顯眼的、需要故意寫出來的程式碼**，而不是讓它跟
正常寫法長得一樣不小心就漏過去。判準只有一句：**問「繞過會不會被看見」，
不是問「繞得過去方不方便」。**

### `DbUuidSchema` 比 Postgres 本身還嚴，驗證要跟著儲存層走（P0-1，#414）

`z.uuid()` 會檢查 RFC4122 的 version／variant 位元；`supabase/seed.sql` 的種子資料
用的是人類可讀但不合規的 id（`00000000-0000-0000-0000-000000000001` 這類），
Postgres 的原生 `uuid` 型別本身完全接受，但 `z.uuid()` 比資料庫還嚴，於是拒絕了
應用程式自己存的合法資料。決策是**放寬驗證、不動 seed**（seed 是既有資料、
改它的風險面比改驗證大），改用專案裡本來就有、卻沒被普遍採用的
`DbUuidSchema`（32 hex、標準分組、不查 version/variant）。30 個 route 檔一次換掉，
**理由是要有單一定義而不是 32 處各自決定**——分散決定的下場就是下次有人「順手」
把某一處改回 `z.uuid()`，看起來像是在加嚴格檢查，其實是重新挖開這個洞。
**判準：驗證的嚴格度要對齊儲存層實際接受的範圍，不能比儲存層更嚴** ——
更嚴的驗證聽起來像是「更安全」，但如果儲存層本來就存了驗證會拒絕的資料，
那就是應用層在阻擋自己的合法資料，而不是在擋壞資料。

### 一個 meta 教訓：session 自我監控可能失準

這次交接的觸發是外部監控（ops-warden 的 context 用量）跟這個 session 自己算出來的
數字**互相矛盾**——一旦工具輸出開始自我矛盾，這個 session 就不能再用自己的輸出來
驗證自己的狀態（自相矛盾這件事本身，從矛盾的那一側是看不出來的）。判準：
**當自我報告可能已經失準，要信外部訊號，不要信內部計算**——跟計畫席那條
「工具輸出退化，bash 退出碼／URL／SendMessage msg_id 都會自我矛盾」是同一族。
