# api-2 席

> 後端 API 第二席。**主 charter 是 [`billing-api.md`](billing-api.md)** —— 那 700 行是這個
> domain 的知識沉澱，接手第一件事是讀它，不是讀這頁。**這頁只放 billing-api.md 沒有的增量**：
> 兩席怎麼分工，以及這一席自己踩出來的判準。
>
> 抄一份 billing-api.md 的坑到這裡是最容易做、也最必然腐化的事（c11）。不要做。

## 為什麼有第二席

2026-09-06 開席。近 36 小時的檔案觸碰統計：`web:shared` + `web:core` 73 次由 design-web 與
design-web-2 兩席分擔（**兩席沒有換到平行度**），而 `apps/api` 側 128 次全部壓在 billing-api
一席 —— **輪替時等於單點故障**。所以把第二席從前端移到後端（pane 前身是 design-web-2）。

**這一席存在的理由是「API 側不能只有一個人知道」**，不是「有更多工單要做」。所以：
**優先接會產生可傳承知識的工單**（語意查證、跨檔案收斂、外部依賴），而不是搶量。

## 跟 billing-api 的分工

兩席同時在 `apps/api`，**沒有靜態的檔案分界** —— 分界是動態的：

```sh
gh pr list --state open          # 動共用檔案前先看對方有沒有在飛的
gh issue list --label seat:api-2 --state open   # 自己的佇列
```

- **撞車直接跟對方談，不用經過計畫席。**
- 慣例上 billing-api 拿金流/auth/schema 的主線，api-2 拿收斂類與查證類；**但這是慣例不是規則**，
  以工單標籤為準。
- **工單載體是 GitHub issues**（2026-09-06 起），不是 `backlog.md`。PR 描述寫 `Closes #N`。

## 這一席累積的判準

### 收斂之前先問「共用的是哪一半」

#437 把「帳單逾期」兩處獨立實作收斂進 `lib/invoice-overdue.ts`，但**只收了日期那一半**：

|                  | `routes/invoices.ts`                | `lib/revenue-report.ts`             |
| ---------------- | ----------------------------------- | ----------------------------------- |
| 「過了到期日沒」 | SQL `lt('due_date', today)`         | `dueDate < today`                   | ← **同一個問題，收斂** |
| 「未繳清」       | `status !== 'paid'`（**成員資格**） | `max(0, billed - paid)`（**金額**） | ← **不同問題，不收**   |

兩處放在一起看都叫「逾期判斷」，但下半場問的根本不是同一件事。**壓成一支函式會讓其中一端
拿到別人定義的子集**，而那正是 charter 裡「該不該算進某個計數是消費端的語意」那條。

> **判準：重複的是「同一個問題的兩個答案」才收斂；「兩個問題碰巧共用一段條件」不是重複。**
> 收斂前把兩邊的問題各寫成一句話，兩句話不一樣就只收交集。

### 守衛守的是「名字」，不是「概念」（#503）

`middleware/auth.ts` 的 `campusRequestGuard` 掛在 `/api/*` 上，讀的是 query string 的
`campusId` 與 `campusIds` **兩個字串**。於是：

- `GET /api/academy-exams` 的列表參數叫 **`campus_id`**（snake_case）→ 守衛看不見它，
  而它會被餵進 `applyCampusFilter` **覆蓋**使用者的分校範圍
- body 帶進來的分校（六支寫入端點）→ 守衛整個看不見

**一道全域守衛給人的心理保證是「這件事已經被統一處理了」，而它實際保護的只是它認得的
那幾個名字。** 判準：看到「全域 guard」時問一句 —— **它攔截的是概念，還是概念的某幾種
拼法？** 前者才配叫全域。

### 規則寫在守護點旁邊，但只寫在**其中一個**守護點旁邊（#503）

`routes/daily-checkins.ts:56-60` 早就把正確做法寫下來了，註解逐字是：

> **body 帶的分校要自己驗。** 全域的 `campusRequestGuard` 只看 query string ——
> 少了這一段，只管 A 校的人可以替 B 校的學生打卡。

**那句話說對了，然後就停在那個檔案裡。** 其餘六處寫入端點沒有一處照做，而寫下那句話的人
當時大概認為自己已經把規則記錄下來了。

> **一條規則寫在它其中一個守護點旁邊，看起來跟寫進規範裡一樣有安全感，但它的作用範圍
> 只有那個檔案。** 判準：寫下「這裡要 X，否則 Y」的時候問一句 ——
> **還有誰在同一個位置上？** 答案不是「只有我」的話，那句註解要嘛變成共用函式，
> 要嘛去每一處都寫一次，**要嘛變成 gate**。留在原地是三者裡最糟的：
> 它讓下一個人以為這件事有人管。

### 突變測試自己失效時，症狀跟「測試沒有辨識力」一模一樣（#503）

驗 #503 的守衛時，第一次突變我寫了一支 regex 去刪掉四支路由裡的守衛區塊，然後跑測試 ——
**6 條全綠**。差一點就得出「這些測試沒有辨識力」的結論，回頭去重寫測試。

`grep -c "沒有這個分校的權限"` 一查：**四個檔案裡守衛一行都沒少**（1 / 1 / 2 / 2）。
regex 沒對上縮排，靜靜地什麼都沒改，而「突變後仍然綠」與「突變根本沒發生」在測試輸出上
**完全同色**。

> **突變測試是拿來驗「測試有沒有辨識力」的工具，而它自己失效時的症狀，跟它要偵測的問題
> 一模一樣。** 所以突變之後、跑測試之前，要先**證明突變發生了**：`grep` 一次那個標記
> （這次改成把 `isCampusAllowed` / `campusIdsWithinScope` 改成 `return true; // MUTANT`，
> 先 `grep -c MUTANT` 拿到 2 才跑測試）。
>
> 這是全席通則「驗證步驟本身要能失敗給你看」的一個特別陰的成員：**這裡的驗證步驟是
> 「驗證的驗證」**，而它沒有任何人在驗。

**推論**：突變要挑一個**改了就一定編不過或一定看得見**的位置（helper 的第一行 `return true`），
不要挑一個「刪掉一段文字」的位置 —— 前者失敗時是紅的，後者失敗時是安靜的。

### 我們依賴一個外部系統的行為，而我們只寫了註解沒有量過（#511）

`applyCampusFilter` 對「一個分校都沒被指派」的管理員會下出 `query.in(col, [])`，
而整條 fail-closed 靠的是「**空清單的 `in` 是零筆，不是沒有條件**」。

那句話在本 repo 只以**設計註解**的形式存在 —— 沒有量測、沒有測試釘住，而它是
**PostgREST 的行為，不是我們的程式碼**。如果 `in.()` 其實是被忽略，那條 fail-closed
從第一天就是假的，症狀是「那個管理員看得到全部」而**沒有任何訊號**。

實測（三分鐘，本機 supabase 就在跑）：

```sh
curl -sI ".../campuses?select=id&id=in.()" -H "apikey: $K" -H "Prefer: count=exact"
# → 200, Content-Range: */0, body []
# supabase-js .in('id', []) → count 0（無條件是 11）
```

> **判準：凡是「我們的安全性 / 正確性靠外部系統的某個行為」，那個行為要被量過一次，
> 而且量測要連同日期與指令寫在依賴它的那段程式碼旁邊。**
>
> 這一族跟 [[lessons/silent-tool-failures]] 同源，但主角是**依賴**不是工具，
> 而且**它的失效會等到升級那天才發生** —— 到時候沒有人記得這裡有一個沒被驗過的前提。
> 註解裡留指令的用意就是讓那天的人知道要重跑什麼。

同族的實例（都在 charter 或 kb 裡）：PostgREST 的 `!inner` 對 embed 條件的影響、
`waitUntil` 不延後 promise 執行、`z.uuid()` 比 Postgres 本身還嚴。
**共同形狀：我們以為那是「我們的邏輯」，其實那一步的語意是別人定義的。**

### 四處寫法一致，那不是漏，那是規則

#438 的工單說「`campusNames` 沒有像 `classNames` 一樣濾掉退班」。查下去：「學生 → 分校」
在 `apps/api` 有**四處**推導，**四處一致地不濾**；而濾 status 的兩處都是「在籍」語意。

**n=1 是漏，n=4 且方向一致是規則。** 動手前先數一下有幾處、方向是否一致 ——
`rg` 一次的成本，換掉「把一條沒人寫理由的規則當 bug 修掉」的代價。

**而且它同時是授權路徑**（`campusScope` 走同一條關聯），所以「加個濾條件」在那裡不是顯示
調整，是**可見性收縮**。改之前先問：這條關聯除了畫面還餵給誰？

### 註解的不對稱，會讓對的程式碼看起來像 bug

#438 真正的根因不在程式碼 —— `classNames` 有一行「只算在籍的班」的註解，`campusNames`
旁邊什麼都沒有。**兩處相鄰、行為相反、只有一處寫了理由**，於是另一處看起來像忘了寫。

修法因此是**補註解不是補條件**。

> **推論：一組刻意不一致的相鄰程式碼，要嘛每一處都寫理由，要嘛一處都不寫。**
> 只寫一半比都不寫更糟 —— 沒寫的那半會被讀成「漏了」，而且是被一個正在認真幫忙的人讀成漏了。

### 外部依賴查證：結論寫在工單，不寫進 `kb/`

#428（LINE Messaging）產出的是資費、審核天數、方案額度 —— **這些數字有保鮮期，而 `kb/`
沒有欄位逼讀者去看查證日期**。所以報告落在 issue（有日期、有來源連結、可被時間推遠），
不進 kb（c11）。

**但查證裡有一種東西必須另外撈出來寫進 `kb/`：不可逆的決定。**
例：Messaging API channel 必須跟現有的 LINE Login channel **同一個 provider**，否則 userId
對不起來、家長得重新綁定，而 **channel 不能事後換 provider**。這種「按下去就回不了頭、
而按的人不會是今天讀報告的人」的點，要跟資費分開放。

### 交付完先切回 origin/main 再開下一件（2026-09-06 自己犯的）

出完 PR #440 之後，直接在**那支 PR 的分支上**做了下一張工單的 commit（幸好還沒推）。
`git status -sb` 會告訴你在哪一支，但**交付完的那一刻最不會去看它** —— 因為感覺上
「那件事已經結束了」。

> **做法而不是決心：下一件工作的第一個指令是 `git fetch -p origin && git checkout -b <新分支> origin/main`，
> 在讀工單之前。** 讀完工單再開分支，就已經在寫 code 的路上了。

## 交付

照 billing-api.md 的「交付」節（一切片一分支一 PR、絕不自行 merge、PR 寫取捨與**沒驗到的部分**）。
加兩條這一席特別容易漏的：

- **`refactor` / `docs` 類 PR 也要有驗證證據。** 「純搬移」不等於「不用驗」——
  #437 的證據是突變測試（`lt` 改 `lte` 得到 4 支紅），那才證明測試看得見那條規則。
- **停在 STOP gate 時，調查結果要落在 issue 上，不是只送 SendMessage。** 訊息會隨 session 消失；
  下一個接手的人看到的是 issue。裁決回來時同理（計畫席也走雙載體）。
