## 一、成績的兩條共用判準

- **不及格判準有兩份**：web `shared/utils/score-threshold.util.ts` 與 api `lib/score-threshold.ts`。
  防它們漂走的方式是 **api 的 `score-threshold.spec.ts` 用相對路徑直接 import web 那份**，同一張
  ±1 fixture 表兩邊各跑一次 —— 改任一邊沒改另一邊就紅（兩邊都塞過突變驗證）。
  **為什麼不合成一份**：`packages/*` 的別名在 api 沒人引用過、Workers 打包吃不吃 paths 沒驗過
  （`invoice-overdue.ts` 檔頭也寫了同一件事）。升級路徑寫在 api 那份的 `ponytail:` 註解。
- **跨場比較一律走 `lib/score-percent.ts` 的 `scorePercent`**（總覽平均、排序、進退步 `deltaVsPrev`）。
  **總分 ≤ 0 回 null**：DB 對 `academy_exams.total_score` 只有 `NOT NULL DEFAULT 100`，沒有 `> 0` 的
  CHECK，API 建考試也收 0。拿到 null 的那一筆不進平均、不進排序（排序時排最後）。
  單場自己的平均（班級列、最近考試列）不換算，回原尺度＋`totalScore` 讓前端畫分母。

## 二、會騙人的東西（實測踩到）

- **NaN／Infinity 經 JSON 變成 null —— 路由層測不出「有沒有防 0」**。`deltaVsPrev` 改回直接相除的
  突變在路由 spec 全綠：`0/0`、`70/0` 序列化後跟正確的 `null` 一模一樣。**防 0 要在純函式本身用
  `toBeNull()` 釘**（`score-percent.spec.ts`），路由 spec 只能證明「接線後輸出對」。
  凡是「回 null 代替壞值」的防線，先想 HTTP 層看不看得出差別。
- **git merge 沒報衝突 ≠ 合得對**：兩支分支各自加了同一行 import（`taipei-date`），自動合併留下兩行，
  tsc 報 Duplicate identifier。**併完一定跑 typecheck，不要只看 merge 有沒有 CONFLICT。**
- **squash 倉庫裡「取 ours」解衝突前要先證明 theirs 沒有別人的東西**：比對 main 上那幾檔與疊在下面那支
  分支尾端的 diff（`git diff <下層分支尾端> origin/main -- <檔>` 為空），再比下層分支尾端與自己分支起點
  （也為空）—— 兩個都空才能整檔取自己的版本。
- **`git reset --soft origin/main` 整理 WIP commit 時，`origin/main` 若比分支基底新**，會把 main 新加的
  檔當成「刪除」一起 commit（G8 誤刪過 #1575 的 charter，用新 commit 還原）。
  整理前先確認 `git merge-base HEAD origin/main` 就是 `origin/main`，不是就 reset 到 merge-base。
- **`nx test web --include=<glob>` 回 failed 可能只是 glob 沒對到檔**（`No tests found matching`），
  不是測試紅。輸出要看完，不要只看最後那行 failed。
- **`contact-logs.spec.ts` 在機器忙時前兩條逾時**（#1580）：spec 在第一條測試裡才 `await import('../index')`，
  整個 app 的 transform 算進 5 秒。看到它紅，先在乾淨的 main 上同時刻重跑，再判斷是不是自己造成的。

## 三、做法的索引

- **分頁撈齊有兩種介面，別混用**：`lib/fetch-all-pages.ts` 的 `fetchAllPages` 回 `{ rows, error }`
  （invoices、class-latest-exam 用）；`scores.ts` 內部的 `fetchAllRows<T>` **出錯直接 throw**、帶泛型
  （scores 系列用，呼叫端包 try/catch 回 500）。兩者都要求頂層 `.order('id')` 這類穩定排序再 `.range()`。
  要統一的話要先決定錯誤語意，不是單純搬檔。
- **契約測試 `BRANCHES` 的 `!` 前綴＝取代 `ALWAYS`**（`list-endpoints.contract.ts`）。`ALWAYS` 會強制
  帶那支端點的必帶參數（例：`/api/scores/students` 永遠帶 `studentId=`），而有些分支跟它互斥
  （`scope=all` 帶 `studentId` 會 400）。寫 `'!scope=all&campusId={campus}'` 就只送分支本身。
- **新參數要「只准搭某幾個」時用白名單式的拒絕**：`/scores/students?scope=all` 列出 8 個不准同時出現的 key，
  任一出現回 400 `SCOPE_ALL_PARAMS`；`campusId` 沒搭 `scope=all` 也回 400（原本不收的參數不默默忽略）。
  reviewer 對 8 個 key **逐一拿掉**做突變 —— 白名單的每一格都要有 spec 打到。
- **載入失敗時省略欄位（`undefined`）而不是回 null／0** 的設計（`latestExam`），會讓契約測試的 200
  證明不了查詢能跑。這種欄位一定要另外用探針打真 PostgREST 看值有沒有回來。
- **「排除作廢報名」「別 org 不進」這種過濾條件，fixture 裡要真的放一筆會被濾掉的列** ——
  #1579、#1583 都是 reviewer 拿掉 `.neq('status','void')`／`.eq('school_exams.org_id')` 後全綠才補上的，
  原因都是 fixture 根本沒有那種列（段考成績是空陣列）。
