## ⚠️ 先講撞名警告（#315 記過的教訓，這裡重申一次避免重犯）

`features/admin/pages/staff/teaching-log-dialog/` **跟這個功能無關**——那是授課時數統計
（人事視角）。這份構圖**完全沒有參考它**，指的「教務日誌」全部是 `class_logs` 表
（班級×日期，教學紀錄+作業安排）。表名本身就是刻意避開撞名取的，設計時再撞一次
會是雙重諷刺。

## 這個功能其實是兩型分流，不是一個表單

`class_logs.uses_contact_book`（班級層級開關）決定老師寫的是哪一種東西：

| 開關                    | 模式       | 實體                                  | 現況                                                                                                    |
| ----------------------- | ---------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `true`（國小班）        | 個人聯絡簿 | 每生每日一則自由文字                  | **撰寫介面不存在，但編輯 dialog 已經寫好**（`ContactBookEntryDialogComponent`，admin 頁用它做「補寫」） |
| `false`（國中班，預設） | 教務日誌   | 班級×日期一篇，教學紀錄＋作業安排兩欄 | **全新，API 有、前端零**                                                                                |

**兩型的表單不應該是同一支元件裡的 if/else，是兩條完全不同的資料模型**（一個是
`studentId+entryDate→content`，一個是 `classId+logDate→teachingRecord+homework`）。
唯一共用的是「今天要寫哪些」的入口列表，見下一節。

## 入口：不開新的「今日待寫清單」頁，長在 schedule 卡片上

**先問三層**：teacher-pages 的 `schedule.page.ts` 已經是「今天/近日教哪些班」的權威列表
（`teacher-schedule-mobile-day.md`，單日卡片、橫向 scroll-snap）。班級日誌列表**答的是
同一個問題**（今天教了什麼班），只是多一個「寫了沒」的維度——**不要另開一份課表**，
那正是 §三 反覆出現的「分岔靠一次次只修手上這份長出來」的起點（點名、成績登錄都已經
撞過這個坑）。

做法：在既有的每日課堂卡片上加一顆狀態點 + 動作：

```
┌───────────────────────────────┐
│ 09:00–10:30  數學  A303         │
│ 三年級忠班                       │
│                                 │
│  ○ 日誌尚未撰寫          [寫日誌]│  ← pending（中空），點了直接開對應表單
└───────────────────────────────┘
```

已寫的班級卡片：

```
┌───────────────────────────────┐
│ 09:00–10:30  數學  A303         │
│ 三年級忠班                       │
│                                 │
│  ● 已發布              [查看/改]│  ← done（實心）
└───────────────────────────────┘
```

**這把「可見性挪到動作發生的瞬間」用第二次**（第一次是作業台的存檔提示）：老師下課收
東西時視線本來就會落在這張卡片上，不需要再去別的選單找「今天有沒有漏寫」。

**歷史/補寫（超出 schedule 頁近日範圍的）留給下一步、不在這輪做**——schedule 頁目前
只看近幾天，回溯更久的日誌是另一個問題（要不要做、怎麼查），不要為了這份構圖硬塞一個
沒被要求過的歷史列表頁。

## 發布狀態呈現：沿用既有 `status-dot` 詞彙，不新增 tone

`status-dot` 的既有 tone 表**已經把「尚未撰寫」列成 `pending` 的例子**（元件註解原文），
直接對上：

| class_logs 狀態                | tone      | 形狀 | 色相    |
| ------------------------------ | --------- | ---- | ------- |
| 草稿（`published_at` 為 null） | `pending` | 中空 | 中性    |
| 已發布                         | `done`    | 實心 | success |

**沒有用 `overdue`**：雖然「上完課三天還沒發布」跟「漏點名」形狀很像（都是逾期未完成），
但目前沒有任何人要求追蹤這個逾期——加 tone 要過§三兩道關卡的第一關（先有使用者），
這裡沒有。**如果 teacher-pages 或使用者提出「要看哪些班拖太久沒發布」，那時候
`overdue` 現成，不用發明新色**——先在這裡記一筆，避免以後有人以為要造新東西。

## 表單構圖

### 教務日誌表單（`usesContactBook=false`，國中班）

```
┌───────────────────────────────┐
│ 三年級忠班 · 數學 · 9/5(五)      │
├───────────────────────────────┤
│ 教學紀錄（內部，家長看不到）      │
│ ┌───────────────────────────┐ │
│ │                           │ │
│ └───────────────────────────┘ │
├───────────────────────────────┤
│ 作業安排（家長會看到）           │
│ ┌───────────────────────────┐ │
│ │                           │ │
│ └───────────────────────────┘ │
├───────────────────────────────┤
│        [存草稿]    [發布]       │
└───────────────────────────────┘
```

**兩個 textarea 要用視覺區分可見度**，不要讓老師誤把只給內部看的教學紀錄寫成家長也看得到
（rules 明文「老師會寫不給家長看的話」，寫錯的代價是洩漏內部溝通，方向是「靜默做錯」不是
「沒反應」，屬於坑 11 那一族）。建議：作業安排欄位加一個小型「家長會看到」提示 icon + 文字，
教學紀錄不用特別標（預設就是內部，不用提醒「這是安全的」）。

**存草稿 vs 發布是兩個分開的按鈕，不是一個「儲存」+一個開關**——發布是廣播扳機
（rules：`published_at` 有值觸發家長端可見 + LINE 推播），這個動作的後果比存檔重很多，
兩個層級的動作放兩個視覺權重不同的按鈕，避免「以為只是存檔，其實通知了所有家長」——
呼應坑 11「使用者以為自己在導覽，實際在編輯」的同族風險，這裡是「以為在存草稿，
實際在發布」。**發布前是否需要二次確認交由 teacher-pages／使用者決定**，
構圖只確保兩個按鈕視覺上分得開。

**兩欄都可以留白**（API `UpsertSchema` 兩欄都是 optional，rules 也寫「老師可能先寫作業、
下課後再補教學紀錄」）——表單不擋空欄位存草稿，只有「發布」可能需要至少一欄有內容
（這是業務判斷，不是我拍板，列進待確認）。

### 聯絡簿撰寫（`usesContactBook=true`，國小班）——不重畫，接既有 dialog

老師視角要新增的**只有一個列表**：今天這堂課的學生名單 + 誰已經寫了。

```
┌───────────────────────────────┐
│ 一年級勤班 · 9/5(五)            │
├───────────────────────────────┤
│  ○ 王小明              [撰寫]  │  ← pending，點開既有 ContactBookEntryDialogComponent
│  ● 李小華              [查看]  │  ← done
│  ○ 陳小美              [撰寫]  │
└───────────────────────────────┘
```

`ContactBookEntryDialogComponent` 已經支援「用 draft（studentId+studentName+entryDate）
開一則新的」這條路（元件註解裡明寫這是設計給老師端用的），**這裡不需要新元件，
只需要老師端這支「今天這堂課的學生名單」把 draft 餵給它**——名單來源是這堂課的
`enrollments`（跟簽到表同一份資料，不必新查詢，呼應 §三「資料是不是已經在手上」）。

## 兩型的分流點在哪裡做

`schedule.page.ts` 的卡片已經知道 `classId`，讀一次班級的 `usesContactBook` 就能決定
「寫日誌」按鈕點下去要開哪個表單——**分流邏輯放在入口，不要讓使用者自己選模式**，
老師不應該被問「這堂課是哪一種」，那是班級設定決定的事實，不是每次操作的選擇。

## 待 teacher-pages / 使用者確認的點（彙整）

1. 發布前要不要二次確認彈窗
2. 「發布」是否要求至少一欄（教學紀錄或作業）有內容才能按
3. 歷史日誌（超出 schedule 近日範圍）要不要做、什麼時候做——這輪刻意不做
4. `overdue` tone 要不要現在就加（目前判斷還沒有使用者提出這個需求，先不加）
