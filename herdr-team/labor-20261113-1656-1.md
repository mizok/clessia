## 一、接手「舊端點待契約認領」：清單在哪、怎麼接

- **清單就是 `tools/agent-harness/campus-scope-contract-baseline.json`**。值以「舊端點：#2493 盤點範圍 OK，缺契約認領」開頭的，是盤點時判定範圍正確、只是沒有契約釘住的端點；以「缺口」開頭的是還沒修的洞。
  - 列出舊端點：`node -e 'for (const [k,v] of Object.entries(require("./tools/agent-harness/campus-scope-contract-baseline.json"))) if (v.startsWith("舊端點")) console.log(k)'`
  - 每支當初怎麼收斂（哪個 helper、path:line）在 #2493 盤點表留言（issuecomment-6848802291），寫契約前先對照，**行號會漂，以程式為準**。
- **認領的做法**：在契約檔（`apps/api/src/contract/*.contract.ts`）開頭加一行 `// scope-contract: METHOD /api/path`（Hono 路徑格式，例 `/api/enrollments/:id`），同一個 PR 從 baseline 刪那一筆。沒刪的話 A30 會紅（「已有契約認領 —— 從 baseline 刪掉」），只降不升。
- **契約至少斷言三件事**（盤點時定的範圍契約下限）：受限一校看不到／寫不進別校、指名別校 403 或 404、空範圍 0 列。另外一條「不受限照常」，證明不是無腦擋。

- 新增 admin 端點時：要嘛帶契約標記，要嘛本來不分校就列 `campus-scope-org.json`（reason＋evidence＋ruling 三欄都要），兩者都沒有就紅。

## 二、範圍修法的共用判準（這輪定下來的）

- **範圍外＝不存在**：單筆讀寫範圍外一律回該端點「不存在」的那個回應（多半 404；`GET /sessions/:id/changes` 對不存在本來回 200 空陣列，範圍外就同一個）。不要另開一種回應，否則洩漏「存在但不給看」。
- **修在共用入口，不修呼叫端**：academy-exams 是 `ensureExamOwnedByOrg`／`ensureClassesInOrg` 帶 `campusScope`；reports 是 `matchesFilter` 一處；staff 是 `staffOutOfScope(…, 'read'|'write')`。
- **讀與寫的判準可以不同**：人員讀＝任一分校在範圍、寫＝全部分校在範圍（跨校人員只有不受限者能改）。沒有任何分校的人員／沒有報名的學生，對受限者都是範圍外。
- **body 帶 id 的寫入**要驗那個 id 本身的範圍，連 org 都要驗：`session-packs.invoiceItemId`、`classes.nextClassId` 原本都只靠 FK，是 c1 洞。
- **受限者不能造出「全機構」的東西**：公告、校內考的 `campusId` 省略／null、新增分校，受限者一律 403。
- **側管道計數也算洩漏**：`inUseCount`、`scoreCount` 這種全機構筆數要收到範圍；代價是「看到 0 但刪除 409」，計畫席接受。
- **金額類只縮範圍、不動計算**：契約要同時斷言「不受限者數字不變」。

## 三、實作陷阱

- `applyCampusFilter` 直接套 supabase builder 常 TS2589。改用 `campusFilterIds(scope, …)` 算出 ids 後自己 `.in('classes.campus_id', [...ids])`，select 字串用 `const select: string = …` 變數。
- `findInOrg` 預設只選 `id`：拿它的結果判 `campus_id` 前要明寫欄位（`'id, campus_id'`），否則 `undefined` → 一律判範圍外。這次是契約抓到的。
- route 新增 404 回應要在 `createRoute` 的 `responses` 宣告，不然 TS 報 handler 型別不合。
- spec 替身（自組 Hono app、假 supabase）常沒有範圍查詢要的表：加了範圍檢查後，原本測別的守衛（`*`、`all_campuses`）的案例會先被範圍擋成 404。補替身讓目標在範圍內，**不要改斷言**。
- 讀取失敗要 fail-closed（拒絕）。審核席會突變「讀不到就放行」，要有一支 spec 讓替身回 error 抓它。

## 四、契約與驗證的操作

- 範本：`apps/api/src/contract/enrollments-scope-2493.contract.ts`（mock `authMiddleware` 設 `campusScope`，自建 org 與兩個分校，測完整個刪掉）。人員要真帳號時經 `createAuth(...).api.createUser`，不直寫 `ba_*`（`staff-scope-2493.contract.ts`）。
- fixture 同一 org 建第二個科目／課程要換名字（`subjects (org_id, name)`、`courses (campus_id, name)` 唯一鍵）。
- 證明舊碼紅：`git show origin/main:<route> > <route>` 跑契約，跑完蓋回新檔，`git diff --stat` 確認沒留舊碼。契約輸出 `N skipped` 是**沒跑**（fixture 在 beforeAll 就炸了），不是綠。
- **等鎖只 `until mkdir`**，pid 檔只寫 `$$`，席名寫同目錄 `who` 檔；不判過期、不動別人的鎖。過期分支（`kill -0` 失敗就刪）會把別席寫了文字的 pid 判成死鎖搶走，11-13 因此出事。
- 全套驗證可以寫成一支依序跑的腳本（每張：暫存 worktree 切到分支 head、併 `origin/main`、拿鎖跑 api（`--maxWorkers=2`）／web／affected typecheck／harness／該張契約、放鎖）。web 的 nx executor 不吃 `--maxWorkers`，api 與 web 要分開叫。
- 推 merge commit 時，若同時有別的 git 操作（腳本的 `git fetch`）在跑，推送會失敗；推完一律 `git ls-remote` 對 SHA，回報 PR head 貼 `gh pr view --json headRefOid` 的輸出。
