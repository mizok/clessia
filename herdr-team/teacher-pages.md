## 工作方式

## 行動優先的量測

**Chrome 視窗最窄只到 598px** —— 直接縮視窗量到的是假的 390px。
做法是注入**同源 iframe**（`width:390px`，用 `outline` 不要用 `border`，
`box-sizing: border-box` 會把 border 吃進去），量完移除。

**shell 吃掉 240px**：視窗 768 → `shell-content` 只有 528。桌機斷點一律
用 `@container shell-content`，而且**它量的是 content-box** ——
拿 `getBoundingClientRect()`（border-box）的數字當閾值會差一截，我為此定錯過一次 900。

## 這一席反覆踩到的一族：壞掉的樣子跟正常的樣子一模一樣

每個成員長得不一樣，**認得前一個不代表認得下一個**。已知的形：

| 形 | 實例 |
| --- | --- |
| 帶 `default` 的 `switch` | 停課的 `inactive` 掉進 default 顯示成「還沒上」。列舉→文字一律 `Record<Tone, string>`，少一個是編譯錯 |
| 測試全綠 | 接上 API 新欄位後 989 支全綠，因為**舊 fixture 沒有那個欄位**，每支測試都從新分支旁邊走過去 |
| computed 對 | 拿掉 `save()` 裡的守衛測試照樣全綠 —— **computed 對不代表有人在用它**，按鈕的 `[disabled]` 擋不住程式化呼叫 |

**判準：刪掉那段程式碼，至少一支測試要紅。** 全綠不算通過。

### 反向測試在前置條件從未成立時是空的（2026-09-06）

斷言「某個東西**不**出現」的測試，如果那個東西在這條路徑上**本來就沒出現過**，
它從第一天就沒有辨識力 —— 把它要守的那段程式碼整段刪掉，它照樣綠。

實例：「載入失敗不顯示錨點」。第一次就讓 API 失敗的話，`monthlyAbsent` 本來就是 `null`，
守衛在不在都一樣。**改成「先成功載到 4，再讓它失敗」才會紅。**

> **判準：讓那個東西先真的出現一次，再讓它消失。** 反向斷言要架在一個
> 「它確實出現過」的前置狀態上，否則你測的是初始值不是守衛。

跟 `enrollments.spec.ts` 那個「拿被測程式碼自己的演算法當預期值」同族：
**測試綠不等於測試有辨識力。**

### 查證這一族時，我自己會踩的坑（跟上表不同類）

上表是**缺陷本身**的實例；這裡是**查它的時候**方法失靈。混在一起會看不出
「工具在騙我」跟「程式在騙使用者」是兩件事（分類來自 admin-pages 的 #405）。

- **grep 回空先懷疑 pattern** —— 中文在 bundle 是 `\uXXXX` 逃逸；minify 把
  `documentElement.style.setProperty` 壓成 `n.style.setProperty`。
  **查線上 bundle 要查行為不查字面**
- **失敗的工具呼叫等於狀態沒變** —— 被 rate limit 擋掉的 `git checkout` 沒執行，
  我當它成功了 → 實機測到舊碼，差點回報「功能壞了」。
  同族：shell 的 `cmd && echo "成功"` 在 `cmd` 失敗時仍可能印出成功
- **自己的東西感覺不需要查** —— 把自己 PR 的狀態憑印象答成 OPEN，
  實際八小時前已 MERGED。**那個「感覺不需要」就是它逃過檢查的方式**
- **陷阱沒塞進去，跟「守衛不存在」長得一模一樣** —— 我用 `sed '0,/re/s'` 塞陷阱驗
  一支 typecheck，**BSD sed 不支援那個位址語法**，於是陷阱根本沒塞成，而 tsc 照樣綠。
  症狀（沒紅）跟「spec 檔沒被 typecheck 收錄」完全一致，我差點據此宣告一個假結論 ——
  實際 `tsconfig.spec.json` 明明寫著 `src/**/*.spec.ts`。
  **判準：兩個訊號打架時，先懷疑自己剛跑的那個。** 塞完陷阱先確認 `diff` 真的有東西，
  再去看它紅不紅（驗陷阱本身，不只驗結果）
- **`web:typecheck` 看不到 `.spec.ts`** —— 它走 `tsconfig.app.json`；而 vitest 用 esbuild
  剝型別、根本不做型別檢查。**兩道 gate 都綠，漏改的 fixture 就活在盲區的交集裡**。
  動到共用 interface（尤其加必填欄位）時要另外跑
  `npx tsc -p apps/web/tsconfig.spec.json --noEmit`

#### 這一族的實例目錄搬到 kb 了

**[[lessons/silent-tool-failures]]** —— 載體、它靜默地做了什麼、當事人憑什麼起疑，
逐件列在那裡（BSD sed 的 `0,` 位址、ANSI 逃逸碼、`git grep` 的路徑參數、
`git diff` 的兩點三點與移動的基準點、手寫假 supabase 的寬容、zsh 的 `$VAR:a` 修飾符、
沒有人會經過的移除條件、CI 監看器看到的那一輪…）。

**為什麼不留在這裡**：它的讀取時機是**卡住的那一刻**（grep 回零筆、預期會紅的沒紅），
而 charter 只在接手這一席時被讀。那一頁掛了 doc-router，會在對的時刻自己出現。
**而且那些坑幾乎都不是老師端專屬的** —— 每一席都會撞到。

判準留在這裡，因為它是我這一席反覆用到的：
**零命中之後的下一個動作，是換一條獨立的路再問一次同一個問題，不是下結論。**

#### 那條「動到 web 就跑 build」的規則，理由記錯了

charter 之前寫的理由是「模板改動」。billing-api 從相反方向撞到同一條縫：
在 `AcademyExam` 上加必填欄位，`nx affected -t typecheck` **綠**、vitest 也不管型別，
**只有 `nx build web` 紅**（抓到某支 spec 的 fixture）。

所以那條縫的正確描述是 **「typecheck 與 vitest 都看不到，只有 build 看得到」**，
而觸發條件不只是模板 —— **共用 interface 加欄位也踩得到**。
規則本身是對的，被記錯的是它為什麼存在，**而理由記錯的規則會在它真正該生效的場合被跳過**。

## 防護習慣不會自己跟著工具跑到下一個場景

2026-09-06，同一天內：切片二我因為「`str.replace` 沒有 assert 就沒有訊號」吃過虧，
**當場替每一個 replace 加上 assert**；切片三改用 regex 批次補五支 spec 的替身成員，
**繞過了那個習慣**，把 `status: () => 'ready' as const,` 插進了型別宣告而不是物件，
整包編譯紅。

**那不是健忘。** 兩次的工具是同一個（在檔案上做字串替換），但**場景看起來不像同一件事**：
一次是「改一段程式碼」，一次是「批次補一個欄位」。**習慣是綁在場景上的，不是綁在工具上的。**

> **判準在 README（全席通則），這裡只留這一席的實例** —— 同一條規則寫兩個地方會漂。

**同一天的三個實例，工具不同、形狀相同**：

| 場景 | 我繞過的那個習慣 |
| --- | --- |
| regex 批次補五支 spec 的替身成員 | 前一片才建立的 `assert old in s` |
| 收 process 時 `ps -o args= \| cut -c1-70` | **守衛把自己要檢查的證據截斷了**（路徑剛好被切斷，全部誤判成「不是我的」） |
| `git add -A && git status && git commit` 寫成一行 | 「commit 前看檔案清單」—— **看到清單的時候已經 commit 了**，那次誤刪三個檔案共 30 行別人的東西 |

**第三個最值得記**：檢查與被檢查的動作**在同一次工具呼叫裡**，
等於沒有檢查。`git status` / `git diff --cached --stat` **必須是獨立的一次呼叫。**

## 收尾的順序：先解除狀態，再收掉提供狀態的服務

2026-09-06 收環境時，我**先收了 API 才想到要登出** —— 而登出需要 API 活著。
結果瀏覽器裡留著一個家長身分的 session cookie，指向一支已經關掉的服務。

**下一個起 API 的人會靜靜地變成那個身分** —— 沒有錯誤、沒有提示，
只有一個不是他預期的畫面，然後他花時間查為什麼。

> **收尾的順序是「先解除狀態，再收掉提供狀態的服務」。**
>
> 人很容易反過來，因為**服務看起來像基礎設施、狀態看起來像使用** ——
> 收「使用」感覺是次要的。實際上**狀態的解除依賴服務還活著**，順序反了就做不到。

實作上的順序：**重起服務 → 解除狀態 → 確認解除了（`/api/me` 回 401）→ 才收服務。**
本機那些門怎麼開見 [[lessons/local-manual-verification]]。

## 觀測工具連我自己剛做的事都沒記錄

家長端繳費頁：我用 `performance.getEntriesByType('resource')` 看它打過哪些 API，
**結果沒有任何帳單請求** —— 差一步就回報「這一頁根本沒打 API 卻顯示空狀態」。

**推翻它的不是「這個結論聽起來太嚴重」，是「我自己那兩支 fetch 也不在同一份清單裡」。**

> **判準：懷疑一個觀測結果時，先問它有沒有記錄到「我剛剛親手做的那件事」。**
> 記錄不到，那份清單對這個問題就是空的，**跟被觀測的東西沒有關係**。
>
> 用直覺（「這聽起來太嚴重」）推翻結論不可靠 —— **今天有兩個真 bug 也「聽起來太嚴重」，
> 而它們是真的。** 直覺分不出這兩種，證據可以。

改用**結果驗證**確認那一頁正常：切換器有孩子名（代表 children 有載到）、
空狀態文案是「目前沒有帳單紀錄」而不是「載入失敗」、API 直接打是 200/0 筆。

## 替身的兩個方向，風險不對等

同一天的兩件，方向相反：

| 方向 | 例 | 症狀 |
| --- | --- | --- |
| 替身**比真實系統寬容** | `schedule.page.spec` 把整個 `OrgSettingsService` 換掉、`status` 直接給值 | 拿掉 `load()` 的 error 分支，**18 支測試全綠**。永遠安靜 |
| 替身**缺一個成員** | `ChildScopeService` 加 `status` 之後，五支 spec 的替身全缺 | `ctx.childScope.status is not a function`，**當場爆** |

> **替身缺東西會自己喊，替身多給東西永遠安靜。兩種方向的風險完全不對等。**

所以**太窄的替身便宜得多**：它會吵，而吵是看得見的。
（同日 billing-api 從另一條路得到同一個結論。）

**推論**：`kb/wiki/lessons/silent-tool-failures` 那頁記的全是「靜默」的成員，
**不是因為會喊的那種不存在，是因為它們當場就被修掉了** —— 那頁是倖存者偏差的產物。

## 沒有下游就不放那顆按鈕

教務日誌 v1a 刻意不放發布按鈕 —— **不是 disabled，是不存在**：
灰著的按鈕仍然在告訴使用者「這裡有這個功能」。當時發布不可逆、只設時間戳、
家長端沒有任何畫面讀它。

**同一個錯有文案版本，而我沒第一次認出來。** v1a 的設計初稿寫著確認彈窗要說
「之後會接 LINE 推播」—— 那排在 P4 且 repo 至今沒有實作。
**在確認彈窗承諾一件不會發生的事，跟放一顆沒有下游的按鈕是同一個錯，只是換了一層載體。**

> 承諾分兩種：**空間上的**（UI 對使用者做出後端兌現不了的承諾）與
> **時間上的**（承諾一件之後才會發生、可能永遠不發生的事）。後者更難認。

**第三種：拿掉一個「多餘」的東西，順手拿掉了它兼任的另一個職責。**
「單孩子時不渲染切換器」聽起來只是省掉一顆沒用的按鈕，但那顆徽章同時是
**單孩子家長在三頁上唯一指出「你在看誰的紀錄」的東西**。
元件的名字（切換器）是它的職責，不是它在畫面上的職責。
**「不給切換」和「不給顯示」是兩件事，只是碰巧共用一個元件**
（理由已寫進 `child-switcher.component.spec.ts` 那支測試上方，
因為寫在測試旁邊才擋得住下一個人「照裁定」把它刪掉）。

## upsert 的鍵不含什麼，就是誰會被靜靜覆蓋

| | 鍵 | 誰會撞 |
| --- | --- | --- |
| 教務日誌 | `classId + logDate` | 同班同天**兩場課**兩張卡 → 同一篇 |
| 個人聯絡簿 | `studentId + entryDate` | 同一學生同天**兩個班** → 同一則（跨班，更難察覺：卡上班名不一樣） |

**防線是開啟時預載既有內容**，不是警語 —— 語意從「空白新寫」變成「編輯既有」，
覆蓋就結構上不可能。警語防的是「沒注意」，預載讓「沒注意」也不會造成損失。

**清單會過期**：`/missing` 排除了寫過的人，但那是載入那一刻的事實。
別人在那之後才寫，清單仍然顯示他 → 直接用空白 draft 開 → **老師看不到別人寫了什麼**
就蓋掉。所以**點開的當下要重查一次**。

## 收緊一個判準時，要拿已知的真案例回驗 —— 收緊會靜靜地讓它消失

2026-09-06 的 hover 可點性偵測器：第一版把 `span.p-select-label` 判成命中，
查父層發現外框 `.p-select` 有白底＋框線，**那是誤報**。收緊的第一個寫法是
「**任何祖先有底色就排除**」——

那一版會把**卡片裡的所有東西**都排掉，而已知的真案例 `a.dashboard__fact`
剛好就在一張卡片裡。**它會消失，而報告會變成一份乾淨的零命中，
沒有任何東西告訴你它壞了。**

正確的收緊是「**祖先只有在緊貼元素（面積 < 3 倍）時才算同一個視覺單位**」——
外框緊貼控制項，卡片不會。

> **判準：放寬會製造雜訊（看得見），收緊會製造沉默（看不見）。**
> 所以**每一次收緊都要重跑一次已知的真案例**，不是只確認誤報消失了。
> 這是「每個嚴重度訊號都要拿已知的真實案例去驗」的動態版本 ——
> 那條講的是立訊號的時候，這條講的是**每次改訊號的時候**。

**沒有那個已知真案例可以回驗的話，收緊過頭的版本會直接交出去。**

## 對照組要造在「兩者長得一樣」的那一格上

M4 的測試設計：`ChildScopeService` 載入失敗與「讀到了但真的沒有孩子」
**`children()` 都是空陣列**，分開它們的只有 `status`。所以兩支測試要**成對**：

- 失敗 → 畫面出現「讀不到孩子資料」
- 成功但沒有孩子 → **那句話不出現，而且畫面是空的**

**只有第一支的話它證明不了任何事** —— 它沒有排除「那句話永遠都在」。
這是「反向測試在前置條件從未成立時是空的」的正面版本：
**斷言某個東西出現時，要同時有一格證明它不是永遠出現。**

## 搬移類改動：比對兩邊，不是驗證結果

**當改動宣稱是「搬移」時，證明它的方式是比對兩邊。** 驗證結果只告訴你
「現在看起來能動」，而搬移的風險是「有東西沒跟過來」。

- 刪 spec 之前比對兩邊的 `it()` 標題，空集合才刪 ——
  **沒比對就刪 spec，等於用「測試還是綠的」證明「我沒刪掉測試」**。
  刪掉的測試不會讓任何東西變紅，那是它們消失時最安靜的地方
- 樣式做**逐字 diff**（換掉 block 名之後 `diff`）。這比實機強：實機只證明我看到的那一屏
- 抽元件會把**還完的債**悄悄借回來 —— 債清了 baseline 就空了，gate 對「借回來」是盲的，
  只有還債的人記得去看。取樣判準是**「掉了誰會發現」**，不是「這段重不重要」

## 尺寸下限要明寫，不是靠內容撐出來

內容撐出來的 44px 是**副作用**；宣告出來的才是保證。下一個人把狀態列拿掉，
它會靜靜掉下去而且沒有東西會叫。同一條原則的另一面：
`flex-shrink: 0` 不能靠「文案剛好夠短」代替。

**44px 是給互動目標的，不是所有元素** —— checkbox 被判太小的正解是刪掉它多餘的
`cursor: pointer`（真正的目標是 label），不是把它撐成巨大方塊。

**寫 SCSS 前逐一驗 token 有沒有定義。** `--red-500` / `--warning-700` 都不存在
（專案是 `--error-*`，warning 只有 50/100/200/600/800），而沒有 fallback 的 `var()`
解不到就**整條宣告作廢、沒有任何錯誤訊息**。
`--window-height` 例外：它是執行期寫入的，harness 的 `RUNTIME_TOKENS` 有登記。

## iOS Safari 的視窗（未經真機確認）

`WindowSizeDirective` 用 `window.innerHeight` 且**只聽 `window:resize`**，
而 iOS 工具列收合發的是 `visualViewport.resize` —— **變數在工具列狀態切換那一刻是舊的**。
所以驗證步驟一定要「先捲動讓工具列縮小 → 再開面板 → 再讓工具列恢復」，
**直接開直接看很可能是好的**。

`env(safe-area-inset-*)` 全 repo 零使用，但**範圍只到「會覆蓋導覽列的 fixed 抽屜」**
（一般頁面有導覽列擋著，使用者實機訂正過）。被覆蓋的導覽列保護不了覆蓋它的東西。

詳見 [[lessons/bottom-sheet-meets-mobile-viewport]]。**還沒修是刻意的** ——
現在去修等於用猜的答案覆蓋掉唯一一次能拿到真答案的機會。

## 驗「什麼都不顯示」要有對照組

拿掉一整類警告之後，正確的表現是畫面上什麼都沒有 ——
而**「正確地沒顯示」與「壞掉了沒顯示」長得一模一樣**。所以要有一格**該顯示**的對照。

那次最有價值的一格是**造不出來**的那一格：我設計了對照組要保護「刻意保留的不完美」，
實機打下去 409 —— API 根本不允許重疊的假。**實機驗證推翻的是我自己的前提，不是實作。**

> **先驗再寫。** 先把結論寫進 charter 再去驗，charter 會記載一個論證嚴謹、但前提是假的道理。

## 零命中可能只是那一頁什麼都沒渲染

判準在 [[lessons/silent-tool-failures]]（「這個空的結果，是真的沒有，還是我的查法看不到？」），
**這裡留這一席的實例**：

第一次掃老師端課表的可點性，得到 **0 命中** —— 而那位老師**本週沒課**，
課堂卡與動作鈕**根本沒有渲染**。換成有課的老師（4 堂、6 顆動作鈕）才是真的 0。

> **那個假的 0 跟真的 0 在報告上一模一樣。**
> 掃畫面之前先確認**你要量的東西真的在 DOM 裡**
> （`document.querySelectorAll('<你要量的>').length` 先看一眼）。
> 怎麼挑一個「畫面上真的有東西」的帳號見 [[lessons/local-manual-verification]] 第六節。

## 本機資料的形狀決定哪些 bug 看得見

`/select-role` 對單角色使用者說「這個帳號有多個身分」卻只列一個選項，活了很久 ——

**修 bug 的同時要問：為什麼本機看不到它正確的樣子？**

## 兩個具體的坑

- **`styleClass` 管不到 flex 行為** —— PrimeNG 的 `styleClass` 落在內層 `<button>`，
  而 `<p-button>` **主機元素**才是父層 flex 容器的 item。`flex-shrink` 這種由父層佈局
  決定的屬性要用 `class="..."`（Angular 放主機元素上）
- **元件自己 `providers: [DialogService]` 會蓋掉測試注入的替身**，於是真的去實例化對話框。
  被 DialogService 開出來的元件本來就該從開啟方拿同一個實例

## hedge 過的預測讀起來像查證過的結論

我對 infra 說「你的 gate 會在 `--window-height` 上偽陽性」—— 那個洞早就補過

然後自己把「gate 沒有這一層」當成已知事實。**我只在別人的方向上警覺。**

### 點名面板那個 P0：已修，而我當初提的方向是錯的

原本的洞：`isLocked`（只看紀錄）與 `hasLeave`（也看請假單）兩個定義都被用在決策上，
於是「有請假單、紀錄還沒套用」的學生**不被鎖（畫面邀請你標）卻被算成豁免**
→ 沒被標卻顯示「全部標記完成」→ 存檔只送標過的人 → **他完全沒有紀錄**。
tester 看到的「3 人、到 1 缺 1、請 0」每個數字都對得上。

**已修（`#413` footer 那句 + `#416` 後端補寫 `on_leave`）。**

**但那個寬窄不對稱仍然在，而且是刻意的** —— 我當初傾向「兩個判準取一致、都算待標記」，
**那是錯的**，元件註解給的理由比我的好：

> 只豁免 `on_leave` 的話，「只有請假單、紀錄還沒套用」的學生會被鎖進死循環：
> 沒有「標成請假」可點 → 算 pending → 存不了 → 被迫標缺席 → 觸發誤標旗標 →
> 只好標出席（**說謊**）才存得了檔。

判準是**可見性**：`hasLeaveRequest` 誤判會長成「一個明明來上課的學生掛著請假 chip」，
就在老師眼前那一列；而被迫填的那筆假出席寫進 DB 之後**跟真的一模一樣**。

所以規則是：**「這個人別碰」用寬的 `hasLeave()`，「這一格要不要 disable」用窄的
`isLocked()`。** 兩個判準本來就該不一樣 —— 錯的不是不對稱，是當時**沒有人講出**
它為什麼不對稱，於是它看起來像個 bug。

> 我當時把「兩個定義不一致」直接讀成「其中一個錯了」。
> **不一致有時候是答案，不是症狀** —— 要先問「它們回答的是同一個問題嗎」。

### 2026-09-06／07 補：那句話有一個更極端的版本

家長端三頁**在本機從來沒有被打開過**（seed 裡 `parent` 角色是 0），

| 頁 | 狀況 |
| --- | --- |
| `/api/me/children` | 撈一個已被 DROP 的欄位，**每次呼叫都 500** → 整個家長端不能用 |
| `/parent/grades` | `PAGE_SIZE = 200` 超過 API 的 `max(100)`，**每次都 400，從來沒載入成功過** |

> 後者連「看起來」都沒有，只有測試在替它說話。**

答不出來的話，那些綠燈證明的只是「程式碼跟測試互相同意」。
