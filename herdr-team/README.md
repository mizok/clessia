# Agent Team 席位章程

> 這個專案由一個 agent team 開發：計畫席（planning session）派工、驗收、裁決；
> 實作席按 **domain** 分工。每席一份 charter —— 席位的專長外化在這裡，
> **session 會死，席位不死**：新 session 接手一席，先讀該席 charter 繼承專長。
>
> 維護規則：每完成一個被驗收的切片，該席把「下一個接手的人必須知道的事」
> 蒸餾進自己的 charter（不是流水帳 —— 是會再次用到的知識）。計畫席驗收時檢查。
> charter 是操作設定不是專案文件：專案知識仍歸 `kb/`，charter 只放
> 「這一席怎麼工作」與指向 kb 的地圖。

## 通用協定（每席都適用）

- 工單來自計畫席（SendMessage），完成/卡住回報計畫席，不直接對使用者
- **合併授權 v2（2026-09-03 使用者定案,取代 08-29 版）**:CI 綠＋計畫席驗收的 PR
  由計畫席自行合併並部署。**保留給使用者親合的三類:migration(schema)、金額計算路徑、
  授權/權限邏輯** —— 攢到每日 12:00/17:00 的窗口。設計文件由計畫席批准即可動工;
  「方向級」改動(刪頁面、視覺改向)先做但標記窗口確認項,使用者有否決權(保持可 revert)。
  使用者只在 12:00/17:00 出現,其餘時間**計畫席就是專案負責人,專案不因等待而停**;
  業務問題做可逆暫定決策標記待確認
- 開工前：`git fetch` 從最新 origin/main 開分支；worktree 內 root 與 apps/api 各 `npm ci`
- 憲法（`kb/wiki/architecture/constitution.md`）與 AGENTS.md 永遠先讀
- 設計裁決回計畫席，不自行擴範圍；「刻意的判斷」與「需要人工看的點」寫進 PR

## 開席操作（herdr）

開新席一律用 `herdr worktree open --workspace w2 --path <worktree> --label <席名>` ——
它會在 clessia-plan 底下開成 worktree 連結的子 space。**不要用 `tab create` 硬湊**
（已犯兩次：admin-pages、design-web-2 初開時）。然後 `herdr agent start <席名> --kind claude --pane <root_pane>`。

### 退場提示的固定範本（輪替前，計畫席送出）

**這是「輪替前檢查未開 PR 的分支」那條通則的載體** —— 它原本只是一句規則,沒有任何動作
會觸發它,而輪替是計畫席發起的、計畫席發那則提示時一定會讀這一節。**掛在必然發生的動作上。**

送給要退場的席位,照這個順序（第 2 步在 context 更滿時會做不好,所以排在第 1 步之後）:

1. **把未推的東西 commit + push**,即使沒做完
2. **蒸餾 charter** —— 問「這是狀態還是知識」:狀態(誰在做什麼、哪支 PR 在飛)不要寫,
   它明天就是假的;知識(這個坑長什麼樣、為什麼那樣修、什麼訊號可以信)要寫
3. **開 PR** —— 這一步不能省。**推上去 ≠ 交接完成,沒有 PR 的分支等於沒寫**
   （2026-09-06 兩天內抓到兩次:billing-api 與 design-web-2 的交接都只活在已推的分支上）
4. 回報:PR 編號、未完成的工作、**只存在於這個 session 記憶裡而沒寫進 charter 的東西**

**計畫席在送上任提示之前要跑的檢查**（不是請對方跑,對方已經下線了）:

```bash
gh pr list --state open --search "<席名>"          # 還有沒有它的東西沒開 PR / 沒合
git ls-remote --heads origin | grep -i "<席名>"    # 分支還在但沒有對應 PR 的

**交接訊息裡凡是宣稱「某個背景的東西還在跑」,要附查法不附 PID**(2026-09-07 事故):

計畫席在輪替 infra 時選了「移到背景並離開」,並在上任提示裡寫「磁碟看門狗還在跑,
你不用重開」—— **`ps -p <那個 PID>` 是空的,它早就死了**。

**PID 是狀態不是知識**,而背景任務掛在 session 上、**session 一輪替它就死,
沒有任何東西會發出聲音**。這是「壞掉的監控比沒有監控糟」的合體版本:
**死掉的那個版本讓下一任更放心,因為交接訊息替它背書。**

**所以退場／上任提示裡不要寫「X 還在跑」,要寫「X 的查法是 Y」** ——
下一任跑一次就知道,而不是從一個可能已經是假的前提開始。

**被監控的東西自己要能證明活著**:infra 把磁碟看門狗改成每輪寫一行 heartbeat
(`tools/disk-watch.sh`),**於是「它死了」變成 log 最後一行過期這件看得見的事**。
```

### 上任提示的第一行必須是 `/rename`（2026-09-06 使用者提出）

**問題**：Claude app 的 session title 是從對話內容自動生成的，所以列表上看到的是
「這個 session 現在在幹嘛」，**不是它是哪一席** —— 七個 session 併排時分不出誰是誰。

**解法**：`herdr agent prompt` 送進 pane 的上任提示，**第一行寫 `/rename <席名>`**。
session 一啟動就自己正名，而 `terminalTitleFromRename` 預設 `true`，所以終端分頁標題
也會跟著改。**每次輪替自動生效，不需要使用者手動命名。**

### `git worktree move` 之前先查那個目錄裡有沒有跑著的行程

**2026-09-06 事故**：計畫席輪替 design-web 時把 `.worktrees/bundle-analysis` 改名成
`.worktrees/design-web`,**而那個目錄裡有一支 workerd(API dev server)正在跑**。

inode 跟著搬,所以**行程沒死** —— 但它的模組解析與檔案監看還指著搬走前的路徑,
於是它**LISTEN 著、接受連線、永遠不回**。三小時後另一席要做家長端實測時才撞到,
而症狀(`curl` 十秒逾時、`code=000`)看起來像那支 server 掛了或別席沒收乾淨,
**沒有任何東西指向「有人把目錄搬走了」**。

**搬之前跑這個**:

```bash
lsof -a +D .worktrees/<舊名> -d cwd 2>/dev/null   # 誰的 cwd 在裡面
lsof -nP -iTCP -sTCP:LISTEN | grep <舊名>          # 誰在裡面開了 port
```

**有東西就先請那一席收掉再搬。** 搬完通知所有席位那個路徑變了 ——
**別席的 dev server 可能還指著舊路徑,而它不會報錯。**

### worktree 目錄名必須等於席位名

**下游全部繼承它** —— `ListAgents` 的 peer 名、cwd 顯示、herdr 的 pane 名。

2026-09-06 查到兩處不符，都是「當初為別的用途開的 worktree 留下的名字」：

| 席位          | 目錄                         | 來源                            |
| ------------- | ---------------------------- | ------------------------------- |
| `billing-api` | `.worktrees/pin-better-auth` | 當初為了釘 better-auth 版本開的 |
| `design-web`  | `.worktrees/bundle-analysis` | 當初為了分析 bundle 開的        |

於是 peer 名變成 `pin-better-auth-ce` / `bundle-analysis-00`，**而那正是「識別字跟它代表的
東西對不上」那一族**。目錄名要改只能趁輪替（跑著的 session 的 cwd 不能消失）。

## 開分支規範（2026-08-30 事故後新增）

worktree 裡開新分支**一律** `git fetch -p origin && git checkout -b feat/x origin/main`，
**絕對不要** `git checkout -B main` / `git reset --hard` 動本地 `main` —— `main` 是主 checkout
擁有的共用 ref，從 worktree 移動它會讓主 checkout 的 HEAD 與 index 脫鉤，顯示成一批
「回退已合併工作」的幽靈變更（已發生兩次，診斷見 reflog 2026-08-30）。

**替代品（2026-09-06 第三次事故後補）**：要最新的內容就 **`git checkout --detach origin/main`**
—— **同樣拿到最新檔案，但不碰任何分支 ref**。

> **「我要最新的程式碼」跟「我要 `main` 這個名字指到最新」是兩件事**，
> 而 `-B main origin/main` 同時做了兩件，**其中第二件不是你需要的、也不是你有權做的。**

**這條原本只有禁令沒有替代品** —— 而**一條只有禁令的規則，在你有一個正當需求的時候擋不住你**。
第三次違反的那一席**讀過這條、當天還在別處引用過它**，它要的只是「讓本機檔案是最新的」，
而那個需求本身完全合理。**禁令沒有回答「那我該怎麼做」，所以它被繞過了。**

**修法（在主 checkout 跑，指名單一檔案）**：

```bash
git restore --source=HEAD --staged --worktree <那個檔>
```

**不要用 `git reset`** —— 主 checkout 可能有別人未提交的東西
（例如使用者刻意不進版控的 `.claude/settings.json`），一次性的做法會把它一起掃掉。

## 疊 PR / squash 倉庫的兩條鐵律

1. **「MERGED」只說明它合進了某個東西，沒說是 main**（#89 事故；#129 重演 —— 使用者
   在下層合併後 51 秒就合了上層，人工轉 base 根本搶不到那個空檔）。因此**疊 PR 開出來
   就標 draft，等 base 轉成 main 才轉 ready** —— 讓「還不能合」變成 GitHub 擋得住的狀態，
   不是靠人搶時間差。下層合併後上層 base 立刻人工轉 main、下層分支即刪；合併後才推上去的 commit 會在已合併分支上擱淺，
   永遠不會自己變成 PR（#105 事故 —— 手機版兩筆 commit 擱淺，#110 撿回）。
2. **squash merge 之後，「commit 在不在 main」只能用內容判斷**（grep 關鍵字串,
   且**要挑只有那支 PR 會產生的字串** —— 命中別支也會提到的關鍵字,驗證本身就是假的），
   `git merge-base --is-ancestor` 對原始 SHA 永遠回「不在」—— 它在 squash 倉庫裡
   對這個問題永遠給錯的答案。

## 全席通則（自 #108/#109 提煉）

- **gate 寫完一定要塞陷阱看它會不會紅** —— 綠燈有兩種，輸出上一模一樣。
- **規則寫進元件/測試比寫進文件便宜** —— 能用測試釘住的約定就不要只寫在 charter。
- **charter 會腐化，接手時先驗一遍再信它**；寫進 charter 前先問「這是狀態還是知識」。

## 零 idle 制(2026-09-03)

> **2026-09-06 訂正:這條原本沒有檢查點,而它當天就整批失效了** —— 使用者指出八席裡
> 六席 idle,而其中五席各自都有開著的 issue。計畫席在那之前還回報「七席都有工單在做」,
> **那句話是從 issue 板推論的,不是查 herdr 來的**。
>
> 兩個修正:
>
> 1. **檢查點是「送出交付訊息的那一刻」** —— 那是必然發生的動作。
>    交付訊息的最後一個動作是 `gh issue list --label seat:<自己> --state open`,
>    **不是等回覆**。等我回覆不算工作。
> 2. **「我不能做」也要說出來。** 前置沒到、需要裁決、或工單本身有問題,
>    都要回報 ——「這支我不能做,因為 X」是合格的交付,**沉默不是**。
>    當天 infra 自己的診斷最準:「**不是被什麼擋住,是我把『等指令』當成了預設**」;
>    而待命與正常工作在 herdr 上看起來一模一樣,所以它不會被誰發現。
> 3. **計畫席回報席位狀態一律查 `herdr agent list`,不查 issue 板。**
>    issue 有指派 ≠ 席位在動。

席位不等餵:**交付即繼續**:送出交付訊息後不等待,直接用
`gh issue list --label seat:<自己席位> --state open` 認領下一項開工
(2026-09-06 起工單載體是 GitHub issues,不再是 backlog.md);回覆到了再切回處理(15 分鐘規則只留給「追訊息」用)(在 issue 上留言認領、通知計畫席、直接開工;PR 描述寫 `Closes #N`)。佇列裡的項目

> **什麼時候停是對的(2026-09-07 補,這一節原本只有「不能等餵」那一半)**:
>
> **不是「沒事做就停」,是「查過佇列、確認每一項的卡點、把卡點報出去」之後才停。**
> **三個動作都做完了才是交付,只做最後一個是待命。**
>
> **「佇列裡剩下的都卡在裁決上」這個回報本身就是合格的交付** ——
> 而**「不要為了不 idle 而找事做」是它的另一半**:
> 佇列真的空了、卡點也報出去了之後,**硬找事做會製造需要別人審的東西,
> 那不是產出是負債**。
> 都是計畫席預先批准的;設計類產出照舊過 STOP gate。idle 的定義是「沒有在推進任何事」,
> 等待回覆時要嘛並行做佇列項,要嘛照送達協定追訊息 —— 兩者都不做才叫 idle。

## 共享資源協定(2026-09-02)

Docker、本機 supabase、dev server 這類**共享資源:開是加法誰都可以,關要經過計畫席** ——
收工時回報「還開著」而不是自行回收(2026-08-31 一席收環境關 Docker,殺了另一席進行中的
DB 驗證)。計畫席決定關不關或轉問還在用的席。

- **「刻意不做」的記錄必須寫出為什麼不做** —— 不寫理由,下一個人會合理地把它當缺失補上
  (#141 的 6.2 是範本)。
- **判斷規則歸屬先問「這條規則是誰決定的?」** —— 答案若是查詢、分組、參數解析或執行環境,
  測試就得跨到那一層,純函式測試從定義上看不到(billing-api 三次同形事故的提煉)。
- `gh pr list --author @me` 列的是**全隊**的 PR(共用同一個 GitHub 帳號)—— 盤點自己的
  PR 要用分支名或標題過濾。

- **兩處對狀態語意不一致時,看確認文案怎麼寫,不看 enum 名字** —— enum 是作者的意圖,確認文案是對
  使用者的承諾,衝突時承諾贏。跨席問狀態語意,問「確認彈窗怎麼寫」比問定義有效。
- **拒絕擴張共用詞彙時要給出替代載體** —— 只說不行,對方會繞過你自己畫一個,而新畫的
  沒有人管。
- **要刪掉一個防禦分支前,先問它是不是留給未來的呼叫端** —— 型別是當下的保證,不是永久的: 別因為呼叫端型別保證非 null 就刪掉 null 分支,
  那個分支是給未來的呼叫端用的。
- **dev server 開之前先確認 port 是不是別人的;被佔就換 port,不要 kill** —— nx 遇 port
  被佔只印一行就放棄起 web 但 API 照起,你會對著別人的 app 下結論(已發生兩次:4200 被
  fvg 佔、8787 被同專案另一席佔)。
- **「放行」不等於「沒人在做」** —— 放行的人不一定知道另一條線的進度;動工前先問計畫席
  有沒有人已經在同一個檔案上(兩線平行做了同一道守衛的重工事故)。
- **大衝突的驗收要兩道方向相反的證明** —— 一道證明「我的都進去了」(自己的識別字齊),
  一道證明「別人的沒被壓掉」(對方的識別字計數與 main 一致)。第一道不涵蓋第二道
  (#215 的 10 檔衝突解法,出處 billing-api)。
- **完成與認領走同一條落檔路** —— 訊息 ≠ 紀錄。這條原本要求計畫席在席位宣告完成後手動更新
  backlog,而那個手動步驟失效了六次(最後一次:ops-warden 讀到十七小時前就已合併的 v1c,
  把剛上任的 teacher-pages 派去重做)。**2026-09-06 起改由機制承擔**:PR 描述寫 `Closes #N`,
  合併時 issue 自己關掉。**要人記得的紀律,在輪替面前一定會輸;能自動關的就不要用記的。**
  **輪替之前違反這條多半沒事(舊 session 記得),輪替之後它是機制性的:每次輪替把
  只存在於訊息裡的東西清空一次**(及格線雙席未遂重工)。計畫席的驗收因此走雙載體:
  SendMessage+PR 留言(紀錄住在它描述的東西上)。
- **寫「等 X 成立」時,X 必須是你下次會撞到的東西,不是一個日期或別人的里程碑。**
  原本這條寫的是「決策要在 X 成立時被回頭檢查」—— 那描述了一個**需要有人主動想起來的動作**,
  所以它自己就是「沒有檢查點的規則」(#460 稽核)。
  **實例(#461)**:harness 的 `api-param-coverage.mjs` 有一筆豁免,移除條件寫著
  「v1b 啟用發布時要把這一筆拿掉」。v1b 已於 2026-09-05 啟用 —— **條件成立了,
  但沒有任何動作會在那一刻讀到那行字**,因為那天沒有人在讀豁免表。
  billing-api 把它改成「**出現一次列出多篇日誌的消費端時**」:
  舊條件掛在**沒有人會經過的時刻**,新條件掛在**你一定會撞到的時刻** ——
  你要做那個消費端,你就在讀這個檔。
  **照自己留的條件被推翻不是錯誤,是設計良好的決策該有的死法**;後記要把「還成立的部分」
  一起留下(dashboard-v1 決策後記,出處 billing-api)。
- **使用者的問題不得用工程理由結案** —— 第一動作是列解方選項(含成本),不是列做不到的
  理由;解方空間含改架構、換供應商/DB 平台,**但架構級解法一律先提案給使用者討論,
  不直接排單動工**(使用者 2026-09-05 訂)。
- **驗證失敗時,先懷疑驗證器** —— 「東西不見了」的第一反應該是查自己的 pattern/基準/視窗,
  三次誤報三次都是檢查本身壞掉(出處 design-web);它與「grep 回空先懷疑 pattern」同族,
  方向相反的孿生是「驗證通過時,問它驗的是不是你以為的那件事」。
- **可機械化的檢查交給腳本,只能被人看見的漂移靠主動巡** —— 兩類問題混用同一種解法,
  兩邊都會做不好(合併守衛腳本 vs 註解漂移的對照,出處 review-steward)。
- **會過期的狀態欄寫成「怎麼查」而不是「是什麼」** —— 在飛清單、PR 狀態這類每小時都在變的
  東西,charter/狀態節裡寫查詢指令(`gh pr list --state open`),不寫快照;快照寫得再勤都是
  記憶的清單(billing-api 三次同型帳面漂移的提煉:有些東西該被查,不該被寫)。

## 計畫席消失時怎麼辦(2026-09-06 訂,夜間無人值守用)

**計畫席不會自己復活。** 它的 session 死掉(額度耗盡、context 滿、機器重開)就是死掉,
**沒有任何東西會把它重新拉起來**。而七席的零 idle 制不依賴它,所以會繼續工作 ——
**於是 PR 會堆積、裁決會卡住,而沒有人告訴使用者發生了什麼。**

**判定計畫席已消失**:你送出一則需要裁決的訊息之後 **超過 60 分鐘沒有任何回覆**,
而 ops-warden 的巡檢也顯示它不在 working。**不要用「我覺得它很久沒回」判定** —— 用時間。

**判定成立後,每一席照這個做:**

1. **繼續做不需要裁決的事。** 佇列裡的、charter 改善清單裡的、自己查出來的缺陷。
   **不要停下來等。**
2. **需要裁決的先做到 STOP gate 前一步就停**,把選項寫成報告貼在 issue 上,
   **不要自己拍板**,也不要找別席代裁 —— **同儕不能授權**。
3. **非保留類的綠 PR 交給 `review-steward`** —— 它本來就有 v2 代合的職責,
   不需要計畫席在場。**保留類(migration / 金額計算路徑 / 授權權限邏輯)一律等使用者。**
4. **每一席在自己 Ctx 到 90% 時主動蒸餾 charter 並開 PR** ——
   沒有計畫席叫你,你得自己盯。**charter 進了 main,下一任才拿得到。**
5. **`review-steward` 額外負責**:把「使用者早上回來會想先看的東西」寫進
   `herdr-team/status-snapshot.md` —— 合了什麼、卡在哪些裁決、有沒有紅燈。
   **那是唯一會被復活的計畫席讀到的檔案。**

**這一節存在的理由**:2026-09-06 使用者要過夜跑,而當時七席都在動、計畫席在裁決迴圈裡,
**沒有任何一條規則說明它斷線之後會發生什麼** —— 那本身就是「條件成立時沒人回頭接」的形狀。

## 席位復活程序(額度耗盡時)

計畫席的自主巡檢 tick 固定包含**席位存活檢查**:`herdr agent read` 看有無
「/low-priority to continue」橫幅或 Session 0% —— 有則等額度回流後 `ctrl+u` 清殘字、
nudge 席位吃佇列(工單都在 SendMessage 佇列不會丟)。計畫席自己死了的話,
下一次成功的 wakeup 會執行全面點名復活;最壞情況 12:00/17:00 使用者任何輸入都會喚醒計畫席。

- **清理自己的 process 用精準 kill**:先 `lsof -ti:<自己的port>` 拿 PID,或 pkill pattern
  必含自己的 worktree 路徑 —— 裸 `pkill -f "workerd serve"` 會殺掉所有席的 API
  (已發生:teacher-pages 誤殺 bundle-analysis 的 8787)。「不 kill 別人的 port」的
  原則同樣適用於 pattern 匹配的入口。

## 交付送達協定(2026-09-03,兩次沉默失敗後制定)

訊息的病:寫在自己 pane 上的字**別人看不到**;打進輸入框沒按 Enter 的字**誰都看不到**。
「我覺得我送了」不算送了 —— msg_id 才算。

1. **交付/請示的最後一個動作必須是 SendMessage 工具呼叫**,並確認回傳 `success:true`
   ＋ msg_id;把 msg_id 寫進自己回合的收尾文字(自證:沒有 msg_id = 沒送)。
2. **15 分鐘無回音 → 重送一次**(訊息開頭標 `RESEND`);再 15 分鐘 → 改用
   `herdr agent prompt` 直接敲計畫席 pane(第二通道)。
3. **等待回覆期間不許沉默 idle**:回合收尾明寫一行
   `WAITING-ON: 計畫席 <等什麼> since <HH:MM> msg_id=<id>`。
4. **計畫席巡檢對帳**:每輪 tick 對 idle/done 的席讀 pane 尾部,見 WAITING-ON 或
   「等你/等批准」字樣就跟自己的收件記錄對帳 —— 對不上即為送達失敗,主動補救。

- **解 `backlog.md` 衝突一律以 main 為基底、只改自己那一行**,解完 diff 對照確認沒動到
  別席的內容(「取我方」曾抹掉別席的認領記錄)。席位佇列已移出該檔,衝突面因此小了很多,
  但技術債與觸發條件段落還在。
- **遷移一個載體時,要同時遷移所有指向它的規則** —— 2026-09-06 工單從 backlog 遷到 issue,
  但本檔的零 idle 制那節還寫著「從 backlog.md 認領」,於是**兩份文件同時活著且說法相反**,
  讀不同檔案的人得到不同答案。這不是誰讀錯了,是遷移只做了一半。
  搬家之後 `grep -rn '<舊載體名>'` 一次,是唯一便宜的收尾。
- **提案經過計畫席會變成命令,所以計畫席那一關本來就是驗證關,不是轉發關。**
  2026-09-06:design-web 的家長端 mockup 明寫「提案不是規格」,計畫席把它的「出席/遲到/
  請假/缺席四態」原封不動寫進工單並冠上「裁定」二字。**`attendance_status` 這個 enum
  從來只有三態**,前端註解早就寫著「畫面不該有它的位置」。同一份工單還寫著
  「確認是空殼還是有內容」—— 等於**明知自己沒查證,還是用命令的語氣發了出去**,
  把查證缺口當成可以外包給下游的待辦。提案的語氣是「我認為」,裁定的語氣是「就這樣做」;
  **升級語氣的那個人要為升級後的確定性負責**。
- **推上去 ≠ 交接完成;沒有 PR 的分支等於沒寫。** 兩天內兩次:billing-api 的 charter 蒸餾、
  design-web-2 的 76 行交接,都只活在已推的分支上,`git pull` 之後在 main 讀不到。
  輪替時知識沒消失純屬僥倖 —— **它只是找不到,而找不到的知識跟不存在沒有差別**。
  輪替前的檢查是 `gh pr list --state open --search <席名>`,不是 `git log` 看有沒有 commit。
- **收到一條裁定時,先問它的依據是觀察還是類比。** teacher-pages 2026-09-06 提出,
  比計畫席自己的說法準:計畫席那條講的是傳遞過程(「提案的不確定性在轉手時消失」),
  這條直接給接收方一個可執行的檢查。當天計畫席出錯的三次**全部是類比**——
  四態(類比 mockup 的想像)、三頁已完成(沒查)、單孩子切換器(類比角色徽章先例)。
  **而類比失效的地方通常不在被類比的那件事上,在它沒有兼任的那個職責上**:
  角色徽章不兼任「告訴你在看誰」,孩子徽章兼任了;`conflict-modal` 的遮罩不兼任任何東西
  所以可以整段刪掉,切換器不行。**類比只搬移一個職責,而被類比的東西通常有兩個。**
- **規則要寫在它守護的東西旁邊,離得越遠越沒有約束力。** #445:裁定講「單孩子時渲染成
  靜態徽章」,而下一個人是**照著上一版裁定去刪那個分支**的——他會先看到測試,
  不會先看到 charter。所以理由寫進那支測試的正上方,不是寫進 charter。
  同一條的另一面就是當天早上的載體事故:規則(「從 backlog 認領」)離它的執行點太遠,
  載體換了而規則沒跟著換。
- **在你控制不了的時序上不要疊東西。** 一支已經綠、正在等驗收的 PR,合併時機在計畫席手上;
  往它的分支再推 commit,合併後那些 commit 會擱淺在已合併分支上(#105 的形狀)。
  新東西另開一支,即使內容相關。
- **一段正確的理由掛在一個不存在的前提上,比錯的理由更難被發現。** 2026-09-06 有三支
  幻影工單(v1c、家長端三頁、#450 儀表板 handoff)**全都帶著一段站得住腳的推導** ——
  那正是它們能通過檢查的原因。#450 的順序約束(「儀表板與課堂管理頁必須用同一支已結束
  判定,否則卡片說 15、落地頁含今天還沒到點名時間的課」)每一句都經得起檢查,
  而它要保護的那件事早在十七小時前就發生了。
  **錯的理由會被駁回,對的理由只會被相信** —— 唯一擋得住的是去查前提,
  而**推導寫得越好,越沒有人想去查它**。所以查前提要當成無條件動作,不是「覺得可疑才查」。
  發現者:teacher-pages。
- **`Closes #N` 有一類例外:跨多片的 issue。** 前幾片不能關它(還沒做完),
  所以它們用 `Refs #N`,而那支 issue 就退回人工關閉 —— **正是那個失效過六次的人工步驟**。
  處置是**驗收時順手關**,不另立「最後一片要記得換成 Closes」的規則:那條一樣要人記得,
  而計畫席本來就在驗收。**把責任放在已經會發生的動作上,不要新增一個要記得的動作。**
- **上面兩條是同一條的兩個面,teacher-pages 2026-09-06 綜合**:「規則寫在它守護的東西旁邊」
  講的是**空間**上要靠近,「把責任掛在已經會發生的動作上」講的是**時間**上要掛在
  必然發生的事件上。兩者解的是同一個問題 —— **需要人主動想起來的規則,
  在輪替面前一定會輸。** 所以設計一條規則時要問的不是「這條夠不夠清楚」,
  是「它會在誰的什麼動作裡被讀到」;答案若是「他得先想起來去讀它」,那條規則等於沒有。
- **載體框架的已知缺口:「它會在誰的什麼動作裡被讀到」解決的是「有沒有被看到」,
  不解決「看到了有沒有照做」。** teacher-pages 2026-09-06 親身證明:
  doc-router 每一則 prompt 都在提醒它「動工前先查它還沒被做掉」,
- **開工前查一次,擋得住「已經在飛的」,擋不住「正在同時開始的」。**
  api-2 2026-09-07:它動工前**有**照規矩跑 `gh pr list --state open`,**當時那支 PR 還不存在** ——
  它是在做的過程中被另一席開的。兩席各自完整做完同一件事(實測、測試、端到端驗證),
  **而兩邊的開工前檢查都是乾淨的。**
  **這一族只有派工端擋得住**(單一來源、開單前查對方佇列);
  席位端能做的只有一件:**動工前在 issue 上留言認領**。
  **處置**:照「**誰先開 PR**」切,後者整支撤掉、不開競爭 PR,
  **但要比對一次有沒有獨有的正確性** —— 2026-09-07 那次撤掉的那份確實有一項獨有的測試。
  **計畫席那次還多錯一層**:它從 `git ls-remote` 沒有分支推論「對方還沒動工」,
  **而對方已經推過然後刪掉了** —— 又一次用「不存在」推論現況。
- **一個假設可以「現象對、機制錯」,而寫成結論會把修法導向錯的地方。**
  infra 2026-09-07:它在報告裡寫「並行下兩支都插、只有一支認領到 → 孤兒」,
  **並標明那是假設不是結論**。實測證明**競態被 CAS 守住了**,
  孤兒**全部**來自失敗的請求(孤兒數 = 失敗數 × 該日課堂數,逐格吻合)。
  **現象存在(有孤兒)、機制錯(不是競態)** —— **如果當初把它寫成結論,
  下一個人會去修競態,然後孤兒照樣長出來**,而且他會以為修好了。
  檢查點:**你正要把一個「為什麼會這樣」寫進報告的那一刻** ——
  問「我量到的是現象還是機制」,量到現象就標成假設。
- **「schema 存在」不蘊含「schema 會生效」。宣告可能只是文件、只是型別、只是給工具讀的。**
  **計畫席 2026-09-07 犯的,而且是它自己加上去的那一句。** admin-pages 的原文只寫
  「`SessionHistoryTypeSchema` 缺 `makeup`」;**把它升級成「回應驗證可能整個失敗 →
  整支端點 500」的是計畫席**,並據此把它排成 issue #605 的第一項。
  **一次都沒查過這個框架驗不驗 response。**
  billing-api 動手前實測(真 route + 回 `change_type: 'makeup'` 的替身):
  **`200`,而且那個值原樣送出去** —— `@hono/zod-openapi` **只驗 request,不驗 response**。
  **優先序因此完全相反**:真正會 400 的是排在最後、被標成「解除 web 一個限制」的
  查詢 schema(那是 request 側)。
  **分辨方法只有一個:跑一次。** 打一個違反那個宣告的請求或回應,看它擋不擋。
  檢查點:**你正要從一個宣告推論它在執行期會做某件事的那一刻。**
  (旁證比那一次實測更強:`SessionListItemSchema` 從來沒宣告過 `attendanceTakenAt`
  那五個欄位,而 `mapSession` 一直在回、web 一直在用,**沒有任何東西吵過**。)
  **這條跟下一條是同一天的兩個實例**:那條是把推論跟量測寫在同一句,
  這條是**把一個宣告的存在讀成它的效力** —— 而兩次放大它的都是轉述的那個人。
  **證據等級不會跟著轉述走,而轉述者是唯一能重新標記它的人。** admin-pages 在工單裡
  明寫「四筆都是我開檔確認的,不是推論」——**那句話當時為真、標記也正確**,
  然後計畫席在轉述時加了一句推論,**於是下游讀到的是一個沒有等級標記的斷言**。
  這是「提案經過計畫席會變成命令」的下一層:那條講的是**語氣**會升級(我認為 → 就這樣做),
  這條講的是**證據等級會消失** —— 而它比語氣更難察覺,因為升級後的句子讀起來
  跟一個查證過的事實一模一樣。**缺的不是規則是執行**,所以這裡只記形狀:
  **你正在轉述別人的發現時,原文的等級標記不會自己跟過來,你得重新標一次。**
- **量到的那一半與推出來的那一半寫在同一句話裡,讀的人分不出哪一半驗過。**
  billing-api 2026-09-07,一天三次跨席命中,**三個載體互不相干**:
  ①它跑出 orphan gate `count = 0`(**量的**)然後推論「所以新增任何端點都會變成第 1 筆」
  (**推的**),兩者一起寫進 charter **並據此向計畫席要了兩次裁示** ——
  實際上 gate 只抓「另起頂層前綴的帶參數 GET」,三條路解的是一個不存在的問題;
  ②`git status` 顯示一個沒碰過的檔案被刪了 8 行(**真的**),它給的成因
  「`add -A` 掃進舊檔」(**推的**)是錯的,真因是 `reset --soft` 到已經前進的 `origin/main`;

  **只看 `count === 0` 驗到的是「這個函式有沒有提早 return」,不是「它會不會抓到東西」。**
  **量到的與推的要分開寫** —— 在同一段文字裡它們讀起來一模一樣,
  **而下一個人會把整段當成量到的**。
- **一個局部為真的假設被寫成全域前提 —— 而寫下它的動作本身讓它更可信。**
  infra 2026-09-06:A17 觸控 gate 的檔頭寫著「PrimeNG 元件不在掃描範圍,
  它們由全域 coarse token 統一負責」。**那句話讓讀的人合理地相信「有別人在看」** ——
  而實際上 `min-height: 44px` **只掛在 `.clessia-filter-bar` 底下**,
  其餘位置的 `p-button` 只拿到加大的內距,高度由字級決定(實測 34px)。
  **那個別人只看了一小塊。**
  這比「gate 沒寫理由」危險:**沒有理由的豁免會被質疑,有理由的豁免不會** ——
  而理由的適用範圍沒有人會回頭量。
  **為什麼理由會過期而沒人發現 —— infra 2026-09-07 對照出機制:豁免表分兩種。**

  | 豁免表                                                  | 理由過期時                                                                                                      |
  | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
  | **可否證的**(`TOUCH_TARGET_EXEMPT` / `CONTRAST_EXEMPT`) | **gate 紅** —— `check-harness.mjs:884-890` 明著寫「豁免必須是可否證的:**對不上任何實際違規時就是謊,不是保險**」 |
  | **不可否證的**(`api-param-coverage` 的 `EXEMPT`)        | **什麼都不會發生** —— 全部用法就是一行 `if (EXEMPT.has(key)) continue;`                                         |

  **同一個 repo、兩張表,而三次「理由過期沒人發現」全部出自不可否證的那一張。**
  **不是誰不細心:可否證的那張沒有機會過期太久,因為它會自己叫。**
  **所以寫一張豁免表時,先決定它過期的時候會不會有人知道** ——
  「豁免了什麼」要能對回「實際存在的違規」,對不上就該紅。
  檢查點:**你正要寫下「這一塊由 X 負責所以我不看」的那一刻** ——
  去確認 X 負責的範圍**逐字**涵蓋你要跳過的範圍,不要用「應該有」。

- **要求證據的規格,比要求結論正確的規格有用。** billing-api 2026-09-06 從 #481 提煉:
  那支工單如果照它自己的(錯誤)前提填完,會是一份**可以直接拿去給使用者裁決**的產出 ——
  格式正確、事實附 `path:line`、選項齊全。**它通不過的唯一檢查是「去把那個畫面找出來」,
  而那一步不在任何流程裡。**
  **產出的品質檢查(格式、證據、完整性)全部會通過,因為它們檢查的是產出本身,
  不是產出的前提。**
  破綻是被工單第 1 項「逐一查證附 `path:line`」逼出來的 ——
  **那條要求不只是提高品質,它是唯一會撞到前提的那一步**。
  檢查點:**寫工單的時候**。與其寫「結論要正確」,不如寫「這一項要附什麼證據」。
- **引用一條理由之前回去看出處;「大家都這樣寫」在這裡是反指標。**
  四份一致的抄本比一份原文更容易讓人放心,**而它們可能全部來自同一次漂移**
  (#486:同一個宣稱有五份抄本,原文說的是機制,五份說的是畫面,而那個畫面不存在)。
  可操作的第二步:**理由若宣稱一個「使用者看得到的後果」,去把那個畫面找出來** ——
  找不到就是漂過了。**機制型的理由不需要畫面支撐,後果型的需要,
  而後果型的比較好講,所以它會贏。**
- **待辦清單記的是「我當時看到的缺口」,而缺口會被別人填掉。** billing-api 2026-09-06:
  它的 charter 改善清單九項,逐項查證後**五項已經不成立** —— gate 是 infra 補的、
  verify 序列是 infra 改的、`waitUntilFrom` 是別人抽的。**每一項都是「別人順手做掉
  也不會來通知你」的東西。**
  跟「狀態不要寫進 charter」是同一條的兩半:**數字會被別人改掉,缺口會被別人填掉,
  而兩者在清單上都長得跟還沒發生一樣。**
  處置:清單的第一條使用規則是「**動手前先驗它,不要先信它**」,並且**表格化** ——
  每一項旁邊放驗證結果與日期,下一個人一眼看得出哪些是查過的。
- **一個函式如果把「現在幾點」當參數收,那它就沒有在守時區;守時區的是它的呼叫端。**
  **檢查點在餵值的地方,不在用值的地方**(billing-api 從 #467 提煉)。
  最毒的部分:`payments.util.ts` 那段用心寫的「為什麼不能轉 Date」註解
  **本身變成了假的安全訊號** —— 下一個人看到「這裡處理過時區了」就跳過去,
  而檔案裡確實處理對了,錯的是餵進來的那個值。
  **寫得越用心的防禦註解,越容易讓人不去看呼叫端。**
  同族判準:問「**錯的寫法還寫不寫得出來**」——可以呼叫的 helper 就是可以忘記呼叫的 helper。
- **沒有檢查點的通則會退化成「大家都同意的正確廢話」。** billing-api 2026-09-06 提出的
  分辨訊號:**這條規則有沒有指定檢查點?**

  | 通則                                   | 檢查點                                        |
  | -------------------------------------- | --------------------------------------------- |
  | 函式把「現在幾點」當參數收就沒在守時區 | **有** —— 餵值的地方                          |
  | gate 寫完一定要塞陷阱看它會不會紅      | **有** —— 寫完 gate 的當下                    |
  | charter 會腐化,接手時先驗一遍再信它    | **有** —— 接手時                              |
  | 規則寫在它守護的東西旁邊               | **沒有** —— 它描述的是一個好狀態,不是一個動作 |

  沒有檢查點的那些,讀的人會點頭,然後照原本的方式做事 ——
  **而且因為他同意了,他會覺得自己已經照做了**。
  這正是「用心寫的防禦註解變成假的安全訊號」在規則層的版本。
  處置:**不是刪,是改寫成有動作的版本,或把「背景知識」與「操作規則」分開放** ——
  二十幾條混在一起時,讀的人分不出哪些是要照做的。
  **再收一格(teacher-pages 2026-09-06)**:有檢查點還不夠,**檢查點必須在你還沒有
  這個洞見的時候就認得出來**。否則它是循環的 —— 要先懂那條規則,才知道現在該讀那條規則。
  用這個篩子重跑一次,原本被判定「本質上掛不住」的十一條裡有**九條其實是 C1**
  (只是寫成了狀態的樣子),真正掛不住的只有兩條:
  「壞掉的樣子跟正常的樣子一模一樣」(**它的定義就是「沒有訊號」**,任何
  「在 X 時刻檢查」的改寫都會落空,因為 X 不會通知你 —— 它是元判準,
  底下每個成員各自才有檢查點)與「在兩個錯誤之間選會被發現的那個」
  (**設計價值不是偵測規則**;硬要說檢查點就是「每一次取捨」,而
  **涵蓋一切的檢查點等於沒有檢查點**)。

- **PR 送驗收/合併前,先 rebase 到最新 origin/main 再看一次燈** —— 合併速率高的日子,
  「出 PR 當下綠」與「輪到合併時綠」是兩件事;紅在別席剛合進去的 gate 上時,
  純 rebase 即綠,不要對著不是自己的檔案發呆(#217/#221 案例)。
- **結論有保鮮期,重送結論要重驗** —— 訊息會隨 session 消失所以重送是對的反射,但重送的
  是**結論**。`grep` 的零命中保鮮期最短:它證明的是「某個時間點的不存在」
  (billing-api 重送 session-packs「全站零命中」,而 #348 早已把前端接上;
  同族還有:把 SKIPPED 當紅燈得出「五支 PR 全紅」、憑印象說自己的 PR 是 OPEN 而它已 MERGED、
  查線上 bundle 沒想到 minify 會改掉識別字)。**一個當時正確的結論,跟一個現在正確的結論,
  在訊息裡長得一模一樣** —— 又一個「壞掉的樣子跟正常的樣子一模一樣」。重送時帶量測時間,
  或乾脆重跑那條查詢(通常只要三秒)。
- **席位到 95% 用量就落檔,不要等症狀** —— 症狀是工具輸出自我矛盾,而**症狀出現時你已經
  不能用自己的輸出確認自己的狀態了**(計畫席 clessia-c8 輪替事件)。判斷點只能是用量,
  不能是「我覺得還好」。**半份落了檔的工作 > 一份只存在於 context 裡的完整工作** ——
  後者在輪替瞬間歸零,且下一個人不知道你做過哪些、得從頭再來。
- **收到上游遞來的結論時,先跑一次它引用的那條指令** —— 診斷本身也可能是症狀: 一份讀起來像病因的報告,可能只是**另一個工具的盲區的產物**。
  出處:計畫席跑 `grep courses__badge **/*.scss` 得零筆,據此背書「全庫零 CSS」,
  還拿去當一道新 gate 的立案理由 —— 實際上 BEM 寫成 `&__badge`,**那個字串在 SCSS
  原始碼裡根本不存在**,天真字面 grep 對本 repo 幾乎所有 BEM class 都回零筆
  (infra 讀原始碼才攔下,差一步就用假前提立了真規則)。
  **與「驗證失敗時先懷疑驗證器」的差別**:那條講的是**自己的**驗證器;這條講的是
  **上游遞給你的結論** —— 而上游是計畫席時它更容易被直接採信。**計畫席說「我驗過」
  不構成證據,證據是那條指令本身**(出處 infra,2026-09-05)。
- **「我被 X 擋住了」也是一個要驗的結論,而且它比別種結論更少被驗。**
  上面那條講的是別人遞給你的**發現**;這條講的是別人遞給你的**阻塞**。
  兩者差在動機:回報阻塞的人**已經繞過它了**(他升級了),所以沒有任何東西促使他再查一次;
  而阻塞會停掉下游所有人的工作,還會佔掉一次裁決。
  出處:2026-09-06 billing-api 回報「可補清單端點卡在零 baseline 的 orphan gate ——
  端點先落地就是第一筆 orphan」,並送了三條路(豁免/等 UI 一起進 main/自己加 service 方法)
  請計畫席裁。design-web 去讀那支 gate,**兩個獨立的理由都讓它不成立**:
  `servicePrefixes()` 只抓一段(`/api/<name>`),而 `sessions.service.ts` 已經宣告
  `/api/sessions` → **底下所有路徑都算已認領**;而且 `collectApiParams` 是
  `if (p.length > 0) out[path] = p`,**零 query 參數的路徑根本進不了那張表**。
  **三條路一條都不需要,那次裁決不必發生。**
  驗的時候照樣要塞陷阱:餵一個 `/api/totally-unrelated-thing` 進去確認它**真的**被判 orphan,
  否則「沒有 orphan」跟「函式提早 return」在輸出上一模一樣。
  **檢查點:你收到「我被 X 擋住了」的那一刻,以及你正要為別人回報的阻塞裁決的那一刻。**
- **精確的訊息在急著解阻塞的時候會被讀成通則 —— 而被丟掉的永遠是那個限定詞。**
  同一件事的第二層:那支 gate 的訊息**是準的** ——
  `check-harness.mjs:1639` 寫的是「N 個**帶 query 參數的**端點沒有任何 service 認領」,
  而它被讀成了「每一支 API 端點都必須被認領」。**沒有人寫錯,是限定詞在轉述中掉了。**
  這跟「四份一致的抄本比一份原文更容易讓人放心」同族,但方向相反:
  那條是**抄本漂移**,這條是**原文正確而讀的人自己放寬了它**。
  推論:**寫 gate 訊息時,把限定詞放在句子最前面**——「帶 query 參數的端點中,有 N 個…」
  比「N 個帶 query 參數的端點…」難掉。
- **清不完的 ratchet 等於裝飾** —— baseline 大到沒人會去清時,它會長期發出「有債」的
  訊號但那個訊號永遠不變,於是沒有人再看它。**一個沒人清的 baseline 和一個清乾淨的,
  CI 輸出上都是綠的**(「壞掉的樣子跟正常的樣子一模一樣」的又一個成員)。
  嚴重度差太多的孤兒清單適合當一次性交付,不適合當常設 gate;
  要立 gate 就挑**零 baseline 的窄訊號** —— 立法時零違規是最便宜的立法時機(出處 infra)。
- **grep 回零筆時,先問「這個字串在這個載體裡真的會長這樣嗎?」** ——

  比較寬鬆的那個(admin-pages 收下後補的操作方式,2026-09-05)。
- **同一項工作對兩席都說過「你想接就說一聲」= 重複派工,製造重工的是放行的人本人** ——
  「放行不等於沒人在做」那條原本是講席位之間,但**計畫席自己最容易犯**:
  它同時在跟多席對話,而每一則訊息裡的「你想接就說」在對方看來都是唯一的邀請。
  發生時**用「誰先回報動工」切,不看誰比較適配** —— 平手案例上快速止血比正確分派重要
  (2026-09-05 M2 雙認領)。
- **查不到回報者說的那個機制時,回去問現象,不要宣告他錯了** —— 「現象是真的」與「我對現象的解釋是真的」是兩件事,可以一真一假:
  回報者看到的通常是真的;他對成因的推論常常不是。**否定成因不等於否定現象。**
  出處:tester 報「學生列表關聯家長排序空值排前面」,admin-pages 查證「純姓名排序、
  跟關聯家長無關」——**兩邊都對**。真因是 12 個 seed 學生都叫「出勤測試學生NN」,
  「出」(51FA) 排在所有真實姓氏之前,而那 12 個剛好全部沒有關聯家長 ——
  **視覺結果跟「空值排前面」一模一樣,機制是巧合**。
  照原本的建議去改排序邏輯是**修一個不存在的問題,而且改完現象還在**(根因是資料)。
  收到「我查不到那個機制」時,正確的下一步是**回去問現象**,不是宣告回報者錯了。
- **接線一條既有路徑時,先問「這條路徑原本從哪裡走」** ——
  同一個對話框可能有多個開啟點,而它們傳的參數不同 = 能力不同。
  出處:#364 給學生頁接上「新增學生」(正確,那條路本來就寫好只是沒入口),
  但家長頁的既有入口帶 `parentId`、新的不帶,表單又沒有選擇器 ——
  **同一個對話框、兩條建立路徑、能力不同,而使用者看不出差別**,
  從學生頁建的學生必然是孤兒。接線前 grep 一次「還有誰開這個對話框」。
- **「宣告的語意」與「渲染的結果」是兩件事,程式碼只證明前者** ——
  查證 UI 回報時,**成因與現象要分開回報**:查到程式碼語意正確,不等於視覺結果正確。
  2026-09-05 一天兩個實例:
  - `severity="info"` 從第一個 commit 就是 info(成因對),但 `--accent-600 #a8340f`
    配 `--accent-100 #ffdcce` 跟 `--error-700 #b91c1c` 配 `--error-100 #fee2e2`
    **同屬深紅配淡粉**,使用者看到的就是錯誤樣式
  - `z-index` / `background` 都設對了(成因對),但 sticky 表頭下緣沒有遮罩,
    **上一列仍然被攔腰切一半**
    查到「程式碼是對的」時,正確的下一步不是「所以現象不成立」,
    而是「**那為什麼它看起來是壞的?**」—— 那個問題會把你帶到真正的載體
    (出處 admin-pages 自我歸納,2026-09-05)。
- **寫了「因為 X 所以這樣做」的決策,在 X 不再成立時也要被回頭檢查** ——
  這是「等 X 成立再說的決策要在 X 成立時被檢查」的鏡像,而且更難發現:
  前者有人在等,後者沒有。
  出處:`inline-notice.component.scss:29` 註解寫「info 是 accent 語意,所以走 token ——
  換色系時要跟著走」。**那在 accent 是天藍色時完全正確**,但色系換成橘紅之後,
  info 跟著 accent 走進了 error 的鄰居家。**註解把前提寫出來了,所以它是可檢查的
  —— 只是沒人檢查。**
  (AGENTS.md 至今仍寫「Accent sky blue」,是同一個漂移的另一個面。)
- **判定「不算缺口」時,要指出它跟哪個既有模式同族** —— 一致性工作最大的風險不是漏改幾頁,是把有意義的差異抹平:
  抹平之後那個理由就永遠消失了,因為**沒有人會為「我們曾經刻意不一樣」寫紀錄**。
  判定「不算缺口」時要指出**它跟哪個既有模式同族**,不是只說「我覺得可以」。
  範例(admin-pages 未被提醒就自行做到):`fee-templates` 兩顆「新增」是兩個獨立實體
  各自的 section 層級動作,同 `courses.page.html` 每個課程群組底下的「新增班」;
  `courses`/`exams` 的 popover 篩選是篩選維度太多的漸進式揭露,不是沒跟上共用 class。
- **狀態描述聽起來像預測,實際上是條件句 —— 而條件句沒有執行者** ——
  「rebase 後會綠」在文法上不需要主詞,所以寫的人不會注意到自己沒指派執行者;
  它真正的意思是「**如果有人 rebase**,就會綠」,而省略的那半正好是唯一需要有人動手的那半。
  這是「等 X 成立的決策要在 X 成立時被回頭檢查」的語法版本,而且更難自覺:
  前者是忘了回頭看,後者是**根本沒意識到自己描述的是條件不是結果**。
  **回報狀態時,把「誰在什麼時候做」一起寫出來**(出處 review-steward,2026-09-06)。
- **紅燈的歸屬要先查清楚再決定通知誰 —— 掃到紅燈不等於要派工** ——
  2026-09-06 板上八支全紅,逐支比對後確認全部繼承自 main 的同一條失敗
  (#397 只動一個 `.md` 卻紅在 api 測試上,是最明確的證據)。
  **當下不通知是對的**(動作在 billing-api 手上,通知只會製造八份「我沒問題啊」);
  **main 修好之後通知是對的**(動作變成在他們手上,因為 GitHub 不會因 main 更新而自動重跑)。
  **差別不在紅的性質,在有沒有他們能做的事。**
  通知時挑**兩支當驗證樣本**先做 —— 診斷若錯,是兩個人白做工不是八個。
- **「新開的 PR 也紅」與「main 根本沒好」在 PR 列表上長得一模一樣** ——
  分開它們的是時間戳:`gh api repos/../actions/runs/<id> --jq .run_started_at` 對照
  修正 PR 的 `mergedAt`。2026-09-06 那次差 **81 秒** ——
  最新開的 PR 其 CI 比修正合併早 81 秒開跑,所以跑的是沒有修正的 base。
  **本地綠不蘊含 CI 綠**(「PR 綠不蘊含 main 綠」的鄰居),兩邊都要驗。
- **不要用 `gh pr merge --delete-branch`** —— 它把「合」跟「刪」綁成不可分的一步,
  而疊 PR 的正確順序要求它們之間插一步(把上層 base 轉成 main)。
  base 分支一消失,GitHub **自動關閉上層 PR 而且不給重開**(留言、review 歷史全沒)。
  **計畫席 2026-09-06 一個晚上犯兩次**:第一次關掉 #376/#378/#384,
  第二次在寫下「合併前先掃 base 不是 main 的」這句指示之後、用一個 `for` 迴圈跳過了它,
  又關掉重開的 #408。
  **改流程而不是改決心**:分支留著的成本是幾個過期 ref(可統一清),
  `--delete-branch` 的成本是靜默關掉別人的 PR。**兩者不對等。**
  這是「移除碰撞源優於增加檢查」—— 要求「記得先掃」是增加人為檢查,
  **而人為檢查在批次操作時會被跳過**(迴圈本身讓人覺得每一支都一樣)。
- **匯總表是用來排序的,不是用來代替驗證的** —— 給別人的掃描表要標明它是怎麼產生的,
  而收表的人仍然要逐支驗。出處:review-steward 的 base 掃描腳本把
  `git fetch` 失敗時的靜默失敗餵給 `git merge-base`,**而 `FETCH_HEAD` 停在上一輪的值**,
  四支被標成「缺 402」而實際都含。計畫席逐支 `is-ancestor` 驗過才收,擋掉了那份假資訊。
  **殘留值比空值陰險:空值至少是空的,殘留值長得像有效資料**,
  所以判斷式永遠會給出一個答案 —— 只是可能是上一輪的答案(steward 自己逮到)。
- **測試不能用被測程式碼自己的算法當裁判** —— 那不是測試,是**兩個地方犯同一個錯然後互相確認**。
  綠燈證明的只有「它們一致」,不是「它們對」。
  出處:`enrollments.spec.ts` 斷言 `effectiveFrom === new Date().toISOString().slice(0,10)` ——
  **跟程式碼同一個 UTC 算法**。程式碼算錯一天、斷言也算錯一天,兩邊永遠相等。
  **更尖的後果**:修對之後那條測試在台北凌晨反而會紅(程式碼對、斷言錯)——
  **一個把正確實作判為失敗的測試**,會讓下一個人以為自己改壞了然後把修正回滾掉。
  **判準**:斷言的期望值是**獨立算出來的**,還是**用被測的那條路徑算出來的**?
  後者的話,那條測試從第一天就沒有辨識力。
- **「沒有人在那個條件下觀察」和「觀測工具本身就壞掉」是兩層,疊起來 bug 永遠不產生訊號** ——
  時區那批 bug 活這麼久有兩個原因:**沒有人在台北凌晨跑 CI**(觀測窗口不涵蓋出錯條件),
  **而且既有測試用同一個錯誤算法當標準答案**(觀測工具本身壞掉)。
  只修第一層(在凌晨跑 CI)不會抓到它,因為第二層會同意那個 bug。
  查一族 bug 為什麼活這麼久時,**兩層都要問**(出處 billing-api,2026-09-06)。
- **自動化會把風險趕到沒被自動化的那一半,而那一半看起來最安全** ——
  因為它出錯的次數少,而次數少是「沒人在那裡量」的結果不是「那裡沒問題」的結果。
  出處:review-steward 的 `steward-merge.sh` 守的全是「**收**別人的 PR」
  (state / CI / mergeable / 鎖 SHA / 確認 MERGED 才刪 / backlog 不在 diff),
  而「**推自己的 PR**」那條路徑一道守衛都沒有 —— 2026-09-06 一晚在那條路徑上犯兩次
  (commit 擱淺在已合併分支、`git diff` 兩點三點的假警報),兩次都靠「剛好多查了一次」逮到。
  **機械化一條路徑之後,要回頭問「它的反方向是誰在守」。**
- **一份資料只在它自己的維度上正確** —— 問「**我查的這個欄位,回答的是不是我要問的那個問題?**」
  出處:steward 用 `headRefOid`(回答「這支跑在什麼 base 上」)的驗證結果,
  去回答「這支 PR 還開不開著」(該問 `state`)。兩者都對,而且可以同時成立或不成立。
  **這種錯特別容易在「剛修好一個 bug 之後」發生** —— 修完之後那份資料的可信度上升了,
  而可信度是對「它說的那件事」而言,不是對「你拿它來說的那件事」。
- **`git diff origin/main..HEAD` 要寫三個點** —— 兩點是雙向差異,把 main 領先你的 commit
  顯示成你「刪掉」了它們;三點才是「只有這支做了什麼」。
  實測:同一支只改一個檔的分支,兩點顯示 `104 files, 3437 deletions`、三點顯示 `1 file, 42 insertions`。
  **分支落後 main 越多假警報越大,而落後很多正是最需要這道警報的時候** ——
  它的失效方向是「叫得太大聲」,所以人會學會忽略它,**忽略之後真正的污染就進得來了**。
  (計畫席原本寫進 charter 的「解完看 `git diff origin/main --stat`」沒指定幾個點 ——
  **指令寫錯的規則比沒有規則糟,因為它會消耗掉人對那道檢查的信任**。)

## 判準（不是規則：沒有動作能承載）

> **這兩條跟上面所有的通則不同：它們沒有檢查點,而且不是寫法的問題。**
>
> 上面的通則多數能指出「在什麼時刻讀到它」——grep 回零筆時、預期會紅的沒紅時、
> 收到裁定時。**下面這兩條指不出來**,而且原因各不相同:
>
> - **「壞掉的樣子跟正常的樣子一模一樣」**:它的定義就是**沒有訊號**。
>   任何「在 X 時刻檢查」的改寫都會落空,因為 X 不會通知你。
>   它是**元判準**,底下每個成員(零命中、空值當終態、替身太寬容…)各自才有檢查點。
> - **「在兩個錯誤之間選會被發現的那個」**:它是**設計價值不是偵測規則**。
>   硬要說檢查點就是「每一次取捨」,而**涵蓋一切的檢查點等於沒有檢查點**。
>
> - **「工具做了它該做的事,而那個正確答案剛好跟我的錯誤前提相容」**:
>   出處 review-steward 逼出的真機制(2026-09-06,`gh pr checks <N>` 那件) ——
>   它回答的是**那支 PR 的 head**,PR 合併後 head 就凍結,而分支繼續往前走。
>   **指令忠實地回答了它被問到的問題,答案也是對的,錯的是提問者的前提。**
>   這一族比「工具靜默地不做你以為它在做的事」更難防:那一族會給出**跟現實不符**的
>   結果(零命中、空輸出),至少有機會覺得不對勁;**這一族的輸出跟現實完全相符,
>   只是那個現實不是你以為的那個 —— 沒有任何不一致會讓人停下來。**
>   沒有檢查點,因為**沒有任何時刻會顯得可疑**。
>
> **掛不住不是缺點,是本質。** 2026-09-06 一天內認出八種
> 「工具靜默地不做你以為它在做的事」,**沒有一種是靠規則抓到的,全部是靠判準**。
>
> 分開放的理由是**強制力**:混在規則裡時,讀的人發現清單裡有幾條沒法照做,
> 就會把整份讀成「參考」。**規則要能照做,判準要能記住 —— 混在一起兩邊都會輸。**
>
> (出處:#460 載體稽核。**一條也沒有刪**,每一條背後都有一次真實事故。)

**邊界(api-2 2026-09-07,踩第二次時定出來的)**:
**三個點解掉的是「main 領先我的 commit 被顯示成刪除」那種假警報;
它解不掉「我的分支帶著已經被 squash 進 main 的 commit」** ——
後者三個點會顯示成「整個檔案都是我加的」(因為基準在那次合併之前),
**而那不是假警報,是它在回答另一個問題**(相對於分岔點,而你要問的是相對於現在的 main)。
**後者要靠讀 commit 清單,不是靠 diff 的點數。**
**前置動作也記一下**:兩次踩到的共同起點都是**在一支已經被 squash 合掉的分支上繼續 commit**。
**PR 合掉之後要繼續改同一個檔案,一律從 `origin/main` 重開分支,不要在原分支上接** ——
原分支從合併那一刻起就帶著一顆會炸的 commit。

- **在兩個錯誤之間選擇時,選會被發現的那個** —— 看得見的錯誤會被修,沉默的錯誤永遠是真的
  (#169 的請假誤判取捨,出處 admin-pages)。

- **「壞掉的樣子跟正常的樣子一模一樣」是同一族病** —— 沒標範圍的 0、空值當終態、
  被撿回來的 +、範圍靜靜縮小、寫死尺寸的 fallback…全是「失敗不產生訊號」。解法也同一個:
  **讓失敗產生訊號**(ratchet、反例探針、把審查寫成測試)。看到「它壞了我們會知道嗎?」
  答不出來的地方,就是這族的下一個案發現場。**每個成員長得不一樣,認得前一個不代表
  認得下一個** —— 只能一條一條累積,沒有記住一個原則就免疫這回事(steward 歸納,infra 提請)。
