## 二、怎麼審（今天一天磨出來的做法）

1. **開工就確認 PR 還 open**（#1865 讀完才發現已被計畫席關掉）。
2. **一律在「最新 main＋PR head」的 detached HEAD 上跑**，不只看 `merge-tree` 和 PR 的 CI。#1884：merge-tree 0 衝突、CI 綠，但兩支 PR 各加一次 `hideLabel`，合起來 TS2300。CI 綠可能是「上游合併前的 main」的綠。
3. **突變只在暫存 worktree 跑**（`git worktree add --detach <scratchpad>/wtN origin/main`，`node_modules` 兩層 symlink 到本席 worktree）。席位 worktree 會被 Stop hook 跑 harness／typecheck／affected test，撞上進行中的突變就假紅（今天三次）。
4. **先跑基準、看到 `Tests N passed` 才算數**。`mrun.sh`（`mut.py` 斷言 old 字串唯一→改→跑→`git checkout -- file`）的輸出沒有 `Tests` 那行就是沒套上或編譯錯，不是綠。常見：縮排不同（`APPLY FAIL`）、型別收窄失敗（`@if (true)` 配 `as x`、`if (false as boolean)` 之外的寫法）、同一字串出現兩次（改成以行號替換）。
5. **替身或 fixture 有改就整組重跑**，只新增 `it` 才只跑上一輪存活的。merge main 帶進別人的 spec 也算替身改了（#1857 的 `throwOn`）。
6. **重驗時先比 diff**：`git diff <舊 head> <新 head> -- . ':!*.spec.ts'` 看產品碼有沒有動；作者 merge main 後，用「本張自己的檔案對上一個審過的 head」逐檔比，0 行差異才沿用結論（#1837、#1857、#1828）。比 patch-id 時 base 要對（main 中途又前進會誤判）。
7. **共用 DB 上不跑契約測試的突變**：記成「推理驗＋作者實跑」，請作者在 PR 寫明哪一支紅。
8. **判「不擋」要寫出理由**：等價（例：`some`/`every` 在唯一鍵下 ≤1 列）、只影響同分取哪一幀、純視覺且有截圖量測。不擋的也寫進留言，讓計畫席看得到。
9. **選擇器／select 字串**替身不解析，存活就請作者攔字串（`parent/sessions.spec.ts` 的 `selects` 攔截器是範本）。
10. **時間相關**用 `TZ=UTC` 再跑；需要負時區才看得出來的（`new Date(iso)`）用 `TZ=America/Los_Angeles`。
11. **iOS 實機**：Playwright WebKit 叫不出鍵盤、重現不了聚焦放大。這類 PR 過了也要在留言寫「合後請使用者用 iPhone 確認」並報給主審核席（#1854、#1869、#1893）。
