# design-web 席

視覺、設計系統、web 效能、公開頁。管的是「使用者看到的那一面」以及它的重量。

## 一、這席的路徑

| 範圍                                             | 路徑                                                      |
| ------------------------------------------------ | --------------------------------------------------------- |
| 全域 design tokens 與 overlay 樣式               | `apps/web/src/styles.scss`                                |
| 公開頁（登入、報名、試聽、QR 打卡、綁定 LINE）   | `apps/web/src/app/features/public/`                       |

## 三、慣例

**寫 SCSS 前一律 invoke `angular-scss-bem-standards`。** 不是形式，它會擋掉深層巢狀與非 token 硬編碼值。做視覺方向用 `impeccable`（流程型，取代 frontend-design），收尾用 `web-design-guidelines`。`ui-ux-pro-max` 可輔助但**它給過違反 c6 的建議**（`clamp(3rem 10vw 12rem)`）與衝突的色票字體，採原則、棄具體值。

**對比不靠記憶，靠兩支 gate。**（別再手抄數字進這裡 —— 上一版 charter 抄了七種底色與
`--warning-100` 上的 4.51，兩週後就有一半不準了。）

| gate                                        | 守什麼                                          | 判例                                                            |
| ------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| `tools/agent-harness/lib/band-contrast.mjs` | 橘帶 token **自己的值**                         | 近黑字降透明度掉出 AA（0.72 只有 4.00）                         |
| `tools/agent-harness/lib/scss-contrast.mjs` | **配對** —— 每個 token 都合格、配在一起卻不合格 | 琥珀 chip hover 換到 200 底剩 4.03，而那個區塊只寫了 background |

兩支的門檻都**從 `styles.scss` 現值算**，不寫死；改了 `--accent-vivid` 或任何 100 階底色
會自動重算。`scss-contrast` 有 baseline（既有 29 處，只擋新增），跑 `npm run harness:write` 重生。

**gate 寫完一定要塞一個陷阱進去看它會不會紅。** 綠燈有兩種：真的沒問題，和檢查提早
return 了 —— 這兩種從輸出上看一模一樣。band-contrast 我弄壞過三種情況、scss-contrast
塞過琥珀 chip 陷阱，都確認會紅才敢說它有效。

**gate 抓不到的那一半仍然要自己算**：`scss-contrast` 只看同一個規則區塊或它的祖先，
底色來自跨檔案 DOM 祖先的它看不到（那需要真的算 CSS 串接，成本高一個量級且會誤判）。
所以動語意色階之前，還是要掃過每一處引用的祖先 `background`。

**改 token 值修不到繞過 token 的地方。** #97 只改了 `--success-600` / `--warning-600`
的值，全站還有 4 處 icon + 2 顆狀態圓點直接寫死同色系，對比 2.13～3.00 全沒過。
**任何「改 token 修對比」的工單，收尾一定要 grep 舊的 hex 確認歸零。**
非文字元件（圓點、icon、border）門檻是 3:1 不是 4.5:1，但也要過。

**修一個 UX 問題之前，先確認同樣的畫面有沒有第二份實作。** 分岔不是靠時間長出來的，
是靠一次一次的「只修我手上這份」長出來的。2026-09 的元件需求分析盤出三個實例，形狀一模一樣：
點名有兩份（#135 / #138 各修一次同一個 bug）、成績登錄有兩份（**#161 是我修 UX 的 PR，
方向完全正確，但它只修了其中一份，於是製造了新的分岔**）、`selectionMode="range"`
已用在 8 處卻有 3 處沒用。

配套的兩條：

- **先問三層，再問要不要造**：**能力**（現有依賴是不是已經支援？查型別/文件，不要憑記憶）
  → **資料**（需要的東西是不是已經在手上、只是沒帶過去？）→ 才問造不造。
  第一層的判例是使用者一句「PrimeNG 的 datepicker 難道沒有支援範圍選取嗎」問掉我的第一候選；
  第二層的判例是 `sessions.page.ts` 已經配對到 `eventId` 卻沒帶下去，害對話框又打一次同一支 API。
- **收斂重複實作時，先列出「只有 A 有」與「只有 B 有」兩欄。** 分岔久了兩邊都會長出東西，
  而**後長出來的那些正是別人踩過坑才加的**。只挑一份當基底、另一份直接刪，會**靜默弄丟一道防線**。
  活教材：一席只看到 A 有請假感知、另一席只看到 B 有未完成防護，**兩個人各看到一半**，
  而我一開始把它寫成「誰併進誰」。

**「全站遷移某個 token」是逐處工作，不是機械替換。** 同一個 token 疊在不同底上是不同的東西：
`--zinc-400` 對白 2.60 不合格，但 `shell-header` 的底是 `--zinc-900`，它在那裡是 **6.92 本來就過**，
機械遷移到 `zinc-500` 反而掉到 3.5 以下 —— 而 `scss-contrast` 的跨檔盲區看不到這一處，
沒有任何自動化會攔下這個改壞。所以這類工單三條：

- **逐處開檔確認祖先 `background`**，尤其是深色殼層（header、sidebar、footer、tooltip）
- **保留不改的理由寫進程式碼，不是寫進 PR** —— PR 會沉，程式碼會被下一個人讀到。
  刀 5 保留的 30 處裡，理由不顯而易見的 4 處各補了一行註解，就是為了擋「順手收斂」
- **baseline 少的筆數 ≠ 改的處數**，回報時講清楚。刀 5 改 79 處、baseline 只少 6 筆，
  因為另外 73 處的底色在 gate 的盲區裡；不講的話 reviewer 會以為沒改到東西

`::placeholder` 與 `disabled` 控制項**不適用 4.5:1**：前者「還沒填」本來就該比「已填」淡
（提高對比會讓空欄位讀起來像有值），後者 WCAG 1.4.3 明文豁免（提高對比會讓它看起來可以按）。
這兩類永遠留在 baseline 外面。

**色相只編碼嚴重度。** 身分、數值、編輯狀態一律不准碰色相 —— 這是狀態編碼系統的法則
（工單 3，設計稿見 PR #108）。形狀編碼「是否還在等」，位置與字重編碼編輯狀態。
`--accent-*` 是品牌色，它從來就不是嚴重度（#100）。

**分類要看值域，不是看標籤。** 刀 2 漏了 3 處身分著色，根因是我讀 template 的字來分類：
標籤長得像狀態的，值域可能是身分；標籤中性的，身分性可能藏在 `severity()` 函式裡面。
**兩邊都要讀** —— 值域決定它是什麼，標籤只決定它看起來像什麼。

**狀態的權威定義在確認文案裡，不在 enum 名字裡。** 我把 `closed` 讀成「已完成」，
admin-pages 用那顆確認彈窗的「結束後將無法再登錄分數」證明它**不保證分數登錄完** ——
所以是 `inactive` 不是 `done`。enum 名字是作者當時的意圖，確認文案是對使用者的承諾；承諾贏。
**跨席問狀態語意時，問「這個狀態的確認彈窗怎麼寫」比問定義有效。**

**規則寫進元件，比寫進文件便宜。** `app-page-band` 的流場 `frozen` **刻意不做成 input**
—— D 明令「資料表格後面永遠不放持續動態」，開放成參數等於留一個口子給下一個人違反。
同理 `app-data-chip` **刻意沒有 severity 參數**：沒有那個參數，就沒有人會拿它表達狀態。
兩條都有測試釘住。

一般化之後：**當「可以表達錯的東西」本身就是問題時，元件的價值在於讓那個錯誤變成
「不可表達」的。** 第三個實例是「沒有給去處就不該渲染成可點的樣子」（死路 chip 靠
「看起來可點但不是」在騙人）。這也回答了「那合併成一份函式就好，為什麼非得是元件」——
**合併成函式或樣式，還是做得出錯的東西；元件可以讓它在型別層就不成立。**
（出處：bundle-analysis 席，2026-09 元件需求分析）

**判準是「哪一種錯誤會被看見」，不是「缺的 vs 錯的」本身。** 我原本用的是
「缺的資料比錯的資料更沉默」，那條不夠 —— 它在點名的請假豁免那題會給出相反的答案，
而正解是：被豁免的誤判**可見**（那個人畫面上掛著「請假」chip，明明來上課卻掛著它，老師會發現），
被迫填的假出席**不可見**（進 DB 之後跟真的一模一樣）。

一條判準能推出相反結論而且兩次都對，那才是判準；我原本那條只是它的特例。
**設計時要問「如果這裡判斷錯了，錯誤會不會留在使用者眼前」** —— 會，可以接受較寬的判斷；
不會，寧可保守。延伸做法：把可見性從「被動掃視」挪到**動作發生的瞬間**
（存檔時說「3 人因請假未標記」，而不是只讓 chip 躺在列表裡）。
（出處：admin-pages 席）

**擴張共用視覺詞彙要過兩道關卡。** 詞彙的價值來自它小而封閉，每加一個都在花本金。

1. **雙軸保證是「成對」性質，不是整體性質。** 別只看矩陣哪一格空著 —— `status-dot` 的中空
   目前只有 `pending` 一個成員，所以**形狀本身就是它的識別特徵**；一旦中空有第二個成員，
   那一對就退化成只靠色相分，灰階／色盲／8px 下全糊掉。**要加 tone，先跟現有每一個逐對
   檢查兩軸是否都不同**，過不了就是不能加。（我提「中空 + warning」時只看了空格，
   被 teacher-pages 拿我自己寫在 `status-dot.component.scss` 的註解打回來。他對。）
2. **回答不同問題的東西該用不同載體。** 五個 tone 回答的都是「這件事現在怎麼樣」（狀態）；
   「你不小心點了不該點的人」回答的是「你得做什麼」（對那一列的旗標）。同一個載體扛兩種
   語意，正是詞彙開始漂移的方式。**拒絕擴張時要給出替代載體**，否則對方只會繞過你自己畫
   一個 —— 那比讓他加更糟，因為新畫的那個沒有人管。

**這席的共用元件與詞彙**（實作在 `shared/components/`，不要在 feature 裡各寫一份 —— c5）：

| 詞                 | 指的是                                                   | 元件              |
| ------------------ | -------------------------------------------------------- | ----------------- |
| **橘帶**（band）   | 內部頁的入口色面，一頁一條                               | `app-page-band`   |
| **錨點**（anchor） | 帶上那個放大的關鍵數字，**最可行動的那個、不一定是總數** | `app-band-anchor` |
| **咬合**（seam）   | 白工作面往上壓進橘帶的深度，`--band-seam`                | —                 |
| **身分 chip**      | 類別／種類／所屬，中性、無嚴重度                         | `app-data-chip`   |
| **狀態點＋字**     | 形狀 × 色相兩個軸                                        | `app-status-dot`  |

命名跟 design-web 第一席（session 名 `bundle-analysis-*`）對齊過：**band 是帶、anchor 是
帶上的數字**，不要拿 anchor 指帶本身。

**bundle 驗收線的量法**（不要抄數字，數字會腐化，抄方法）：

    npx nx reset          # Nx 的計算快取（不清的話它會整個回你上一次的 build 產物）
    rm -rf .angular/cache # Angular builder 的增量快取（nx reset 不碰這個）
    npx nx build web --configuration=production

> **不要用 `npx ng cache clean`。** 這個 workspace 沒有 `angular.json`，
> Angular CLI 會往上找到**別的 workspace** 然後對那邊動手（AGENTS.md 有記）——
> 比報錯更糟，因為它會安靜地成功。
>
> **兩個快取、兩個主人**：`nx reset` 清的是 `.nx/cache`（目前 30 MB），
> `.angular/cache`（4.5 MB）是 `@angular/build:application` 自己的，它不碰。
> 量 bundle 要兩個都清，只清一個的話拿到的可能是上一次的產物。

要比較就**兩邊各自量**：commit 後 `git checkout --detach origin/main`，清 cache 再 build 一次拿 baseline，切回來再量。同機、同 cache 狀態才是真數字 —— 我曾經因為拿舊 cache 的數字當 baseline，回報過一次偏差 0.23 kB 的假差異。

**初始 chunk 的歸因方法**：`--source-map` build，然後解析 `.js.map` 的 mappings 把 generated bytes 歸給 source。`source-map-explorer` 對 Angular 21 的 map 會噴 `generated column Infinity` 掛掉，別浪費時間。要確認某個東西有沒有洩漏進初始 bundle，最直接是掃 `index.html` 列出的初始 chunk 找特徵字串（例如 `p-dialog-header`）。

**視覺我看不到。** 每個視覺 PR 都要明列「需要人工確認」的項目，別假裝驗收過了。

## 四、坑（都踩過）

1. **`angular.json` 不生效**。Nx 讀的是 `apps/web/project.json`。改錯檔案會出現「build 照樣印舊 budget」的鬼打牆，清 cache 也沒用。兩份目前已對齊但仍是重複設定，遲早再漂移。

2. **root component 掛什麼，所有人就下載什麼**。`app.component.ts` 曾靜態 import `DialogService` + 一個 feature 元件，把整棵 PrimeNG dialog 依賴樹釘進初始 bundle（約 140 kB）。**root component 只放 `<router-outlet>`**，任何 UI 元件、任何 `providers` 裡的 UI service 放上去都等於放進初始 bundle。

3. **PrimeNG 的 `DialogService.open` 沿 elementInjector 往上找**（`primeng-dynamicdialog.mjs` 的 `new DynamicDialogInjector(this.injector, ...)`）。所以只要**開窗方**有 local provider 就安全，被開的那支不需要自己 provide。移除 root provider 前用這條判斷，不必盲目補 provider。

4. **動態 import 開彈窗要防孤兒**。import 完成前元件若已銷毀（選完角色馬上導航就會如此），會開出沒有主人的彈窗並拋 NG0911。要有 `destroyed` 檢查，且銷毀時用 `ref.destroy()` 而不是 `close()` —— `close()` 會走 `onClose`，那條路的語意是「使用者做了選擇」，會誤觸發第二次導航。

5. **推理贏不過截圖**。我用 CSS mask 把 LINE 官方白色 icon 染成品牌綠，理由是使用者說過「icon 同綠」——結果那素材是白泡泡加**鏤空的字**，染成單色後 24px 下就是一團綠塊，認不出是 LINE。**視覺假設要等實機截圖再定案**，尤其是小尺寸下的形狀辨識。

   **mockup 也要放進瀏覽器看，不要只在腦裡跑。** 光是這一輪就靠實際開來看抓到四個推不出來的問題：橘帶縱向堆疊高達 360px（來看表格的人要先滑過一大片）、用 emoji 當 icon 在暖橘色盤裡是彩色異物、「已停用」的灰實心＋描邊在 8px 下跟中空環分不出來、未儲存的近黑左緣放在靠右對齊的分數欄會變成浮在表格中間的線。**四個都是我寫的時候覺得沒問題的。** 本機開檔要記得補 `<meta charset="utf-8">`，否則中文全變亂碼。

6. **prettier 會在 Write 之後重排檔案**（PostToolUse hook）。之後所有針對「單行 CSS」的字串替換都會 miss。**每個 replace 都加 assert**，否則靜默失敗，你會以為改好了。

7. **`.claude/skills/*` 是指向 `.agents/skills/` 的 symlink**。impeccable 的 `concept-seed.mjs` 有 `argv[1] === import.meta.url` 自我檢查，在 symlink 下不成立 → **靜默 exit 0、零輸出、零錯誤訊息**。用 realpath 呼叫（`~/.agents/skills/impeccable/scripts/...`）。同理它的 `detect.mjs`。

8. **`impeccable` 要求 PRODUCT.md 才發牌**，但憲法 c9 說專案文件只住 `kb/`。解法是放 `.design-explorations/PRODUCT.md`（工具輸入、不是專案文件、不 commit），內容從既有 kb/ 濃縮、不發明事實。

9. **`db:reset` 是破壞性的且會被權限擋**。要驗 SQL 就開 transaction 套用完 `ROLLBACK` —— 真跑過、零副作用。但它驗不到「在既有正式資料上跑會怎樣」，那需要 staging。

10. **「看起來重複」的兩個函式，要明寫它們不是重複**。`shared/utils/session-time.util.ts` 的
    `hasSessionStarted` 與 teacher `dashboard.util.ts` 的 `hasStarted`，**null 行為刻意相反**
    （前者無 `startTime` 回 false，保守不誤標；後者回 true）。沒有那行註解，下一個人會合併
    它們，而合併會**靜默**改掉其中一邊的語意。null 分支也不要因為呼叫端的型別保證非 null
    就刪掉 —— 通則見 `README.md`（「型別是當下的保證」），這裡只留判例。

    同族的沉默失效：**常數漂移不會有任何測試變紅**。列表頁大小曾同時有 8/15/20 三種值，
    沒有一支測試在意。抽成 `LIST_PAGE_SIZE` 時**例外要寫理由**（兩個彈窗選擇器留 8，
    因為 `max-height: 340–380px`），沒寫理由的例外下一輪就會被「統一」掉。

11. **誤點的失敗模式不是「沒反應」，是「靜默改資料」**。2026-09-02 實走 demo 各撞一次：
    - 產生課堂的日曆 popup **蓋住對話框的動作按鈕**，我瞄準「預覽課堂」按下去，
      實際點到日曆的「9」，結束日期被改成 10-09 —— 沒有錯誤、沒有動靜，只有一個
      不顯眼的值變了
    - 成績表看起來像試算表，`↓` 的心智模型是「移到下一列」，實際是把分數**減 1**

    兩者同構：**使用者以為自己在導覽，實際在編輯。** 檢查方式是問「這個位置如果點歪了/
    按錯鍵，會發生什麼」—— 答案若是「改掉一個值」而不是「什麼都沒有」，那就是要修的。
    浮層蓋住動作區是這一類的溫床，所以**對話框裡的 popup 幾何要在 dialog 模式層解決**，
    不是逐個元件補。

    順帶：這也是**實走才抓得到**的一類。讀程式碼看不到「popup 剛好蓋住按鈕」。

12. **`grep` 數使用點會同時產生假陽性與假陰性，而且方向相反**。2026-09 一輪盤點裡撞了三次：
    我查 `dashboard__card` 用了幾處，子字串命中 `teacher-dashboard__card`，**差點報一個
    不存在的孤兒 class**；別席查 `_dashboard.scss` 有沒有消費者，第一次 grep `shared/dashboard`
    漏掉實際寫法 `shared/styles/dashboard`，**差點把有人用的檔案判成死檔**。

    規律：BEM 的 block 名天生互為子字串（`dashboard__` ⊂ `teacher-dashboard__`），
    而 `@use` / import 的路徑有多種寫法。

    **規則：grep 只用來產生候選，結論一定要開檔確認** —— 尤其當你要拿數字去做決定的時候
    （「只有 2 個使用點所以不立案」「零消費者所以刪掉」）。那兩種結論剛好各自對應一種誤判方向。

13. **量 RWD 用同源 iframe，但先確認那個 port 上跑的是自己的東西**。Chrome 的視窗縮不到
    390px，所以「調整視窗看 RWD」在這台機器上做不到。**同源 iframe 內的 media query 是依
    iframe 的 viewport 計算的** —— 是真的走斷點不是模擬，而且同源讓你能直接量內部元素的
    `getBoundingClientRect()`。

    ⚠️ `localhost:4200` 會被其他席的專案佔用。有一次 dev server 沒起來但 API 起了，
    瀏覽器打開看到的是**別人的 app**（幸好長相完全不同）。

    **登入態拿不到時，有時候可以把問題換成純 CSS 問題。** 2026-09-04 要量一支 dialog
    裡的表格會不會橫向溢出，而那支 dialog 在登入之後 —— 我不能自己登入。

    改成獨立 harness（`npx sass` 編元件 SCSS + tokens，靜態頁載入，量
    `scrollWidth` vs `clientWidth`）。**判準是這一句：**

    > **harness 忠不忠實，取決於「你要量的東西會不會受到 harness 缺的那些影響」。**

    那次 harness 缺的是 PrimeNG 的 runtime CSS-in-JS（cell 裡有 `p-inputnumber` /
    `p-select`），我本來以為那讓它不可用 —— 但表格是 `table-layout: fixed`，
    **固有寬度根本不參與計算**，我擔心的那個維度剛好被同一個屬性消掉了。

    反過來說：要量的若是「內容把欄位撐多寬」，同一個 harness 就**完全不可信**。
    先問缺的東西影不影響答案，再決定要不要用它。

14. **跨席送訊息要驗證收件人 —— 送錯人比沒送更難發現。** 2026-09-03 我把整晚的跨席
    回報（PR 完成、副作用通知、設計初審請求）全部投進了錯的信箱，而且**兩邊都以為
    自己在正常運作**：我以為送出了，計畫席以為我在 idle。

    三件事同時錯：

    - **有兩套傳輸層，別混用。** `mcp__claude-peers__send_message` 吃 **peer id**，
      `SendMessage` 吃 **名稱**。我用前者，而它的 `list_peers` 清單是**過期的**
      （停在前一天，而且根本沒有列出計畫席的 PID）。**用 `ListAgents` + `SendMessage`。**
    - **席名 ≠ session 名。** billing-api 席的當班 session 叫 `pin-better-auth-3c`，
      design-web 席可能叫 `bundle-analysis-*`。**派工前 `ListAgents` 對一次**，
      對不出來就問計畫席，**不要從 CWD 猜**（我就是看到某個 session 的 CWD 是 repo
      根目錄，就假設那是計畫席）。
    - **交付之後要確認回音，不是等。** 沒有回音超過 15 分鐘就再敲一次 —— 但那治的是
      症狀，根因是沒驗收件人。

    **結構性的解：重要的跨席交接走檔案，不走訊息。** `herdr-team/<席>-<主題>.md`
    是既有慣例（見 `billing-api-p3-*.md`）。**session 會死、席位會換、訊息會投錯，
    檔案不會。** 訊息只用來通知「單子在哪」。

15. **branch ref 是整個 repo 共用的，別的 worktree 會移動你腳下的分支。**
    2026-09-03 我在這個 worktree 上 commit 完，切分支時發現本地的
    `fix/table-overflow-mobile` 指標已經被移到另一個 commit —— **我的 HEAD reflog
    完全沒有那次移動**，因為動它的是別的 worktree。

    症狀是 `git status` 突然冒出幾十個你沒動過的暫存變更（那是「工作區 vs 新指標」
    的差異，不是誰的工作）。**先驗證再修**：`git diff --cached <你自己的 commit>`
    是空的就代表工作區還是你的東西，切走不會掉。

    **不要反射性地把指標改回去** —— 對方可能是刻意移的。確認自己的 commit 在
    `origin` 上，然後換一條分支走。

    附帶一條：**收到跨席工單時先確認那個 PR / 分支的擁有者。** 同一晚我照做了一張
    誤派給我的工單（#174），因為它的 commit 系譜看起來像這席的線 ——
    **相似不等於同一個席位**。做完才被告知派錯。所幸是疊加不是 force-push，
    沒有人掉東西。

16. **fixture 寫成單行，逐行 parser 什麼都掃不到 —— 而「預期是空的」那種測試會照樣綠。**

    寫 icon 門檻的測試時，我把 fixture 寫成 `.x { background: …; color: …; }` 一行。
    scss 掃描是逐行的，單行規則它根本進不去。「該抓卻抓到 0」那條紅了所以被抓到，
    但**「該放行、預期 0」那條也是 0，它綠得理直氣壯** —— 那是假綠。

    通則：**只斷言「沒有結果」的測試，必須另外有一條同結構、只差一個變數、
    斷言「有結果」的測試陪著。** 沒有那條對照，你分不出「規則放行了」和
    「掃描器根本沒讀到你的輸入」。

    （這次沒有變成 repo 漏洞，因為 PostToolUse 的 Prettier 一律把規則展開成多行，
    單行規則進不了版控。但那是運氣好，不是設計。）

17. **ratchet 的範圍應該由另一個 ratchet 推導，不要手寫。**（infra 席的教訓）

    手寫「哪些檔案要納入這個 gate」的清單，跟手抄任何清單一樣會腐化（c11）：
    新增的檔案不會自己進去，於是 gate 看起來是綠的，其實只是沒在看。
    範圍要從既有的另一個指標推導出來（例如「所有 `*.component.scss`」），
    要排除就在推導後**明列排除項並附理由**，這樣至少排除是可見的。

18. **`backlog.md` 有衝突時，一律以 main 為基底、只改自己那一行。**

    我曾經用「take mine」整檔解衝突，結果把 teacher-pages 剛認領的那一項還原、
    順手弄掉了 billing-api 的第 4 項。整檔覆蓋在共用佇列檔上等於靜默地否決別人的工作。

    解法：`git checkout main -- herdr-team/backlog.md`，然後只重新編輯自己那一行。
    解完 **diff 一次 main** 確認除了自己那行沒有別的變動。

19. **驗證失敗時，先懷疑驗證器。** 2026-09-05 我要確認治理目錄改名之後 charter 的內容
    有沒有掉，**連續三次得到「東西不見了」，三次都是我的檢查壞掉**：

    | #   | 檢查                                                                  | 錯在哪                                                           |
    | --- | --------------------------------------------------------------------- | ---------------------------------------------------------------- |
    | 1   | 派唯讀 agent 掃工作區                                                 | 掃到的是**我的舊分支**（早於改名）。對那個分支為真，對 main 為假 |
    | 2   | shell 複合條件 `[ -n "$c" ] && [ "$c" != "0" ] && echo A \|\| echo B` | 兩條路徑都印同一句，**把「檔案不存在」與「0 個命中」混成一件事** |
    | 3   | `grep "常數名 已經不存在"`                                            | 實際文字有**反引號**包住常數名，字面比對不中                     |

    每一次的第一反應都是「東西不見了」，而三次都不是。

    **誤報比漏報安全，但它會讓人去救不需要救的東西** —— 上一輪就因此差點重做一份已經
    修好的報告。所以：**在回報「東西不見了」之前，先用第二種方法確認一次**
    （換關鍵字、換工具、或直接把檔案印出來看）。

    這是「別信形式、要驗內容」的反面：**驗證本身也是形式，它也會壞，而且壞的方向偏向誤報。**

20. **量測要對到「掛著那個 class」的元素本身，且量兩個節點才能排除「量錯節點」的
    假設。** 追 `session-filters` 的 `min-width` 為什麼算出來是 `auto`，直接比對過
    wrapper 與內層 `<input>` 的 computed style，兩者都是 `auto` 才敢說「不是量錯節點」——
    排除一個假設要對兩邊都下手，不能只查看起來像的那一個就下結論。

21. **`document.styleSheets` 掃描要遞迴進 `@container` / `@media` 區塊，只掃
    top-level `cssRules` 會漏規則。** 第一輪掃描就漏了這層，沒挖到
    `session-filters.component.scss` 裡一條 container-query 內、贏過全域 class 的
    規則——掃描器跟被掃的東西一樣會有盲區，這是坑 #19「驗證本身也會壞」的具體實例。

22. **`ch` 不是精算單位，只按字型的 `0` 寬度估，不同元件的 padding／字級不同就會差。**
    從 26ch 改到 30ch 那次，同一個數字在有 `-sm` 尺寸的頁面夠用、沒套的頁面就不夠——
    量到的餘裕不是算出來的定值，下一次抄這個數字之前要重新量一次自己的情境。

23. **兩個東西撞在一起時，先問能不能讓其中一個安靜下來，不要急著加區分裝置。**
    M2「狀態」欄正常態不畫點、`inline-notice` 的 info 改中性色，兩次都是同一個
    判斷——移除碰撞源優於增加顏色/圖示/分隔線，加法只會讓兩邊都更複雜，而複雜
    本身才是問題。

24. **驗證的形式要對得上要證明的性質。** 視覺撞色要用截圖證明（人眼判斷相似度），
    貼色碼或算色相角度只是輸入不是結果——這輪兩個都做了才敢說驗證完，少一個都不算。

25. **上游（含計畫席）給的結論，先驗再信——這輪三次推翻上游都是用量測，不是用感覺。**
    驗過 `taipei-date.ts` 真的存在才接受一個裁決、量過兩個節點才排除一個假設、讀過
    兩支後端分支的實際實作才發現 `endedOnly` 只加在其中一支——三次裡有兩次上游是錯的。
    這不是懷疑上游的權威，是把「這個結論建立在什麼證據上」當成習慣性要問的問題；
    上游也會踩到同樣的坑（信了一個沒驗過的 grep、記了一個過期的直覺）。

26. **同一個根因如果有好幾條呼叫路徑，工單只點名其中一條時，先確認其他路徑是不是
    同一個坑，一次修完。** #315（500 被 `authGuard` 當成未登入彈去登入頁）工單只點名
    `authGuard`，但 `roleGuard`/`permissionGuard` 是同一份「沒登入就導向 /login」的
    邏輯複製了三份，同樣的 catch-不分狀態碼也在那兩支裡。抽出共用的
    `unauthenticatedRedirect()` 三支一起修，不是因為工單要求，是因為只修
    `authGuard` 等於留兩個一模一樣的地雷沒拆。**工單描述的是症狀被看見的那一條路徑，
    不是根因的邊界。**

27. **PrimeNG 的 disabled 樣式全站只有一條全域規則
    `.p-component:disabled{opacity:var(--p-disabled-opacity)}`（0.6），對飽和色
    疊透明度會把文字對比壓到 WCAG 門檻以下，而且看起來只是「同一顆按鈕變淡」不是
    「按不了」。**光改 CSS 變數不夠 —— PrimeNG 把元件樣式在執行期動態插入
    `<style>` 到 `<head>`，永遠排在這支全域 `styles.scss` 之後，選擇器優先度打平時
    它必贏。改 `.p-button:disabled` 的 `opacity`/`cursor` 沒加 `!important`
    完全沒生效，實測確認才發現 —— `.p-skeleton` 那組舊覆寫早就用 `!important`
    解過同一個問題，這次是同一個坑第二次被踩到，早該寫進來。

    另外：`opacity` 是同時淡化文字跟背景的機制，對比不是靠「調透明度」能救回來的
    ——文字跟背景都往同一個底色（通常是白）靠，兩者差距只會縮小。要保對比，
    disabled 狀態要換成跟原色脫鉤的實色（灰階），不是調那個 0.6。

28. **判「這支 PR 是誰的」只有一個可靠訊號：commit 的 `Claude-Session:` trailer。**

    2026-09-06 一天之內被誤派三次（刀 B、#378、#398/#400/#403）。用過而失敗的代理指標：

    | 訊號                        | 為什麼沒用                                                       |
    | --------------------------- | ---------------------------------------------------------------- |
    | git 作者                    | **全席都是 `Mizok`**，這欄完全沒有資訊                           |
    | worktree 現在 checkout 在哪 | 別席為了驗證也會 checkout 過去（review-steward 因此誤判過 #200） |
    | 分支在不在我的 worktree     | **worktree 共用同一個 repo，所有席位的分支到處都看得到**         |
    | 工作內容像不像我這條線      | 相似不等於同一席 —— 我因此做過一張誤派的工單（#174）             |

    可靠的做法：

    ```bash
    git log -1 --format='%B' <branch> | grep -o 'session_[A-Za-z0-9]*'
    ```

    派工的歸屬則看 **issue 的 `seat:*` 標籤**，不是分支名或內容
    （2026-09-06 從 backlog.md 的欄位標題遷來）。

29. **`git add -A` 在切過分支的工作區不安全 —— 它會把「舊版」提交成「刪除」。**

    分支從較早的 main 開出來，期間別席合了東西進共寫檔（`herdr-team/*.md`、
    baseline JSON）。工作區裡那些檔還是舊版，`git add -A` 就把差異當成你的改動。

    我因此在 #401 裡刪掉了 review-steward 當天寫的 18 行 charter，**而且原本那筆
    commit 就帶著它，是三天後 rebase 才被看到**。

    收尾的固定動作：`git diff origin/main --stat` —— **出現你沒碰過的檔就是警報**。
    更精確的反向驗證：`comm -23 <(main 的條目) <(我的條目)` 要是空的。

30. **驗「rebase 之後 CI 會不會綠」不需要推。**

    本機 `git rebase origin/main` + 跑測試就夠：不動遠端、不排 CI、不佔別人時間，
    失敗還能 `git rebase --abort` 零成本回退。

    2026-09-06 全板八支繼承 main 的同一條紅，協調的做法是「挑兩支當樣本先推」——
    本機驗等價而且更省，八支可以同時各自驗。

31. **觸控 gate 認不得逗號群組的選擇器 —— 它只認群組裡的最後一個。**

    ```scss
    @media (pointer: coarse) {
      .a,
      .b,
      .c {
        min-height: 44px;
      } // 只有 .c 被認到
    }
    ```

    巢狀沒問題（`.blk { &__x { } }` 認得），**純粹是逗號**。症狀是
    **檔案看起來修好了而 gate 照樣紅** —— 比沒修更難發現，因為下一個人看到
    `min-height` 就以為處理過了。**一條一個選擇器。**

32. **擴大命中區用 `::after` 覆蓋層，不要用 `padding` + 負 `margin`。**

    兩者視覺效果相同，但 gate **只看 `width` / `height` / `min-*`** ——
    負 margin 那種寫法會得到「命中區真的變大了、帳面照樣紅」。

    而且覆蓋層要看**那一列上有沒有第二個動作**：`class-row__name` 的動作是
    navigate、整列是 toggleSelection，覆蓋層的重疊會讓人以為在選取卻跳了頁。
    **動作不同的時候，命中區重疊本身就是問題** —— 那種情況讓看得見的按鈕自己長大。

33. **元件層的 `providers` 會遮蔽 TestBed 的 provider，而症狀是假綠。**

    元件上寫了 `providers: [DialogService]`，TestBed 的
    `{ provide: DialogService, useValue: mock }` 就不生效 —— 元件拿到真的 service，
    mock 永遠不被呼叫。要用 `TestBed.overrideComponent(X, { set: { providers: [...] } })`。

    這次是**正面斷言紅了才暴露**：兩條 `not.toHaveBeenCalled()` 看起來是綠的，
    實際上是流程根本沒走到那裡。呼應坑 16 —— 只斷言「沒有結果」的測試要有對照組。

    同一支 spec 還有第二個：**模組層的 `const mock = { fn: vi.fn() }` 不會自己重置**，
    於是「這條測試有沒有關閉對話框」實際上在問「**前面所有測試加起來**有沒有關過」。
    在 `beforeEach` 清掉。

- **視窗尺寸變數寫在 `documentElement`，不是 `.app`**（#282，2026-09-04）。三支硬寫
  `[appendTo]="'body'"` 的底部抽屜掛在 `.app` 外，繼承不到 `--window-height`，**每台手機
  都被鎖在 `.drawer-auto` 的 fallback 533.6px**。實測 390×900 上修後 720px（+35%）。

  **667 剛好是 iPhone SE 的高度 —— 那就是這個 bug 隱形這麼久的原因**：在那台機器上
  fallback 等於正確值。

  當時三案並陳，判準留著：**方案 C（`.drawer-auto` 改 `max-height: 80%`）被拒**，因為
  `%` 在 `position: fixed` 上解析對象是 ICB，而 iOS Safari 的 ICB 是大視窗、
  `window.innerHeight` 跟著可見視窗縮 —— **兩者恰好在動態工具列出現時分岔，那正是 c6
  立法的場景，而 gate 掃不到 `%`**。桌機上 ICB == innerHeight，所以 harness 分不出 A 與 C：
  **一個只能在測不到的平台上被區分的改動，不該勝過平台無關的改動。**

  ⚠️ **還沒有人在 iOS Safari 上確認過**（PR 的人工確認第 4 項）。**那是這個裁決的核心** ——
  沒驗過的話它只是紙上的。而**方案 C 沒有被否定，只是被延後**：有人拿 iPhone 驗過且乾淨，
  它仍然是更小的刀，值得回頭換。
