## 一、分校範圍：寫判準時踩到的

- **embed 回 `null` 時，可選鏈出來是 `undefined`**。`(row.enrollments)?.classes?.campus_id` 對餐費明細
  （`enrollment_id` null → embed 是 `null`）回 `undefined`，而「沒有班」比的是 `=== null` —— 少一個 `?? null`，
  帶餐費的帳單整張被判出範圍。spec 一寫就紅，讀碼看不出來。**取巢狀 embed 值的 helper 一律收尾 `?? null`。**
- **同一個關聯要 embed 兩次要用 alias**：`scope_items:invoice_items(enrollments(classes(campus_id)))`，
  主 select 已經有 `invoice_items(...)`。`multi-org-db` 不解析 select，spec 裡直接 seed alias 欄位，
  select 字串本身用本機 PostgREST 打一次驗形狀。
- **三層 `!inner` 的條件會一路往上傳**：`parent_student_relations?select=parent_id,students!inner(enrollments!inner(classes!inner(campus_id)))&students.enrollments.classes.campus_id=in.(…)`
  只回孩子在範圍內有報名的關聯列（本機實測 51 → 16）。從關聯表出發＝一列一條關聯，比「先撈報名再 `.in()` 學生 id」
  少一層截斷、也不撞 URL 長度。替身 `multi-org-db` 的 `fieldValues` 已支援路徑中途的陣列（任一符合即成立）。
- **PostgREST 同一欄兩個 `in` 是 AND**（`user_id=in.(A)&user_id=in.(B)` → 交集）。疊「使用者的角色篩選」與「章節名單」時語意正確，不用自己先取交集。
- **掃碼機台（kiosk）也是 `staff` 列**：任何「人員依角色分章、和＝total」的計數都要有機台那一桶。

## 二、測試與陷阱的工具坑

- **zsh 不會切分未加引號的變數**：`T="a.spec.ts b.spec.ts"; vitest run $T` 傳的是一個參數，跑不到任何檔、
  **grep 不到輸出就像沒事**。陷阱迴圈一律用陣列 `T=(a b); vitest run "${T[@]}"`，並確認每段都印出 `Tests` 那一行。
- **注入失敗的 Proxy 只能打中被測的那一支查詢**：同一張表常有好幾支查詢（`user_roles` 在 staff 列表有三支），
  整張表失敗的話會先在別支回 400，測到的不是「章節計數失敗 → 500」。用該查詢獨有的方法認它
  （翻頁那支攔 `range`、計數那支攔 `select(…, { head: true })`），其他 `bind` 回原 builder。
- **TS2589（supabase builder 型別爆深）**：`applyCampusFilter(supabase.from(…).select(…, {head}).eq(…), …)` 內聯會撞；
  先存成變數再套就過。要寫「對 builder 套一組篩選」的 helper 時，泛型**不加約束**、在裡面轉型成最小介面
  （`staff.ts` 的 `withSummaryFilters`）；有約束的版本必撞。

## 三、harness 與 CI

- **`npm run harness | tail` 之後的 `$?` 是 `tail` 的**。harness 輸出裡「⚠ 提醒（不擋）」與真正的失敗長得很像；
  判斷擋不擋一律單獨跑 `npm run harness >/dev/null 2>&1; echo $?`。這輪把 api-param-coverage 當提醒報出去，CI 實際是紅的。
- **api-param-coverage**：後端列表加 query 參數，`apps/web/src/app/core/<x>.service.ts` 的參數型別**與手寫的 `toQuery`**
  都要認得它，同一支 PR 補（只動 service、不動頁面）。不要加 EXEMPT —— 那是給「刻意不支援」的。

## 四、跨席訊息

- **herdr 沒有 `BSpace` 這個鍵名**（`unsupported key BSpace`）。README「席位復活程序」那段的 `send-keys x → BSpace` 會把 `x`
  留在訊息開頭送出去（無害但難看）。輸入框是**建議提示**時，緩衝本來是空的：直接
  `herdr agent prompt <席> "…" --wait --until working --timeout 15000`，回 `working` 就是送到了。
- **建議提示會長得像事實**：計畫席框裡出現「兩支都合了」，`gh pr view` 兩支都還是 OPEN。框裡的字一律當沒人打過，要的事實去查。

## 六、merge 沒衝突 ≠ 沒重複（#1401，charter 合併後補）

- 兩支 PR 各自在同一檔**不同位置**新增同名的 `export interface InvoiceSummary`（一份是前端席先合的，一份是自己的），
  `git merge origin/main` **沒有任何文字衝突**，結果檔裡有兩份。
- **TypeScript 不會報錯**：同名 `interface` 是宣告合併（declaration merging），兩份的欄位被併成一個型別 ——
  所以 service 檔本身 typecheck 綠，紅的是**別處**（main 的 `payments.page.spec.ts` fixture 少了合併進來的必填欄位）。
- **merge 之後的固定動作**：`grep -n "export interface <你新增的型別>\|^interface " <檔>` 看同名有沒有兩份；
  然後跑**整個 project** 的 typecheck（不是只跑你改的檔），紅在別人的 spec 是正常的，補 fixture 並在 PR 留言寫明多動了哪一檔。
