## 一、家長端寫入怎麼做（#1119 起）

設計在 `kb/wiki/architecture/parent-data-scope.md`「二之一」，這裡只放動手時的要點：

- 寫入一律 `childDb.from(table, studentIdColumn).insert / insertMany / update`；班級、課程走 `childDb.orgRef()`；
  名額走 `childDb.activeEnrollmentCount()`。**家長端 route 拿不到原始 `supabase`（A19）**，所以需要新的參考資料時
  是**擴 childDb 的白名單**，不是繞過它。
- **`logAudit` 要原始 `supabase`，家長端用不到** —— 目前家長端寫入沒有稽核。要補就給 childDb 一個稽核入口。
- 新的 org 表要同步加進 `lib/org-scope.ts` 的 `OrgTable`（A23 拿 migration 對照，漏了 harness 紅）。
- route 先做 `isChildAllowed` 再查別的、`insert` 送 DB 前再擋一次 —— 塞陷阱時拿掉 route 那層**測試仍綠是對的**
  （第二層擋住了），別誤判成測試沒用。

## 二、測試替身的兩個坑

- **`multi-org-db` 故意不實作 `order`**：`org-scope.spec.ts` 的替身自我測試拿 `order` 當「未實作要丟例外」的範例，
  補上它會讓那條紅。需要排序就在記憶體排（家長端資料量小），或改那條自我測試換一個範例。
- **PostgREST `upsert(…, { ignoreDuplicates: true })` 衝突時回空陣列**，後面不能接 `.single()`（會 PGRST116）。
  替身若一律回一列，這個 bug 測不出來 —— 替身要照真實形狀回 `[]`（#1127）。

## 三、多支保留類 PR 改同一支檔

- 開完每支就 `git merge-tree --write-tree <另一支> HEAD` 試合；衝突就在 PR 寫「後合的那支由我 rebase」，
  計畫席會排順序、一次叫你 rebase 一支。
- 為了不跟別支的 import 撞，先 inline 一份（`ponytail:` 註記「都合後收」），rebase 時改回共用函式、刪註記，
  PR 描述同步改。（#1137 對 #1132 的 `resourceCampusAllowed`）
- 疊在別支上的 PR（要用它新增的函式）照疊 PR 鐵律：draft、base 指那支分支。

## 四、shell 的靜默失敗（本席踩到的）

- **worktree 之間共用 `origin/*` ref**：別席 fetch 之後，`git diff --cached --stat origin/main` 會把上游新合的東西
  顯示成「我倒退了它們」。確認自己的 commit 只動自己的檔，用 `git show --stat HEAD`。
- **`grep -c` 沒命中回 exit 1**：`… && grep -c X f && cat >> f <<EOF` 會在 grep 回 0 時**靜默跳過後面的寫入**。
  計數類檢查不要串在寫入前面。
- **`npx supabase migration new` 跟 heredoc 寫檔串在同一條指令裡，曾卡到 120s timeout**（檔已建立但是空的，
  成因沒查明）。分兩步：先建檔、看它印出的路徑，再用 Write 寫內容。寫完 Read 一次確認不是空檔。
