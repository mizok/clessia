## 一、改生產 migration 路徑時，本機怎麼「真的」驗（不靠 act）

`migrate.yml` 的 apply 是內嵌 shell，可以**從 yml 原文抽出來直接跑**，不用重寫一份：

1. 拋棄式 DB：`docker run -d --rm --name <x> -e POSTGRES_PASSWORD=pw -p 55443:5432 postgres:15-alpine`。
   連線字串**要帶 `?sslmode=disable`**，否則 CLI 2.119.0 回 `DbConnectError … tls error`。
2. **釘的 CLI 版本**：在 scratchpad 裡 `npm i supabase@<SUPABASE_CLI_VERSION>`（本機 brew 版是 2.72，太舊不能當證據）。
3. 假 repo：`mktemp -d` 底下建 `supabase/migrations/` ＋複製真的 `config.toml`，放幾支最小 SQL 模仿形狀。
4. 用 python 依 `\n      - ` 切 apply 的 steps、取 `run: |` 本體 `textwrap.dedent` 成 `stepN.sh`，
   `RUNNER_TEMP`／`GITHUB_OUTPUT`／`GITHUB_STEP_SUMMARY` 指到 `mktemp`，`bash -eo pipefail stepN.sh` 照順序跑。
   plan 那段就直接 `node tools/agent-harness/migrate-plan.mjs --remote <psql 撈出來的檔>`（cwd 要在假 repo）。
5. **`rm -rf` 被 deny** —— 每一輪開新的 `mktemp -d`，不要清目錄。

這樣一輪能把「plan 判什麼 → recheck → CLI dry-run → push → 套後差集」整條走完，資料也能 `psql` 看到。

## 二、CLI 對 history 的兩個行為（2.119.0 實測）

- 本機少一支、遠端也沒有 → 什麼都不說，正常（所以「從 checkout 拿掉 backfill 再 push」可行）。
- **遠端有、本機沒有 → `DbPushMissingLocalError`（Remote migration versions not found in local migrations directory）**。
  所以「延後」只能拿掉**正式 DB 還沒有**的檔；apply 拿到過期的 deferred 清單時要先比 remote 再拿。

## 三、「延後」不是永遠安全：被晚來的 schema 卡死

backfill 延後之後，若 dispatch 前又套了**比它新**的 schema，backfill 就成了「比遠端最新還舊卻沒套」，
不帶 `--include-all` 永遠套不上。所以 plan 對「同批裡有比 backfill 新的 schema」仍判 blocked。
**寫任何「先跳過、之後補」的機制時，先問：之後補的那支在 CLI 的順序規則下還補得上嗎？**
