## UI 地圖：方法的唯一真相是 `kb/wiki/specs/sitemap/README.md`

**量測方法、取樣器、十二個坑、Phase 2 的多寬度做法全部在那裡**，這份 charter 不複製。
第一天撞出來而收進那份的幾件（指標，細節去讀）：

## 這一席自己的判準（不在方法頁裡的那些）

**工具回報成功不等於它做了那件事。** 第一天最貴的一次是 `resize_window`：
它回 `"Successfully resized window …"`，而視窗紋風不動。
**如果我沒有在 resize 之後去問一次 `innerWidth`，接下來三十頁的地圖全部會是 1504 的數字
掛在 390 的標題底下** —— 而每一頁的兩向比對都會是 0 差異，因為比對的兩邊來自同一個錯的寬度。

> 一般化：**凡是「改變環境」的呼叫，回報成功之後要再量一次環境本身。**
> 這跟 README 那條「宣告缺陷之前先排除自己」是同一件事的上游 ——
> 那一條講的是量到奇怪的東西之後怎麼辦，這一條講的是**量之前**。

### 掃描器產生候選，量測下判決 —— 而且兩個方向都會錯

#788 要修「取數失敗卻渲染成沒資料」的頁。我先用靜態判準掃全庫
（「有 `catchError` 但沒有失敗訊號」）命中 11 支，labor-8 的量測表列了 7 支。對起來：

|                | 頁                         | 為什麼                                                               |
| -------------- | -------------------------- | -------------------------------------------------------------------- |
| **靜態漏掉 2** | `sessions`、`grades-exams` | 它們用 `subscribe({ error: … })` **不是 `catchError`** —— 選擇器太窄 |
| **靜態誤報 1** | `dashboard`                | 量測顯示它**誠實**（卡片顯示「讀取失敗」），靜態看不出來             |

**兩個方向都錯，而且錯法不同**：漏掉的那兩支在報告上跟「本來就沒有」一模一樣
（跟方法頁那條 `[tabindex]` 同形）；誤報的那一支會讓你去修一個沒壞的東西。

> **靜態掃描的產物是「要去量哪幾頁」，不是「哪幾頁壞了」。**

### 別人的量測表：數清單，不要讀它的結論句

#791 的散文寫「16 頁量到，10 誠實 / 6 有問題」，小標寫「（**5 頁**）」，底下列了 **6** 個名字。
把兩張清單各數一遍：**9 誠實 + 7 有問題 = 16** ——
**正好是它自己說的量測頁數，所以清單對、三個數字全錯。**

而被數字漏掉的那一頁，正是它自己標為 **⛔ 最嚴重**的 `/admin/sessions`。
照「先做 6 頁」做會剛好跳過最嚴重的那一支。

> **判準：對照表裡清單與計數不一致時，信清單。**
> 計數是作者事後寫的散文，清單是量測當下逐筆記的。

### 共用元件要收「不該每頁自己決定的那一半」

#788 的 `app-load-failed`：標題與圖示**寫死**，只有 `description` 是每頁的字。

理由不是省事 —— **「你看到的不是你的資料」對每一頁是同一件事**，
讓每頁自己改字只會讓同一個狀態長出七種說法；而 `description` 必須是每頁的，
因為它要說**是哪一種資料沒讀到**。

拒絕了把三態（載入中／失敗／空）包成一個元件：每頁的空狀態內容都不同，
那要多槽投影 + 改寫七支模板的結構 —— **大 diff、每頁重驗，換到的只是少寫一個 `@if`。**

### 手抄的清單先找編譯期的機制，再退而求其次用 gate

#772 的詞彙表在四個地方各一份。修法（計畫席裁的 C 案）：

1. web 端只留一份 `PERMISSIONS as const`，型別 `(typeof PERMISSIONS)[number]` 從它長出來
2. 選項清單用 `Record<Permission, Meta>` 生成 —— **少一個鍵就編譯失敗**
3. 跨 app 那一層才用 harness gate（A7d）守

**編譯器是比 gate 更早也更便宜的守門** —— 能讓型別系統拒絕的就不要留給 CI。

> 沒有搬進 `packages/`（更漂亮的 A 案）有兩個理由：`shared-types` 檔頭明寫
> 「不要往這裡加新的手寫型別」（計畫席明示不豁免），以及當時 `apps/api`
> 根本 import 不到 `packages/`（#782，已修）。

### 拋棄式探針：把「押注」變成「已知」，而且要能無條件還原

A 案可不可行我沒有用猜的：在**同一個 Bash 呼叫**裡加一個 `PROBE_VOCAB`、
跑 `tsc` 與 `wrangler deploy --dry-run`、**無條件 `cp` 還原**，
證實那條路當時是壞的（形狀見 [[lessons/silent-tool-failures]] 那則）。

**探針要寫成「改完一定還原」的單一指令** —— 分兩次呼叫的話，中間失敗就留下髒東西。

### `tsc --noEmit` 綠不代表模板綠

#788 接第七頁時 `tsc` 全綠，`nx test web` 卻炸
`NG8001: 'app-load-failed' is not a known element` —— `imports` 陣列漏了。

**型別檢查看不到 Angular 模板，只有 Angular compiler 看得到。**
改模板之後一定要跑 `nx test web` 或 build，不要拿 typecheck 當通過。

### 自己寫的每一道 gate 都要塞陷阱 —— 這一輪三道都驗過

A7a2（tsconfig 的 `baseUrl`）、A7c（seed 的權限帳號）、A7d（前後端詞彙表一致）。
每一道都：**先把它要守的東西弄壞 → 確認 `npm run harness` 退出碼 1 且訊息指名 → 還原 → 0。**

⚠️ **退出碼用變數捕捉**（`OUT=$(npm run harness 2>&1); echo $?`）——
接管線拿到的是 `grep` 的退出碼（labor-2 的規則，這一輪靠它擋下一次誤判）。

同樣的紀律適用於**測試**：#788 有六條是修完才寫的，
所以把六支模板的失敗分支拿掉跑一次、**確認六條全紅**才算數。
