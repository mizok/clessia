## 量測這件事的核心紀律：宣告缺陷之前先排除自己

**這一輪四次「看起來是 bug」，四次都是我的量測方式有問題。** 沒有一次是真的缺陷。

| 現象                         | 當下幾乎要送出的結論                     | 真相                                                           |
| ---------------------------- | ---------------------------------------- | -------------------------------------------------------------- |
| 孩子切換器按了沒反應         | 「有 3 個孩子的家長換不了孩子」（P1）    | **我按了兩次**，它是 toggle                                    |
| 課堂列 ⋮ 對兩種狀態回 `null` | 「已完成的列沒有選單」                   | **選擇器抓錯**（是專案自己的 `PopupMenuComponent`）            |
| 停課列的「管理出勤狀況」可按 | 「`PopupMenuComponent` 沒綁 `disabled`」 | **它有綁，還有專門的測試**；那一列的 `eventId` 不是 null       |
| 課程垃圾桶按了沒反應         | 「刪除按鈕沒作用」                       | `[disabled]="group.classes.length > 0"`，20 顆裡 7 顆 disabled |

**擋下每一次的都是同一個動作：去讀那個元件的原始碼，而不是從畫面推論。**

> 畫面告訴你「發生了什麼」，只有原始碼告訴你「為什麼」。
> 而**一支不存在的缺陷，它的成本不是那張單，是它會讓某個人去修一個不存在的東西。**

方法頁的十個坑是這四次的產物；**這一條是坑的上層判準**，所以留在 charter。

## 原生 `window.confirm` / `alert` 絕對不能觸發

`score-entry.component.ts:370` 的 `canDeactivate` 用的是 `window.confirm()`。
**原生 modal 會凍住整個瀏覽器擴充**，之後所有 MCP 指令都收不到，要人去瀏覽器手動關。

動任何「離開前攔截」「刪除確認」之前，先 `grep -n "window.confirm\|window.alert"`。
**碰到了就從原始碼記錄，並在頁內寫明為什麼沒實測。**

（逃生路徑存在：`canDeactivate` 只管 router 導覽，而本 repo `beforeunload` 零註冊，
所以整頁導覽繞得過去。但**沒有值得的東西就不要去試**。）

## 探測動作本身會破壞你要量的狀態

兩個實例，形狀相同：

- 孩子切換器下拉**失焦就關** → 「先按開、下一次工具呼叫再讀 DOM」讀到空的
- 成績登錄的輸入框，**焦點在我的點擊與後續按鍵之間掉了**（`activeElement` 回到 `BODY`），
  所以打不進字、做不出 dirty 狀態、量不到「儲存成績」按鈕

**一次性浮層與需要焦點的東西，要在同一次 `javascript_tool` 呼叫裡讀完**，
或直接截圖存證。做不到就標未驗 —— 試三輪就停手。

## 跨席協作：同儕的結論要驗，尤其是「它在哪裡」這種

labor-2 這一天給了我**三個**有價值的發現（`Origin` 那條、`disabled` 重複、`[tabindex]` 漏報），
**每一個的技術判斷都對**。但它**三次把我的 commit 掛到錯的 PR 號上**
（說在 #707 / 說 #709 還開著，實際分別是 labor-5 的、早就合了）。

**可操作的切法**：同儕訊息裡

- **技術判斷**（「這個選擇器漏了東西」）→ 自己跑一次它引用的指令就能驗，通常是對的
- **狀態宣稱**（「它在 #707 裡」「main 上沒有」）→ **保鮮期極短，一定要自己查**
  （`gh pr view <n> --json state,headRefName`，一次呼叫的事）

反過來也適用：**我給它的資訊裡，「我已經 claim 了哪幾支 `_shared`」也是狀態**，
所以我每次都附上查法而不只是結論。

## 這一輪我自己犯的兩個流程錯，都不是技術問題

### 1. 沒有 PR 的分支等於沒寫

三個 commit 推在 `origin/labor-1` 上、**打算等整組做完再收 PR**，結果 labor-2 要用其中一段方法、
拉 main 零命中才把它逼出來。README 那條我讀過、上一支 PR 還引用過相鄰的規則。

**它的失效是安靜的** —— 沒有人剛好要用的話，它會一直不存在。

**做法：一個選單群做完就開 PR，不要攢。** 攢的理由永遠是「等一下一起交比較整齊」，
而那個「等一下」沒有檢查點。

### 2. 往一支正在等合併的 PR 上疊 commit

`#715` 開出去之後我又推了 `a8bdf384`（`[tabindex]` 修正）。**合併只帶走第一個 commit，
第二個擱淺了。** README 那條「在你控制不了的時序上不要疊東西」我甚至在 PR 留言裡
自己提到了風險，然後照做不誤。

**做法：PR 開出去之後，新東西一律另開一支。** 即使內容相關、即使只有一行。

## 判準：要分辨兩個機制，找「兩種解釋給出相反預測」的那一個情況

magic link 那件的收斂。labor-2 說「只信任 `:4200` 的 port 白名單」，我說「沒有 Origin 就拒」——
**兩種說法都能解釋我們各自量到的兩列**，因為我們都只量了同方向的情況。

分開它們的是第三列（`:4210` + `Origin` → 302）：**它同時否證了兩種說法**。

> 多量幾筆同方向的不會有幫助。**要找的是那個「如果我錯了，結果會相反」的情況。**

這條比「去讀原始碼」泛用 —— 讀原始碼只在有原始碼可讀時成立，而那一列是純黑箱就分得出來的。

## 這個 repo 的兩個程式碼慣例（畫地圖時會一直遇到）

1. **disabled 的選單項會把標籤改寫成理由**，不是灰掉一個動詞：
   `已有歷史課堂，無法刪除`（courses 的班級選單）、`已有報名紀錄，無法刪除`（students，labor-2 觀察）。
   **兩頁獨立出現 ⇒ 是慣例不是個案。**
2. **同一顆按鈕的字在不同頁可能是不同元件**：`/admin/courses` 的「操作紀錄」開
   `AuditLogDialogComponent`（7 頁共用），`/admin/sessions` 的「操作紀錄」開
   `SessionOperationsLogDialogComponent`（自帶兩個分頁）。**照名字併會併錯。**

## 環境（每次開工都要查，不要信交接訊息）

```sh
# 4200 服務的是哪個 checkout
lsof -nP -iTCP:4200 -sTCP:LISTEN -t | head -1 | xargs -I{} lsof -p {} -a -d cwd -Fn | grep '^n'
# 那個 checkout 停在哪一版（可能落後 origin/main 好幾支產品 commit）
git -C <那個路徑> log --oneline -1
```

2026-09-12 實測過一次：4200 服務主 checkout，而主 checkout **落後 origin/main 兩支產品 commit**。
我改用自己 worktree 的 4201 並在每頁記 commit。

**auth cookie 是 host 層級不分 port，三席互踢。** 這一天我被踢兩次（一次變成家長）。
**好消息是失敗很大聲**：`roleGuard` 直接轉走，不會靜靜量到別的角色的頁 ——
但方法頁還是加了「量測前後各打一次 `GET /api/me`」。

被踢了自己產連結（`.dev.vars` 在主 checkout，**沒有 `WEB_URL`，那個在 `wrangler.toml` 的 `[vars]`**）：

```sh
cd <主 checkout> && set -a; . apps/api/.dev.vars; set +a
LOGIN_EMAIL=admin@demo.clessia.app WEB_URL=http://localhost:4201 \
  npx tsx apps/api/src/scripts/login-link.ts
```

**頂層導覽兌換會被 `INVALID_CALLBACK_URL` 擋**（除非 callback 指向 `:4200`）——
從已開啟的頁面用 `fetch(..., {credentials:'include'})` 兌換就會帶上 `Origin`。
