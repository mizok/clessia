# 內部人訪談 2026-08-29 — 金流/聯絡簿/分校現況

受訪者：目標補習班的內部員工（透過傳聲筒轉述）
目的：P1 資料模型的輸入，尤其 fee_templates / invoices / payment_records / meal_records

---
## Q1 收費單位
- **月繳或期繳，家長可自選** → 計費週期掛在「學生的報名」上，不是掛在班上
  （同一個班可以同時有月繳生和期繳生）
- （順帶提前答了 Q9 一部分：可臨櫃、可轉帳）
- 待追問：一期是多長？月繳跟期繳價錢一不一樣？

## Q1a 「期」的定義
- 她公司：一年兩期 —— 「上學期+暑假」「下學期+寒假」
- **老闆（使用者）的產品要求：期要通用化**，不能寫死。可能的形態：
  一年一期（1/1–12/31）、學期制（學期初–學期末，寒暑假另外開班）……
- → schema 含義：「期」不是 enum，是**機構自訂的具名日期區間**
  （admin 建「2026 上學期+暑假」= 2/1–8/31 這種）。月繳是內建的另一種週期。
  不需要 recurrence 引擎 —— 具名日期區間就夠通用。

## Q1b 月繳 vs 期繳的價差
- 期繳比較便宜，**折數看老闆當下心情，每個客人還可能不一樣**
- → schema 含義（重要）：**不要做折扣規則引擎**。
  fee_template 給定價，實際金額是報名/帳單層級的人工覆寫：
  存「定價、實收、調整原因（自由文字）」三欄就涵蓋所有心情折扣。
  結構化的折扣類型（兄弟姊妹折、續讀折）在這間店根本不存在。

## Q2 其他收法
- **要支援買堂數**：小型特殊才藝班用堂數制（買 N 堂慢慢上完）
- 另外「有一些突發特殊狀況」（未展開 —— 佐證 Q1b 的結論：
  金額與形式都要留人工覆寫的空間，不要把規則做死）
- → 計費模式收斂為三種：**月繳 / 期繳（自訂區間）/ 堂數制**
- 堂數制的新需求：要有「剩餘堂數」的概念，出席要能扣堂
- 待追問：堂數有沒有效期？用完/過期怎麼處理？

## Q2a 堂數效期
- 她公司：**沒有效期**；但使用者要求通用設計要能支援
- → 做成可選欄位（nullable `expires_at`），不設就永久有效。一欄搞定，不做規則
- 堂數用完未明確回答 → 預設從寬：不硬擋上課，剩餘堂數 ≤ 0 時警示行政去追補買

## Q3 期中插班
- 期繳：按**當期剩餘比例**收；接近期末時行政會勸客人改月繳（營運慣例，不是系統規則）
- 月繳：也有比例收費原則
- 比例基準有兩種：**剩餘天數** 或 **剩餘堂數**；堂數是按該生實際修的班級的課表算
- → schema/UX 含義：按比例是**試算輔助**不是規則引擎（反正 Q1b 說了金額最後可人工覆寫）。
  開帳單時系統提供「按天數 / 按堂數」兩種試算建議值，行政可改。
  按堂數試算需要 sessions 課表資料 —— 已經有了，接得上。

## Q5 缺課退抵
- 她公司：**不退不抵**；使用者要求通用設計預留空間
- → 不做缺課補償引擎。通用的出口本來就有：下期帳單人工調整（定價/實收/原因）。
  唯一要做的結構化決定在**堂數制**：「請假的那堂扣不扣堂」——一個設定值（org 或班級層級）。

## Q6 退班退費
- 按剩餘比例退，基準同插班：**按天 或 按堂數**
- → 跟 Q3 是同一套試算邏輯的反向 —— 插班算「要收多少」、退班算「要退多少」，
  共用同一個 proration 計算 + 人工覆寫。退費記錄是一筆負向的 payment_record
  （或 refund 類型），要留原因與經手人。

## Q7 憑證
- **只開收據，不開發票**
- → 收款完成要能印一張有編號的收據（瀏覽器列印即可，先例：登入連結卡也是這樣做）
- → **電子發票串接：延後而非排除**（使用者更正：先不考慮，但保留未來空間）。
  保留空間的具體意思：收款記錄存齊發票會需要的資料（金額、日期、付款人、品項），
  不現在做任何串接或抽象 —— 同 Google 登入的處理方式

## Q8 欠繳追討
- 用 LINE 或電話追，**從來沒有停課過**
- → 不做「欠繳自動停課」之類的強制機制。系統要給的是**可見性**：
  欠繳清單（誰、欠多少、欠多久）+ 催繳記錄（何時用什麼方式催過）。
  追討動作本身留在人與人之間 —— LINE 推播（已拍板要做）可以當提醒管道之一。

## Q9 付款方式
- 約 50/50，現金略多；其餘就是轉帳
- 線上金流（LINE Pay / 刷卡 / 金流閘道）：**延後而非排除**（使用者重申）
- → payment_records.method 做成 enum：cash / transfer，之後加值不動 schema

## Q10 轉帳對帳
- 家長回傳**轉帳明細截圖**（走 LINE），行政人工對帳
- → 不做銀行對帳單匯入/自動對帳。payment_record（transfer）支援**附一張憑證圖**
  （Supabase Storage 已在 stack 裡）+ 備註欄（後五碼等）。
  家長端未來可以直接在 app 內上傳截圖取代 LINE 傳圖 —— 歸 P4 再說。

## Q11 分期
- 有，偶爾有家長要求分期
- → schema 關鍵決定：**invoice 與 payment_record 必須是一對多**。
  帳單狀態由「已收總額 vs 應收」推導：未繳 / 部分繳 / 繳清。
  不做排程式分期計畫（第幾期幾號扣多少）—— 就是一張帳單分好幾筆收，每筆記日期金額。

## Q12 多子女合繳
- 現實：家長一筆錢繳兩個小孩，帳記同一筆
- **使用者與內部人都接受系統內拆開記**（per-child）
- → schema 維持簡單：payment_record 屬於單一 invoice（一對多不跨張）。
  一筆合繳 = 行政錄成兩筆、備註同筆轉帳。
  之後頂多在 UX 加「一筆金額分配到多張帳單」的輸入輔助，schema 不變。

## Q13 餐費計算
- 按學生排課表訂便當，**月底結算**：這個月吃了幾個 × 每個便當的價格
- 邊界狀況（重要，人工裁量）：
  - 小孩超過下午 N 點才請假、便當已送到 → **收不收看當下實際情況決定**
  - 提前請假 → 當天就不訂他的便當
- → schema：meal_records = 每生每日一筆（日期、單價、訂了沒、**收不收費**）。
  單價存在每筆上（可能變動），有預設值。
  「收不收」是每筆可翻的開關 —— **不要自動化 N 點截止邏輯**，那是人工裁量。
  月結 = 加總該月「要收費」的筆數金額，生成一張餐費帳單（或併入月帳單）。
  與請假模組的關係：請假只是**提示**行政別訂便當，不自動改 meal_record。

## Q13 補充：有上課 ≠ 有訂餐
- 有學生天天來上課但家長不訂便當
- → 訂餐與出席**解耦**：學生要有一個「訂不訂餐」的預設設定（opt-in），
  排課表只是產生候選名單，不是訂餐名單。每日實際訂單以 meal_record 為準。

## Q14 訂餐記錄現況
- 記在 Excel，**跟點名是不同動作**（行政記餐、老師點名）
- → UI 設計：餐務是獨立的管理端頁面（每日名單勾選），不塞進點名流程。
  操作者是行政不是老師 —— 跟 admin/meals 這個既有空殼頁的定位一致。

## Q15 聯絡簿現況
- 紙本。**班級層級 opt-in**：低年級班有、國中以上的班沒有
- 內容：該生**今天**上課狀況的自由敘述，**不分課堂科目**
- → schema：每生每日一則（student, date, content 自由文字, 作者）。
  班級加一個「使用聯絡簿」開關。不做科目/課堂維度 —— 現實裡就沒有。

## Q16 聯絡簿撰寫
- 帶班老師寫；一天上多個班也是**同一篇**
- → 確認了「每生每日一則」的唯一性（unique: student + date）。
  多位老師可能都碰同一篇 → 就是共同編輯一則，記最後編輯者即可，不做分段作者。
  老師端（P3）要有寫聯絡簿的入口。

## Q17 家長簽名
- 紙本要簽名；**電子版最好也要**
- → 家長端（P4）要有「已閱簽收」動作：記誰、何時按的（家長帳號 + timestamp），
  不做手寫簽名畫板 —— 按鈕簽收就是電子版的簽名。
  管理端/老師端要能看到「哪些還沒簽」。這也是 LINE 推播的天然觸發點（有新聯絡簿 → 推）。

## Q17 補充
- **老師要看得到家長已讀/已簽**（不只管理端）→ 老師端聯絡簿列表直接帶簽收狀態欄

## Q18 分校
- 分校數量不設限（通用設計；現有 campuses 表本來就沒限制）
- **行政人員會跨分校支援**
- → 直接佐證 2026-08-29 拍板的多分校決定：跨頁記憶的統一 filter 是對的，
  而且**分校權限隔離不只是「不急」，做了反而礙事** —— 跨校支援的行政會被擋住。

## Q19 跨分校彙總
- 老闆要看跨分校彙總（全公司營收、各分校比較）
- → 營收報表（admin/reports）要有「全部分校」視角 + 分校維度的比較。
  再次確認 filter 的「全部」選項不能拿掉 —— 全域切換器方案（被否決的 C 案）在這裡會卡住。

## Q20 現有工具與最痛的工作
- Excel + 紙本為主；LINE 群組 = 跟家長溝通，**無法取代**（要共存不是消滅）
- 最痛苦的工作排行：
  1. 人工點名
  2. 餐費
  3. 成績登記（補習班內考試 + 學校段考）
  4. **各科老師的教務日誌**（本次訪談最大發現）：
     - 內容 = 當天教學紀錄 + 要廣播給「有上該堂課的小孩」的作業安排
     - 現行流程：老師紙本寫完 → 拍照傳公司 LINE 群組的該分校該年級相簿
       → 行政再人工轉貼作業到官方 LINE 該分校該年級群組
     - **既有 bug**：廣播粒度是「分校×年級」，不是「班」。小孩沒修自然課，
       但同年級有開自然課 → 也收到自然課作業
- → 含義：
  - 教務日誌 = 班級×日期層級（教學紀錄 + 作業），與聯絡簿（學生×日期）是兩個東西
  - 作業廣播的正確粒度系統天生就有：**班級名冊**。日誌一發布，
    作業自動出現在該班學生的家長端 + LINE 推播 —— 直接治掉「自然課誤報」
  - 行政的二次轉貼整段消失 —— 這是提案時最有力的 before/after 故事
