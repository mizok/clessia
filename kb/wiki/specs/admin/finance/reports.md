# 營收報表

**路徑**: `/admin/reports`
**角色**: Admin + `view_reports` 權限
**分組**: 財務管理

> 2026-08-29 依 [[rules/billing-rules]] 校對。原版（2026-02-13）的功能範圍大致成立 ——
> 這次的修訂主要是把每個數字的定義釘死，並記下一個會安靜出錯的實作陷阱。

## 核心目的

看錢進來多少、還有多少沒收到。

## 權限：`view_reports`，不是 `manage_finance`

兩者是不同的權限（`core/staff.service.ts` 的 union）：`manage_finance`＝改價目表、開帳單、
收款（**寫**）；`view_reports`＝看營收與統計（**唯讀**）。老闆可能只給主任看報表而不給
動錢，所以本頁用 `view_reports`。

`features/admin/pages/dashboard/dashboard.component.ts:157` 的經營區兩張卡已經用這個權限
——**照抄它，不要另立名目**。

## MVP 功能

### 篩選列

- 日期範圍
- 分校
- 課程

### 營收摘要

| 數字     | 定義                                                    |
| -------- | ------------------------------------------------------- |
| 實收     | 區間內 `payment_records` 的正向金額總和                 |
| 退款     | 區間內的負向收款（`refund`）總和，單獨列不要淨額混算    |
| 應收未收 | 區間內開出的帳單應繳總額 − 已收；其中**逾期**的另外標出 |

「應收未收」是 billing-rules 規則 7 的可見性需求在報表層的表現：
知道誰欠、欠多少，但**不觸發任何自動處置**。

### 分組統計

- 依分校
- 依課程
- 依月份

### 匯出

- 依篩選條件匯出 CSV
- 欄位：日期、分校、課程、金額、類型（實收 / 退款）

## 🔴 實作陷阱：不要在前端加總

列表 API 的 `pageSize` 上限多半是 100。抓一頁明細自己加總，會在**量大的月份悄悄少算，
而且錯得沒有任何徵兆** —— 報表看起來完全正常，只是數字是錯的。

→ 每個摘要數字都必須來自**後端的聚合端點**（或至少是可信的 `meta.total` / `meta.sum`）。
這一條是 charter 坑 #4 的實例，也是儀表板 v1 踩過的同一個坑。

## 資料依賴

| 操作 | 資料表                                               |
| ---- | ---------------------------------------------------- |
| 讀取 | `invoices`、`payment_records`、`classes`、`campuses` |

> ✅ **聚合端點已存在**：`GET /api/reports/revenue`（`apps/api/src/routes/reports.ts`，
> 掛在 `/api/reports`，權限 `view_reports`）。管理端頁在
> `apps/web/src/app/features/admin/pages/reports/`，**前端一個數字都不加總**。
>
> **分組的歸屬有兩個明著標出來的模糊桶**（2026-08-30 實作時確認的後端語意）：
> 一張帳單可以跨班（同一個學生修兩科）也可以完全沒有班（純餐費帳單）。後端刻意
> **不做比例拆分**（拆出來的數字沒有人能跟收據對得起來）也**不重複計入多個組**
> （那會讓小計加起來大於總計），而是給 `（跨分校）` / `（跨課程）` / `（未分類）`
> 三個桶。代價是多一列，換來**小計永遠加得回總計**。UI 照實顯示並附說明，
> 不藏也不合併。
>
> **篩選與分組的語意不同**：`campusId` / `courseId` 是「這張帳單有沒有沾到」（任一
> 明細命中就算），分組則是「一張帳單只進一個組」。
>
> ⏳ **「匯出 CSV」還做不了**：spec 要的欄位是明細層（日期、分校、課程、金額、
> 類型），而聚合端點只回摘要與分組小計。要匯出明細得有另一支端點 —— 已回報，未派工。
