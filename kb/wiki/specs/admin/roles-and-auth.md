# 角色與帳號管理規格

> 討論日期：2026-03-19
> 狀態：部分實作（帳號設定 dialog、家長身份啟用已完成）。
> **root 帳號與所有密碼路徑已於 2026-08 移除**，見下方「沒有超級帳號」。

---

## 角色定義

| 角色     | DB 值     | 說明                           |
| -------- | --------- | ------------------------------ |
| 管理者   | `admin`   | 日常營運、系統設定、人員管理   |
| 任課老師 | `teacher` | 課表、點名、學生學習紀錄       |
| 家長     | `parent`  | 查看孩子出缺席、學習進度、繳費 |

一個使用者可同時擁有多個角色（`user_roles` junction table）。

---

## 沒有超級帳號

**這個系統沒有 root、沒有超級管理者、沒有任何「拿不掉的最高權限」。**

曾經有一個 `root`（只存在於 `seed.sql`，本機開發用），已於 2026-08-28 移除。移除的
理由不是它危險，而是**它早就沒有任何實例**：

- 它沒有密碼 —— 密碼登入整條路已刪（`seed.sql` 曾硬編一組 scrypt hash，但那對所有
  客戶是**同一組**，已於 PR #24 移除）
- 它的 `email` 是 NULL，所以 `npm run login-link`（用 email 查人）對它無效
- `bootstrap-org.ts`（乾淨開站的唯一路徑）**從來不建它**

留著一個登不進去、正式站也不存在的「超級帳號」，只會讓讀文件的人以為有後門。
`me.ts` 的 `isRootUser` 與前端對應的判斷一併移除。

> **`ba_user.username` 欄位沒有跟著移除。** username plugin 是走了、它也不再是登入
> 憑證，但只有手機的家長仍把手機存進這個欄位當唯一性鍵（`parents.ts`）。

### 破窗管道

供應商要進客戶的站，用 `npm run login-link`：持有 `DATABASE_URL` 的人才產得出連結，
**客戶換掉 DB 密碼就能撤銷供應商的存取**。這比永久 root 更符合憲法 c12 ——
**後門不該是拿不掉的**。見 [[architecture/line-oauth-login]]。

## 角色獲得流程

### `admin` 管理者

| 情境           | 流程                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| 第一個管理者   | 由 `bootstrap-org.ts` 建立並印出一次性登入連結，預設擁有所有權限          |
| 後續管理者     | 由擁有「**角色管理**」permission 的管理者，在人員管理頁新增並勾選 `admin` |
| 管理者兼任老師 | 由另一個擁有「**角色管理**」permission 的管理者幫他加上 `teacher` 角色    |

### `teacher` 老師

| 情境     | 流程                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 一般老師 | 由擁有「**角色管理**」permission 的管理者，在人員管理頁新增並勾選 `teacher` |

### `parent` 家長

| 情境                            | 流程                                                                                                                                                                 |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一般家長（無帳號）              | 公開報名頁自助註冊，建立帳號並關聯子女                                                                                                                               |
| 內部人員（admin/teacher）兼家長 | **由行政在家長頁一次完成**：新增家長時輸入他的 Email／手機 → 確認「把 ○○ 設為家長」→ 加角色、建家長資料、綁孩子（#1844；見 [[specs/admin/student-affairs/parents]]） |
| 已有帳號卻走報名頁              | 提示「請洽補習班行政把你設為家長」（#1844 起不再有自助啟用）                                                                                                         |

---

## 自助規則

| 角色      | 可以自己加嗎？                  |
| --------- | ------------------------------- |
| `admin`   | 否，只能由他人指派              |
| `teacher` | 否，只能由他人指派              |
| `parent`  | 否，由行政在家長頁設定（#1844） |

~~`parent` 可自助的原因：啟用後只能看自己子女的資料，風險低。~~ #1844（使用者 10-22 選 A）改成不能自助：
自助啟用只建出一筆**沒有孩子**的家長資料，家長自己又不能綁孩子，行政也不知道有人啟用了（列表上只多一個人，
10-22 正式環境還因為名字退路寫成「家長」而找不到人，#1840）。綁孩子本來就只有行政能做，那就一次由行政做完。

## Permission 機制

人員管理表單的「管理權限」勾選項，需新增：

| Permission     | 說明                               |
| -------------- | ---------------------------------- |
| `manage_roles` | 可在人員管理頁修改他人的角色與權限 |

沒有 `manage_roles` 的管理者，人員管理頁只能查看，不能修改角色。

## ~~家長身份啟用流程~~（#1844 移除）

原本：個人帳號設定 →「啟用家長身份」→ `POST /api/me/activate-parent` 在 `user_roles` 加 `parent`、
建一筆沒有孩子的家長資料。**#1844 把按鈕與端點一起拿掉**，改由行政在家長頁做（流程見
[[specs/admin/student-affairs/parents]]「新增家長：Email／手機已是本機構教職員的帳號」）。

一起移除的：`account-settings-dialog` 的按鈕、確認框與 `activateParent()`；`AuthService.adoptRoles()`（只有它在用）；
`routes/me.ts` 的端點與 `me-identity-cache.spec.ts` 裡 activate-parent 的測試、`index.spec.ts` 的那支；
`lib/identity-cache.ts` 與 `architecture/authorization-scope.md` 提到它的句子。
`invalidateIdentity` 留著（`PATCH /api/me` 還在用），家長頁設為家長的那條路徑也要呼叫它。

## 公開報名頁邏輯（待實作）

1. 家長填寫基本資料（姓名、email 或手機）
2. 系統檢查 email/phone 是否已存在
   - **已存在** → 提示「帳號已存在，請洽補習班行政把你設為家長」（#1844 起沒有自助啟用）
   - **不存在** → 建立新帳號，賦予 `parent` 角色，進入關聯子女流程
3. 完成後可登入家長 portal
