# 取數失敗要有自己的畫面狀態（#788）

> **狀態：計畫席已批准（2026-09-13），範圍以 #791 的量測對照表為準。**

## 問題

取數失敗時，有些頁面把主體渲染成**「尚未有資料」**，而唯一的錯誤訊號是**會自己消失的 toast**。
幾秒之後畫面上只剩「這個補習班還沒有學生」，外加一顆邀請你手動新增的按鈕（#788 量到）。

**錯的那一半還附了行動呼籲** —— 使用者照做就會建出重複資料。

## 根因：`EMPTY` 讓兩種結局共用同一個狀態

```ts
catchError((err) => {
  this.messageService.add({ severity: 'error', summary: '載入失敗', detail: '無法載入學生列表' });
  return EMPTY; // ← subscribe 不執行 → 陣列維持初始的 [] → 走空狀態分支
});
```

畫面只看得到 `rows().length === 0`，而那個 0 有兩個來源。

> ⚠️ **`return EMPTY` 本身不是 bug，不要拆掉它。**
> `students.page.ts:229` 的註解寫著它是 **#689 的修法**：`catchError` 必須在內層，
> 一次網路錯誤才不會終止整條管線、讓這一頁再也載不了任何東西。
> **修法必須是加法** —— 在同一個 `catchError` 裡多設一個失敗訊號，其餘不動。

## 正例已經在 repo 裡

`/admin/payments`：`failed = signal(false)`（`payments.page.ts:105`），
模板 `@if (loading) … @else if (failed()) …` 渲染

```
載入失敗 / 沒有讀到帳單資料，可能是連線問題   [重試]
```

**修法不需要新設計，照它。**

## 範圍：以 #791 的**量測**對照表為準，不是以我的靜態掃描為準

計畫席裁定（2026-09-13）：**以 #791 的對照表為清單**，先接上面的頁，其餘等 labor-7 鋪完再補。

### #791 的清單是 7 頁，不是 6 頁

那支 issue 的散文寫「16 頁量到，10 誠實 / 6 有問題」、小標寫「🔴 謊稱沒資料（5 頁）」，
**但底下列了 6 個名字**。把兩張清單數出來：

|                | 列出的名字                                                                                    | 篇數     |
| -------------- | --------------------------------------------------------------------------------------------- | -------- |
| ✅ 誠實        | payments、contact-book、meals、reports、dashboard、enrollments、leave、notifications、changes | **9**    |
| 🔴 / ⛔ 有問題 | **sessions**、courses、students、parents、staff、fee-templates、grades-exams                  | **7**    |
| 合計           |                                                                                               | **16** ✓ |

**合計正好是它自己說的 16，所以清單是對的、散文的數字是錯的。**
而被數字漏掉的那一頁正好是它自己標為 **⛔ 最嚴重**的 `/admin/sessions`
（5 個請求全失敗，畫面只說「此期間沒有課堂」，**沒有 toast、沒有 empty-state、沒有任何錯誤字樣**）。

**所以這一支做 7 頁。**

### 🔴 我的靜態掃描兩個方向都錯過 —— 它是候選產生器，不是判決

動手前我用「有 `catchError` 但沒有失敗訊號」掃全庫，命中 11 支。對照 #791 的量測結果：

|            | 頁                                                                         | 為什麼                                                                    |
| ---------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **漏掉 2** | `sessions`、`grades-exams`                                                 | 它們用 `subscribe({ error: … })`，**不是 `catchError`** —— 我的選擇器太窄 |
| **誤報 1** | `dashboard`                                                                | 量測顯示它是**誠實**的（卡片顯示「讀取失敗」而不是 `0`），靜態看不出來    |
| 未被量測   | `campuses`、`schools`、`class-view`、`student-view`、`school-score-editor` | #791 沒量到這幾支                                                         |

> **「選擇器太窄」跟 UI 地圖方法頁那條 `[tabindex]` 的教訓同形** ——
> 掃描器漏掉的東西，在報告上跟「本來就沒有」長得一模一樣。
>
> **結論：靜態掃描拿來產生候選，量測拿來下判決。** 那 5 支未被量測的留給 labor-7 的下一輪。

## 設計

### 共用的那一塊：`app-load-failed`

一支薄元件，內部就是 `app-empty-state` 的「載入失敗」變體加一顆重試鈕：

```html
<app-load-failed description="沒有讀到學生資料，可能是連線問題" (retry)="load()" />
```

```ts
@Component({ selector: 'app-load-failed', standalone: true, imports: [EmptyStateComponent, ButtonModule], … })
export class LoadFailedComponent {
  readonly description = input.required<string>();
  readonly retry = output<void>();
}
```

**標題與圖示由元件寫死**（`載入失敗` / `pi pi-exclamation-circle`），
只有 `description` 是每頁的字 —— 因為那一句要說**是哪一種資料沒讀到**。

### 每頁接上（兩處，加法）

```ts
protected readonly failed = signal(false);          // ①
// …
catchError((err) => {
  this.failed.set(true);                            // ② 加一行，EMPTY 照舊
  return EMPTY;
})
```

```html
@if (failed()) { @* ③ 擺在空狀態分支之前 *@
<app-load-failed description="沒有讀到學生資料，可能是連線問題" (retry)="load()" />
} @else if (rows().length === 0) { …原本的空狀態，一字不動… }
```

**每次重新載入要先 `failed.set(false)`**（照 `payments.page.ts:260`）。

### 拒絕的替代方案

| 方案                                                                   | 為什麼不                                                                                                                                     |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **把三態（載入中／失敗／空）收進一個 `app-load-state` 包住整個內容區** | 每一頁的空狀態內容都不同，要多槽 content projection；而且它會改寫 11 支模板的結構 —— **大 diff、每一頁都要重新驗**，換到的只是少寫一個 `@if` |
| **在 service 層統一攔截並轉成錯誤狀態**                                | 錯誤狀態是**畫面**的概念，service 不知道哪一頁要怎麼呈現；而且會跟 #689 的「內層 catchError」打架                                            |
| **只改 toast（延長／改成常駐）**                                       | 不解決主體說謊的問題。**錯的畫面留著、對的訊號消失**才是 P1 的成因                                                                           |

### toast 要不要留？

**建議拿掉載入失敗的 toast。** 正例（payments）沒有 toast，而主體已經是常駐的、
帶重試的錯誤狀態 —— 再加一則會消失的 toast 只是噪音。

**這是行為改變，需要裁示。** 要留的話我照留，兩者不衝突。

## 影響到的既有元件

| 元件                            | 影響                                          |
| ------------------------------- | --------------------------------------------- |
| `shared/components/empty-state` | **不動** —— `app-load-failed` 包它            |
| 11 支頁面                       | 各加一個 signal、一行 `set(true)`、一段 `@if` |
| `#689` 的管線修法               | **不動** —— `EMPTY` 照舊回                    |
| toast                           | 視裁示                                        |

## 明確不做什麼

- **不動載入中那一半**（工單末段記的「切篩選時 3 秒沒有任何反應」）——
  那是另一個形狀（skeleton / disabled），而且 #760 還沒量完。
- **不碰 `features/parent` 與 `features/teacher`** —— 掃描顯示它們沒有這個形狀
  （家長端三頁工單量過，是**對的**那一組）。
- **不碰那 5 支「靜態命中但沒有被量測」的頁** —— 等 labor-7 鋪完 #760 再補（計畫席裁定）。
- **不碰 `dashboard`** —— 量測顯示它是誠實的，我的靜態掃描誤報了它。

## 驗證計畫（修前紅）

| 順序 | 動作                                                                  | 預期         |
| ---- | --------------------------------------------------------------------- | ------------ |
| 1    | 挑 `students` 寫一條 spec：取數失敗時**不渲染空狀態、要渲染載入失敗** | **紅**       |
| 2    | 加 `app-load-failed` + 該頁接上                                       | 轉綠         |
| 3    | 其餘各頁比照，每頁一條同形的 spec                                     | 各自先紅後綠 |
| 4    | `npx nx affected -t typecheck,test`                                   | 綠           |

**每一頁都要有自己的那條測試** —— 這一族的教訓就是「一頁對不代表另一頁對」。

## 風險

- **11 支頁面的模板都會多一個分支** —— 測試要蓋到，否則下一次重構可能把它拿掉而沒有人發現。
  所以每頁一條 spec，不是只測共用元件。
- 使用者會**第一次看到**這些頁面的失敗狀態（以前被偽裝成空狀態）——
  那正是目的，但客服會收到「這個畫面以前沒看過」的回報。
