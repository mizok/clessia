# LINE 登入的設計

## 為什麼要改

兩個原本無關的問題指向同一個解法。

### 一、密碼雜湊跑不動

2026-08-24 首次上線後，登入**間歇性失敗**——大約每三到五次壞一次，重試又會好。
Worker log 給出直接答案：

```
13x  EXC: Worker exceeded CPU time limit.
```

Better Auth 預設用 scrypt 驗證密碼。scrypt **刻意設計成昂貴**——那正是它防暴力破解的
原理，大約消耗 50–200ms CPU。而 Cloudflare Workers **免費方案每個請求只有 10ms CPU**。

實測（真帳號 + 錯密碼，取並發批次）：

| 並發 | 成功 | 503 |
| ---- | ---- | --- |
| 1    | 0    | 1   |
| 3    | 2    | 1   |
| 5    | 4    | 1   |
| 10   | 6    | 4   |
| 40   | 31   | 9   |

**並發 1 也會失敗**——這不是負載問題，是每次登入都在賭。

這無法靠改程式碼修好。任何安全的密碼雜湊都會超過 10ms，**那是它們存在的意義**；
快到能塞進 10ms 的雜湊等於沒有保護。只有兩條路：升級付費方案（每月 5 美元，
CPU 上限變 30 秒），或**讓日常登入路徑不再做密碼雜湊**。

### 二、家長不一定有 email

先前已確立的事實：補習班家長裡有隔代教養家庭，阿公阿嬤有手機但不一定有 email。
既有做法是用手機合成佔位 email（`0912345678@phone.internal`，見
`PLACEHOLDER_EMAIL_DOMAIN`），可用但等於還是要記一組密碼。

**LINE 同時解掉這兩件事**：OAuth 沒有密碼要雜湊（CPU 從 50–200ms 降到約 1ms 的
簽章驗證），而台灣家長人手一個 LINE，包含最不會用 email 的那一群。

## 決策

### 一、密碼登入完全移除，破窗走 CLI 產生的一次性連結

**所有角色（admin / teacher / parent）只有 OAuth 一種登入方式。** 沒有任何密碼路徑，
scrypt 因此從整個系統消失，10ms 的 CPU 限制不再被觸及。

原本的規劃是「root 保留密碼當破窗管道」。2026-08-24 的 drift 稽核推翻了它：

- `ROOT_PASSWORD` 這個環境變數**只存在於文件裡**，不在 `Bindings`、不在 `wrangler.toml`、
  不在任何 `.ts`
- 實際的 root 來自 `supabase/seed.sql` **硬編的 scrypt hash** —— 意思是**每個從 seed 開的站，
  root 密碼都一樣**。一間補習班的資料庫外洩，等於所有客戶的最高權限一起外洩
- 而 `bootstrap-org.ts`（乾淨開站的唯一路徑）**根本不建 root**

所以那個「安全網」在乾淨部署上不存在，在 seed 部署上則是個跨客戶的共用秘密。

**改成：持有 `DATABASE_URL` 的人，用 CLI 產生一次性、短效期的管理員登入連結。**

|                        | 為什麼                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **不增加攻擊面**       | 能拿到 `DATABASE_URL` 的人本來就掌握全部資料。用它換一個 session，不新增任何能力；而一組永久密碼會新增一個可被猜測、外洩、重複使用的秘密 |
| **客戶切得斷**         | 換掉 `DATABASE_URL`，供應商的存取就沒了。**這正是 c12 要的** —— 客戶拿不掉的永久後門與「客戶必須能脫離」直接衝突                         |
| **零 scrypt**          | 破窗路徑也不做密碼雜湊                                                                                                                   |
| **幾乎不用多寫程式碼** | 綁定連結本來就需要「一次性 token → 兌換 → 建立 session」整套。破窗只是同一套機制的第二個用途                                             |

同一支 CLI 服務三件事：**第一個管理員的登入連結**（取代 `bootstrap-org.ts` 現在印密碼的行為）、
**破窗恢復**、**重發弄丟的綁定連結**。

**明確接受的代價**：客戶自架、換掉 DB 密碼、然後營運人員忘記帳號 —— 這時供應商進不去。
這是正確的行為：他們已經離開了，不該還有鑰匙。

### 二、先做 LINE，Google 延後

台灣家長 100% 有 LINE，包含隔代教養的長輩；Google 帳號在同一群人身上覆蓋率明顯較低。
先做一個 provider 讓客戶上線少一個卡點（每個部署都要自己申請憑證，見下方 c12 影響）。

**Google 是延後，不是排除。** 員工用 Google 登入比 LINE 順（辦公室電腦、已登入的
瀏覽器），之後應該會加。Better Auth 內建數十個 provider（`line` 與 `google` 都在內），
加一組設定與一顆按鈕即可。

因此本次的實作**不得寫死成「只有 LINE」**：provider 清單、登入按鈕、綁定流程都要能
容納第二個 provider，否則加 Google 時得回頭重做。這是本設計的一條約束，不是選配。

### 三、帳號不是報名的前提，是成交之後的產物

| 階段                     | 需要帳號     | 理由                                                   |
| ------------------------ | ------------ | ------------------------------------------------------ |
| 詢問、試聽、填報名表     | 否           | 人還沒決定要不要來，要求交出身分與個資會直接殺掉詢問量 |
| 實際入學、繳費           | 否           | 臨櫃處理，家長不必碰系統                               |
| 自己查出缺席／成績／繳費 | **這時才綁** | 有東西可看了，才有理由登入                             |

對補習班而言**潛在客戶比帳號重要**。這條原則排除了「報名第一步先 LINE 登入」
這種常見但錯誤的設計。

### 四、綁定用一次性連結／QR，一個機制對應三種來源

LINE 只會告訴系統「這是 LINE 使用者 U1234」，**不會告訴系統他是誰的家長**。
兩者之間需要一次由校方背書的對應。

| 家長怎麼進到系統                     | 綁定怎麼發生                                    |
| ------------------------------------ | ----------------------------------------------- |
| 臨櫃註冊（行政人員代填，**主流程**） | 註冊完成的畫面直接顯示 QR，家長當場拿自己手機掃 |
| 家長自己線上填表                     | 校方確認後發出綁定連結                          |
| Excel 批次匯入舊生                   | 產生一批連結，行政人員個別或群組發送            |

**臨櫃掃 QR 是成功率最高的時刻**——家長本人就站在旁邊，有真人可以帶著操作，
長輩不需要看懂連結或自己完成任何步驟。錯過這個時刻就得靠事後追。

連結**必須可重發**：一定會有人弄丟、換手機、或當下說「我回家再用」然後忘記。

員工（20 人上下）走同一套機制。人少，不值得為此另建一套。

### 五、沒綁定是合法且永久的狀態

**這個系統絕對不能設計成「家長沒登入就無法運作」。**

- 阿嬤永遠沒綁 → 她看不到出缺席、成績、通知
- **補習班的運作完全不受影響**——學生照樣報名、點名、考試、繳費
- 要聯絡她就用原本的方式（電話、LINE 群組、聯絡簿）
- 她的資料在系統裡是完整的，只是她本人沒有登入管道

如果報名、繳費、點名任何一環卡在「家長必須先綁定」，補習班第一天就會退回紙本。

## 實作靠現成的東西，不自己刻

2026-08-24 查證 Better Auth 1.5.5 的型別定義後（本專案有過假設 SDK 方法存在而繞遠路的
紀錄，見 [[lessons/better-auth-session-delegation]]），原本估計要自建的東西**全部是內建的**：

| 需求                   | 現成的機制                                                             |
| ---------------------- | ---------------------------------------------------------------------- |
| LINE OAuth             | `socialProviders.line`（`@better-auth/core` 內建，與 `google` 同一組） |
| 一次性綁定連結         | `magic-link` plugin 的 `POST /api/auth/sign-in/magic-link`             |
| 兌換連結、建立 session | `GET /api/auth/magic-link/verify`                                      |
| 把 LINE 綁到既有帳號   | `POST /api/auth/link-social`                                           |
| 破窗 CLI               | 同一支 magic-link                                                      |

**關鍵在 `sendMagicLink` 這個 callback**：它收到 `{ email, url, token }`。一般用法是把 `url`
寄出去，**我們不寄信 —— 直接把 `url` 攔下來**，變成畫面上的 QR、可複製的連結、或 CLI 的
stdout。同一個機制服務三種送達方式。

因此：

- **不需要新的 migration** —— token 存在既有的 `ba_verification` 表
- **不需要自寫兌換端點** —— `magic-link/verify` 已經處理過期、單次使用（`allowedAttempts`
  預設 1）、以及 session 建立
- `disableSignUp: true` 防止綁定連結被拿來建新帳號

> ⚠️ **magic-link 需要一個 email 當識別碼。** 家長的佔位 email（`0912345678@phone.internal`）
> 完全夠用 —— 那個 domain 不存在於公開網路，而我們本來就不寄信。

## 拒絕的替代方案

| 方案                                   | 為什麼不                                                                                                                                                                                                                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **升級 Workers 付費方案**              | 每月 5 美元其實便宜，而且客戶自付。但 OAuth 同時解掉家長無 email 的問題，而且 API 除了雜湊之外全部是 I/O 密集（依賴裡沒有 xlsx / pdfmake / 加密運算，Excel 與 PDF 都在瀏覽器做），拿掉 scrypt 後很可能真的塞得進 10ms。**若上線後量測顯示仍會超，該付就付**——那時是用數據決定，不是猜 |
| **調弱 scrypt 參數**                   | 塞得進 10ms 的密碼雜湊等於沒有保護。用安全性換 CPU 是最糟的交易                                                                                                                                                                                                                       |
| **LINE 登入後填手機比對既有記錄**      | 知道別人手機就能冒名頂替。要補這個洞得加簡訊驗證，那會引入新的付費服務——與省下訂閱費的初衷矛盾                                                                                                                                                                                        |
| **管理員逐一手動綁定**                 | 每個新家長都要人工介入，且首次登入的人會卡在一個沒有出口的狀態                                                                                                                                                                                                                        |
| **保留密碼登入當作 LINE 的備援**       | 只要密碼路徑還在，scrypt 就還在，CPU 問題原封不動。**備援等於沒改**                                                                                                                                                                                                                   |
| **保留一個永久的 root 超級帳號當後門** | 現行的 root 密碼硬編在 `seed.sql`，**所有客戶共用同一組** —— 一處外洩全部淪陷。就算改成每個部署各自產生，它仍是客戶**拿不掉**的永久最高權限，與 c12「客戶必須能夠脫離」直接衝突。供應商需要的存取，用已經持有的 `DATABASE_URL` 換一次性 session 就足夠，不必多保管一組秘密            |

## 對憲法 c12 的影響

c12 要求客戶能自己脫離架構、自行 host。這次的設計在兩處直接服務 c12：

1. **OAuth 憑證是每個部署自己的** —— 客戶自架就得自己申請 LINE Developers channel
   與 callback URL。多一個上線步驟，但沒有綁死在供應商的任何東西上
2. **供應商的存取是客戶可撤銷的** —— 破窗用 `DATABASE_URL` 換 session，客戶換掉密碼
   就切斷了。這比原本規劃的永久 root 帳號更符合 c12：**後門不該是拿不掉的**

這**不違反** c12（沒有綁死在任何單一供應商的專屬服務上，LINE 是客戶自己的帳號），
但**新增了一個上線步驟**，必須寫進 `bootstrapping-a-deployment.md`。

## 實作時做的取捨

| 決定                                        | 為什麼                                                                                                                                                                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `angularx-qrcode` 釘在 **21.x**             | 最新的 22.x 要 Angular 22，本專案是 21。**Angular 22 的升級刻意延後成獨立的 PR** —— Signal Forms 值得升，但把框架大版號混進認證重寫會讓 PR 沒人審得動、也沒辦法乾淨 revert。而且 PrimeNG 21→22 才是主要風險（幾乎每一頁都在用） |
| 移除 `pdfmake`                              | 帳號資訊卡在有密碼的年代合理（一張可以帶走的紙）。登入連結太長，沒有人會用手打 —— 它只有配 QR 才有意義，而 QR 已經在畫面上。改用瀏覽器內建列印，順帶少一個 CommonJS 依賴                                                        |
| `qrcode` 列入 `allowedCommonJsDependencies` | 它是 `angularx-qrcode` 的 transitive dep。不列的話每次建置都有警告，而長期存在的警告會讓人不再看警告                                                                                                                            |

## 未解的問題

- **公開報名端點不存在** —— `/enrollment`、`/trial` 前端頁面是空殼，後端只有 ADMIN_ONLY。
  招生宣傳來的家長按下「還沒報名？前往報名」會落在空頁面。**招生漏斗的入口是斷的**
- **`ba_user.orgId` 是 nullable** —— `decideLoginLinkTarget()` 因此不能用 `===` 比較。
  根本問題是那個欄位允許 NULL，但改它要動 schema
- **better-auth 版本歪斜** —— web 解析到 root 的 1.4.18，`apps/api` 是 1.5.5。
  根因是 `apps/api/package.json` 把版本寫成 `"latest"`，那本身就不可重現

## 明確不做

- **公開報名端點**——目前 `/api/enrollments` 是 ADMIN_ONLY，臨櫃註冊是刻意的主流程。線上自助報名是另一個切片
- **簡訊驗證**——會引入付費服務
- **Google 登入**——**延後而非排除**，架構要預留（見上方決策二）
- **既有密碼帳號的遷移**——正式站資料庫是空的（本機 `seed.sql` 另有 demo 資料），沒有既有帳號要遷移
- **LINE 訊息推播**——通知管道是獨立決策，跟登入無關

## 已知風險

| 風險                              | 說明                                                                                                                                                                                                                                                                                                        |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **LINE 服務中斷 = 全員登不進去**  | root 是唯一的破窗管道。這是刻意接受的取捨，但要讓客戶知道                                                                                                                                                                                                                                                   |
| **拿掉 scrypt 後仍可能超過 10ms** | 未經量測。目前資料庫是空的，量不到真實負載下的 Zod 驗證與 JSON 序列化成本。**上線後要實際量**，超了就升級付費方案                                                                                                                                                                                           |
| **綁定連結外洩等於帳號被奪**      | 一次性、要過期。細節在強制機制層決定，不在本文                                                                                                                                                                                                                                                              |
| **連線池從未關閉**                | `createAuth()` 每次都 `new Pool()` 且沒有任何一處 `.end()`（全 repo 唯一的 `.end()` 在一次性腳本 `bootstrap-org.ts`）。呼叫點散落在 `index.ts` / `middleware/auth.ts` / `parents.ts` / `staff.ts`，其中 `authMiddleware` 每支 `/api/*` 都跑。**與本次改動無關的既有缺陷**，但會在真實負載下咬人，應另案處理 |
