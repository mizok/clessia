# 分校資料隔離 —— 現況是沒有

> 使用者 2026-09-02：「理論上分校的資料隔離必須要設計權限。」
>
> **這一頁是需求與現況的紀錄，不是已實作的設計。** 起因是日到班看板
> （[[architecture/daily-checkin-board]]）要按分校列出未到班學生，一問之下發現
> 底下沒有地基。

## 現況：資料模型有，授權沒有

| 層             | 現況                                                                                    |
| -------------- | --------------------------------------------------------------------------------------- |
| 資料模型       | `staff_campuses (staff_id, campus_id)` **存在**（`20260215100000_create_staff.sql:17`） |
| authMiddleware | 掛上 `userId` / `orgId` / `roles` / `permissions` / `supabase` —— **沒有 campus**       |
| 各路由         | 一律只用 `org_id` 過濾（憲法 c1）。**campus 不在授權的詞彙裡**                          |

淨結果：**任何管理員都看得到所有分校的資料。** 分校主任看得到別校的收入、名單、
出勤，也改得動。

`staff_campuses` 目前只被三個地方讀，而且都是**業務規則不是資料隔離**：

| 位置                    | 用途                     |
| ----------------------- | ------------------------ |
| `announcements.ts:159`  | 公告要發給哪些分校的人   |
| `staff.ts`（多處）      | 員工的分校指派 CRUD      |
| `sessions.ts:1253,1740` | 代課老師是不是這個分校的 |

沒有任何一支查詢會因為「你不屬於這個分校」而少回一列。

## 為什麼不能在單一功能裡解

在到班看板裡自己做一層分校過濾，會得到**一個守得住的畫面，和其餘全部守不住的畫面**
—— 而使用者無從分辨哪些是哪些。那比全都不守更糟：它讓人相信系統有分校隔離。

隔離要成立就得**每一支路由都成立**，這正是憲法 c1 把授權收斂到 Hono middleware
的理由：`org_id` 過濾之所以可信，是因為它沒有例外。**分校要的是同一種待遇，
不是第二種做法。**

## 形狀（未實作，供將來的設計參考）

1. `authMiddleware` 多查一次 `staff_campuses`，把 `campusIds: string[] | null` 掛進
   context（與 roles / permissions 同一批平行查詢，不多一次往返）。
2. 一支 `scopeToCampuses(query, c)` helper，各路由在既有的 `.eq('org_id', orgId)`
   之後接上去。跟 c1 一樣，**沒有例外才可信**。
3. 請求帶 `campusId` 參數時（例如看板），驗證它在允許清單裡，不在就 403 ——
   不是默默回空陣列。默默回空會讓越權嘗試看起來像「那天沒人」。

### 誰算是跨分校，需要業務裁決

| 選項                                               | 說明                                                                                             | 風險                                                                                                                                      |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **建議**：用權限（`*` 或新增 `view_all_campuses`） | 明確宣告，與 `requirePermission` 的 fail-closed 慣例一致；bootstrap 建的第一個管理員拿的就是 `*` | 上線前要先補既有管理員的權限或分校列                                                                                                      |
| 沒有 `staff_campuses` 列 = 看得到全部              | 不用改資料                                                                                       | **fail-open** —— 而 `bootstrap-org.util.ts:58` 明說「沒有列就是還沒指派」，把「還沒指派」讀成「全部看得到」正好是授權的洞最常長出來的地方 |

**上線順序是真風險**：既有機構的管理員多半沒有 `staff_campuses` 列。直接套
fail-closed 規則的話，他們隔天登入會看到一片空白 —— 不是報錯，是空資料，
最難診斷的那一種。**遷移要先補資料再開開關。**

## 這一頁不主張什麼

- 不主張現在就做。它比任何一支功能都大，該獨立成一刀。
- 不主張改 RLS。業務表刻意 fail-closed 沒有 policy，API 走 service role
  （c1）—— 分校隔離跟 org 隔離一樣，是 middleware 的事，不是 RLS 的事。
- 不裁決「誰算跨分校」。見上表。

## 在它落地之前，功能該怎麼寫

**不要自己做一半。** 該做的是不要擋路：

- 帶 `campusId` 的端點就照收，等 middleware 那層長出來時它自然被驗證
- 畫面上**依分校分組**而不是「先選分校再看」 —— 分組在隔離前後都對：
  沒有隔離時管理者看到全部分校各自的缺口；有隔離之後他只會拿到自己那組，
  同一段 UI 不用改
