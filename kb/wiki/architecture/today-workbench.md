# 今天的作業台 —— 一個頁面，兩種形狀

> **這是設計，還沒實作。** 依 `clessia-feature-slice` 的 STOP gate：計畫席初審 +
> 使用者批准之後才寫產品碼。
>
> 這一份**整併**了原本的兩份設計：作業台（A 提案）與日到班看板（B 提案）。
> `daily-checkin-board.md` 由這一頁取代 —— 它們是同一件事的兩面。

## 一句話

**作業台回答「今天有什麼要我處理」，而 `attendanceMode` 決定那件事長什麼樣子。**

| 模式            | 今天要處理的事     | 作業台的形狀                                       |
| --------------- | ------------------ | -------------------------------------------------- |
| `per_session`   | 每一堂課要點名     | **逐堂脊椎**：今天的課由上而下排開，每一堂就地點名 |
| `daily_checkin` | 誰今天該來但還沒到 | **到班看板**：還沒到的人排在最上面，就地勾到班     |

## 為什麼是一個頁面，不是兩個

因為**使用者的問題是同一個**：「我今天要做什麼？」。兩個模式的差別在於補習班怎麼
記錄出席，不在於行政早上打開系統想知道什麼。

做成兩個獨立頁的代價，現況已經示範過了：

- 儀表板**刻意隱藏**日到班模式的「未點名課堂」卡（`dashboard.util.ts` 的
  `countUntakenSessions` 非 per_session 時回 `null`）—— 等於把功能挖掉卻不給替代品
- 但橘帶仍然說「今天 N 堂課，其中 M 堂還沒點名」、課表列仍掛「未點名」chip

**畫面報一個在這間補習班的設定下不存在的問題，拿掉了修它的捷徑，再把使用者導到
一個用不同模型運作的頁面。** 那正是兩個獨立頁會長出來的東西。

一個頁面兩種形狀還有一個實際好處：**兩邊共用同一套資料取用、同一套時窗政策、
同一套分校範圍**。分家的話這三樣會各長一份，然後其中一份會忘記更新。

### 打卡與出勤：已經有答案了，而且已經出貨

我 2026-09-02 拿選項題問使用者時，得到的答案是「**只認 `daily_checkins`，不寫課堂
出勤**」，「只寫他有報名的課」當時一併被否掉。**那個版本已經過期。**

2026-09-03 使用者裁的是**過濾後寫入**，而且已經在 main：

| 證據                | 內容                                                                                   |
| ------------------- | -------------------------------------------------------------------------------------- |
| `#178`（`fe6d859`） | `daily-checkins.ts` 改成只替**當天實際在籍**的課堂寫 `present`，在籍條件與點名名單同源 |
| 程式碼註解          | 「使用者 2026-09-03 裁定」                                                             |
| `#182`（`29d9957`） | `kb/wiki/rules/attendance-rules.md` 第 5、6 節把它寫成規則                             |

**所以這份設計照「過濾後寫入」走**，不是我原本寫的「完全不寫」。

**這讓三處下游全部不需要動**（原本在「完全不寫」之下會靜默失效）：

|                                      | 在「完全不寫」之下                   | 在**已出貨的「過濾後寫入」**之下                   |
| ------------------------------------ | ------------------------------------ | -------------------------------------------------- |
| `session-packs` 的堂數扣課           | 歸零，要改讀 `daily_checkins`        | **照常運作**，而且比以前正確（不再算到沒報名的班） |
| `checkEnrollmentAttendance` 刪除守門 | 失效                                 | **照常運作**                                       |
| 請假折抵 `leave_deducts_session`     | 永遠不扣，要從 `leave_requests` 推導 | **照常運作**（`leaves.ts` 寫的 `on_leave` 仍在）   |

> 這一段留著不刪，因為它記錄的是**「完全不寫」那條路的代價**。哪天有人再提
> 「日到班乾脆別碰 `attendance_records`」，這三處就是要先看的。

**「過濾後寫入」仍然留下一個真的邊界，值得寫下來但不擋這一刀**：學生早上打卡、
晚上那堂課之前就走了，系統仍然替晚課寫 `present`，而**沒有任何人判斷過那件事**。
`attendance-rules.md` 第 6 節寫的是「沒有紀錄 ≠ 缺席」，這是它的鏡像 ——
**有紀錄 ≠ 有人判斷過**。

現有的緩解是對的、也夠用：`recorded_by_role = 'system'` 把機器寫的跟人寫的分開，
而掃碼**撞到既有紀錄一律跳過**（規則 5：機器不推翻人）。作業台不需要為這件事
做任何事，但**它決定了看板該顯示什麼**：勾完之後那一列顯示「已到班 09:12」，
**不顯示「已為 N 堂課記錄出席」** —— 後者是機器的推論，不是觀察到的事實。

## 構圖

```
┌─────────────────────────────────────────────────────────┐
│ 橘帶（可收合）                                            │
│   「今天 8 堂課，其中 5 堂還沒點名」                        │
│   ─ per_session：一日時間軸                               │
│   ─ daily_checkin：已到 12 / 應到 15 的進度               │
├──────────────────────────────┬──────────────────────────┤
│ 左欄：今天的脊椎（主軸）        │ 右欄：待處理與脈絡         │
│                              │                          │
│ per_session：                 │  逾期未點名 N            │
│   09:00 數學班A  [點名]       │  今日請假 M              │
│   09:30 自然班C  已點名       │  本月新生 / 在學人數      │
│   11:00 數學班A  [點名]       │  成績待登錄               │
│                              │                          │
│ daily_checkin：               │                          │
│   還沒到（3）                  │                          │
│     林小明 七年級 [勾到班]     │                          │
│   已請假（1）                  │                          │
│   已到（12）  ▸收合            │                          │
└──────────────────────────────┴──────────────────────────┘
```

**橘帶可收合**（裁定 2）。收的是**帶裡的資訊圖**，不是整條帶 —— 帶上那句話是這一頁
的錨點，它要一直在。日到班模式下時間軸換成「已到 X / 應到 Y」的進度，因為那個模式
沒有逐堂的形狀可畫。

> **N=3 是這裡的實測依據**（裁定 4）：時間軸每多一條 lane 高 30px，4 條 lane 時
> 橘帶佔 48% 視窗、整頁 1.76 螢幕，課表脊椎整段掉到摺線下。所以 `lane > 3` 預設收合
> （已實作，常數在 `dashboard.component.ts` 的 `TIMELINE_COLLAPSE_LANE_THRESHOLD`）。
>
> **收合是止血，不是解。** 真正的解是換一種畫法（每半小時一根、以濃度表示同時
> 上課的堂數）—— 那件事屬於這份設計，見〈延後〉。

**左右分欄**（裁定 2）：左欄是**今天要做的事**，右欄是**要知道的事**。分欄的判準不是
重要性，是「需不需要動手」。手機上垂直堆疊，左欄在上 —— 要動手的先出現。

## per_session 的形狀：逐堂脊椎 + 就地點名

今天的課由上而下排開，每一堂一列：時間 · 班級 · 老師 · 出席概況 · 動作。

**就地點名**：`[點名]` 直接開既有的點名 dialog，不換頁。這是這一刀真正的價值 ——
今天要點五堂名，現在得走「儀表板 → 課堂管理 → 找到那一堂 → 開 dialog」四步，
而那四步每天重複五次。

**已點名的那幾堂不消失**，改成低調的一列（實心點 + 出席人數）。消失的話行政
會不確定自己是不是漏了一堂。

## daily_checkin 的形狀：誰還沒到 + 就地勾到班

三段，順序就是它們的重要性：

```
還沒到（N）      ← 這是工作，預設展開，排最上面
  學生 · 年級 · 今天第一堂課的時間與班級 · [勾到班]
已請假（L）      ← 第三種狀態，不是「還沒到」的一種
  學生 · 請假區間 · 送出者
已到（M）        ← 這是確認，預設收合
  學生 · 到班時間 · [取消]
```

**晨間視角是「誰還沒到」不是「誰到了」**。一張列出全部學生的表，行政要自己掃描找出
缺口；而晨間真正的工作是**追還沒到的人**（打電話問家長、確認是不是請假）。

**「已請假」分開列，不混在「還沒到」裡** —— 混在一起行政會去打一通不必要的電話。
這一條沿用 UX 審查驗過的縫：`attendance_status` 已經有 `on_leave`，而點名 dialog
顯示得出來（會鎖住那一列）卻設定不了。作業台要從一開始就把 `leave_requests`
讀進來，不要重蹈覆轍。

**看板兼作記錄面**（裁定 5）。理由是查證出來的：

| 元件                       | 現況                                        |
| -------------------------- | ------------------------------------------- |
| `POST /api/daily-checkins` | 存在且完整（`routes/daily-checkins.ts`）    |
| 讀取端點                   | **不存在**                                  |
| QR 打卡頁（唯一的寫入者）  | `qr-checkin.component.html` 共 9 行，佔位頁 |

**沒有任何路徑會產生一筆 `daily_checkins`。** 唯讀看板顯示的是永遠空的資料 ——
交付一個無法驗證的東西。而櫃台點一下勾到班不依賴任何尚未存在的東西，
掃碼做好之後兩者寫進同一張表，自然相容。

**分校分組不是分校選擇器**（裁定 6）。儀表板現在完全沒有分校範圍
（`dashboard.component.ts` 一個 `campus` 字樣都沒有）。分組在分校隔離落地前後都
成立：現在管理者看到全部分校各自的缺口，有隔離之後他只會拿到自己那組，同一段 UI
不用改。「先選分校再看」則兩邊都要改。見 [[architecture/authorization-scope]]。

## 兩種形狀共用的東西

|              | 規則                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **請假**     | 兩邊都是第三態，都從 `leave_requests` 讀，都不靠 `attendance_records.on_leave`                                                  |
| **時窗**     | 補登與取消一律走 `assertAttendanceWindow`（`attendance.ts:1257+`）—— 另寫一套的話，同一間補習班對「昨天還能不能改」會有兩個答案 |
| **分校範圍** | 端點照收 `campusId`，由 middleware 的 `campusScope` 驗證（已落地）                                                              |
| **老師範圍** | 老師只碰自己的課，寫入含代課（已落地，見 [[architecture/authorization-scope]] 洞 4）                                            |

## 前置：資料取用重整先行（裁定 3）

**互動不能先進來。** 作業台要把點名 dialog 與勾到班搬進儀表板，而儀表板已經是
最慢的頁 —— 現在逐支訂閱六支請求（`dashboard.component.ts:299` 起，
刻意不用 `forkJoin`，因為那要全部完成才 emit）。

再加上「每一堂的 roster」或「今天應該有誰」，就會變成
`課 × 班 × 在籍學生` 的 N+1。那正是
[[lessons/workers-fanout-costs-before-the-db]] 記的坑：8 支並行時每支慢 2.4 倍。

**所以先做一支聚合端點，再搬互動。**

### `GET /api/workbench/today?date=&campusId=`

一支端點，回**兩種形狀共用的一份資料**：

```
{
  mode: 'per_session' | 'daily_checkin',
  sessions: [...],          // 兩種模式都要（帶的句子與時間軸吃它）
  // per_session
  rosters: [...],           // 每堂的在籍人數 / 已點狀態
  // daily_checkin
  expected: [...],          // 今天有課的在籍學生
  arrived: [...],           // 今天的打卡
  onLeave: [...],           // 今天的請假
}
```

**由 API 決定形狀、前端不各打各的**，理由同「一個頁面兩種形狀」：兩套取數會各長
一份分校過濾與時窗判斷，其中一份會忘記更新。

其餘需求（要開單給 billing-api）：

| #       | 端點 / 改動                           | 說明                                                                    |
| ------- | ------------------------------------- | ----------------------------------------------------------------------- |
| 1       | `GET /api/workbench/today`            | 上述聚合端點                                                            |
| 2       | 取消打卡                              | 走 `assertAttendanceWindow`，並處理它衍生的資料                         |
| ~~3–6~~ | ~~fan-out／扣課／刪除守門／請假折抵~~ | **不需要** —— `#178` 已照「過濾後寫入」出貨，三處下游照常運作（見附錄） |

## 附錄：「完全不寫課堂出勤」那條路的代價（**目前不走這條**）

> 保留這一節是因為它記錄的東西不容易重新推導出來。**現況走的是 `#178` 的
> 「過濾後寫入」，下面三件事都不會發生。**

API 層對 `attendance_mode` **完全沒有分支**（全 repo 只有 `org-settings.ts` 與
`dashboard.component.ts` 讀它），所以下面兩件事會**靜默失效**：

1. **堂數包的扣課歸零** —— `session-packs.ts:97-120` 的 `deducted` / `remaining`
   由該班 events 上的 `attendance_records.status` 算出。買 20 堂 → 永遠 `deducted` 0
2. **「已有出勤紀錄」的刪除守門失效** —— `checkEnrollmentAttendance` 一律回 `none`，
   有真實到班歷史的報名可以被刪掉

**修法兩處相同且語意不變**：日到班改讀 `daily_checkins`，「消耗幾堂」＝
**打卡日期 ∩ 該班有 session 的日期**。

> 有意思的是，`#178` 出貨之後 `attendance_records` 裡存的**正好就是這個交集**
> —— 只是它是寫下來的，不是每次算出來的。兩條路殊途同歸，差別在真相存在哪裡。

### 請假折抵

`leave_deducts_session`（請假那堂扣不扣）是堂數制唯一的結構化決定（billing rules
規則 8）。它靠 `attendance_records.status = 'on_leave'`，而那些記錄由
`POST /api/leaves`（`leaves.ts:314-362`）寫入 —— **請假是透過 `attendance_records`
進帳的**。不寫課堂出勤就等於請假永遠不扣。

公式跟出席那一半同形：

```
日到班的應扣堂數
  = |打卡日 ∩ 該班上課日|
  + (leave_deducts_session ? |請假蓋到的上課日 ∩ 該班上課日| : 0)
  （兩者去重）
```

第二項**已經有現成的推導函式**：`lib/leave-covers-session.ts` 的
`leaveCoversSession`。它存在的理由正好就是「不要靠 `attendance_records` 的
`on_leave`」—— 出勤事件是懶生成的，家長提前請假時那些 event 還不存在。

**缺席那一半不受影響**：沒打卡就沒有記錄，今天本來就不扣
（`session-pack.ts` 的註解已承認這個邊界：「少記就少扣，錯的方向是安全的那邊」）。

## 明確不做

- **不做 QR 掃碼介面。** 公開頁的 `qr-checkin` 是佔位頁，另一支工單。作業台不依賴它
- **不做家長端到班紀錄。** 那頁是 `<p>attendance works!</p>` 的鷹架殘骸，家長端工單
- **不處理離開時間。** `daily_checkins` 只有 `checked_in_at`，加欄位是 schema 變更
- **不做「批次全部到班」。** 一鍵全到會讓看板變成橡皮圖章，而它要防的正是
  「沒有人真的看過」
- **不在這一刀換時間軸的畫法。** 濃度圖是另一個問題（見〈延後〉），這一刀先用
  已實作的 `lane > 3 收合`
- **不回填既有資料。** 現況沒有任何路徑產生 `daily_checkins`，衍生的
  `attendance_records` 也就不存在（seed 除外）。實作前確認一次

## 延後

**時間軸換成濃度圖**（每半小時一根、以濃度表示同時上課的堂數）。N=3 的實測說明
lane 式畫法在密集日會擋路，但換畫法是獨立的一刀，而且要重做
`day-timeline.util.ts` 的佈局數學與它的 28 條測試。**先讓作業台的結構立起來，
再回頭換那張圖** —— 順序反過來的話，會在一個還沒定案的版面上調圖。

## 手機版

**櫃台的晨間工作很可能就是拿著手機在門口勾** —— 這一頁的手機版不是降級版，是主場景。

- 左右分欄改垂直堆疊，**左欄（要動手的）在上**
- 「勾到班」與「點名」是主要動作，觸控目標 ≥ 44×44
- 名單列窄螢幕改兩行（姓名＋年級 / 課程時間），**不砍掉姓名以外的欄位** ——
  行政要靠「今天上什麼課」確認是不是找錯人
- 橘帶預設收合的門檻（lane > 3）在手機上要重新量 —— 桌機的 3 條在 390px 可能是 2
- 不用 viewport 單位（c6）

## 驗證

demo 目前是 `per_session`（為了驗密集日 seed 翻過去的），所以驗 `daily_checkin`
**用本機** —— 翻 demo 會讓其他席正在驗的東西變樣。

1. per_session 機構：作業台是逐堂脊椎，點 `[點名]` 就地開 dialog，不換頁
2. daily_checkin 機構：作業台是到班看板，**畫面上沒有「未點名」三個字**
3. 勾一個學生 → 他從「還沒到」移到「已到」，時間正確
4. 有請假的學生**不在「還沒到」裡**
5. 多分校機構：未到班依分校分組；單分校不顯示分組標題
6. 昨天的作業台：時窗政策生效（`retroactiveDays = 0` 時管理員可改但留 audit log）
7. **請求數**：整頁的 API 請求數不多於現在（聚合端點應該讓它變少）
8. 390px：無橫向溢出，兩個主要動作觸控目標達標
