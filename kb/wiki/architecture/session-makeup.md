# 補課（課堂標記「補的是哪一堂停課」）

> **使用者 2026-09-06 三項全裁**（[issue #544](https://github.com/mizok/clessia/issues/544)），
> 本頁已照裁示改寫。**改寫後要過計畫席再看一次才動實作碼。**
> 原工單 [issue #499](https://github.com/mizok/clessia/issues/499)。

## 這個功能不改變扣費規則 —— 先讀懂這一句

計畫席的範圍裁定：**補課是純加法，不動任何既有的扣費路徑。**

補課那堂就是一堂正常的課：學生來上、老師點名、`attendance_records` 寫 `present`、
`session-packs` **本來就會扣一堂**。而停掉的那堂照
[#485 的裁示](https://github.com/mizok/clessia/issues/485) **不扣**
（`routes/session-packs.ts` 的 `.neq('status','cancelled')`）。

所以使用者裁定的「**補了才扣，沒補不扣**」在資料上**自動成立**：

| 情況 | 發生什麼 | 扣不扣 |
| --- | --- | --- |
| 停課，沒補 | 沒有課發生 | 不扣（`cancelled` 被過濾掉） |
| 停課，補了 | 補課那堂是真的上了 | 扣一堂（那堂是 `scheduled`，正常計入） |

> **「補哪一堂」這個連結對計費完全不必要。** 它的價值在**可解釋性**：家長看到帳單少一堂
> 會問為什麼，行政看到補課那堂會問這是補什麼的。

**推論：設計時如果發現需要動扣費邏輯，那表示走偏了，要停下來回報。**
這一頁底下的每個決定都以「不碰 `lib/session-pack.ts` 與 `routes/session-packs.ts`
的計算」為前提。

## 已裁定的三件（使用者 2026-09-06）

| 問題 | 裁定 |
| --- | --- |
| 補課要不要限制同班 | **限制。** 只能補同一個班已停課的課堂 |
| 停課多久內要補完 | **無限制** —— 補課非強制 |
| 一堂停課能配幾堂補課 | **最多一堂（1:1）** —— 2026-09-06 使用者裁定，**取代原設計的多對一** |
| 一堂補課能補幾堂停課 | **一堂**（`makeup_for_session_id` 是單一 FK） |

## 決策 1：連結存在 `sessions` 的自我參照 FK

```sql
ALTER TABLE public.sessions
  ADD COLUMN makeup_for_session_id uuid REFERENCES public.sessions(id) ON DELETE SET NULL;

-- 1:1：一堂停課最多配一堂補課。**部分索引，不是普通 UNIQUE** —— 理由見下。
CREATE UNIQUE INDEX sessions_makeup_for_unique
  ON public.sessions (makeup_for_session_id)
  WHERE makeup_for_session_id IS NOT NULL AND status <> 'cancelled';
```

### ⚠️ 為什麼是**部分**唯一索引 —— 1:1 裁示與決策 5.1 有衝突，這是解法

裁示說「加 `UNIQUE`」，而**普通 `UNIQUE` 會跟決策 5.1 打架**：

5.1 裁定「補課那堂又被停掉 → 允許，連結保留」。普通 `UNIQUE` 之下，
**那堂停掉的補課會永久佔住它的目標** —— A 再也補不了第二次，除非有人手動清掉
B 的 FK。而 5.1 的整個用意是「那是真實發生過的事，不要抹掉」。

部分索引把約束的語意收窄成**「一堂停課最多配一堂*有效的*補課」** ——
正好對上本文件決策 5.1 已經寫死的那個區別（「有幾堂補課」vs「有幾堂**有效的**補課」）。

**對真 DB 實跑驗過四個行為**（`BEGIN … ROLLBACK`，非破壞性）：

| 情境 | 結果 |
| --- | --- |
| B 補 A | ✅ 成功 |
| C 也想補 A（B 仍有效） | ❌ `duplicate key value violates unique constraint` |
| B 停課後，C 補 A | ✅ **成功 —— A 沒有被那堂停掉的補課永久卡住** |
| 把 B 復課（會變成兩堂有效補課指向 A） | ❌ 被同一個索引擋下 |

**第四列是這個設計新長出來的邊界**，見決策 5.5。

**這個形狀成立**，理由與被拒絕的替代方案：

| 方案 | 為什麼不選 |
| --- | --- |
| join table `session_makeups(makeup_session_id, cancelled_session_id)` | **1:1 更不需要它** —— join table 的價值在多對多。而且 1:1 的唯一性用一個索引就守得住，join table 反而要在兩個欄位上各建一個 |
| 存在 `schedule_changes` 上 | 見決策 4 —— 那張表是**事件流水**，不是課堂的當前狀態 |

**`ON DELETE SET NULL` 而不是 `CASCADE`**：被補的那堂如果真的被刪掉，補課那堂**仍然是一堂
真的發生過的課**，不該跟著消失。連結斷掉是可接受的退化（欄位變 null，畫面退回「這是一般課堂」），
而 CASCADE 會刪掉一堂學生真的上過、而且已經扣過堂數的課。

> 這是本 repo 反覆出現的判準：**在兩個錯誤之間選會被發現的那個。**
> 連結消失看得見（標記不見了），課堂消失是靜默的資料損失。

### 同班限制守在 API 層，不守在 DB 層

**建議：API 層（`routes/sessions.ts` 建立/更新補課連結時檢查），不加 CHECK/trigger。**

理由：

- **CHECK 約束做不到。** Postgres 的 `CHECK` 不能查別的列，而同班限制需要比對
  「這兩列的 `class_id` 相不相等」——那要 trigger。
- **trigger 是可以的，但它是這個 repo 沒有的東西。** 現行 schema 的所有約束都是
  宣告式的（FK / UNIQUE / CHECK 單列）；引入第一支 trigger 會讓「規則住在哪裡」多一個地方，
  而且 plpgsql 有本 repo 記過的坑（變數名稱解析、42702，見 charter）。
- **fail-closed 的層級不同。** 授權層的 fail-closed 之所以必須在 DB 之外（憲法 c1），
  是因為 API 用 service role key。同班限制**不是授權**，它是資料一致性 ——
  而寫入這張表的路徑**只有 API**（沒有任何非 service-role client）。

**⚠️ 這個選擇的代價要寫出來**：直接對 DB 下 SQL（seed、修資料、將來的匯入腳本）
繞得過這條規則。**接受它**，理由是那些路徑本來就繞得過所有 API 層規則，
而這條規則錯了的後果是「畫面上顯示一個跨班的補課連結」——**看得見，不是靜默的**。

> 若計畫席認為要 DB 層守，那是一個明確的取捨變更（多一支 trigger + plpgsql 的坑），
> **不是實作細節**，要回到這一頁重新批准。

## 決策 2：「可以補哪些課堂」的查詢

排課 UI 要列出候選。**候選 = 同一個班、`status = 'cancelled'` 的課堂。**

```
sessions WHERE class_id = <這堂課的班> AND status = 'cancelled'
```

### 已被補過的**排除在清單外**（2026-09-06 裁定）

1:1 之下這不再是 UI 偏好，是**資料約束的鏡像**：清單列出一個補不了的選項，
使用者按下去只會拿到一個資料庫錯誤。

```
sessions
WHERE class_id = <這堂課的班>
  AND status = 'cancelled'
  AND NOT EXISTS (            -- 已經有「有效的」補課的排除掉
        SELECT 1 FROM sessions m
        WHERE m.makeup_for_session_id = sessions.id
          AND m.status <> 'cancelled')
```

**排除條件必須跟部分唯一索引的述詞逐字一致**（`status <> 'cancelled'`）——
兩者不同步的話，清單會列出一個索引會拒絕的選項，或藏起一個其實補得成的。
**它們是同一條規則的兩個載體，而載體之間漂移是本 repo 記過最多次的一族。**

## 決策 3：顯示面 —— 雙向可見

| 畫面 | 補課那堂顯示 | 被補的那堂顯示 |
| --- | --- | --- |
| 管理端課表（`admin/sessions`） | 標記「補課」＋原停課日期 | 已停課（現況）＋「已於 X/X 補課」 |
| 課堂詳情對話框 | 「補 X/X 的課」，可點回去 | 「已由 X/X 補課」（多堂就列多筆） |
| 老師端課表 | 標記「補課」 | 現況不變（停課的課堂本來就看得到） |
| 家長端出缺席 | 「補 X/X 停課」 | 「已停課 · 已於 X/X 補課」（**載體見下**） |

**雙向可見是刻意的**：只做單向的話，行政從停課那堂看不出它有沒有被補回來，
而「這堂補回來了嗎」正是這個功能要回答的問題。

### 家長端**兩端都顯示**（2026-09-06 裁定），而載體已經到位

| 家長看到 | 顯示 |
| --- | --- |
| **停課的那一堂** | 「已停課 · 已於 X/X 補課」 |
| **補課的那一堂** | 「補 X/X 停課」 |

**為什麼兩端都要**：家長會從任一端進來（他滑到哪一天就看到哪一堂）。
**只顯示一邊，另一邊就會看起來像一堂無故多出來、或無故消失的課** ——
而那正是這個功能要消除的困惑。

**載體已經有了，不需要新端點**：

- `ATTENDANCE_SELECT` 已經帶回 `sessionStatus`（PR #514），家長端出缺席已經標得出「停課」（PR #525）
- 補課那一堂只需要**多帶被補那堂的日期**；停課那一堂需要**多帶補課那堂的日期**
- 兩者都是同一個自我參照 FK 的兩個方向，一支查詢兩個 embed 就拿得到

⚠️ **停課的課堂在家長端目前根本沒有載體。** 它沒有出勤紀錄
（[issue #485](https://github.com/mizok/clessia/issues/485) 之後更是如此），
而家長端出缺席回的是 `attendance_records` —— **所以「已於 X/X 補課」要掛在哪一列，
本身是個未解的問題**。

**這一片必須跟 [issue #502](https://github.com/mizok/clessia/issues/502) 一起做**
（停課的課堂在家長端仍顯示成一筆正常的請假）：兩者在**同一個畫面、同一批列**上，
而 #502 的第 1 項（那筆 `on_leave` 該不該存在）**決定了停課的課堂在家長端有沒有列可掛**。
分開做會改同一個檔案兩次，而且第二次會發現第一次的假設不成立。

## 決策 4：**進** `schedule_changes`，而 FK 與流水回答不同的問題

> **2026-09-06 翻面。** 原設計主張不進表，理由是「兩份紀錄會漂移」。
> 使用者裁定要進，而計畫席把那個技術疑慮一併裁掉了 —— **理由比原設計的更好**。

需要一支 migration：`ALTER TYPE public.schedule_change_type ADD VALUE 'makeup';`
**那是不可逆的**（Postgres 不支援移除 enum 值，而已提交的 migration 不可改，c3）。
使用者已知情並決定要。

### 為什麼「衝突時信誰」不是一個問題

| | 回答什麼 | 可變嗎 |
| --- | --- | --- |
| `sessions.makeup_for_session_id` | **現況**：這堂課**現在**補的是哪一堂 | 可改、可清空 |
| `schedule_changes` 的那一筆 | **歷史**：某年某月某日，有人把它設成補 X | **不可變** |

> **兩者不一致不是矛盾，是「發生過然後被改掉了」。**
> 連結後來被解除時，FK 是 `null` 而流水仍然記著那件事發生過 ——
> **那是正確的，不要去修流水。**

### 兩條硬性規則

1. **不要用 `schedule_changes` 推導現況。** 任何「這堂補的是哪一堂」的查詢一律走 FK。
   **這條要寫在讀 `schedule_changes` 的程式碼旁邊，不是只寫在這裡。**
2. **FK 與流水必須在同一個 transaction 裡寫。** 分開寫會出現「FK 有但流水沒記」——
   **那才是真的資料問題**（而它跟第 1 條的方向相反：第 1 條說不一致是正常的，
   這一條說**某一種**不一致不正常。差別是「後來被改掉」vs「從來沒寫成功」）。

### ⚠️ `changes.component.ts:81` 要一起看

那一頁的篩選是 `Object.entries(CHANGE_TYPE_LABELS).filter(([value]) => value !== 'creation')`
—— **黑名單，不是白名單**。所以 `makeup` 只要進了 `CHANGE_TYPE_LABELS` 就會自動出現，
**不會落在 `creation` 那個處境**。

**但它需要一個標籤，而漏掉的後果不是報錯**（逐行查證過 `changes.component.ts:26-33`、
`:81`、`:114`）：

| 沒把 `makeup` 加進 `CHANGE_TYPE_LABELS` | 後果 |
| --- | --- |
| 篩選選項（`:81` 從那張表 `Object.entries` 產生） | **那個選項整個不存在** —— 使用者篩不到補課，而下拉選單看起來完全正常 |
| 表格的類型欄（`:114` 是 `CHANGE_TYPE_LABELS[value] ?? value`） | 顯示原始 enum 值 `makeup`，**不是 `undefined`** |

**列會出現、但篩不到，而且顯示成一個英文字。** 兩個都不會拋錯 ——
這是「**壞掉的樣子跟正常的樣子一模一樣**」在 UI 上的形式。顯示端那一片必須補這張表。

### 單堂歷史仍然照舊

`routes/sessions.ts:394` 的 `buildSessionCreationHistory()` 合成 `creation` 那個機制不動 ——
`makeup` 現在**兩邊都有**（流水裡有一筆、單堂歷史從流水讀得到），不需要合成。

## 決策 5：邊界 —— 這一節是工單說最容易漏的那一項

### 5.1 補課那堂又被停掉

**允許，連結保留。** 補課那堂變成 `cancelled`，`makeup_for_session_id` 不動。

- 語意：「本來要補，結果補課也停了」——那是真實發生過的事
- 計費：補課那堂變 `cancelled` → 照 #485 **不扣**。原本停課那堂也不扣。**兩堂都不扣，正確**
- 顯示：被補的那堂要能看出「有一堂補課但它也停了」——**不能只數 `makeup_for_session_id` 指向我的筆數**，
  要排除 `cancelled` 的那些，否則畫面會說「已補課」而其實沒補成

> **這是最容易寫錯的一處**：「有幾堂補課」與「有幾堂**有效的**補課」是兩個數字，
> 而它們在多數情況下相等 —— **相等的時候你不會發現自己用錯了那一個。**
>
> 它比一般的空值問題陰險：**空值至少偶爾會是空的**，而這種錯誤**只在補課也被停掉時
> 才顯形** —— 罕見到你不會為它寫測試，常見到它遲早會發生。

#### 所以每一個顯示點要數哪一個，在這裡寫死，不留給實作時判斷

| 顯示點 | 數哪一個 | 為什麼 |
| --- | --- | --- |
| 被補那堂的「已補課」標記 | **有效的**（排除 `cancelled` 的補課） | 它回答的是「這堂補回來了嗎」。補課也停了就是**沒補回來** |
| 被補那堂詳情的「由哪幾堂補」清單 | **全部**（含已停的，但標出來） | 它回答的是「發生過什麼」。藏起來會讓人以為那筆連結不存在 |
| 補課那堂的「補 X/X 的課」 | 不涉及計數 | 單一 FK |
| 可補清單的「已有 N 堂補課」（若決策 2 選「全部列出」） | **有效的** | 它是給人判斷「還要不要再補一堂」的，停掉的那些不該讓人以為已經補過 |

**判準一句話**：**問「這堂補回來了嗎」就數有效的，問「發生過什麼」就數全部。**
兩者都要的地方（詳情頁）**兩個都顯示**，不要挑一個。

**測試要求**：每一個「數有效的」的顯示點，都要有一支測試餵**一堂已停的補課**，
斷言它**不**被算進去。這一族只有在那個罕見情境下才顯形，所以它必須被測試釘住 ——
**不能靠「多數時候相等」蒙混過去。**

### 5.2 被補的那堂被 `uncancel` —— **已裁定：擋住**

`uncancel`（`classes.ts:2513` 的 batch-uncancel）把 `cancelled` 改回 `scheduled`。
一旦它復活，「補課」的前提就沒了 —— 會產生一堂補課指向一堂沒有停課的課堂。

**計畫席 2026-09-06 裁定：擋住，回一筆 `conflict`。**

被拒絕的兩個替代方案與理由：

| 選項 | 為什麼不選 |
| --- | --- |
| 允許，清掉補課那堂的 FK | **靜靜抹掉一段真實歷史**（那堂補課真的發生過），而且行政不會知道自己剛剛拆掉了一個連結 |
| 允許，保留 FK，顯示成「原課堂已復課」 | 資料保真，但**每一個顯示點都要各處理一次矛盾態** |

**擋住的額外好處是它把選擇推回給人**：行政要復活那堂課，就得先處理補課那堂 ——
**而那正是他該想一想的時刻。**

實作上它跟批次 uncancel 既有的 `conflicts` 形狀一致（`classes.ts:2405-2436`
已經會回報「這幾筆不能做、原因是什麼」），所以是**加一種 conflict reason**，
不是新機制。

**錯誤訊息要說得出為什麼**，不能只說「不能復活」：

> 「這堂課已經由 X/X 的補課接手，要復活請先解除那個連結」

> **順帶一個事實，記成觸發條件、不要在這一支裡順手加**：`uncancel` 的守衛是
> `target.status !== 'cancelled'` 就跳過（`classes.ts:2640`），**沒有日期限制** ——
> 可以復活一堂很久以前的課。要處理它的觸發條件是**「有人回報復活了不該復活的課」**，
> 或**課堂狀態機被重新設計時**（見 [#488](https://github.com/mizok/clessia/issues/488)
> 的 `status='completed'` 那一題）。

### 5.3 被補的那堂被刪除

`ON DELETE SET NULL`（決策 1）。補課那堂留著、連結斷掉、退回一般課堂。

**但實務上碰不到**：刪班會擋在「有過去課堂」那道守衛上（`classes.ts:1191`），
而停課的課堂**只看日期不看 status**，所以它算「過去課堂」。
這裡的 `SET NULL` 是**防禦性的**，不是常見路徑。

### 5.4 一堂課可不可以既是補課、又被別人補 —— **1:1 之下仍然成立**

語意上是「A 停課 → B 補 A → B 也停課 → C 補 B」。

**唯一索引不會誤擋它**，而理由要寫清楚（計畫席特別要求確認這一點）：
索引建在 **`makeup_for_session_id` 這一個欄位**上，也就是**「被補的那一端」**。

| 列 | `makeup_for_session_id` | 索引看到的鍵 |
| --- | --- | --- |
| B | A | `A` |
| C | B | `B` |

**兩個不同的鍵，不衝突。** B 同時是「指著 A 的那一列」與「被 C 指著的那個值」——
**前者是它的欄位，後者是別人的欄位**，索引只約束前者。

顯示時只展開一層（「補 X/X 的課」），不做遞迴追溯 —— 要追溯的人有單堂歷史可看。

### 5.5 ⚠️ 1:1 新長出來的邊界：**把一堂停掉的補課復課**

部分唯一索引的述詞含 `status <> 'cancelled'`，所以這個序列會撞上它：

1. B 補 A，B 後來停課 → A 重新可補（決策 1 的實測第三列）
2. C 補 A → 成功
3. **有人把 B 復課** → 現在兩堂**有效的**補課指向 A → **唯一索引拒絕**（實測第四列）

**這是對的行為，但它會以資料庫錯誤的形式出現**，而 `uncancel` 那條路徑目前不預期
這種失敗。處置**照決策 5.2 的同一個形狀**：在 batch-uncancel 的 `conflicts` 裡加一種原因，
**在 update 之前就擋下來**，不要讓它變成 500。

錯誤訊息一樣要說得出為什麼：

> 「這堂補課的目標（X/X）已經另外有補課了，要復課請先解除那一個連結」

> **判準（值得記在這一族之外）：一個約束加上「排除某狀態」的述詞之後，
> 那個狀態的每一條回頭路都變成新的失敗點。** 部分索引的成本不在建立它，
> 在於**把述詞裡那個狀態的所有轉出路徑找出來**。
