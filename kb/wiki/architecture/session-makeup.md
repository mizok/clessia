# 補課（課堂標記「補的是哪一堂停課」）

> **狀態：設計草案，等計畫席批准。** 批准前不得寫實作程式碼
> （`clessia-feature-slice` 的 STOP gate）。工單 [#499](https://github.com/mizok/clessia/issues/499)。

## 這個功能不改變扣費規則 —— 先讀懂這一句

計畫席的範圍裁定：**補課是純加法，不動任何既有的扣費路徑。**

補課那堂就是一堂正常的課：學生來上、老師點名、`attendance_records` 寫 `present`、
`session-packs` **本來就會扣一堂**。而停掉的那堂照
[#485 的裁示](https://github.com/mizok/clessia/issues/485) **不扣**
（`routes/session-packs.ts` 的 `.neq('status','cancelled')`）。

所以使用者裁定的「**補了才扣，沒補不扣**」在資料上**自動成立**：

| 情況 | 發生什麼 | 扣不扣 |
| --- | --- | --- |
| 停課，沒補 | 沒有課發生 | 不扣（`cancelled` 被過濾掉） |
| 停課，補了 | 補課那堂是真的上了 | 扣一堂（那堂是 `scheduled`，正常計入） |

> **「補哪一堂」這個連結對計費完全不必要。** 它的價值在**可解釋性**：家長看到帳單少一堂
> 會問為什麼，行政看到補課那堂會問這是補什麼的。

**推論：設計時如果發現需要動扣費邏輯，那表示走偏了，要停下來回報。**
這一頁底下的每個決定都以「不碰 `lib/session-pack.ts` 與 `routes/session-packs.ts`
的計算」為前提。

## 已裁定的三件（使用者 2026-09-06）

| 問題 | 裁定 |
| --- | --- |
| 補課要不要限制同班 | **限制。** 只能補同一個班已停課的課堂 |
| 停課多久內要補完 | **無限制** —— 補課非強制 |
| 一堂補課能補幾堂停課 | **多對一**：多堂補課可指向同一堂停課。**不做**「一堂補兩堂」（要 join table，判斷罕見） |

## 決策 1：連結存在 `sessions` 的自我參照 FK

```sql
ALTER TABLE public.sessions
  ADD COLUMN makeup_for_session_id uuid REFERENCES public.sessions(id) ON DELETE SET NULL;
CREATE INDEX sessions_makeup_for_idx ON public.sessions (makeup_for_session_id);
```

**這個形狀成立**，理由與被拒絕的替代方案：

| 方案 | 為什麼不選 |
| --- | --- |
| join table `session_makeups(makeup_session_id, cancelled_session_id)` | 多對一不需要它。**join table 的價值在多對多**，而「一堂補兩堂」已被裁定不做。先加一張表，之後要拿掉比留著難 |
| 存在 `schedule_changes` 上 | 見決策 4 —— 那張表是**事件流水**，不是課堂的當前狀態 |

**`ON DELETE SET NULL` 而不是 `CASCADE`**：被補的那堂如果真的被刪掉，補課那堂**仍然是一堂
真的發生過的課**，不該跟著消失。連結斷掉是可接受的退化（欄位變 null，畫面退回「這是一般課堂」），
而 CASCADE 會刪掉一堂學生真的上過、而且已經扣過堂數的課。

> 這是本 repo 反覆出現的判準：**在兩個錯誤之間選會被發現的那個。**
> 連結消失看得見（標記不見了），課堂消失是靜默的資料損失。

### 同班限制守在 API 層，不守在 DB 層

**建議：API 層（`routes/sessions.ts` 建立/更新補課連結時檢查），不加 CHECK/trigger。**

理由：

- **CHECK 約束做不到。** Postgres 的 `CHECK` 不能查別的列，而同班限制需要比對
  「這兩列的 `class_id` 相不相等」——那要 trigger。
- **trigger 是可以的，但它是這個 repo 沒有的東西。** 現行 schema 的所有約束都是
  宣告式的（FK / UNIQUE / CHECK 單列）；引入第一支 trigger 會讓「規則住在哪裡」多一個地方，
  而且 plpgsql 有本 repo 記過的坑（變數名稱解析、42702，見 charter）。
- **fail-closed 的層級不同。** 授權層的 fail-closed 之所以必須在 DB 之外（憲法 c1），
  是因為 API 用 service role key。同班限制**不是授權**，它是資料一致性 ——
  而寫入這張表的路徑**只有 API**（沒有任何非 service-role client）。

**⚠️ 這個選擇的代價要寫出來**：直接對 DB 下 SQL（seed、修資料、將來的匯入腳本）
繞得過這條規則。**接受它**，理由是那些路徑本來就繞得過所有 API 層規則，
而這條規則錯了的後果是「畫面上顯示一個跨班的補課連結」——**看得見，不是靜默的**。

> 若計畫席認為要 DB 層守，那是一個明確的取捨變更（多一支 trigger + plpgsql 的坑），
> **不是實作細節**，要回到這一頁重新批准。

## 決策 2：「可以補哪些課堂」的查詢

排課 UI 要列出候選。**候選 = 同一個班、`status = 'cancelled'` 的課堂。**

```
sessions WHERE class_id = <這堂課的班> AND status = 'cancelled'
```

### ⚠️ 「還沒被補過」不列為硬性條件 —— 但這一項要使用者確認

多對一**允許**重複指向（多堂補課補同一堂停課），所以「還沒被補過」在資料上不是限制。
問題是 **UI 要不要預設把已經被補過的藏起來**：

| 選項 | 後果 |
| --- | --- |
| 全部列出，已被補過的標「已有 N 堂補課」 | 不會擋住合法操作（真的要補兩堂就補得成），但清單會越來越長 |
| 預設隱藏已被補過的，可展開 | 清單乾淨，但**「補第二堂」變成一個要先發現的操作** |

**這一項列為待確認，我不自己決定** —— 它取決於「一堂停課配多堂補課」在實務上是常態還是例外，
而那是使用者才知道的事。工單裡計畫席也明確要求不要自己決定。

## 決策 3：顯示面 —— 雙向可見

| 畫面 | 補課那堂顯示 | 被補的那堂顯示 |
| --- | --- | --- |
| 管理端課表（`admin/sessions`） | 標記「補課」＋原停課日期 | 已停課（現況）＋「已於 X/X 補課」 |
| 課堂詳情對話框 | 「補 X/X 的課」，可點回去 | 「已由 X/X 補課」（多堂就列多筆） |
| 老師端課表 | 標記「補課」 | 現況不變（停課的課堂本來就看得到） |
| 家長端出缺席 | **待確認**（見下） | **待確認** |

**雙向可見是刻意的**：只做單向的話，行政從停課那堂看不出它有沒有被補回來，
而「這堂補回來了嗎」正是這個功能要回答的問題。

### 家長端列為待確認

家長端出缺席（`routes/parent/attendance.ts`）目前回的是 `attendance_records`。
停課的課堂**沒有出勤紀錄**（照 #485 之後更是如此），所以家長根本看不到那一堂 ——
**「已補課」對家長端可能是沒有載體的**。

要不要讓家長看到「X/X 停課、已於 Y/Y 補回」是一個產品問題，
而且它跟 [#502](https://github.com/mizok/clessia/issues/502)（停課的課堂仍會被寫
`on_leave`，家長看得到「停掉的課請假了」）**在同一個畫面上**。
**建議兩者一起決定，不要在這一支裡單獨決定。**

## 決策 4：不進 `schedule_changes`，在單堂歷史裡合成

`schedule_changes` 是**課務異動的事件流水**（表註解原話：「課務異動紀錄（調課/代課/停課）」），
`change_type` 目前有 `reschedule` / `substitute` / `cancellation` / `uncancel` / `time_change`。

**建議：不新增 enum 值，補課的連結只存在 `sessions.makeup_for_session_id`。**

理由：

1. **兩份紀錄會漂移。** FK 是課堂的**當前狀態**（可以被改、被清空），流水是**發生過的事**
   （不可變）。同一件事存兩份，改了 FK 沒補流水、或補了流水沒改 FK，都會產生
   「兩邊說法不一致」——而**沒有人會知道該信哪一邊**。
2. **這個 repo 已經有「合成歷史項目」的先例。** `routes/sessions.ts:394` 的
   `buildSessionCreationHistory()` 造出一筆 `changeType: 'creation'`，
   **那個值在 DB enum 裡根本不存在**。單堂課的歷史是「流水 + 合成」拼起來的。
   補課可以照同一條路：從 FK 合成一筆 `makeup` 顯示在單堂歷史裡。
3. **`ALTER TYPE ... ADD VALUE` 是不可逆的**（Postgres 不支援移除 enum 值），
   而已提交的 migration 不可改（憲法 c3）。加一個之後拿不掉。

### ⚠️ 這個選擇有一個已知的代價，必須寫出來

**組織級的「異動紀錄」頁（`admin/pages/changes`）看不到補課。**

那一頁直接查 `schedule_changes`（`routes/sessions.ts:1010`），而且它的篩選選項
**明確排除了 `creation`**（`changes.component.ts:81`：`.filter(([value]) => value !== 'creation')`）
—— 因為那個類型從來不在表裡。補課會落在同一個處境。

| | 不進表（建議） | 進表 |
| --- | --- | --- |
| 單堂歷史 | ✅ 合成 | ✅ |
| 組織級異動紀錄頁 | ❌ 看不到 | ✅ |
| 漂移風險 | 無（單一來源） | **有** |
| enum 不可逆 | 不涉及 | 加了拿不掉 |

**如果「補課要出現在組織級異動紀錄」是需求，那這個決策要翻過來** ——
但那時候要一併決定「FK 與流水衝突時信誰」，而我建議的答案會是「FK 是真相，
流水只是 log」。**這一項請計畫席明確裁一次，不要讓它靠預設落地。**

## 決策 5：邊界 —— 這一節是工單說最容易漏的那一項

### 5.1 補課那堂又被停掉

**允許，連結保留。** 補課那堂變成 `cancelled`，`makeup_for_session_id` 不動。

- 語意：「本來要補，結果補課也停了」——那是真實發生過的事
- 計費：補課那堂變 `cancelled` → 照 #485 **不扣**。原本停課那堂也不扣。**兩堂都不扣，正確**
- 顯示：被補的那堂要能看出「有一堂補課但它也停了」——**不能只數 `makeup_for_session_id` 指向我的筆數**，
  要排除 `cancelled` 的那些，否則畫面會說「已補課」而其實沒補成

> **這是最容易寫錯的一處**：「有幾堂補課」與「有幾堂**有效的**補課」是兩個數字，
> 而它們在多數情況下相等 —— 相等的時候你不會發現自己用錯了那一個。

### 5.2 被補的那堂被 `uncancel`

`uncancel`（`classes.ts:2513` 的 batch-uncancel）把 `cancelled` 改回 `scheduled`。
一旦它復活，「補課」的前提就沒了 —— **會產生一堂補課指向一堂沒有停課的課堂**。

三個選項：

| 選項 | 後果 |
| --- | --- |
| **甲：擋住** —— 有補課指向它就不准 uncancel | 最保守，但**它會在批次 uncancel 裡變成一筆 conflict**（那條路徑已經有 `conflicts` 的形狀，`classes.ts:2405-2436`），使用者要先去解掉補課 |
| **乙：允許，清掉補課那堂的 FK** | 資料一致，但**靜靜抹掉一段真實歷史**（那堂補課真的發生過） |
| **丙：允許，保留 FK，顯示成「原課堂已復課」** | 資料保真，但畫面要處理一個矛盾態 |

**我建議甲**，理由是它跟既有的 `conflicts` 形狀一致（批次操作已經會回報「這幾筆不能做、原因是什麼」），
而且**乙會刪掉歷史、丙要在每個顯示點處理矛盾態**。但這是**業務判斷**，列為待裁。

> 順帶一個事實：`uncancel` 的守衛是 `target.status !== 'cancelled'` 就跳過
> （`classes.ts:2640`），**沒有日期限制** —— 可以復活一堂很久以前的課。

### 5.3 被補的那堂被刪除

`ON DELETE SET NULL`（決策 1）。補課那堂留著、連結斷掉、退回一般課堂。

**但實務上碰不到**：刪班會擋在「有過去課堂」那道守衛上（`classes.ts:1191`），
而停課的課堂**只看日期不看 status**，所以它算「過去課堂」。
這裡的 `SET NULL` 是**防禦性的**，不是常見路徑。

### 5.4 一堂課可不可以既是補課、又被別人補

**技術上可以**（欄位互相獨立），語意上是「A 停課 → B 補 A → B 也停課 → C 補 B」。
**允許，不特別處理** —— 鏈狀關係在顯示時只展開一層（「補 X/X 的課」），
不做遞迴追溯。要追溯的人有單堂歷史可看。

## 影響的既有元件

| 元件 | 影響 |
| --- | --- |
| `supabase/migrations/` | **新增一支 ALTER**（加欄位 + index）。**保留類，使用者親合** |
| `routes/sessions.ts` | 建立/清除連結的端點；`mapSession` 多回兩個欄位；單堂歷史合成 `makeup` |
| `routes/classes.ts` | 若採 5.2 甲：batch-uncancel 多一種 conflict |
| `core/sessions.service.ts` | 型別同步 |
| **`lib/session-pack.ts` / `routes/session-packs.ts`** | **完全不動**（見開頭的範圍裁定） |
| `admin/pages/sessions` | 標記與詳情顯示（admin-pages 席） |
| `teacher/pages/schedule` | 標記顯示（teacher-pages 席） |

## 明確不做

- **不做一堂補兩堂**（要 join table，使用者裁定罕見）
- **不做補課時限**（非強制，所以無期限）
- **不改任何扣費邏輯**（範圍裁定；發現需要動就是走偏了）
- **不動 `schedule_changes` 既有的任何行為**（工單明令）
- **不做家長端顯示**（待確認，且建議跟 #502 一起決定）
