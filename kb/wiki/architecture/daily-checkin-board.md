# 日到班看板與兩種點名模式的介面分流

> **這是設計，不是實作紀錄。** 依 `clessia-feature-slice` 的 STOP gate：
> 待計畫席初審 + 使用者批准之後才寫產品碼。
>
> 使用者已裁決兩項（2026-09-02）：**日到班只認 `daily_checkins`，不寫課堂出勤**、
> **看板兼作記錄面**。第一項的兩個下游後果見〈裁決的代價〉。

## 這份設計要解的問題

demo 的機構是 `attendanceMode: 'daily_checkin'`，而：

- **管理端沒有任何日到班介面。**「到班紀錄」是家長端路由（`/parent/attendance`）
- 儀表板**刻意隱藏**「未點名課堂」卡（`dashboard.util.ts` 的 `countUntakenSessions`
  在非 per_session 時回 `null`）—— 等於告訴使用者「這不是你的工作方式」
- 但橘帶仍然說「今天 N 堂課，其中 M 堂還沒點名」、課表列仍掛「未點名」chip、
  課堂管理頁自己還掛「此分校今日未點名 N 堂」

淨效果：**畫面報一個在這間補習班的設定下不存在的問題，拿掉了修它的捷徑，
再把使用者導到一個用不同模型運作的頁面。**

## 開工前先講三件查證出來的事實

### 一、整個日到班功能目前是「一支沒有人呼叫的 POST」

| 元件                       | 現況                                                    |
| -------------------------- | ------------------------------------------------------- |
| `POST /api/daily-checkins` | **存在且完整**（`routes/daily-checkins.ts`，117 行）    |
| 讀取端點                   | **不存在** —— 那個檔案只有一個 `app.openapi`            |
| QR 打卡頁（寫入者）        | `qr-checkin.component.html` 共 9 行，是「開發中」佔位頁 |
| 家長端到班紀錄（讀取者）   | `<p>attendance works!</p>` —— Angular 鷹架殘骸          |

**所以現在沒有任何路徑會產生一筆 `daily_checkins`。** 一個唯讀的看板顯示的會是
永遠空的資料。

### 二、打卡會把出勤散給當天同分校的**每一堂課**，不比對報名

`daily-checkins.ts:72-80`：撈 events 的條件是 `org_id + event_date`（有給 campus 才加
campus），**沒有任何 enrollment 過濾**。接著對「該學生 × 每一個 event」寫
`attendance_records.status = 'present'`。

**這已經被裁掉了**（決策 5）：日到班不再衍生課堂出勤。

### 三、日到班的出勤永遠不會標記 `attendance_taken_at`

`dashboard.util.ts:11-12` 已經記載：打卡建立 `attendance_records` 但從不寫
`events.attendance_taken_at`，所以日到班模式下每一堂被推算出席的課，在「有沒有
點名」的判斷裡都算成**沒點名**。

這是「未點名課堂」卡在日到班模式被隱藏的真正原因，也是**看板不能沿用
`takenAt` 當狀態來源**的原因。

### 附帶事實：API 層對 `attendance_mode` 完全沒有分支

全 repo 只有兩個地方讀 `attendance_mode`：`routes/org-settings.ts`（CRUD）與
`dashboard.component.ts`（隱藏那張卡）。**API 的業務邏輯一律當成 per_session 在跑。**
決策 5 之後這件事必須改變 —— 見〈裁決的代價〉。

## 設計決策

### 決策 1：看板是**記錄的地方**，不只是看的地方（已裁決）

**理由**：事實一。沒有寫入者，唯讀看板等於一張永遠空的表。

而且從任務出發也該如此 —— 補習班櫃台的晨間工作就是「小孩進來，我把他勾起來」。
掃碼是**其中一種**輸入方式：它依賴硬體、依賴 QR 頁做完、依賴學生帶卡。
**點一下勾到班是最原始也最可靠的那一種**，而且不依賴任何尚未存在的東西。

**被拒絕的替代方案**：先做唯讀看板、等 QR 頁做完再說 —— 那會交付一個無法驗證的
東西，因為它永遠是空的。

### 決策 2：晨間視角是「**誰還沒到**」，不是「誰到了」

一張列出全部學生的表，行政要自己掃描找出缺口。而晨間真正的工作是**追還沒到的人**
（打電話問家長、確認是不是請假）。

```
還沒到（N）      ← 這是工作，預設展開、排在上面
  每一列：學生 · 年級 · 今天的課（時間 + 班級）· [勾到班]

已請假（L）      ← 第三種狀態，不是「還沒到」的一種
  每一列：學生 · 請假區間 · 送出者

已到（M）        ← 這是確認，預設收合
  每一列：學生 · 到班時間 · [取消]
```

**把請假的人混在「還沒到」裡，行政會去打一通不必要的電話。**

> 這一條沿用 UX 審查裡驗過的縫：`attendance_status` 已經有 `on_leave`，而點名
> dialog 顯示得出來（會鎖住那一列）卻設定不了。看板要從一開始就把
> `leave_requests` 讀進來，不要重蹈覆轍。

### 決策 3：名單來自「今天有課的在籍學生」，不是「全部在籍學生」

看板要回答「今天**應該**有誰」。多分校、多班級的機構，全部在籍學生會是一張與今天
無關的長名單。

名單 = 今天在這個分校有課的班級 ∪ 那些班的在籍學生（`enrollments.status = 'active'`）。

### 決策 4：狀態來源是 `daily_checkins`，唯一

事實三：`attendance_taken_at` 永遠是空的。看板顯示的是「這個人今天到了沒」，
那件事的真相在 `daily_checkins`（`UNIQUE (student_id, checkin_date)`，一天一筆）。

### 決策 5：日到班**不衍生課堂出勤**（已裁決）

打卡只寫 `daily_checkins`。`POST /api/daily-checkins` 那段對當天所有 events 寫
`attendance_records` 的 fan-out **要移除**。

**理由**：日到班模式下「這孩子今天來了嗎」就是全部的問題。逐堂出勤率在這種機構
不是一個存在的量 —— 硬要衍生一個，得到的是一個沒有人量測過、卻會出現在家長端與
統計裡的假數字。

**被拒絕的替代方案**：加 enrollment 過濾、只寫他有報名的課。那修掉了污染，
但仍然憑空產生一個「他每一堂都出席」的宣稱 —— 系統從來沒有觀察過那件事。

**含意**：看板不讀也不寫 `attendance_records`。

### 決策 7：儀表板要有「今天有課但還沒到」的**清單**，不只是一個數字

> 使用者 2026-09-02：「管理者會很需要知道目前某個分校有哪一個小孩今天有課但還沒到班，
> 這會需要出現在日到班版本的儀表板。」

一個「還沒到 3」的數字回答不了「要打電話給誰」。儀表板已經有兩支清單
（今日課表、今日請假），日到班模式加第三支 **今日未到班**，與它們同構。

**分校怎麼處理 —— 儀表板現在沒有分校範圍。** `dashboard.component.ts` 全篇沒有
一個 `campus` 字樣，整頁是全機構的；分校選擇只存在於課堂管理頁自己的
`selectedCampusIds`。

要滿足「某個分校有哪些小孩」有兩條路：

|          | 做法                                                 | 取捨                                                                                 |
| -------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **採用** | 清單**依分校分組**，機構只有一個分校時不顯示分組標題 | 不新增控制項；多分校時一眼看到每個分校各缺誰，比先選再看更快                         |
| 拒絕     | 儀表板加一個分校選擇器                               | 它會連帶影響同頁其他卡片的語意（收入、報名數要不要跟著縮？），是比這一刀大得多的問題 |

清單顯示：學生 · 年級 · 今天第一堂課的時間與班級。點一列進到班看板並鎖定該分校。
超過一定筆數收尾成「還有 N 位 → 看板」，儀表板不是名冊。

**分組這個選擇在分校隔離落地前後都成立**：現在管理者看到全部分校各自的缺口；
有隔離之後他只會拿到自己那組，同一段 UI 不用改。「先選分校再看」則兩邊都要改。
見 [[architecture/authorization-scope]]。

### 決策 6：時窗政策沿用既有的，不另立一套

`attendance.ts:1257+` 的 `assertAttendanceWindow` 已經有一套規則：
`attendance_responsible`（admin / teacher）+ `attendance_retroactive_days`，
管理員豁免但窗外修改留 audit log。

**看板的補登與取消走同一條規則。** 另寫一套的話，同一間補習班對「昨天的紀錄
還能不能改」會有兩個答案。

## 裁決的代價 —— 兩處靠 `attendance_records` 的東西會失效

決策 5 拿掉的不只是污染。有兩個既有機制**正是靠那些衍生記錄在運作**，
API 層又完全沒有 mode 分支（見附帶事實），所以它們會**靜默地**變成錯的。

### 一、堂數包的扣課會歸零

`routes/session-packs.ts:97-120` 的 `summariseEnrollment`：
`deducted` / `remaining` 由該班 events 上的 `attendance_records.status` 算出來
（`lib/session-pack.ts` 的 `countDeductedSessions`）。

日到班機構沒有那些記錄之後：**買 20 堂 → `deducted` 永遠 0、`remaining` 永遠 20。**

> 諷刺的是 `session-packs.ts:55` 的註解**正好在描述那個 fan-out**，並用「濾到這個
> 報名的班」把它變成正確的扣課。那不是將就，是這條路徑目前唯一的扣課機制。

### 二、「已有出勤紀錄」的刪除守門會失效

`routes/enrollments/validation.ts` 的 `checkEnrollmentAttendance` 用「這個班的
events 上有沒有這個學生的 attendance_records」擋掉刪除／改班。

日到班機構一律回 `none`，於是**一筆有真實到班歷史的報名可以被刪掉**。
這支函式的註解自己寫著「舊版把錯誤吞掉，於是守門從來沒有生效過」——
決策 5 會讓它在日到班機構上再次沒有生效，只是換一個原因。

### 修法：兩處都改讀 `daily_checkins`，語意不變

日到班模式下，「這個學生在這個班消耗了幾堂」＝
**他的打卡日期 ∩ 這個班有 session 的日期**。

這**精確重現今天的行為**（今天是 fan-out 寫進所有 events，再由 class 過濾撈回來），
只是不再把中間那批假記錄落地。`checkEnrollmentAttendance` 同理：問的變成
「這個班的上課日裡有沒有他的打卡」。

**請假折抵**（`leave_deducts_session`）在日到班怎麼算是**未解的一小塊**：
現在靠 `attendance_records.status = 'on_leave'`，而那些記錄不會再存在。
`leaves.ts:314` 已經有「只更新該學生實際有報名的 attendance_records」的邏輯，
日到班要改成從 `leave_requests` 直接推導。**列為需求單的一項，不在這一刀裡解。**

## 分校隔離：這一刀**不做**，但也不擋路

使用者指出分校的資料隔離必須要設計權限。查證結果是**目前完全沒有**：
`staff_campuses` 這張表存在，但 `authMiddleware` 不讀它（context 只有 `orgId` /
`roles` / `permissions`），所以任何管理員都看得到所有分校的資料。

**這比一支看板大，而且在單一功能裡解會更糟** —— 會得到一個守得住的畫面
和其餘全部守不住的畫面，使用者無從分辨。隔離要跟 c1 的 `org_id` 一樣沒有例外
才可信。現況、形狀與待裁決的部分記在 [[architecture/authorization-scope]]。

這一刀的責任只有兩條：**端點照收 `campusId`**（等 middleware 長出來時它自然被
驗證）、**畫面依分校分組而不是先選再看**（見決策 7）。

## 介面分流：哪些地方要隨 `attendanceMode` 改變

原則是：**per_session 的機構完全看不到日到班的東西，反之亦然。**
不是把兩套都顯示出來讓使用者自己忽略一半。

| 位置                      | `per_session`                      | `daily_checkin`                       |
| ------------------------- | ---------------------------------- | ------------------------------------- |
| 側欄（課務管理）          | 課堂管理                           | 課堂管理 **+ 到班看板**               |
| 儀表板橘帶那句話          | 「今天 N 堂課，其中 M 堂還沒點名」 | 「今天 N 堂課 · **已到 X / 應到 Y**」 |
| 儀表板待處理卡            | 「未點名課堂 N」                   | 「**還沒到 N**」                      |
| 課表列的 chip             | 已點名 / 未點名                    | **不顯示**                            |
| 課堂管理頁首 chip         | 「此分校今日未點名 N 堂」          | **不顯示**                            |
| 課堂 ⋮ 的「管理出勤狀況」 | 顯示                               | **不顯示** —— 見下                    |

「管理出勤狀況」原本我列為待決。**決策 5 之後它沒有懸念了**：日到班既然不承認
逐堂出勤，留著那個入口等於允許行政手動製造決策 5 說不存在的資料 —— 一個混合模型，
而混合模型正是這份設計要收掉的東西。日到班要更正的是**到班紀錄本身**，
入口在看板上（取消／補登）。

## 需要的新 API（需求單給 billing-api）

| #   | 端點 / 改動                                                      | 說明                        |
| --- | ---------------------------------------------------------------- | --------------------------- |
| 1   | `POST /api/daily-checkins` **移除** `attendance_records` fan-out | 決策 5                      |
| 2   | `GET /api/daily-checkins?date=&campusId=`                        | 現在**完全沒有讀取端點**    |
| 3   | 取消打卡（`DELETE` 或帶旗標的 `POST`）                           | 走 `assertAttendanceWindow` |
| 4   | `session-packs` 的扣課在日到班改讀 `daily_checkins`              | 否則堂數包永遠不扣          |
| 5   | `checkEnrollmentAttendance` 在日到班改讀 `daily_checkins`        | 否則刪除守門失效            |
| 6   | 請假折抵在日到班的算法                                           | 未解，另開                  |

4、5、6 是決策 5 的下游，**與看板同一批上線，不能落後** —— 它們失效的方式是靜默的
（數字看起來正常，只是永遠不動）。

**「今天應該有誰」為什麼做成聚合端點。** 原本打算用既有的
`GET /api/attendance/sessions` 加 enrollments 查詢在前端串起來。決策 7 之後
**儀表板也要同一份資料、而且是全機構分組**，前端串就變成「課 × 班 × 在籍學生」
的 N+1，而且要串兩次（儀表板一次、看板一次）。

這正是 `lessons/workers-fanout-costs-before-the-db` 記的那個坑（8 支並行時每支慢
2.4 倍）。**一支端點回四段名單，兩個畫面共用。**

## 這份設計**不做**什麼

- **不做 QR 掃碼介面。** 公開頁的 `qr-checkin` 現在是佔位頁，屬於另一支工單。
  看板不依賴它；它做好之後兩者寫進同一張表，自然相容。
- **不做家長端到班紀錄。** 那頁是鷹架殘骸，屬於家長端工單。
- **不處理離開時間。** `daily_checkins` 只有 `checked_in_at`。加欄位是 schema 變更。
- **不解請假折抵在日到班的算法**（需求單 6）。
- **不做「批次全部到班」。** 晨間的價值在於逐一確認誰還沒來；一鍵全到會讓這張看板
  變成橡皮圖章，而它要防的正是「沒有人真的看過」。
- **不回填既有資料。** 現況沒有任何路徑產生 `daily_checkins`，衍生的
  `attendance_records` 也就不存在（seed 除外）—— 沒有東西要遷移。**實作前確認一次。**

## 重量與元件

**先問：既有的東西夠不夠？**

| 需要         | 既有的                           | 結論                                          |
| ------------ | -------------------------------- | --------------------------------------------- |
| 橘帶         | `app-page-band`                  | **夠** —— 這頁的帶是「一句話 + 一個錨點數字」 |
| 空狀態       | `app-empty-state`（17 個使用點） | **夠**                                        |
| 可收合的分段 | `app-collapsible`                | **夠**（「已到」段預設收合）                  |
| 狀態點＋字   | `app-status-dot`（22 個使用點）  | **夠** —— 到班／未到／請假三態                |
| 名單列       | 無                               | **拼裝就好** —— 唯一使用點，不立元件          |

**預期新增元件：0。**

**重量風險在請求數不在 bytes**：如果「今天應該有誰」要打「今天的課」+「每個班的
在籍學生」共 N+1 支請求，會重演儀表板 fan-out 的問題
（`lessons/workers-fanout-costs-before-the-db`：8 支並行時每支慢 2.4 倍）。
**實作前先量真實班級數**；超過 3–4 個班就開聚合端點，不要在前端串。

## 手機版

櫃台的晨間工作很可能就是拿著手機在門口勾 —— **這一頁的手機版不是降級版，
是主場景**。設計時一起做，不是之後補（見 `day-timeline` 那次的教訓）。

- 「勾到班」是主要動作，觸控目標 ≥ 44×44
- 名單列在窄螢幕改成兩行（姓名＋年級 / 課程時間），**不砍掉姓名以外的欄位** ——
  行政要靠「今天上什麼課」確認是不是找錯人
- 不用 viewport 單位（c6）

## 驗證

demo 目前是 `per_session`（為了驗密集日 seed 翻過去的），所以驗 `daily_checkin`
**用本機** —— 翻 demo 會讓其他席正在驗的東西變樣。

至少要看到的：

1. 日到班機構的側欄有「到班看板」，per_session 機構沒有
2. 日到班機構的橘帶與課表**不再出現「未點名」三個字**，⋮ 選單沒有「管理出勤狀況」
3. 看板上勾一個學生 → 他從「還沒到」移到「已到」，時間正確
