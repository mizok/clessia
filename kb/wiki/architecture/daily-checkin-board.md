# 日到班看板與兩種點名模式的介面分流

> **這是設計，不是實作紀錄。** 依 `clessia-feature-slice` 的 STOP gate：
> 待計畫席初審 + 使用者批准之後才寫產品碼。

## 這份設計要解的問題

demo 的機構是 `attendanceMode: 'daily_checkin'`，而：

- **管理端沒有任何日到班介面。**「到班紀錄」是家長端路由（`/parent/attendance`）
- 儀表板**刻意隱藏**「未點名課堂」卡（`dashboard.util.ts` 的 `countUntakenSessions`
  在非 per_session 時回 `null`）—— 等於告訴使用者「這不是你的工作方式」
- 但橘帶仍然說「今天 N 堂課，其中 M 堂還沒點名」、課表列仍掛「未點名」chip、
  課堂管理頁自己還掛「此分校今日未點名 N 堂」

淨效果：**畫面報一個在這間補習班的設定下不存在的問題，拿掉了修它的捷徑，
再把使用者導到一個用不同模型運作的頁面。**

## 開工前先講三件查證出來的事實 —— 它們改變了這個工單的形狀

### 一、整個日到班功能目前是「一支沒有人呼叫的 POST」

| 元件                       | 現況                                                    |
| -------------------------- | ------------------------------------------------------- |
| `POST /api/daily-checkins` | **存在且完整**（`routes/daily-checkins.ts`，117 行）    |
| 讀取端點                   | **不存在** —— 那個檔案只有一個 `app.openapi`            |
| QR 打卡頁（寫入者）        | `qr-checkin.component.html` 共 9 行，是「開發中」佔位頁 |
| 家長端到班紀錄（讀取者）   | `<p>attendance works!</p>` —— Angular 鷹架殘骸          |

**所以現在沒有任何路徑會產生一筆 `daily_checkins`。** 一個唯讀的看板顯示的會是
永遠空的資料。

### 二、打卡會把出勤散給當天同分校的**每一堂課**，不比對報名

`daily-checkins.ts:72-80`：撈 events 的條件是 `org_id + event_date`（有給 campus 才加
campus），**沒有任何 enrollment 過濾**。接著對「該學生 × 每一個 event」寫
`attendance_records.status = 'present'`。

也就是說：學生打一次卡 → 當天該分校**所有班**都算他出席，包含他沒報名的班。

> 計畫席說「掃碼不比對報名」是**懸而未裁**的業務題。**現況已經站在其中一邊了**，
> 而且是比「不比對」更強的版本 —— 它不只略過驗證，是主動寫入不相關班級的出勤。
> 這份設計把它當成**待裁決事項**（見下），不預設答案。

### 三、日到班的出勤永遠不會標記 `attendance_taken_at`

`dashboard.util.ts:11-12` 已經記載了這件事：打卡建立 `attendance_records` 但從不寫
`events.attendance_taken_at`，所以日到班模式下每一堂被推算出席的課，
在「有沒有點名」的判斷裡都會算成**沒點名**。

這是「未點名課堂」卡在日到班模式被隱藏的真正原因，也是**看板不能沿用
`takenAt` 當狀態來源**的原因。

## 設計決策

### 決策 1：看板是**記錄的地方**，不只是看的地方

**理由**：事實一。沒有寫入者，唯讀看板等於一張永遠空的表。

而且從任務出發也該如此 —— 補習班櫃台的晨間工作就是「小孩進來，我把他勾起來」。
掃碼是**其中一種**輸入方式，不是唯一：它依賴硬體、依賴 QR 頁做完、依賴學生帶卡。
**點一下勾到班是最原始也最可靠的那一種**，而且不依賴任何尚未存在的東西。

**被拒絕的替代方案**：先做唯讀看板、等 QR 頁做完再說。
拒絕理由是那會交付一個無法驗證的東西 —— 我們無法判斷它對不對，因為它永遠是空的。

### 決策 2：晨間視角是「**誰還沒到**」，不是「誰到了」

一張列出全部學生的表，行政要自己掃描找出缺口。而晨間真正的工作是**追還沒到的人**
（打電話問家長、確認是不是請假）。

所以看板的主結構是兩段：

```
還沒到（N）      ← 這是工作，預設展開、排在上面
  每一列：學生 · 年級 · 今天的課（時間 + 班級）· [勾到班]
  已請假的學生不出現在這裡，另外標示

已到（M）        ← 這是確認，預設收合
  每一列：學生 · 到班時間 · [取消]
```

**「已請假」是第三種狀態，不是「還沒到」的一種。** 它們在畫面上要分開 ——
把請假的人混在「還沒到」裡，行政會去打一通不必要的電話。

> 這一條直接沿用 UX 審查裡驗證過的縫：`attendance_status` 已經有 `on_leave`，
> 而點名 dialog 顯示得出來（會鎖住那一列）卻設定不了。看板要從一開始就把
> `leave_requests` 讀進來，不要重蹈覆轍。

### 決策 3：名單來自「今天有課的在籍學生」，不是「全部在籍學生」

看板要回答「今天**應該**有誰」。多分校、多班級的機構，全部在籍學生會是一張
與今天無關的長名單。

名單 = 今天在這個分校有課的班級 ∪ 那些班的在籍學生（`enrollments.status = 'active'`）。

**這個定義只用在「顯示」。** 打卡寫入時要不要比對報名，是決策 5 的待裁事項 ——
兩者刻意分開，因為顯示的正確答案很清楚，寫入的不清楚。

### 決策 4：狀態來源是 `daily_checkins`，不是 `attendance_records`

事實三：日到班模式下 `attendance_taken_at` 永遠是空的，而 `attendance_records`
是打卡的**衍生物**。看板顯示的是「這個人今天到了沒」，那件事的真相在
`daily_checkins`（`UNIQUE (student_id, checkin_date)`，一天一筆）。

**含意**：看板不該去讀或寫 `attendance_records`。那些是 API 在打卡時自己處理的
副作用，看板只負責「到了／沒到」這一個事實。

### 決策 5：待裁決事項 —— 兩種可能都留活口

| 問題               | 選項 A                         | 選項 B                       |
| ------------------ | ------------------------------ | ---------------------------- |
| 打卡要不要比對報名 | 只寫該學生**有報名**的當天課程 | 維持現況：寫當天同分校所有課 |

**設計上怎麼留活口**：看板本身不做這個判斷 —— 它只呼叫 `POST /api/daily-checkins`，
散給哪些 events 是那支 API 的職責。哪一邊被選中，看板的程式碼都不用改。

**但畫面上要誠實**：勾到班之後，那一列顯示的是「已到班 09:12」，
**不顯示「已為 N 堂課記錄出席」** —— 因為那個數字取決於未裁決的規則，
現在寫死任何一種說法，之後都會變成謊。

### 決策 6：時窗政策沿用既有的，不另立一套

`attendance.ts` 的 `assertAttendanceWindow` 已經有一套規則：
`attendance_responsible`（admin / teacher）+ `attendance_retroactive_days`，
管理員豁免但窗外修改留 audit log。

**看板的補登與取消要走同一條規則。** 另寫一套的話，同一間補習班對「昨天的出勤
還能不能改」會有兩個答案。

## 介面分流：哪些地方要隨 `attendanceMode` 改變

分流的原則是：**per_session 的機構完全看不到日到班的東西，反之亦然。**
不是把兩套都顯示出來讓使用者自己忽略一半。

| 位置                          | `per_session`                      | `daily_checkin`                          |
| ----------------------------- | ---------------------------------- | ---------------------------------------- |
| 側欄（課務管理）              | 課堂管理                           | 課堂管理 **+ 到班看板**                  |
| 儀表板橘帶那句話              | 「今天 N 堂課，其中 M 堂還沒點名」 | 「今天 N 堂課 · **已到 X / 應到 Y**」    |
| 儀表板待處理卡                | 「未點名課堂 N」                   | 「**還沒到 N**」                         |
| 課表列的 chip                 | 已點名 / 未點名                    | **不顯示**（那個狀態在這個模式沒有意義） |
| 課堂管理頁首 chip             | 「此分校今日未點名 N 堂」          | **不顯示**                               |
| 課堂 ⋮ 選單的「管理出勤狀況」 | 顯示                               | **待裁決** —— 見下                       |

**「管理出勤狀況」在日到班模式下要不要留**，我沒有答案，列為需要業務判斷的一項：
留著等於允許逐堂覆寫打卡推算的結果（有時候是對的：某堂課學生中途離開）；
拿掉則行政沒有任何更正的手段。**建議先留，並在 dialog 裡標明「此機構採日到班，
這裡的修改只影響這一堂」。**

## 需要的新 API（要開需求單給 billing-api）

| 端點                                                  | 用途                   | 備註                                                               |
| ----------------------------------------------------- | ---------------------- | ------------------------------------------------------------------ |
| `GET /api/daily-checkins`                             | 查某日某分校的打卡紀錄 | 現在**完全沒有讀取端點**                                           |
| `DELETE /api/daily-checkins/:id` 或 `POST` 帶取消旗標 | 勾錯了要取消           | 要走 `assertAttendanceWindow`，並處理它衍生的 `attendance_records` |

「今天應該有誰」那份名單**不需要新端點** —— 可以用既有的
`GET /api/attendance/sessions?date=…&campusId=…` 拿到今天的課與班級，
再用既有的 enrollments 查詢取得在籍學生。**先確認這條路的請求數可以接受**
（見下面的重量一節），不行再開一支聚合端點。

## 這份設計**不做**什麼

- **不做 QR 掃碼介面。** 那是另一支工單（公開頁的 `qr-checkin` 現在是佔位頁）。
  看板不依賴它，它做好之後兩者寫進同一張表，自然相容。
- **不做家長端到班紀錄。** 那頁現在是鷹架殘骸，屬於家長端工單。
- **不裁決「掃碼要不要比對報名」。** 見決策 5 —— 設計對兩種答案都成立。
- **不處理離開時間。** `daily_checkins` 只有 `checked_in_at`，沒有離開欄位。
  加欄位是 schema 變更，超出這一刀。
- **不動 `attendance_records` 的既有語意。** 看板不讀不寫它。
- **不做「批次全部到班」。** 晨間的價值在於逐一確認誰還沒來；一鍵全到會讓這張
  看板變成一個橡皮圖章，而它要防的正是「沒有人真的看過」。

## 重量與元件（套用剛鑄的分析方法）

**先問：既有的東西夠不夠？**

| 需要         | 既有的                           | 結論                                                        |
| ------------ | -------------------------------- | ----------------------------------------------------------- |
| 橘帶         | `app-page-band`（左右兩欄骨架）  | **夠** —— 這頁的帶是「一句話 + 一個錨點數字」，正是它的形狀 |
| 空狀態       | `app-empty-state`（17 個使用點） | **夠**                                                      |
| 可收合的分段 | `app-collapsible`                | **夠**（「已到」段預設收合）                                |
| 狀態點＋字   | `app-status-dot`（22 個使用點）  | **夠** —— 到班／未到／請假三態                              |
| 名單列       | 無                               | **拼裝就好** —— 這一頁是唯一使用點，不立元件                |

**預期新增元件：0。** 這一刀應該是純拼裝。

**重量風險在請求數不在 bytes**：如果「今天應該有誰」要打「今天的課」+「每個班的
在籍學生」共 N+1 支請求，那會重演儀表板 fan-out 的問題
（見 `lessons/workers-fanout-costs-before-the-db.md`：8 支並行時每支慢 2.4 倍）。
**實作前先量一次真實班級數**；超過 3–4 個班就該開聚合端點，不要在前端串。

## 驗證

demo 目前是 `per_session`（為了驗密集日 seed 翻過去的），所以驗 `daily_checkin`
要嘛把 demo 翻回來、要嘛用本機。**建議用本機**：翻 demo 會讓其他席正在驗的東西變樣。

至少要看到的：

1. 日到班機構的側欄有「到班看板」，per_session 機構沒有
2. 日到班機構的橘帶與課表**不再出現「未點名」三個字**
3. 看板上勾一個學生 → 他從「還沒到」移到「已到」，時間正確
4. 有請假的學生**不在「還沒到」裡**
5. 昨天的看板：時窗政策生效（`retroactiveDays = 0` 時管理員可改但留 audit log）
