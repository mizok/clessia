# 載入態與空狀態共用視覺槽的掃描

**掃描是完整的**（涵蓋 `apps/web/src/app` 全部模板）。**提案尚未批准，未動任何實作程式碼。**

## 一句話

整個 repo 把「還在載」跟「查完了，沒有」render 成同一個樣子。
使用者分不出來 —— 而其中一處會讓行政重複催繳。

## 最值得記的數字

```
16 支印「載入中」文字的模板
  ├─  7 支替失敗態加了 --error 之類的修飾字   ← 失敗其實有被區分
  └─  1 支替載入態加了修飾字                  ← 載入幾乎沒有
```

**7 比 1。** 不是隨機疏漏，是一致的盲點：大家都記得標「失敗」，都忘記標「還在載」。

推測是失敗感覺像個「事件」值得標，載入感覺是過渡、等一下就沒了。
**但被誤讀的正是載入態** —— 因為它跟「沒有資料」共用同一個槽。

> 這一點修正了工單原本的假設。工單說「三態被 render 成同一種形狀」，
> 實際上**失敗態在多數地方是好的**，沒被區分的是「載入」對「空」。

## 最硬的一處證據

`features/admin/pages/payments/invoice-detail-dialog/invoice-detail-dialog.component.html`
的 `invoice-detail__empty` 這個 class 同時裝著：

| 行  | 文字                           | 性質         |
| --- | ------------------------------ | ------------ |
| 50  | 這張帳單還沒有明細，金額是 0。 | 對資料的斷言 |
| 125 | 還沒有任何收款。               | 對資料的斷言 |
| 235 | **載入中…**                    | **不是斷言** |
| 237 | 還沒有催繳過。                 | 對資料的斷言 |

催繳那一段，「載入中」跟「還沒有催繳過」是**同一個位置、同一個樣式、同一種灰字**。
行政沒有任何線索能分辨系統是「還在查」還是「查完了說沒有」。

**誤讀的後果是重複催繳** —— 對已繳完或已被催過的家長再發一次，是會被記住的那種錯。

`contact-book.page.html` 的 `__missing-note` 是同一個形狀（載入／失敗／空共用一個 class）。

## 機制早就有了，缺的是規則

不是「缺一套骨架系統」。`styles.scss` 已經有 `.skeleton-bar`、`.skeleton-list`、
`@keyframes skeleton-wave`，**而且是多數慣例**：

| 模板                         | 支數 |
| ---------------------------- | ---- |
| 用骨架                       | 27   |
| 印「載入中」文字             | 16   |
| **同一支兩套都有**（半遷移） | 2    |

而且原則**已經被寫下來過一次**。`dashboard.component.html:278`：

```html
<!-- null = 還不知道。載入中不得宣稱「今日尚無排課」 -->
```

有人已經想清楚了，就寫在那一行上面。但那是一句註解不是一條規則 ——
它守住了那一個 `@if`，沒守住隔壁檔案，**也沒守住同一支檔案的第 76 行**
（那裡的「載入中」還站在數字的位置上）。

## 掃描結果（按槽位分類）

槽位決定它會被誤讀成什麼。

| 類     | 支  | 槽位                                                                                                                                       | 會被讀成                                               |
| ------ | --- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| **甲** | 3   | 值槽／空狀態槽 —— dashboard `__todo-value`、invoice-detail `__empty`、contact-book `__missing-note`                                        | **一個查完的結果**                                     |
| **乙** | 10  | 專屬 `__state` 段落 —— changes、enrollments、notifications、teaching-log、schedule、class-log-sheet、teacher-students、announcement-inbox… | 位置不誤導，但**載完會跳版**、且與「沒有資料」同 class |
| **丙** | 3   | 有 spinner —— schools、兩支 exam-form-dialog                                                                                               | 不是這個病（spinner 本身講明「進行中」）               |

## 提案（**待批准**）

1. **原則升成規則**：「還不知道」不得借用「知道了」的任何一個槽。
   空狀態文字是對資料的斷言，載入態不是 —— 共用 class 就是讓 UI 宣稱它不知道的事。
2. **甲類 3 支換骨架。** 骨架要占住最終內容的形狀與尺寸，否則載完跳版 ——
   而跳版本身又是另一個「看起來像壞了」。
3. **乙類 10 支先加 `--loading` 修飾字**，讓它跟同 class 的空狀態分得開；骨架化排後面。
4. **丙類 3 支不動。**

### 防復發

這個病的特徵是**不會有任何測試變紅** —— 兩種狀態都「正常顯示」。所以要嘛有 gate，
要嘛它會回來。

可偵測的形狀：**同一支模板裡，同一個 class 同時出現在「載入分支」與「空／值分支」。**

**未驗誤報率。** 會不會一堆假陽性是這個提案最大的未知；要做的話先原型再決定進不進 gate。

## 這件事只解掉四分之一 —— Tester 的切分

Tester 席（desktop-44）2026-09-05 的桌機評測抓到同族的四項，完整報告在
`herdr-team/tester-admin-ux-audit-2026-09-05.md`。他點出的關鍵是
**本體不是「載入中」三個字，是「狀態轉換期間畫面是壞的」**：

| #   | 現象                                                                      | 骨架解得掉嗎                  |
| --- | ------------------------------------------------------------------------- | ----------------------------- |
| 1   | 儀表板「載入中」粗體佔數字位 4–5 秒                                       | **是** —— 本文的甲類          |
| 2   | 側邊選單手風琴約 2 秒才展開；收合時上一組項目殘留半截，與下一個群組標題疊 | 否 —— 動畫太慢 + 收合沒清乾淨 |
| 3   | 系統設定 tab 底線：切到「一般」後「分校」下方仍留橘線，**同時兩條**       | 否 —— 同上                    |
| 4   | 課程列表展開鍵按下後 2–3 秒才有東西，中間像沒反應（他第一次誤判成展不開） | 否 —— 同上                    |

**這個切分是他做的，我認為對。** 骨架化只解第 1 項；2/3/4 是另一件事
（轉場動畫的時長與清理），不該混進同一刀。
