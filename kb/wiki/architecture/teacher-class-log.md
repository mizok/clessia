# 教務日誌（老師端寫入）

訪談四大痛點之一（[[rules/teaching-log-rules]]）。後端三支端點早就在
（`GET` / `PUT` / `POST {id}/publish`），**前端零認領**——這一刀補老師端的寫入面。

## 切成 v1a / v1b，理由是「不可逆的死按鈕」

| | 範圍 | 為什麼是這條線 |
| --- | --- | --- |
| **v1a**（本刀） | 老師寫入＋草稿。**不含發布按鈕** | 見下 |
| **v1b**（緊接） | 家長端讀取頁 ＋ 發布啟用 | 發布有了下游才有意義 |

### 為什麼 v1a 不放發布按鈕

三件事同時成立：

1. **沒有 unpublish**——`class-logs.ts` 只有 GET / PUT / publish，`published_at` 設下去拿不掉
2. `publish` **只設時間戳**，沒有任何通知邏輯（全 repo 沒有 LINE Messaging 實作，
   LINE 在這裡只有 OAuth 登入）
3. 家長端**沒有任何畫面讀 `class_logs`**

所以那顆按鈕會是「不可逆、而且什麼都不會發生」。老師按下去的合理預期是
「家長看得到了」，事實是沒有——**畫面說的話要跟實際行為一致**，這一席為此改過
銷假警告的文案、刪過虛構的狀態列舉、標過未實作的 spec 段落。

**按鈕不存在，不是 disabled。** 灰著的按鈕仍然在告訴使用者「這裡有這個功能」，
而它在 v1b 之前根本不該被承諾。

> v1b 啟用發布時，確認彈窗要把後果說死：**之後會接 LINE 推播，發了就收不回。**
>
> 並採納 #338 的構圖論證：**「存草稿」與「發布」是兩顆視覺權重不同的按鈕，
> 不是一個儲存加一個開關**——避免「以為只是存檔，其實通知了所有家長」。
> 另外 v1b 的發布要求**至少一欄有內容**：發布一篇空日誌對家長是純雜訊。

## 入口：課堂卡上的 bottom sheet

老師端只有三頁（課表／學生／通知），而寫日誌是**下課當下**的動作。照
[[architecture/teacher-today-flow]] 的判準（站在教室門口的老師此刻要做什麼），
它跟點名同一個位置。

沿用點名面板已經驗證過的形狀（[[architecture/teacher-schedule-mobile-day]]）：
**手機從下方升起、桌機置中**——老師站著單手用，置中會把主要動作推到拇指構不到的地方。

### 停課的課堂沒有入口

不會發生的課沒有教學紀錄可寫。跟 `canTakeAttendance` 同一個判準的一半
（`status !== 'cancelled'`），但**不需要 `eventId`**——日誌掛在班×日期，
不掛出勤事件，所以停課以外的課堂一律可寫，包含未來的（規則明說
「老師可能先寫作業、下課後再補教學紀錄」）。

### 同一班同一天兩場課，指向同一篇

`sessions` 的唯一鍵是 `(class_id, session_date, start_time)`，
`class_logs` 是 `(class_id, log_date)`——**兩張卡，一篇日誌**。

這是刻意的：規則說「對齊紙本現實（一班一天一篇），不掛 session」。
所以不改 schema，**改成 UI 講出來**：第二張卡打開時，若當天已有內容，
面板要明示「本日已有日誌」而不是讓老師以為自己在開新的一篇。

沒有這句的話，第二場課的老師會覺得自己在寫新的，然後把第一場的內容覆蓋掉。

**但那句話只是提示，真正的防線是開啟時預載既有內容。** 面板一開就把當天已有的
教學紀錄與作業填進輸入框——語意從「空白新寫」變成「編輯既有」，
於是覆蓋在結構上不可能發生，而不是靠老師讀到警語之後自己小心。

所以這一條由測試釘住：**「開啟時載入既有日誌內容」**。有它就不需要二次確認彈窗——
二次確認防的是「使用者沒注意」，而預載讓「沒注意」也不會造成損失。

## 課堂卡上的狀態點：v1a 只有「寫了沒」

沿用既有 `status-dot` 的 tone，不發明新色：**未寫 = `pending`（中空）、已寫 = `done`（實心）**。

design-web 的構圖（#338）提的是「草稿 = `pending`、已發布 = `done`」——**那是 v1b 的映射**。
v1a 沒有發布，照那個映射所有日誌會永遠停在 `pending`：**一個永遠到不了 done 的狀態點，
比沒有狀態點更糟**，它會讓老師以為自己一直有事沒做完。

> **v1b 會重開這一題，這裡先記著。** 發布加進來之後是三個狀態
> （未寫／已寫未發布／已發布），而 `pending` / `done` 只有兩格。
> 「已寫未發布」該落在哪一邊要等發布流程真的存在時再定——
> **現在決定等於替一個還沒有的東西挑名字。**

不加 `overdue`：v1a **根本沒有「逾期」的定義**（沒有任何截止時間），
而 tone 要先有使用者才加。同意 #338 的判斷，理由再往前一步。

## 兩個欄位的可見性不同，v1a 就要標示

規則：**教學紀錄預設內部、作業家長可見**。紙本傳的是公司內部群組，老師會寫
不給家長看的話。

**這不能等家長端做出來再補**——可見性是**寫入當下就決定的後果**。
v1a 若不標，老師會在「等一下家長也看不到」的認知下把話寫進錯的欄位，
而 v1b 上線那天那些話就一次全部曝光。

## 依賴：sessions 要回 `usesContactBook`

規則是「開＝個人聯絡簿，關＝教務日誌」，但老師端**取不到這個欄位**：
`/api/classes` 是 `ADMIN_ONLY`，而 `EventSessionSummary` 沒有它。

已開需求單（billing-api）。**這一刀的合併門檻就是那個欄位落地**——
在那之前入口無法判斷該不該出現，而**兩種錯法都不能接受**：
聯絡簿模式的班多一個入口，或日誌模式的班看不到功能。

> 不用「預設值是 `false` 所以猜日誌模式」——那是拿統計當授權。
> 本機 3 個班有 2 個是日誌模式，剩下那個猜錯就是錯。

## 拒絕的替代方案

| 方案 | 為什麼不 |
| --- | --- |
| 獨立的「教務日誌」頁面 | 那是規劃視角（這個月寫了哪些），而寫入是執行視角。今日流刻意不含月曆也是同一個理由 |
| 內嵌進課堂卡（不用 sheet） | 兩個 5000 字上限的 textarea 塞進水平 snap 軌道，觸控上難調——跟點名面板當初拒絕內嵌同一個理由 |
| 抽進 `shared/` | v1a 只有老師端一個使用者。共用是 2 個以上才提（`shared/` 的既有規則），三行相似好過一個錯的抽象 |
| 用 class-logs 回傳夾帶 `usesContactBook` | 那支不該回答「這個班用哪種模式」——語意錯位 |
| 發布按鈕先做成 disabled | 灰著的按鈕仍然在承諾功能存在 |

## 影響的既有元件

- `features/teacher/pages/schedule/schedule.page.*`——課堂卡多一顆按鈕與一個開啟流程
- `core/` 需要一支 `class-logs.service.ts`（目前不存在）
- `EventSessionSummary`——等 `usesContactBook` 欄位（外部依賴）
- **不影響**點名面板：兩者是課堂卡上的兩個獨立入口，不共用狀態

## v1a 的邊界（明確不做）

- **發布**——留 v1b
- **家長簽收**（`log_acknowledgements`）——無 API，留 P4
- **LINE 推播**——外部依賴未確認（規則文件自己列在「待確認的外部依賴」）
- **管理端的日誌檢視**——`/api/class-logs` 的權限含 admin，但那是另一個角色的頁面
- **歷史檢視**（這個班過去寫過哪些）——v1a 只處理「這一天這一班」
- **聯絡簿模式那一半的撰寫介面**——**刻意不做，不是遺漏。**

  #338 提議：聯絡簿模式的班在課堂卡下開一份「今天這堂課的學生名單 + 誰已經寫了」，
  每一列接既有的 `ContactBookEntryDialogComponent`（那支的註解明寫是設計給老師端用的）。
  **提議本身是對的，而且成本低**——名單來源是這堂課的 `enrollments`，
  跟點名名冊同一份資料，不必新查詢。

  不放進這一刀的理由：**那是另一個功能**（老師端聯絡簿撰寫），只是共用同一個
  「這堂課要寫東西」的入口。把它併進來會讓這一刀同時交付兩套資料模型
  （`classId+logDate→兩欄` 與 `studentId+entryDate→一則自由文字`），
  而它們唯一的共通點只是入口。

  **記在這裡是為了讓它之後不會被讀成缺失。** 要做就開 v1c，`ContactBookEntryDialogComponent`
  與 enrollments 這兩個現成的東西讓它會是很薄的一刀。
