# 家長端的資料範圍模型

> 2026-09-04 起草。**這份文件要使用者批准才動工** —— 它決定的是「誰看得到誰的小孩」，
> 寫錯的代價是把別人小孩的成績或帳單給錯人看。

## 問題

家長端引入了一個 admin 端沒有的維度。現有的兩層是：

| 維度     | 怎麼決定                       | 在哪裡               |
| -------- | ------------------------------ | -------------------- |
| `org_id` | 從 session 取，沒有例外        | `authMiddleware`     |
| 分校     | `staff_campuses` 的清單        | `campusRequestGuard` |
| **學生** | **`parent_student_relations`** | **不存在**           |

`parent_student_relations`（`parent_id` ↔ `student_id`）從 2026-03 的 migration 就在了，
但**沒有任何查詢面用它**：家長身分目前只打得到 `/api/me` 與 `/api/announcements`，
兩支都不回孩子的資料。

## 這不是新問題，是同一個模式的第三個實例

`campusRequestGuard` 的註解已經把理由寫透了，三條全部適用：

> **掛在全域，不是各路由自己檢查。** `org_id` 之所以可信是因為它沒有例外（c1）；
> 分校要的是同一種待遇。14 支路由收 `campusId`，靠每一支自己記得檢查的話，
> 總有一支會忘記 —— 而忘記的方式是安靜的。

> **越權指名回 403 不是空清單。** 默默回空會讓越權嘗試看起來像「那個分校那天
> 沒有人」：越權的人不知道自己被擋，被越權的機構也不會發現有人在試。

> 這一支只看 query string。**寫入時 body 帶的分校由各路由自己驗**
> （middleware 讀 body 會跟 zod-openapi 的驗證器搶同一個 stream）。

**所以設計的起點不是「發明一套家長授權」，是「照分校那層的形狀再做一層」。**

## 但有一個實質差異：檢查 vs 注入

|                | 分校                     | 學生                                         |
| -------------- | ------------------------ | -------------------------------------------- |
| 呼叫端會指名嗎 | 會（`?campusId=…`）      | **多半不會** —— 「我孩子的出缺席」是全部孩子 |
| guard 要做什麼 | **檢查**指名在不在範圍內 | **注入**範圍，讓查詢只撈得到那些             |

`campusRequestGuard` 是純檢查，所以它能只讀 query string 就完事。家長端不行 ——
**沒有指名的查詢也必須被限縮**，而那要影響 route 的查詢本身。

這就是這份設計真正要解的問題：**如何讓「忘記限縮」變成不可能，而不是變成一條規則。**

## 設計

### 一、middleware 注入範圍（單一來源）

`authMiddleware` 已經在查 `parents` 表（拿 name 給 display-name），同一次查詢把
`parent_student_relations` 一起 join，把 `studentScope`（這個人可以看到的 student id
清單）放進 context。

- **不是家長身分 → `null`**（跟 `campusScope` 對管理員一樣的約定：`null` = 不受限）
- **是家長但沒有任何關聯 → 空陣列**（不是 `null`）—— 一個沒綁小孩的家長帳號
  應該什麼都看不到，而不是看到全部。**這兩者的差別是這層最容易寫錯的地方。**

### 二、家長端拿不到原始的 `supabase`，只拿得到已綁 scope 的 `childDb`

> **這一節在預審時被推翻過一次，修正出處記 billing-api 席。**
>
> 原本寫的是「查詢走一個強制吃 scope 的 helper，TypeScript 的必填參數讓忘記變成
> 編譯錯誤」。**那個推論不成立** —— 必填參數守的是「呼叫時不能不給 scope」，
> **守不住「根本沒呼叫」**：route 裡直接寫 `c.get('supabase').from('scores')…`
> 照樣編得過，而那正是最可能發生的寫法（它跟 admin 端的每一支長得一模一樣）。

家長端的 route **不從 context 拿 `supabase`**。它拿到的是 `childDb` —— 一個已經綁好
這個家長的 `studentScope` 的查詢入口，每一次 `from()` 都自動帶上範圍條件。

**為什麼這比 helper 強**：正確的寫法變成**比錯的寫法短**。要繞過它得先去拿原始的
`supabase`，那是一個**看得見的動作**，不是一個忘記。

gate 只是收尾：**禁止家長端的檔案出現 `c.get('supabase')`**。它抓的是那個看得見的
動作，而不是要求 review 的人記得檢查每一支查詢有沒有帶 scope。

三層防線裡，**這個做法才真的在第一層**：

| 防線                 | 擋得住誰         | 這一節的做法     |
| -------------------- | ---------------- | ---------------- |
| **拿不到錯的工具**   | 所有人           | ✅ `childDb`     |
| 函式簽名（必填參數） | **呼叫它的人**   | ✕ 沒呼叫就沒防線 |
| 測試                 | 正在改這段的人   |                  |
| 註解／規則           | 願意停下來讀的人 |                  |

「每支 route 記得 join」是最後一層 —— 而 `campusRequestGuard` 的註解已經說了那條會
發生什麼：**總有一支會忘記，而忘記的方式是安靜的。**

### 三、指名越權回 403，不回空

沿用分校那層的決定。家長帶 `?studentId=<別人的小孩>` 要拿到 403，
不是一個看起來像「那個小孩沒有資料」的空清單。

### 四、多重角色：身分要看 `activeRole`，不是角色陣列的優先序

這是 #291 已經寫進程式碼註解的已知限制：

```ts
export function audienceFor(roles: readonly string[]): Audience | null {
  if (roles.includes('teacher')) return 'all_teachers';
  if (roles.includes('parent')) return 'all_parents'; // ← 到不了
  return null;
}
```

`auth.ts` 放進 context 的是**全部角色的陣列**，不是使用者此刻選的身分。所以
**同時是老師又是家長的人（補習班老師的小孩也在補習班）切到家長身分時，
看到的仍是老師的公告** —— 而且不會知道自己漏了什麼。

**錯的方向是靜默漏看**：不是看到不該看的，是看不到該看的。所以它不是資安漏洞，
是功能缺陷 —— 但它跟資料範圍是同一份模型的兩軸：

- **能看哪些學生** —— 資料範圍
- **此刻以什麼身分在看** —— 身分判定

同一個 codebase 現在對「多重角色」有兩種處理，而且方向相反：

| 位置                     | 做法                                                           |
| ------------------------ | -------------------------------------------------------------- |
| `requireAdminPermission` | **明確拒絕降級** —— 註解寫「不會降級成老師身分，真的出現再拆」 |
| `audienceFor`            | **隱含優先序** —— 誰在前面聽誰的，沒有人決定過                 |

前者是一個決定，後者是一個預設值。**這份設計要把後者也變成決定。**

建議：`activeRole` 進 API context（前端已經有 `AuthService.activeRole`，
現在只活在瀏覽器裡），身分相關的判定一律看它，找不到才退回角色陣列。

## 拒絕的替代方案

### ✕ 每支 route 自己 join `parent_student_relations`

`campusRequestGuard` 的註解就是為了拒絕這個而寫的。差別在於**分校那層錯了會多顯示
一個分校的排課，家長這層錯了會把別人小孩的成績或帳單給錯人看**。

### ✕ 靠 RLS

憲法明講：**API 用 service role key，它會繞過 RLS —— RLS 不是第二道防線。**
業務表啟用 RLS 且沒有 policy 是刻意的 fail-closed 後盾，不是授權機制。
（`AGENTS.md` 的 Supabase 節、c1）

### ✕ 前端過濾

c1 的違反例就是這個：「僅靠前端不顯示按鈕來『限制』」。家長端的每一支查詢都會
直接暴露在瀏覽器的網路面板上。

### ✕ 給家長一組獨立的唯讀端點，不共用 admin 的

聽起來乾淨，實際上是把同一個查詢寫兩遍 —— 這個 codebase 已經為此收斂過三組
（點名、成績鍵盤、匯入解析）。而且兩份會分岔：admin 端修了 bug，家長端不會跟。

**但這一條有例外**：如果某個 admin 端點的回應包含家長不該看到的欄位
（例如成績的班級排名、帳單的內部備註），那該做的是**回應層的欄位過濾**，
不是另開一支端點。哪些欄位要遮，逐支決定。

## 明確不做

- **家長端的寫入**（報名、請假、訂餐）—— v1 唯讀。寫入要各自的業務規則與確認流程，
  而且 `campusRequestGuard` 的第三條提醒了：**body 的驗證不能靠 middleware**
- **細部權限**（家長之間的差異，例如「只有主要聯絡人看得到帳單」）——
  `parent_student_relations` 有 `is_primary` 欄位，但 v1 不用它
- **跨機構的家長**（同一個人在兩間補習班都有小孩）—— `org_id` 那層已經處理，
  不在這份設計的範圍

## 擴充節：學生自己的帳號（v1 不做，但模型已經相容）

**使用者裁定 v1 不做學生帳號。** 這一節寫下來的原因是：**做的時候不需要改這個模型**，
而知道這件事會影響現在的實作長什麼樣。

### 為什麼天然相容

這份設計的核心是 `studentScope` —— **一個「這個登入者可以看到哪些學生」的清單**。
它刻意不叫 `childrenIds`：

| 登入者       | `studentScope`                             |
| ------------ | ------------------------------------------ |
| 家長         | 他綁定的孩子（`parent_student_relations`） |
| **學生本人** | **只含自己那一個 id**                      |
| 管理員       | `null`（不受限）                           |

**學生是家長的退化情形，不是新的一種角色。** 同一個 `childDb`、同一個 403 規則、
同一組 route 都成立 —— 差別只在 middleware 那一步怎麼算出那個清單。

### 因此現在該注意的兩件

1. **不要把 scope 的來源寫死成 `parent_student_relations`。** middleware 算 scope 時
   應該是「依這個登入者的身分決定怎麼查」，而不是「join 家長關聯表」。
   後者會讓將來加學生帳號變成改每一支 route，前者只是多一個 case。
2. **命名不要綁「孩子」。** `studentScope` / `childDb` 這兩個名字裡，前者是對的
   （它說的是範圍涵蓋哪些學生），後者其實偏了 —— 但 `childDb` 已經進了乙案的敘述，
   **改名留到真的做學生帳號時再一起**，現在改只是製造一次無謂的擾動。

### 不在這一節的範圍

**學生帳號怎麼建、誰能建、憑什麼登入** —— 那是 Better Auth 與報名流程的事
（c2：`ba_*` 表只能走 `admin.createUser()`），跟資料範圍模型無關。
這一節只主張一件事：**那件事發生的時候，這份設計不用重寫。**

## 待使用者裁決的三件

1. **`activeRole` 進 API context** —— 影響 `audienceFor` 的行為改變（雙身分的人會
   看到不同的公告），要不要在這輪一起做
2. **回應欄位的遮蔽清單** —— 成績要不要遮排名、帳單要不要遮內部備註
3. **`is_primary` 要不要影響可見性** —— v1 建議不用，但那是產品決定
