# 站內公告的設計

## 範圍：先做站內，不接 LINE

補習班現在用 LINE 群組發通知。要真的取代它得接 LINE 官方帳號的 Messaging API ——
那是產品決策（要申請帳號、要付費），不是技術選擇。

站內公告不需要任何外部服務就能做完，而且它是 LINE 整合的前提：**先有「一則公告」這個
資料實體，之後要多推一個管道只是多一個 sender。** 反過來先接 LINE 的話，資料還是得補。

## 管理端與老師端一起做

只做老師收件匣的話，**沒有人能發公告，那個收件匣永遠是空的** —— 跟報名總覽的
`pending_payment` 篩選是同一種錯：永遠空的東西讓人以為系統壞了。

所以 MVP 是「管理員發、老師讀」。家長收件匣等家長端接上再說（見下方）。

## Schema 的兩個前瞻決定

一般原則是不為想像中的需求預留欄位，但 migration 提交後不能改（c3），所以**改欄位的成本
遠高於改資料**。這兩處因此破例：

| 決定                                                        | 理由                                                                                   |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `audience` enum 寫入 `all_parents`，但只實作 `all_teachers` | enum 加值容易、改欄位貴。家長端接上時不必動 schema                                     |
| `campus_id` nullable（null = 全分校）                       | 多分校是系統現在就有的概念，分校主任只發給自己校區的老師是**現在**存在的情境，不是臆測 |

`published_at` 則**沒有**做成 nullable：這一版沒有草稿功能，要草稿再 ALTER 成 nullable。
那是「加資料狀態」而非「改欄位語意」，成本低。

## 可見範圍抽成純函式

`announcements/visibility.ts` 回答「這則公告該不該出現在這個人的收件匣」。

抽出來的理由跟前幾支範圍限制一樣：**錯的方式很安靜**。漏掉分校條件的話，甲分校的老師會
收到乙分校的公告，而畫面上完全看不出哪裡不對。

規則：`audience` 對得上角色，且（公告是全分校 **或** 這個人隸屬該分校）。
沒有分校歸屬的老師只看得到全分校公告。

## 已讀：複合主鍵天然冪等

`announcement_reads` 的主鍵是 `(announcement_id, user_id)`，所以重複標記不會產生第二列。
重複標記是**正常操作**（重新整理、多分頁、網路重試），不該當成錯誤處理。

前端用**樂觀更新**：先把畫面標成已讀再送請求，失敗就翻回未讀。
顯示成已讀但實際沒存到、下次進來又冒出來，比當下慢半拍更糟。

## 授權

`mount('/api/announcements', announcementsRoute, ANY_ROLE)` —— 收件匣三個角色都要用。
**發布與管理端列表在 route 內另外要求 admin**（`middleware: [requireRoles('admin')]`），
這是[[architecture/role-authorization|角色授權設計]]講的「掛載層是上限，單一 endpoint 可以更嚴」。

## 刻意不做

- **LINE / Email 推播** —— 見上方範圍說明
- **家長收件匣** —— 家長端 11 個頁面全是空殼，發給家長沒人收得到。發送對象因此
  暫時固定為「全體老師」：**選得到但沒人收，比選不到更糟**
- **草稿、排程發布、編輯、刪除** —— 公告是一次性的廣播，改來改去的需求還沒出現
- **針對個人或單一班級的通知** —— 那是聯絡簿（M5）的範疇，不是廣播
