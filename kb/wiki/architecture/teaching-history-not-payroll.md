# 記錄授課歷程，但不做薪資計算

## 決定

老師多為**按時數計酬**，但系統**不計算薪資**，也不儲存時薪費率。
`staff` 表沒有 rate 欄位，這是刻意的。

系統的職責是把**授課歷程記到可信**：誰、在什麼時候、上了哪一堂、實際有沒有上、有沒有換人。
從那份紀錄要怎麼換算成錢，留給人決定。

## 為什麼

薪資規則是這間補習班的商業規則，而且很可能因課別、年級、資歷而異。把它寫進系統要先凍結一套
規則，而現在**沒有人能保證那套規則是穩定的** —— 一旦寫死，之後每次調整都變成改程式。

相對地，「這個月老師 X 上了 12 堂、共 24 小時」這個事實不會因為薪資政策改變而失效。
**先留住不會變的事實，把會變的規則推遲。**

## 資料已經在了

算時數需要的原始資料 100% 已經在資料庫裡：

| 資料                               | 位置                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| 每堂課的老師、日期、起訖時間、狀態 | `sessions`（`teacher_id` / `session_date` / `start_time` / `end_time` / `status`） |
| 調課、代課、停課                   | `schedule_changes`（含 `substitute_teacher_id` 與原老師）                          |
| 課真的上了的證據                   | `events.attendance_taken_at`（首次點名時間，immutable）                            |
| 依老師查課堂                       | `sessions` API 已支援 `teacher_id` 篩選                                            |

**缺的一直是呈現，不是記錄。** `admin/changes`（課務異動）到 2026-08-11 為止仍是空殼 ——
資料一直在寫，但沒有任何畫面看得到。

## 因此該做與不該做

**該做**：把既有資料呈現出來 —— 課務異動紀錄、依老師與期間列出課堂並加總時數。

**不該做**：時薪欄位、薪資結算、薪資單、匯出給會計。那些都要求先凍結規則。

> 若哪天真的要做薪資，前提是先有人明確定義：固定時薪還是分級？算排定的課還是實際上的課？
> 代課的鐘點算給誰？停課算不算？在那之前，加一個 rate 欄位只會製造一個沒人信的數字。
