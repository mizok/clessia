# 報名管理端的設計

## 現況先講清楚

`kb/wiki/roadmap.md` 的現況表把「報名」標成 🔌 僅後端，那是因為磁碟上沒有
`admin/pages/enrollments/` 目錄 —— 但**報名功能實際上已經有兩個入口**：

| 既有入口   | 位置                   | 能做什麼                                                                                  |
| ---------- | ---------------------- | ----------------------------------------------------------------------------------------- |
| 班級詳情頁 | `courses/class-detail` | 學生挑選器（勾多人 → `batchCreate`）、從既有班級複製名單（`copyFromClass`）、報名狀態變更 |
| 學生詳情頁 | `students/detail`      | 把單一學生加入班級（簡化版，直接 `active`）；在籍清單唯讀                                 |

所以 M2 不是「從零建報名功能」。真正缺的只有兩件，而且**它們互不依賴**：

1. **Excel 名單比對匯入**（`POST /api/enrollments/batch-match`）—— 全專案唯一一支寫好了
   卻沒有任何前端呼叫的 API。既有的學生挑選器要求學生已經在系統裡、而且要一個個勾。
2. **報名進出總覽** —— 「這個月進了幾個、退了幾個」目前沒有任何畫面回答得出來。

先做匯入。roadmap 的原則是「每個 milestone 都必須讓某一件事完全脫離 Excel」——
匯入是那件事，總覽頁是報表。

## 切片一：Excel 名單匯入精靈

### 掛在班級詳情頁，不在總覽頁

`batch-match` 的 body 是 `{ classId, items[] }` —— **比對本身綁定單一班級**（要查該班在籍
名單才判得出 `already_enrolled`）。匯入天生是「某一個班的名單」。

班級頁的花名冊區塊已經有「加入學生」「複製名單」兩顆按鈕，第三顆「從 Excel 匯入」
與它們同構。放總覽頁的話得先在總覽頁重建一個班級選擇器，只為了做一件本質上屬於班級的事。

### 位置對應的兩欄範本，不讀標題列

沿用家長匯入的既定慣例（`parent-import-dialog.component.ts:292`）：跳過前兩列、
`row[0]` `row[1]` 位置對應，附一份可下載的範本。報名只需要**姓名**與**就讀學校**兩欄
（年級不用 —— 學生已經在系統裡，年級是學生資料）。

**拒絕讀標題列自動辨識**：真實名單有合併儲存格、座號欄、備註欄、標題橫幅。標題辨識失敗的
方式是**靜默配錯欄**（把備註當學校名送去比對，然後整份 `not_found`，使用者不知道為什麼）。
位置對應失敗的方式是明顯的——第一列就整列錯，一眼看得出來。

### 學校名稱在前端正規化，由人確認

`batch-match` 解析學校是用 `schools.name` **完全相符**（`enrollments.ts:1082` 的
`.in('name', ...)`，外加一次 lowercase 比對）。系統裡的學校叫「台北市立文山國中」，
名單上寫的是「文山國中」—— **每一列都會回 `not_found`，功能等於沒做。**

解法不是把模糊比對塞進後端，而是把它變成精靈的一個步驟：解析完 Excel 後抓出**不重複的
學校名**（30 人的班通常只有 3、4 間），用既有的 `GET /api/schools?search=`（它已經同時
比對 `name` 與 `short_name`）查出候選，讓使用者確認對照，再把**正規化後的完整名稱**送進
`batch-match`。API 一行都不用改。

這是「確認 4 個對照」而不是「確認 30 列」，猜錯了人看得見，而且順便處理「系統裡沒有這間
學校」的情況——標出來、該列無法匯入。**不在這裡建學校**，那是學校管理頁的事。

### 生效日可選，預設今天

`POST /enrollments/batch` 現在寫死 `effective_from = 今天`。而 `effective_from` 是**課堂
名單的閘門**（`attendance.ts:579` 用 `effective_from <= 課堂日期` 決定學生出不出現在點名表）。

寫死今天在一個情況下會出事，而那正好是**上線第一天**：學期已經開跑五週，把現有名單灌進
系統 → 全部生效日是今天 → 前五週的課堂名單是空的，補點名補不了。

所以 `POST /enrollments/batch` 加一個 optional `effectiveFrom`，不給維持今天（學生挑選器
那條路不用改）。精靈裡放日期欄，預設今天，附說明「要讓學生出現在過去的課堂名單，把日期往前調」。

往前調是安全的：`syncLeaveAttendanceForEnrollment`（`enrollments.ts:289`）只針對**已存在的
請假單**補記錄，不會回頭灌出一堆出勤資料。

**不自動抓「該班第一堂課的日期」**：得多打一支 sessions API、排序、還要處理沒有課堂的班；
而且它會變成一條使用者不知道存在的規則——某天日期自己跳到三個月前，沒人知道為什麼。
一個看得見的日期欄勝過一個聰明的預設值。

### 上限 50 人，不切塊

`batch-match` 上限 200、`batchCreate` 上限 50。原本打算切塊循序送，**否決**：

- 衝堂是整批回 409（`enrollments.ts:777`）而非逐筆 → 切三塊、第三塊 409 → 一半進系統一半沒有
- 人數上限也是整批檢查（`validation.ts:128`）→ 錯誤訊息裡的數字對不上使用者看到的名單

改成解析階段就擋掉超過 50 列的檔案。班級 `max_students` 預設 20，補習班大班撐死 40，
這條線實務上碰不到。**用一個不會發生的限制，換掉「部分寫入」整類 bug。**

### 衝堂與人數上限沿用既有模式

- **衝堂**：先不帶 `skipConflictCheck` 送，收到 409 攤開衝堂清單，使用者按「仍要匯入」
  才帶 `skipConflictCheck: true` 重送 —— 跟學生挑選器同一條路
- **`OVER_QUOTA`**：訊息要帶數字（「上限 20 人、目前 12 人、要匯入 30 人」）並指去班級設定，
  不是只說「人數已達上限」

### 沿用四步精靈的形狀，不共用元件

家長匯入已經有一套「拖檔 → 解析 → 逐列檢查 → 送出 → 結果」，使用者學過一次。報名匯入用
同樣的節奏（中間多一步學校對照）。**只共用形狀、不共用元件**：兩者的欄位、比對邏輯、後端
API 完全不同，抽成共用精靈會變成一個帶滿 flag 的殼。

### 比對結果的四種狀態

| `status`           | 畫面行為                                                          |
| ------------------ | ----------------------------------------------------------------- |
| `matched`          | 打勾，預設納入送出                                                |
| `ambiguous`        | 列出 `candidates`（年級、學校、生日），**必須人工選一個**才能送出 |
| `already_enrolled` | 灰掉，「已在班上」，不送出                                        |
| `not_found`        | 標紅，「系統裡沒有這個學生」，不送出                              |

`not_found` **不在這裡建學生**。建學生要一併建家長與關聯（那是家長匯入的職責），
在報名流程裡偷建一個沒有家長的學生，會製造出永遠收不到通知的孤兒資料。

## 切片二：報名進出總覽

### 它是「本月進出」，不是名冊瀏覽器

主任會問的四個問題，三個已經有畫面：某班有誰（班級頁）、某生在哪些班（學生頁）、
誰卡在待繳費（**目前是死狀態**——`invoices` 表不存在，沒有流程會產生 `pending_payment`）。

只有「**這個月進了幾個、退了幾個**」沒有任何畫面回答。那是總覽頁獨佔的價值，
而它是招生進出的檢視，不是名冊瀏覽。

資料對得上：退班會把 `effective_to` 寫成當天（`enrollments.ts:688`）。所以本月進出 =
`effective_from` 落在本月（新進）**或** `effective_to` 落在本月（退出）。

一張表兩種列，用一欄標「新報名 / 退班」。期間欄位**可以清空**，清空後退化成全部在籍的
瀏覽——一頁服務兩種問題，不做兩頁。

**不做 `pending_payment` 篩選**：放一個永遠是空的篩選只會讓人以為系統壞了。M3 做金流時再加。

### 排序用 `updated_at`，不是事件日

兩種列的事件日在不同欄位（新進看 `effective_from`、退班看 `effective_to`），
PostgREST 沒辦法照「兩欄取其一」排序。三條路：

- **前端排序**（抓當月全部再自己排）—— **否決**：上線第一個月會一天匯入十個班、
  250 筆報名，`pageSize` 上限 100，這條路正好在最忙的月份斷掉
- **新增 `enrollment_events` view**（union 兩種事件）—— **否決**：多一個 DB 物件、
  要記得寫 `security_invoker = true`（漏了會繞過 RLS，把刻意保留的 fail-closed 後盾打穿），
  換到的只是排序正確性，成本不對稱
- **`updated_at desc`**（採用）—— 新報名的 `updated_at` 就是建立時間，退班時的
  `updated_at` 就是退班時間。**兩種列的最後異動時間本來就等於它的事件日**，不需要新機制

篩選仍用 `effective_from` / `effective_to` 的 OR 決定「本月有沒有這件事」，排序才用
`updated_at`。已推過的邊界：

| 情境                   | 結果                                                  |
| ---------------------- | ----------------------------------------------------- |
| 二月報名、八月退班     | 八月篩得到（`effective_to`），排序落在八月正確位置 ✅ |
| 二月報名、八月只改備註 | `effective_to` 是 null → 八月篩不到，不會冒出來 ✅    |
| 八月報名、九月改備註   | 八月篩得到，但排在清單最上面 ⚠️ 唯一偏差，可接受      |

欄位標題誠實寫「最後異動」，不假裝它是事件日。

### 完全唯讀

報名狀態變更的唯一入口是班級詳情頁（學生詳情頁的在籍清單也只是唯讀，
`student-detail.page.html:254` 點下去跳班級）。總覽頁沿用這條線：列點下去跳到該筆報名
所屬的班級詳情頁。

**動作只有一個家**：停權要看班況、退班要看剩幾堂、失效要看繳費——三個判斷都需要班級脈絡。
把終止散到第三個地方，往後改規則就得記得改三處，漏掉的那處會靜默用舊規則跑。

### 篩選需要的後端參數

`GET /api/enrollments` 目前只支援 `classId` / `studentId` / `status`，要加：

| 參數          | 用途                                                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `campusId`    | 多分校是核心概念。要透過 `classes!inner(campus_id)` 過濾——不加 `!inner` 的話 PostgREST 預設 left join，條件不成立的列會以 null 關聯留在結果裡 |
| `from` / `to` | 對 `effective_from` **或** `effective_to` 取 OR 區間                                                                                          |

**不加姓名搜尋**：要找特定學生的在籍狀況，學生詳情頁已經完整呈現。

## 需要的改動

| 層          | 切片一（匯入）                                          | 切片二（總覽）                                    |
| ----------- | ------------------------------------------------------- | ------------------------------------------------- |
| DB          | 無                                                      | 無                                                |
| API         | `POST /enrollments/batch` 加 optional `effectiveFrom`   | `GET /enrollments` 加 `campusId` / `from` / `to`  |
| Web service | 無（`batchCreate` 型別加欄位）                          | `EnrollmentQueryParams` 加欄位                    |
| Web UI      | `class-detail` 第三顆按鈕 + 匯入精靈 dialog + 範本 xlsx | 新增 `admin/pages/enrollments/`，掛進課務管理選單 |
| 現況表      | 無                                                      | 「報名」的 `pages` 從 `[]` 改成 `['enrollments']` |

## 刻意不做

- **繳費單與費用計算** —— `fee_templates`、`invoices` 兩張表在 migration 裡不存在。
  規格裡「建立繳費單 → `pending_payment`」整段是 M3 的範圍。
- **報名申請審核、試聽** —— 同樣沒有底層資料表（`enrollment_requests`、`trials`）。
  現況表把它們算進「報名」功能區是誤導：它們是未開始，不是僅後端。
- **續報流程** —— 這間補習班的實際做法就是「下學期開新班，把舊班名單搬過去」，
  `copyFromClass` 已經完全覆蓋。不為此新增 `renewals` 表。
- **從匯入畫面建立學生或學校** —— 見上方 `not_found` 與學校正規化的說明。
- **匯出** —— 目標是讓資料進系統，不是讓它回到 Excel。
