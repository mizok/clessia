# 出勤與請假規則

本文件整理 PRD 8.3-8.4，定義出勤模式、系統推算邏輯、人工修改權限與請假處理規則，作為到班/點名模組的核心行為準則。

## 1. 出勤模式規則

### 1.1 日到班模式（預設）

- 學生打卡後，系統自動將當天符合條件課堂推算為出席（或遲到）。
- 適合學生整天在補習班的場景。

### 1.2 課堂模式

- 打卡僅記錄到班時間，不直接完成課堂出勤。
- 需由管理員或老師逐堂確認。

## 2. 通用出勤規則

1. 學生到班後，系統行為取決於分校設定的出勤模式。
2. 「有報名」判斷條件：
   - 學生已報名該開課班。
   - 當天日期落在 Enrollment 生效期間內。
3. 若課堂出勤已被人工修改，系統推算不得覆蓋。
4. ⚠️ **「課堂結束後仍無任何出勤紀錄，系統自動標記為 `absent`」—— 這條沒有實作，
   而且跟現行設計衝突。**
   - 沒有實作：`wrangler.toml` 沒有任何 cron trigger，程式碼裡也沒有會自動寫
     `absent` 的路徑。**它跟 `late` 是同一款幽靈**（規格上有、實際不存在）。
   - 跟現行設計衝突：整個「未點名」的概念（儀表板的未點名課堂卡、老師課表的
     實心／中空、逾期未點名清單）都建立在**沒有紀錄**這個狀態上。自動補 `absent`
     會把那個訊號抹掉 —— 「還沒有人點名」與「點過名了，這些人沒來」會變得無法分辨。
   - **要做之前先讀第 6 節。** 真要做的話，它必須是一個有明確時間點的、
     看得出來是系統寫的判斷（`recorded_by_role = 'system'`），而不是把
     「沒有紀錄」重新詮釋成缺席。

## 3. 出勤修改權限

| 角色   | 權限邊界                       |
| ------ | ------------------------------ |
| 管理員 | 可修改所有課堂、不限日期       |
| 老師   | 僅可修改自己任課課堂，且限當天 |

超過老師可修改時限的修正，一律由管理員處理。

## 4. 請假規則

1. 請假由管理員或家長建立（`leave_requests.submitted_by_role` 記錄是誰送的）。
2. 允許事後補請。
3. 建立請假後，對應課堂出勤狀態需改為 `on_leave`
   （原本寫 `leave`，但 `attendance_status` enum 只有 `present` / `absent` / `on_leave`）。

## 5. 自動寫入與人工修改的優先順序（陷阱）

出勤紀錄有兩種來源：**人按的**（點名、補登）與**系統連動寫的**（到班掃碼、請假連動、
報名連動）。兩者撞在同一筆 `(event, student)` 上時，誰蓋誰**不是一致的，而且是刻意的**：

| 自動寫入     | 撞到既有紀錄時        | 為什麼                                                                                                            |
| ------------ | --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **到班掃碼** | **跳過，不覆蓋**      | 掃碼是機器讀到一張卡。老師把某人改成缺席、那人事後補掃了碼，覆蓋等於一張卡推翻老師的判斷，而且不留痕跡            |
| **請假連動** | **覆蓋成 `on_leave`** | 請假**也是人工**，只是不同的人（家長或行政）。規則 4.2 允許事後補請 —— 補請就是要更正先前的點名，不覆蓋反而是 bug |
| **報名連動** | 同上                  | 同一個更正流                                                                                                      |

⚠️ **看到「請假連動會覆蓋人工點名」不要當成跟掃碼同一款 bug 修掉。** 兩者長得一樣
（都是 upsert 撞既有紀錄），但一個是機器推翻人、一個是人更正人。判準是
**「來源是不是一個人的決定」**，不是「是不是自動觸發的」。

實作上的區分欄位是 `attendance_records.recorded_by_role`：人工是 `admin` / `teacher`，
自動連動是 `system`。

**到班掃碼另外只算有報名的課**：它只替學生**當天實際在籍**的課堂寫 `present`
（在籍條件與點名名單同源 —— 掃碼寫得出來的紀錄，必須是那堂課點名時看得到的人）。
到班紀錄與課堂出勤是**兩層**：人到了就是到了，即使他今天一堂課都沒有。

## 6. 沒有紀錄 ≠ 缺席（原則）

**這是出勤這一塊最容易被違反的一條，而且每一次違反看起來都很合理。**

`attendance_records` 裡沒有某個 `(課堂, 學生)` 的列，意思是**還沒有人對這件事做過判斷**。
它不是「這個人沒來」。兩者在畫面上、在扣課上、在通知家長上都是完全不同的東西，
而且**假的缺席會流進月結**。

已經修掉的四種違反方式（同一條原則的四個面向）：

| 情境           | 錯誤的做法                          | 正確的做法                       |
| -------------- | ----------------------------------- | -------------------------------- |
| 到班掃碼補寫   | 覆蓋掉老師改過的紀錄                | 只補沒有的，不動已存在的         |
| 課堂還沒點名   | UI 把沒有紀錄畫成「缺席」           | 畫成「未點名」，是另一種狀態     |
| 銷假           | 把 `on_leave` 改成 `absent`         | **刪掉紀錄**，回到「還沒點名」   |
| 管理員刪除請假 | 把區間內的 `on_leave` 全改 `absent` | **刪掉紀錄**；已點過名的日子不動 |

判準：**要寫 `absent`，必須有人（或一個明確的、看得出來是系統的判斷）真的認定他沒來。**
「找不到別的值可以寫」不是理由。

## 7. 銷假

**銷假＝刪除請假單，沒有「已取消」狀態。** 使用者定案（2026-09-03）：不留痕作廢。
（稽核紀錄裡仍保留被刪掉的內容 —— 那是我們查事情用的，不是給使用者看的狀態。）

老師在點名畫面上按「他今天到了」時：

1. **刪的單位是「那一天」，不是整張請假單。** 學生今天到了，不代表他明天的假也不算數。
   - 整張假就是那一天 → 刪掉
   - 今天開始、之後才結束 → 起始日移到明天
   - 之前開始、今天結束 → 結束日移到昨天
   - **今天卡在中間 → 截到昨天，後段一併取消**，而且**必須告訴老師**
     （「後續日期的請假也一併取消，如需請假請重新申請」）
2. **當天所有課堂的 `on_leave` 紀錄一起刪掉**，那位學生回到可標記狀態。
   假已經不蓋到今天了，其他課堂還留著會變成「有紀錄說請假、但沒有假」的矛盾態。
3. 範圍：老師限**自己任課（含代課）且限當天** —— 銷假的依據是「他人就在我面前」，
   那只有當天成立。管理員不限（他在處理事後的更正）。

「今天卡在中間」選擇截斷而不是把請假單切成兩張，是因為**這個決定的錯誤恢復很便宜**：
後段的假若還要，家長重送一張就好（送假是既有的日常操作），而切兩張的複雜度是永久的。
