# 工具靜默地不做你以為它在做的事

## 這一族長什麼樣

你跑了一個檢查，它回**零筆**、或回**綠**。你把它讀成「結果是沒有」「結果是好的」。

實際上它的意思是 —— **這個檢查沒有發生。**

> **共同症狀：`「沒有結果」` 與 `「結果是沒有」` 在畫面上一模一樣。**

這是 [[lessons/broken-looks-identical-to-normal]] 的子族：都是「失敗不產生訊號」，
差別在於**失敗的是工具，不是程式**。程式那邊你至少還有一個畫面可以看；
工具這邊，你看到的就是你要的那個輸出格式，只是它裝著別的東西。

## 判準

> **零命中之後的下一個動作，是換一條獨立的路再問一次同一個問題，不是下結論。**

換 pattern、換路徑、換工具都行 —— 只要是**獨立的第二條路**。
判準的檢查點很明確：**你剛剛收到一個「什麼都沒有」的結果。**

第二條判準給的是事前的姿勢：

> **你要找的東西，在你搜尋的那個載體裡，真的會長成你以為的樣子嗎？**

## 目錄

每一列的第三欄是**當事人憑什麼起疑** —— 那一半只存在於當事人的記憶裡，
現象可以事後補寫，起疑的時刻不行。

| 載體                                  | 它靜默地做了什麼                                                           | 憑什麼起疑                                          |
| ------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| `sed -i '' '0,/re/s/…'`               | **BSD sed 不支援 `0,` 位址**，整條沒生效，陷阱沒塞進去                     | 陷阱塞完 tsc 照樣綠 —— 但「守衛不存在」也是這個樣子 |
| `grep -E "^ +Tests "`                 | 行首有 **ANSI 逃逸碼**，`^ ` 對不上                                        | 明明看得到那一行，grep 卻抓不到                     |
| `git grep "a\|b" <rev> -- <單檔路徑>` | 回零筆；換成目錄路徑立刻命中同一個檔多處                                   | 那個字串「不可能不存在」的直覺                      |
| `git diff` 兩點與三點                 | **兩個都答不了「這東西現在在不在 main」**                                  | 見下節                                              |
| 手寫的假 supabase                     | 不管路由 `select` 什麼都**回全欄位**，「少撈一個欄位」完全觀察不到         | **「我預期會紅的東西沒紅」**                        |
| zsh 的 `"$VAR:apps/…"`                | **`:a` 是參數修飾符**（絕對路徑），revision 被靜默改寫                     | 第一次只回空輸出，像「那個檔不在那支分支上」        |
| harness 豁免的移除條件                | 條件寫成「v1b 啟用時拿掉」，**啟用那天沒有人在讀豁免表**                   | 查別的東西時剛好讀到那行字（運氣）                  |
| CI 監看器 `until [ -z pending ]`      | 回報的是**它看到的那一輪**，不是你關心的那一輪                             | 記得「中間發生過一次 push」                         |
| `git diff` 的基準點                   | 拿工作區比一個**正在前進的 `origin/main`**，別席的新內容顯示成「你刪掉的」 | 被刪的行內容跟自己做的事對不上                      |
| `lsof -ti:<port> \| head -1`          | 回的是**跟這個 port 有關的所有 process**（含瀏覽器的殘留連線），`head -1` 又假設了順序 —— **真正的 listener 可能在清單後面** | 「這個 port 空著」但 `wrangler` 說 `Address already in use` |
| `npx sass` 編譯失敗                   | **exit code 0**，而且把錯誤當註解寫進 `.css`，檔案確實產生了                | 8 kB 的樣式表只編出 753 bytes                       |
| `nx affected … \| tail -12`           | 尾巴切掉了 47 個測試的失敗詳情，只留下一行 `Failed tasks`；管線 exit 0     | 輸出短到不可能裝得下我要看的東西                    |
| `document.styleSheets` 遞迴掃描        | Chrome 的 `CSSStyleRule` **現在也有 `.cssRules`**（原生巢狀 CSS），先判 `.cssRules` 就永遠走不到 `selectorText` | 樣式明明在頁面上生效，「零條規則命中」不可能成立 |

## 兩個靜默的東西疊起來，症狀會指向完全錯的方向

2026-09-06 夜的實例，**兩件各自都很安靜**：

1. 一支 API server 被 `git worktree move` 從腳下改名 →
   **它沒死，只是 accept-then-hang**（LISTEN、接受連線、永遠不回）
2. 我用 `lsof -ti:8787 | head -1` 查它，拿到的是 **Brave 的殘留 ESTABLISHED 連線**，
   **真正的 listener 在清單後面被 `head -1` 藏掉**

於是我的結論是「**8787 空著，那支 server 已經死了**」——
**兩件事都錯，而它們錯的方向剛好一致**，所以結論讀起來毫無破綻：
有 PID、有 port、有一個合理的故事。

**戳破它的是 `wrangler` 的 `Address already in use`** —— 一個跟我的假設互相矛盾的
第二個訊號。正解是 **`lsof -nP -iTCP:<port> -sTCP:LISTEN`**（只列 listener）。

> **「port 被佔」跟「server 健康」是兩件事，而 `lsof -ti` 把兩者混在同一份清單裡。**
>
> 這一族單獨出現時還有機會察覺；**兩個疊起來時，錯誤的結論會比正確的更連貫。**

## 同一個工具，兩種騙法

`git diff` 出現兩次，而**兩次的機制完全不同** —— 並排寫，是因為記住一種不會讓你對另一種免疫。

|            | 騙法                                                               | 形狀                                                             |
| ---------- | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 兩點／三點 | 三點答「分支自己改了什麼」，兩點在舊分支上把 main 的前進顯示成刪除 | **你問錯了問題** —— 工具沒壞、用法也對，它回答的不是你問的那件事 |
| 基準點移動 | 比對的對象 `origin/main` 在你編輯期間前進了兩次                    | **基準點在你不注意的時候移動了** —— 問題問對了，但參照系換了     |

第一種的解法是**改用直接對 `origin/main` grep 該 PR 獨有的識別字**；
第二種的解法是**拿分支起點當基準**，不是拿一個活的 ref。

## 基準點移動的最毒版本：別人在你兩次量測之間改了共用資源

上面表格裡「`git diff` 的基準點」講的是**你自己**沒注意參照系在動。同一個形狀有一個
更難發現的版本：**參照系是一個共用資源，而動它的是別人。**

2026-09-06，design-web 在分支上跑測試拿到 5 支 spec、47 個測試紅，
`git checkout --detach origin/main` 量 baseline **全過**。照那兩個數字讀，
結論是「main 是好的、我的分支壞的」—— 而那個結論會直接寫進 PR。

真相是**另一席在那兩次量測之間，把一支卡死的本機 API 換成了健康的一支**。
那 5 支 spec 沒有 provide 任何 HTTP mock 就 `await fixture.whenStable()`，
而 `environment.ts` 的 `apiUrl` 指著那支 API：**卡死的版本接受連線但永遠不回**，
於是每一支等滿 `beforeEach` 的 10 秒 hook timeout。

發現它靠的是習慣性再量一次那支 API 的現況（PID 換了、回應從 `code=000 time=10.004`
變成 `401 / 7ms`）。回分支用同一個環境重跑，跟 main 一模一樣。

**為什麼這個版本最毒**：兩份輸出都是格式完全正常的測試結果，**沒有任何不一致會讓人停下來**
—— 這正是〈判準〉那族裡「工具忠實地回答了它被問到的問題，錯的是提問者的前提」的樣子，
只是這次的前提是「兩次量測跑在同一個環境上」，而那個前提**在多席共用一台機器時預設不成立**。

順帶一條這一族的通則：**「連得上但不回」比「連不上」毒得多。**
`connection refused` 會讓 fetch 立刻 reject、測試照樣跑完；accept-then-hang
讓每一支等滿逾時。所以一支卡住的本機服務會讓**任何人**在這台機器上看到幾支
莫名其妙的紅，**而且長得像自己改壞的**。

> 檢查點：**你正要拿「兩次量測的差異」下結論的那一刻** —— 問「這兩次之間，
> 有沒有任何我沒有控制的東西變了」。多席共用一台機器時，答案的預設值是「有」。

## 有一件不是命令列工具

**假 supabase 那件在我們自己寫的程式碼裡**，而它跟其他所有件的差別是：
其他件換個指令就抓得到，**這件不會有任何症狀，只會讓測試安靜地失去辨識力**。

機制：`select` 在真 PostgREST 裡是**投影**，在替身裡被當成**語法**
（決定鏈式呼叫能不能接下去）。兩種角色在鏈式 API 上長得一模一樣 ——
你必須寫出 `.select(...)` 才接得到 `.eq()`，所以「有實作 select」在測試通過時完全不可疑。
而 fixture 是照著「這張表有哪些欄位」寫的，**它一定是完整的**。

> **替身永遠比真實系統寬容。**

**替身的寬容度決定了它遮得住哪一種突變**：會改變回傳內容的遮不住；
只改變「你有沒有拿到某個欄位」的**遮得嚴嚴實實** —— 而後者正好是本族的形狀。

**所以「多撞幾發真實案例」不是解法，突變的類型才是**：要驗一個替身有沒有這種盲區，
挑一個**不改變任何回傳筆數、只改變欄位有無**的突變去撞。

推論：**突變測試自己也可能是瞎的** —— 人造的陷阱照著你的心智模型造，
**替身也照著你的心智模型寫**，兩邊同一個盲區時它會安靜地通過，
而且從此有一支綠燈替那個盲區背書。

## 欄位有值，不代表那個值回答了你的問題

兩個 `gh` 的例子，解法都是**把你真正關心的那個東西帶進判斷條件**：

- **CI 監看**：`until [ -z pending ]` 等到的是「有一輪跑完了」。你在它跑的期間推了修正，
  它照樣回報綠 —— 而前後兩次 `gh pr checks` 的輸出**逐字相同**（同一個 run id、同樣的 pass）。
  **解法：把 `head_sha` 帶進條件。**
  ```
  gh api repos/<owner>/<repo>/actions/runs/<id> --jq .head_sha   # 要等於你剛推的 commit
  ```
  `until` 迴圈的空窗期同理：舊 run 剛結束、新 run 還沒被排上時，`pending` 是空的，
  而那不代表沒有新的一輪要跑。
- **`gh pr view --json mergeable`**：它是**非同步計算**的，`UNKNOWN` 不代表沒問題，
  只代表**還沒算完**。要確定就本地釘住實測：
  `git merge-tree --write-tree origin/main HEAD`。

## 這一族最貴的產物是「有說服力的假 bug 報告」

`git grep` 那件差一點變成一份報告：「儀表板打的那支端點根本不支援 `endedOnly`」——
有 grep 證據、有明確的失敗機制、讀起來完全成立。

> **假 bug 報告比假 OK 更貴**：它讓人去修一個不存在的東西，
> 而修完之後「症狀消失」還會反過來確認那個假診斷。

## 寫稽核工具時，工具自己的 bug 會偽裝成「被稽核的對象很乾淨」

這一族有一個專屬於**稽核工具**的變體，而它比一般的靜默失敗更難發現：
**工具壞掉的輸出，跟「這個 repo 沒有問題」的輸出，是同一個東西。**

2026-09-07 寫「程式碼查的欄位在 DB 裡不存在」那支掃描器（issue #608），
過程中出現**五個不同的 bug**：鏈的邊界用固定字元數、常數表跨檔同名互相覆蓋、
把 `.select(a, {count})` 兩個參數串成一個欄位名、切頂層逗號時不認引號、
寫入物件的鍵不限深度而吃到 TypeScript 型別斷言。

**五個 bug 的成因毫無關聯，症狀卻只有兩種**：一種是**假命中**（其中兩個誤報
「長得跟真命中一模一樣」，是開檔看才發現的），另一種是**乾淨的零**。

最毒的是第四個：

> 為了修「兩個參數被串起來」而加的「只取第一個參數」，讓
> `'role, permissions'` 這種完整的字面參數被中間那個逗號切斷。
> 結果是 **198/366 個 select 解析不了 —— 解析失敗率過半，而報告輸出是
> 「0 筆命中」，看起來完美。**

**沒有任何欄位在說「我只讀懂了 46%」。** 覆蓋率是工具自己知道、但預設不會講的東西。

### 可操作的三條

1. **稽核工具要把覆蓋率印在結論旁邊**，而且是**每一次**都印，不是出錯才印。
   「解析成功 373 / 動態無法解析 3」跟「0 筆命中」放在一起，那個零才有意義。
2. **修一個誤抓之後要重看覆蓋率**。上面第四個 bug 是**修第三個時製造出來的** ——
   而且同一輪還發生過一次「修一個漏抓卻讓覆蓋率從 365 掉到 354」。
   **稽核工具的每一次修改都同時改變兩個方向，只看自己在修的那個方向會漏掉另一個。**
3. **數字往好的方向動不等於修好了。** 有一次涵蓋數回升，但去查「那個具體項目
   還在不在盲區清單裡」——**還在**。差一點用「數字變大」當成修好了。
   → 同本頁〈欄位有值，不代表那個值回答了你的問題〉。

> 這一節能被寫下來，是因為那支工具有**硬性的正控**。
> 沒有正控的話，上面每一個 bug 都會安靜地變成一份「掃到零」的報告 ——
> **而它會長得跟一份做完的一模一樣。**
> 正控怎麼挑見 `herdr-team/README.md`（挑「出事最多的那個位置」，不是最典型的）。

## 這一族有大聲的那一半，而它沒有被記錄 —— 因為它當場就被修掉了

這一頁的每一列都是**安靜的**失敗。但同一個知識點常常有**兩個失敗方向**，
而大聲的那一半從來沒進過這頁 —— **不是因為它不存在，是因為它當天就被修掉、
沒有人覺得值得寫下來。**

2026-09-06 兩件同一天出現的實例，來源是同一個 PostgREST 知識點
（「對 embed 的欄位下條件」）：

| 寫法                                                                                 | 失敗方向 | 症狀                                                                                      |
| ------------------------------------------------------------------------------------ | -------- | ----------------------------------------------------------------------------------------- |
| `select('…, events(…)')` + `events.attendance_taken_at=is.null`（**少了 `!inner`**） | **安靜** | 條件什麼都沒篩，回傳筆數看起來完全正常（19 筆 vs 18 筆的實測見 `lib/session-summary.ts`） |
| `select('id')` + `.gte('events.event_date', …)`（**連 embed 都沒有**）               | **大聲** | PostgREST 直接 400 `PGRST108`，端點對每個使用者都 500（#528 的 `/api/me/attendance`）     |

**大聲的那一半反而活了四個半月** —— 因為那支端點在 seed 補上 `parent` 角色之前
沒有任何人打得開（[[lessons/local-manual-verification]] 第三節）。
**「大聲」的前提是有人在聽。**

> **判準：學會一個工具的坑之後，問它的反方向 ——「這個條件如果我寫得更少，
> 它是報錯還是照跑？」** 兩個方向的成本完全不同：報錯的那一半在開發當下就結束，
> 照跑的那一半會活到有人比對數字為止。
>
> 而**這一頁只收得到後者，是倖存者偏差** —— 前者沒有留下任何紀錄，
> 因為它「當場就修好了」。看到這頁很長的時候，要記得**它是同一族裡比較難發現的那一半**。

## 查 Supabase 的表要加 `public.` 前綴 —— `auth` 底下也有一張 `sessions`

**出處：api-2，2026-09-07**（寫 #485 / #488 的量級查詢時查到的）。

Supabase 的 `auth` schema 底下有一張自己的 `sessions`（登入 session），跟業務的
`public.sessions`（課堂）**同名**。所以：

```sql
-- 危險：不知道撈到的是哪一張，或兩張混在一起
select ... from sessions s
select column_name from information_schema.columns where table_name = 'sessions'

-- 正確
select ... from public.sessions s
select column_name from information_schema.columns
 where table_schema = 'public' and table_name = 'sessions'
```

**而不加前綴查錯了不會報錯。** 查詢成功、有結果、結果是錯的 —— 用
`information_schema` 查欄位時尤其陰，因為它會把兩張表的欄位**混在同一份結果裡**，
於是「這張表有哪些欄位」這個問題得到一個看起來很完整的錯答案。

這是本頁的正典形狀，而且它踩中的是同一個弱點：**你以為自己在指名一個東西，
實際上那個名字在那個載體裡不唯一。** 跟「`git grep` 回零筆是因為 BEM 寫成 `&__x`」、
「`gh run list` 不按 workflow 過濾會混進別的 workflow 的成功」是同一族 ——
**識別字在你以為的範圍內不唯一，而多出來的那些不會舉手。**

判準:**寫任何直接打資料庫的查詢時，表名一律帶 schema 前綴。** 不是因為這次撞到了，
是因為**撞到的時候不會有訊號**。

## 自己把條件收窄，然後忘了那是收窄的 —— 也會產出一個乾淨的零

**出處：billing-api，2026-09-07**（review #485 的量級 SQL 時攔到的）。

那份 SQL 把「扣堂數」的條件寫成只看 `present`。而實際規則在
`apps/api/src/lib/session-pack.ts:39`：

```ts
status === 'present' || status === 'absent' || (status === 'on_leave' && leaveDeductsSession)
```

`absent` **一律扣**（學生佔了位子沒來，堂數照消耗），`on_leave` 看
`classes.leave_deducts_session`。**所以只看 `present` 會少算，而少算的方向是「回報沒事」。**

那份 SQL **跑得動、有結果、判讀清楚** —— 它沒有任何一點看起來可疑。

### 為什麼跟上一則（`public.` 前綴）並列

兩者在報告上長得一模一樣：**都是一個乾淨的零**。但機制相反：

| | 誰弄錯的 | 錯在哪 |
| --- | --- | --- |
| `public.` 前綴 | **工具**（名字在那個載體裡不唯一） | 查的對象不是你以為的那個 |
| 收窄的條件 | **你自己** | 對象對了，**問題被你改小了** |

**後者沒有任何工具能救** —— 查詢完全合法，資料庫忠實回答了被問到的那個問題。
唯一的訊號是**回去讀那條規則的實作**，而寫 SQL 的當下你以為自己已經知道規則是什麼。

判準：**把一條業務規則翻譯成查詢時，逐項對照實作的那個布林式，不要憑對規則的印象。**
特別是規則裡有「除了…以外」「看某個旗標」這種分支時 —— **那些分支正是印象裡最先掉的。**

（跟本頁「正控證明抓得到，不證明看得見全部」同源：一個乾淨的零，
證明的是**你問的那個問題沒有答案**，不是**那件事沒發生**。）

## 為什麼這一頁在 `kb/` 而不在 charter 或通則清單裡

因為它的**讀取時機不是「在讀文件的時候」，是「卡住的時候」** ——
我 grep 回零筆、我預期會紅的沒紅、我的檢查沒觸發。

那一刻不會有人回去翻四百行的通則清單。所以規則本身留在
`herdr-team/README.md`（短到讀得完），**實例目錄放這裡並掛 doc-router**——
它每則 prompt 都跑，是唯一「不需要任何人想起來」就會把一頁推到眼前的機制。
