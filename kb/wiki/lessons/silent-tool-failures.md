# 工具靜默地不做你以為它在做的事

## 這一族長什麼樣

你跑了一個檢查，它回**零筆**、或回**綠**。你把它讀成「結果是沒有」「結果是好的」。

實際上它的意思是 —— **這個檢查沒有發生。**

> **共同症狀：`「沒有結果」` 與 `「結果是沒有」` 在畫面上一模一樣。**

這是 [[lessons/broken-looks-identical-to-normal]] 的子族：都是「失敗不產生訊號」，
差別在於**失敗的是工具，不是程式**。程式那邊你至少還有一個畫面可以看；
工具這邊，你看到的就是你要的那個輸出格式，只是它裝著別的東西。

## 判準

> **零命中之後的下一個動作，是換一條獨立的路再問一次同一個問題，不是下結論。**

換 pattern、換路徑、換工具都行 —— 只要是**獨立的第二條路**。
判準的檢查點很明確：**你剛剛收到一個「什麼都沒有」的結果。**

第二條判準給的是事前的姿勢：

> **你要找的東西，在你搜尋的那個載體裡，真的會長成你以為的樣子嗎？**

## 目錄

每一列的第三欄是**當事人憑什麼起疑** —— 那一半只存在於當事人的記憶裡，
現象可以事後補寫，起疑的時刻不行。

| 載體                                  | 它靜默地做了什麼                                                           | 憑什麼起疑                                          |
| ------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| `sed -i '' '0,/re/s/…'`               | **BSD sed 不支援 `0,` 位址**，整條沒生效，陷阱沒塞進去                     | 陷阱塞完 tsc 照樣綠 —— 但「守衛不存在」也是這個樣子 |
| `grep -E "^ +Tests "`                 | 行首有 **ANSI 逃逸碼**，`^ ` 對不上                                        | 明明看得到那一行，grep 卻抓不到                     |
| `git grep "a\|b" <rev> -- <單檔路徑>` | 回零筆；換成目錄路徑立刻命中同一個檔多處                                   | 那個字串「不可能不存在」的直覺                      |
| `git diff` 兩點與三點                 | **兩個都答不了「這東西現在在不在 main」**                                  | 見下節                                              |
| 手寫的假 supabase                     | 不管路由 `select` 什麼都**回全欄位**，「少撈一個欄位」完全觀察不到         | **「我預期會紅的東西沒紅」**                        |
| zsh 的 `"$VAR:apps/…"`                | **`:a` 是參數修飾符**（絕對路徑），revision 被靜默改寫                     | 第一次只回空輸出，像「那個檔不在那支分支上」        |
| harness 豁免的移除條件                | 條件寫成「v1b 啟用時拿掉」，**啟用那天沒有人在讀豁免表**                   | 查別的東西時剛好讀到那行字（運氣）                  |
| CI 監看器 `until [ -z pending ]`      | 回報的是**它看到的那一輪**，不是你關心的那一輪                             | 記得「中間發生過一次 push」                         |
| `git diff` 的基準點                   | 拿工作區比一個**正在前進的 `origin/main`**，別席的新內容顯示成「你刪掉的」 | 被刪的行內容跟自己做的事對不上                      |

## 同一個工具，兩種騙法

`git diff` 出現兩次，而**兩次的機制完全不同** —— 並排寫，是因為記住一種不會讓你對另一種免疫。

|            | 騙法                                                               | 形狀                                                             |
| ---------- | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 兩點／三點 | 三點答「分支自己改了什麼」，兩點在舊分支上把 main 的前進顯示成刪除 | **你問錯了問題** —— 工具沒壞、用法也對，它回答的不是你問的那件事 |
| 基準點移動 | 比對的對象 `origin/main` 在你編輯期間前進了兩次                    | **基準點在你不注意的時候移動了** —— 問題問對了，但參照系換了     |

第一種的解法是**改用直接對 `origin/main` grep 該 PR 獨有的識別字**；
第二種的解法是**拿分支起點當基準**，不是拿一個活的 ref。

## 有一件不是命令列工具

**假 supabase 那件在我們自己寫的程式碼裡**，而它跟其他所有件的差別是：
其他件換個指令就抓得到，**這件不會有任何症狀，只會讓測試安靜地失去辨識力**。

機制：`select` 在真 PostgREST 裡是**投影**，在替身裡被當成**語法**
（決定鏈式呼叫能不能接下去）。兩種角色在鏈式 API 上長得一模一樣 ——
你必須寫出 `.select(...)` 才接得到 `.eq()`，所以「有實作 select」在測試通過時完全不可疑。
而 fixture 是照著「這張表有哪些欄位」寫的，**它一定是完整的**。

> **替身永遠比真實系統寬容。**

**替身的寬容度決定了它遮得住哪一種突變**：會改變回傳內容的遮不住；
只改變「你有沒有拿到某個欄位」的**遮得嚴嚴實實** —— 而後者正好是本族的形狀。

**所以「多撞幾發真實案例」不是解法，突變的類型才是**：要驗一個替身有沒有這種盲區，
挑一個**不改變任何回傳筆數、只改變欄位有無**的突變去撞。

推論：**突變測試自己也可能是瞎的** —— 人造的陷阱照著你的心智模型造，
**替身也照著你的心智模型寫**，兩邊同一個盲區時它會安靜地通過，
而且從此有一支綠燈替那個盲區背書。

## 欄位有值，不代表那個值回答了你的問題

兩個 `gh` 的例子，解法都是**把你真正關心的那個東西帶進判斷條件**：

- **CI 監看**：`until [ -z pending ]` 等到的是「有一輪跑完了」。你在它跑的期間推了修正，
  它照樣回報綠 —— 而前後兩次 `gh pr checks` 的輸出**逐字相同**（同一個 run id、同樣的 pass）。
  **解法：把 `head_sha` 帶進條件。**
  ```
  gh api repos/<owner>/<repo>/actions/runs/<id> --jq .head_sha   # 要等於你剛推的 commit
  ```
  `until` 迴圈的空窗期同理：舊 run 剛結束、新 run 還沒被排上時，`pending` 是空的，
  而那不代表沒有新的一輪要跑。
- **`gh pr view --json mergeable`**：它是**非同步計算**的，`UNKNOWN` 不代表沒問題，
  只代表**還沒算完**。要確定就本地釘住實測：
  `git merge-tree --write-tree origin/main HEAD`。

## 這一族最貴的產物是「有說服力的假 bug 報告」

`git grep` 那件差一點變成一份報告：「儀表板打的那支端點根本不支援 `endedOnly`」——
有 grep 證據、有明確的失敗機制、讀起來完全成立。

> **假 bug 報告比假 OK 更貴**：它讓人去修一個不存在的東西，
> 而修完之後「症狀消失」還會反過來確認那個假診斷。

## 這一族有大聲的那一半，而它沒有被記錄 —— 因為它當場就被修掉了

這一頁的每一列都是**安靜的**失敗。但同一個知識點常常有**兩個失敗方向**，
而大聲的那一半從來沒進過這頁 —— **不是因為它不存在，是因為它當天就被修掉、
沒有人覺得值得寫下來。**

2026-09-06 兩件同一天出現的實例，來源是同一個 PostgREST 知識點
（「對 embed 的欄位下條件」）：

| 寫法                                                                                 | 失敗方向 | 症狀                                                                                      |
| ------------------------------------------------------------------------------------ | -------- | ----------------------------------------------------------------------------------------- |
| `select('…, events(…)')` + `events.attendance_taken_at=is.null`（**少了 `!inner`**） | **安靜** | 條件什麼都沒篩，回傳筆數看起來完全正常（19 筆 vs 18 筆的實測見 `lib/session-summary.ts`） |
| `select('id')` + `.gte('events.event_date', …)`（**連 embed 都沒有**）               | **大聲** | PostgREST 直接 400 `PGRST108`，端點對每個使用者都 500（#528 的 `/api/me/attendance`）     |

**大聲的那一半反而活了四個半月** —— 因為那支端點在 seed 補上 `parent` 角色之前
沒有任何人打得開（[[lessons/local-manual-verification]] 第三節）。
**「大聲」的前提是有人在聽。**

> **判準：學會一個工具的坑之後，問它的反方向 ——「這個條件如果我寫得更少，
> 它是報錯還是照跑？」** 兩個方向的成本完全不同：報錯的那一半在開發當下就結束，
> 照跑的那一半會活到有人比對數字為止。
>
> 而**這一頁只收得到後者，是倖存者偏差** —— 前者沒有留下任何紀錄，
> 因為它「當場就修好了」。看到這頁很長的時候，要記得**它是同一族裡比較難發現的那一半**。

## 為什麼這一頁在 `kb/` 而不在 charter 或通則清單裡

因為它的**讀取時機不是「在讀文件的時候」，是「卡住的時候」** ——
我 grep 回零筆、我預期會紅的沒紅、我的檢查沒觸發。

那一刻不會有人回去翻四百行的通則清單。所以規則本身留在
`herdr-team/README.md`（短到讀得完），**實例目錄放這裡並掛 doc-router**——
它每則 prompt 都跑，是唯一「不需要任何人想起來」就會把一頁推到眼前的機制。
