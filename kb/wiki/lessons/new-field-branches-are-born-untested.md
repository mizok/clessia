# 加了新欄位的分支，天生就沒被測到

## 發生什麼

`#222` 讓 roster API 多回一個 `leaveStartDate`。前端接上它，在銷假警告裡加一個新分支：
起始日等於這堂課的日期就不警告（可以證明零損失）。

改完跑測試：**986 passed，全綠。**

那一刻看起來像「改動很安全」。實際上是**新分支一次都沒有執行過** ——
既有的 roster fixture 是在這個欄位存在之前寫的，`leaveStartDate` 一律是 `undefined`/`null`，
所以每一支測試都從新分支旁邊走過去，落回舊路徑。

綠燈證明的是「舊行為沒壞」，而那正好是**唯一被測到的東西**。

## 為什麼特別容易中

這個形狀有三個條件，湊齊就會發生，而它們常常一起出現：

1. 新欄位是**可選的**（`T | null`）—— 型別不會逼任何 fixture 去補它
2. 新分支的守衛寫成「**有值而且滿足條件**才走新路」（保守的寫法，是對的）
3. fixture 用工廠函式產生，欄位沒列就是沒有

第 2 點是關鍵的反諷：**保守的守衛讓缺欄位的舊資料安全地落回舊行為** ——
那在正式環境是對的設計，在測試裡卻讓新分支變成死碼。寫得越安全，越不會被叫醒。

## 怎麼發現

不是靠讀 diff，是靠**突變測試**：把新分支整行刪掉再跑一次。

```
拿掉零損失分支 → Tests 986 passed   ← 沒有任何測試在乎它
```

刪掉一段程式碼而測試不變色，就是「這段沒有被任何測試釘住」的直接證據。
補上帶新欄位的 fixture 之後再測一次，才會紅：

```
拿掉零損失分支 → 1 failed | 988 passed
```

## 規則

**接上 API 新欄位、或加一個依賴新欄位的分支時，測試全綠不算通過。**
通過的定義是：**把那個分支刪掉，至少一支測試要紅。**

這比「記得補測試」可靠 —— 補了測試但 fixture 沒帶新欄位，
測試會一起從旁邊走過去，而它看起來就像一支正常的綠燈。
