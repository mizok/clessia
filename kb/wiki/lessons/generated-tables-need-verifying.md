# 生成的表不會因為它是生成的就正確

`kb/roadmap.md` 的功能區現況表用來回答「哪些功能是空殼」，而那個答案會直接變成**裁撤決定**。
判定「這個頁面有沒有接後端」的邏輯改了四版才對。

## 四個版本

| 版本 | 判定方式                            | 錯在哪                                                                                                                     |
| ---- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1    | 頁面目錄裡出現過 `'/api/` 字串      | 21 個功能區有 18 個被判成空殼 —— 包括 3184 行、明顯會動的課程頁。這個專案的頁面透過 core 的 service 呼叫後端，不直接 fetch |
| 2    | 有 `from '@core/`                   | 空殼也會 import `RouteObj`，全部變成已接通                                                                                 |
| 3    | 有 `from '@core/<domain>.service'`  | **漏了「薄容器」頁面**                                                                                                     |
| 4    | 遞移追蹤 `@shared` / `@core` 的引用 | 目前逐一驗證過 7 個空殼皆為真                                                                                              |

## 第三版為什麼最危險

前兩版錯得太離譜 —— 18/21 是空殼、或全部都已接通，一看就知道判定壞了。

第三版**看起來完全合理**，而且大多數結果是對的。它只漏了一種形狀：

```html
<!-- admin/subjects：整頁只有 11 行 TS -->
<app-subject-manager />
```

頁面本身是薄容器，真功能在 `@shared/components/subject-manager/` 裡 —— 那裡才 import
domain service。判定只看頁面目錄，於是把它算成空殼。

**而我當時已經根據那張表，提議把「科目頁」刪掉。**

阻止這件事的不是任何 gate，是使用者問了一句「你要刪掉的這些東西目前有既存的進度嗎」。
一問之下才發現 `subjects` 的 commit 訊息是 `style: improve subjects page visual design` ——
有人**特地美化過它**，那不會發生在 `ng generate` 的骨架上。

## 可遷移的原則

1. **生成的資料看起來比手寫的可信，但它只反映判定邏輯的正確性。** 自動化消除的是「忘記更新」，
   不是「一開始就想錯」。
2. **結論越是要拿來做破壞性決定（刪除、裁撤、重寫），越要人工逐一驗證。**
   這張表若只用來顯示進度，錯了頂多誤導；用來決定刪什麼，錯了就是資料損失。
3. **拿已知答案反向對照。** 我最後是逐一打開 7 個空殼確認內容（`<p>meals works!</p>`、
   inline template 的 "coming soon"、`dashboard` 是做好版面但數值全是 `'—'`），
   而不是相信表格。
4. **異常的 commit 訊息是訊號。** 一個「空殼」如果有人特地為它做過視覺設計，那它多半不是空殼。

## 這張表現在還不證明什麼

它證明「某個功能區的 UI／後端接線／API 掛載／規格各自存不存在」。
它**不證明**功能正確、完整、或有人在用。一個有 API 呼叫但邏輯全錯的頁面照樣顯示為已接通。
