# 壞掉的樣子跟正常的樣子一模一樣

## 這個模式長什麼樣

每個實例都能通過「讀程式碼」這一關——語法對、型別對、邏輯看起來也對。但只要
真的去跑一次、點一次、用觸控裝置戳一次，或者查一下這個判斷式**有沒有被任何
資料真正命中過**，就會發現它從來沒有做到它看起來在做的事。

這不是同一個 bug 重複十三次，是同一個**盲點形狀**重複十三次：review 的人跟
寫的人都在看程式碼證明邏輯正確，卻沒有人去驗證「邏輯正確」跟「使用者看到
的結果正確」這兩件事有沒有真的對上。

## 判準：一句話測試

**「它壞了我們會知道嗎？」**

答得出來（有測試、有監控、有人會定期看）就不是這一族。答不出來，就是下一個
案發現場——而且案發現場往往就是**最少人會去看的那個角落**（見下方 session-filters
的例子）。

## 六個變形，同一個核心

這十六個實例不是隨機湊在一起，可以再收斂成六種變形，全部回答同一個問題
「它壞了我們會知道嗎」都是「不會」：

1. **語意宣告 vs 渲染結果對不上**（#3 info/error 撞色、#4 sticky 表頭）——程式碼的
   「意思」是對的，瀏覽器畫出來的「樣子」是錯的。查證成因（severity 值、CSS
   屬性）永遠只答得出前半，要答後半得真的去看畫面。
2. **條件式永遠不觸發**（#2 completed 分支、#7 死掉的 CSS modifier、#8 死檔案）——
   守衛、規則、整支元件形式上都在，**執行到那一行的次數是零**（死分支，
   對任何輸入都不會為真）。跟下面第 6 種變形的差別在這裡：那些程式碼會
   執行、也會給答案，只是答案在特定條件下是錯的。
3. **失敗被吞成正常值的一種**（#9 count 查詢失敗當作 0、#10 聚合值蓋住組成）——
   `null`/失敗跟「真的是 0」在型別上長得一模一樣，程式往下走的路徑也一樣。
4. **名字/文案做出程式碼沒兌現的承諾**（#1 `confirmDelete` 不確認、#14 LINE
   推播承諾）——這個變形最陰險，因為讀的人會被名字或文案說服，連細看實作
   的動機都沒有。**它有空間跟時間兩個方向**：#1 是空間版（此刻就假）,
   #14 是時間版（承諾一件之後才會發生、可能永遠不發生的事）——時間版更難
   認，因為文案寫下的當下完全不假，同一個人在同一份文件裡否決了空間版
   卻認不出自己剛寫的是時間版。
5. **訊號只在部分裝置/部分使用者路徑存在**（#13 兩欄撞色）——在寫程式碼那個人
   自己的環境裡看起來沒問題，另一個消費者的視角看是壞的。
6. **觀測窗口不涵蓋出錯的情況**（#6 hover-only 回饋、#15 `z.uuid()`、#16
   `leaves.ts` UTC）——程式碼**會執行、也會給答案**，跟第 2 種變形（死分支，
   對任何輸入都不會為真）不同，這裡的分支/驗證/計算是活的，只是**觀測它
   的方式剛好沒有涵蓋出錯的那個條件**：用滑鼠測試涵蓋不到觸控裝置沒有
   hover 這件事；測試資料用 RFC 合法的 UUID 涵蓋不到 seed 塞的非法佔位；
   CI 在白天跑涵蓋不到台北凌晨那 8 小時。**判準是一個可以主動問的問題：
   「我們是在什麼條件下觀察它的？那個條件涵蓋出錯的條件嗎？」**
   （這條也解釋了 Tester 的稽核為什麼會漏掉某些東西——如果稽核只測桌機，
   它的觀測窗口天生就不涵蓋觸控裝置專屬的破綻，那不是稽核做得不夠仔細，
   是觀測窗口的必然限制。）

## 解法是同一個：讓失敗產生訊號——但正常也要學會安靜

其餘十三個實例的解法方向都收斂成一句話：**別讓「查不到」「沒檢查」「還沒發生」
偽裝成「確定沒有」**。查詢失敗要回傳能被呼叫端分辨的狀態（`{status:'check-failed'}`
不是 `count ?? 0`）、確認動作要真的跳出確認、規則要真的接到它宣稱要修飾的
class。

但 #13 是這批裡**唯一反過來的一條**，而它同樣重要：

```html
@if (sessionStatusTone(session) === 'pending') {
<!-- 正常態不畫點——兩欄常態都落在 pending，並排會是同一顆點 -->
<span class="session-list__status-plain">{{ sessionStatusLabel(session) }}</span>
} @else {
<app-status-dot [tone]="sessionStatusTone(session)">…</app-status-dot>
}
```

修法不是「加一個更醒目的點」，是**拿掉 19/19 都會亮的那個點**。只有真正不
正常（已停課）才畫。

這兩個方向其實是同一個目標的兩面：**訊號要能被看見，前提是周圍夠安靜。**
只做前半（失敗要吶喊）而不做後半（正常要沉默），下一個人會誤以為這個模式
的解法永遠是「多加一個警示」——而在一個所有東西都在警示的畫面裡，警示
本身就不再是訊號了。「顏色是有預算的」：一個 19/19 都亮著的燈不是提醒，
是背景。

## 怎麼盤點這個模式

每一條都不是靠讀程式碼發現的，是靠問一個問題發現的：

- **這個判斷式，有沒有被任何真實資料命中過？**（#2、#7、#8——grep 賦值端，
  不是只看讀取端）
- **這個查詢失敗的時候，呼叫端看到的值跟「真的是 0」一樣嗎？**（#9、#10）
- **這個樣式規則，套用的 class 字串在模板裡真的存在嗎？**（#7——兩個字串
  長得像不代表是同一個）
- **這個名字宣稱的動作，實作真的做了嗎？**（#1——讀函式名字時的第一反應
  往往是最不可靠的驗證）
- **换成觸控裝置、换成另一個消費者的視角，這個訊號還在嗎？**（#6、#11、#13）
- **我們是在什麼條件下觀察它的？那個條件涵蓋出錯的條件嗎？**（#6、#15、#16
  ——測試資料的形狀、跑測試的時間窗、稽核用的裝置，都是「觀察條件」的一種）

**光看程式碼永遠只能證明「邏輯自洽」，不能證明「邏輯自洽的結果等於使用者
看到的結果」——這兩件事之間那道縫，就是這整篇在講的東西。**

盤點方法本身也會被這一族咬到，兩個實測案例：

- **查線上 bundle 要查行為，不要查字面。** 想確認某個修正部署了沒，搜壓縮後
  bundle 裡的原始碼形狀（例如 `documentElement.style.setProperty`）會回假
  陰性——minify 把它壓成 `n.style.setProperty`，**保留行為、不保留形狀**。
  改搜壓縮動不到的東西（字串常數、CSS class、API 路徑）；但中文字元會被
  轉義成 `\uXXXX`，直接搜中文字串一樣是假陰性。差一點就用「那支修正沒
  部署」的錯誤前提去規劃一整套真機驗證。
- **自己剛做的東西感覺不需要查，而那個「感覺不需要」正是它逃過檢查的方式。**
  剛寫完上面那條「查行為不查字面」的教訓，緊接著就回報「某功能已交付、
  PR 還 OPEN」——而那支 PR 其實八個多小時前就 MERGED 了。查證疲勞不會
  隨機分布，它精準地打在「這是我自己剛做的，不用查」的地方。
