# 壞掉的樣子跟正常的樣子一模一樣

## 這個模式長什麼樣

每個實例都能通過「讀程式碼」這一關——語法對、型別對、邏輯看起來也對。但只要
真的去跑一次、點一次、用觸控裝置戳一次，或者查一下這個判斷式**有沒有被任何
資料真正命中過**，就會發現它從來沒有做到它看起來在做的事。

這不是同一個 bug 重複十三次，是同一個**盲點形狀**重複十三次：review 的人跟
寫的人都在看程式碼證明邏輯正確，卻沒有人去驗證「邏輯正確」跟「使用者看到
的結果正確」這兩件事有沒有真的對上。

## 判準：一句話測試

**「它壞了我們會知道嗎？」**

答得出來（有測試、有監控、有人會定期看）就不是這一族。答不出來，就是下一個
案發現場——而且案發現場往往就是**最少人會去看的那個角落**（見下方 session-filters
的例子）。

## 五個變形，同一個核心

這十三個實例不是隨機湊在一起，可以再收斂成五種變形，全部回答同一個問題
「它壞了我們會知道嗎」都是「不會」：

1. **語意宣告 vs 渲染結果對不上**（#3 info/error 撞色、#4 sticky 表頭）——程式碼的
   「意思」是對的，瀏覽器畫出來的「樣子」是錯的。查證成因（severity 值、CSS
   屬性）永遠只答得出前半，要答後半得真的去看畫面。
2. **條件式永遠不觸發**（#2 completed 分支、#7 死掉的 CSS modifier、#8 死檔案）——
   守衛、規則、整支元件形式上都在，保護/影響的資料量是零。
3. **失敗被吞成正常值的一種**（#9 count 查詢失敗當作 0、#10 聚合值蓋住組成）——
   `null`/失敗跟「真的是 0」在型別上長得一模一樣，程式往下走的路徑也一樣。
4. **名字做出程式碼沒兌現的承諾**（#1 `confirmDelete` 不確認）——這個變形最
   陰險，因為讀程式碼的人會被名字說服，連細看實作的動機都沒有。
5. **訊號只在部分裝置/部分使用者路徑存在**（#6 hover-only 回饋、#13 兩欄撞色）——
   在寫程式碼、用滑鼠測試的那個人的環境裡看起來沒問題，觸控裝置或另一個
   消費者的視角看是壞的。

## 解法是同一個：讓失敗產生訊號——但正常也要學會安靜

前面十二個實例的解法方向都收斂成一句話：**別讓「查不到」「沒檢查」「還沒發生」
偽裝成「確定沒有」**。查詢失敗要回傳能被呼叫端分辨的狀態（`{status:'check-failed'}`
不是 `count ?? 0`）、確認動作要真的跳出確認、規則要真的接到它宣稱要修飾的
class。

但 #13 是這批裡**唯一反過來的一條**，而它同樣重要：

```html
@if (sessionStatusTone(session) === 'pending') {
<!-- 正常態不畫點——兩欄常態都落在 pending，並排會是同一顆點 -->
<span class="session-list__status-plain">{{ sessionStatusLabel(session) }}</span>
} @else {
<app-status-dot [tone]="sessionStatusTone(session)">…</app-status-dot>
}
```

修法不是「加一個更醒目的點」，是**拿掉 19/19 都會亮的那個點**。只有真正不
正常（已停課）才畫。

這兩個方向其實是同一個目標的兩面：**訊號要能被看見，前提是周圍夠安靜。**
只做前半（失敗要吶喊）而不做後半（正常要沉默），下一個人會誤以為這個模式
的解法永遠是「多加一個警示」——而在一個所有東西都在警示的畫面裡，警示
本身就不再是訊號了。「顏色是有預算的」：一個 19/19 都亮著的燈不是提醒，
是背景。

## 怎麼盤點這個模式

每一條都不是靠讀程式碼發現的，是靠問一個問題發現的：

- **這個判斷式，有沒有被任何真實資料命中過？**（#2、#7、#8——grep 賦值端，
  不是只看讀取端）
- **這個查詢失敗的時候，呼叫端看到的值跟「真的是 0」一樣嗎？**（#9、#10）
- **這個樣式規則，套用的 class 字串在模板裡真的存在嗎？**（#7——兩個字串
  長得像不代表是同一個）
- **這個名字宣稱的動作，實作真的做了嗎？**（#1——讀函式名字時的第一反應
  往往是最不可靠的驗證）
- **换成觸控裝置、换成另一個消費者的視角，這個訊號還在嗎？**（#6、#11、#13）

**光看程式碼永遠只能證明「邏輯自洽」，不能證明「邏輯自洽的結果等於使用者
看到的結果」——這兩件事之間那道縫，就是這整篇在講的東西。**
